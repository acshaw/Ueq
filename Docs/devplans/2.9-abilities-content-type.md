# 2.9 — Abilities, Tags & Effects (DB-backed content type)

Status: ✅ Done — verified in-editor 2026-07-17 (AB1–AB8 all as recommended, with one implementation-time
simplification to AB1 — see the log below)

## Goal

Migrate `AbilityDefinition` / `AbilityTag` / `CooldownLink` / `AbilityEffect` (currently ScriptableObject
assets under `Resources/Abilities/` + `Assets/ScriptableObjects/AbilityTags/`) to Postgres + a web
**Ability Editor** and **Ability Tag Editor**, built on the 2.1.1 `ContentGrid`/`CrudModal` framework so
this is the first content type to get it for free. Copies the 2.2 (Items) shape, since — like items —
abilities must reach the **client**, not just the server (see AB2).

## Grounding (read before designing)

- `AbilityDefinition` (SO): `abilityId`, `displayName`, `description`, `targetingType` (Self/SingleTarget),
  `range`, `castTime`, `manaCost`, `animTrigger` (plain string, no asset ref), `tags` (`List<AbilityTag>`),
  `cooldownLinks` (`List<CooldownLink>` — empty ⇒ GCD), `effects` (`List<AbilityEffect>`, applied in order).
- `AbilityTag` (SO): `tagId`, `displayName` — a pure semantic label, referenced both by an ability's own
  `tags` list and by `CooldownLink.tag` (shared-timer key). Only one asset exists today (`MartialAbility`).
- `CooldownLink` (plain serializable struct, not an SO): `{AbilityTag tag, float duration}`.
- `AbilityEffect` (abstract **SO**) with `Apply(caster, target, source)`. Two concrete subclasses exist:
  `DamageEffect` and `HealEffect` — **identical shape**: `baseDamage`/`baseHeal` (int), `scalingStat`
  (`ScalingStatType` enum: None/Str/Sta/Agi/Dex/Int/Wis/Cha), `scalingFactor` (float). They're embedded as
  **sub-assets** of the `AbilityDefinition` asset (see `Kick.asset`: a `DamageEffect` sub-object + the
  ability object referencing it by `fileID`). The roadmap's own 2.9 line already names future effect types
  that don't exist yet: `DotEffect`, `HotEffect`, `BuffEffect`, `DebuffEffect`, `SnareEffect`, `RootEffect`,
  `StunEffect`, `FactionHitEffect`.
- `AbilityRegistry` (MonoBehaviour singleton): `Resources.LoadAll<AbilityDefinition>("Abilities")` in
  `Awake`, dictionary by `abilityId`.
- **`AbilityRegistry` runs on the client too** — `HotbarUI.cs:77` calls
  `AbilityRegistry.Instance?.Get(id)?.displayName` to label hotbar slots. This is the key fact that puts
  2.9 in the same bucket as 2.2 (items), not 2.3–2.7 (server-only): clients need the catalog, so this needs
  a Mirror sync message, not just a server-side loader.
- `PlayerAbilities` (NetworkBehaviour) already stores `_hotbar`/`_knownAbilities` as `SyncList<string>` of
  **ability ids** — it already treats `AbilityDefinition` as an id-keyed lookup (`AbilityRegistry.Instance
  ?.Get(abilityId)`), so nothing here changes shape; it just needs the registry populated from the DB
  instead of `Resources`.
- `ContentCatalog.cs` (built in 2.2) is explicitly designed for this: *"Built generically... so every later
  type that clients need to see — abilities, races, … — reuses this shape rather than reinventing it."*
  Confirms 2.9 is exactly the case it was written for.
- `ClassDefinition.startingAbilities` is `List<AbilityDefinition>` — a **cross-item coupling with 2.10**
  (see AB8).

## Decisions

**AB1 — Effect representation (the real design question).** `DamageEffect`/`HealEffect` are identical in
shape (`baseAmount`, `scalingStat`, `scalingFactor`). Recommend **one child table**
`ability_effects(id, ability_id, sort_order, effect_type TEXT, base_amount INT, scaling_stat INT,
scaling_factor REAL)` — `effect_type` distinguishes `damage` vs `heal` (and future types), the three data
columns cover both existing effects fully. When a genuinely different-shaped effect type is actually built
(e.g. a `StunEffect` needing just a duration, or `FactionHitEffect` needing a faction id + delta), add
nullable columns for it in that type's own migration — same "add a column when you need it" approach
already used everywhere else in this schema (no type-per-table, no JSONB blob; this codebase hasn't used
JSONB anywhere and flat typed columns keep effects queryable/editable in a plain grid). **Not recommending
speculative columns for the other 6 unbuilt effect types now** — YAGNI until one is actually implemented.
- *Unity-side consequence:* `AbilityEffect` can no longer be a `ScriptableObject` sub-asset once it's a DB
  row with zero asset references — it becomes a **plain C# class** (matches the "pure data vs. asset
  bindings" principle; effect params are pure numbers). Concretely: keep the `Apply(caster, target, source)`
  contract, but effects are now constructed by a small `AbilityEffectFactory.Build(effectType, baseAmount,
  scalingStat, scalingFactor)` off an `AbilitySnapshot`'s effect list, not `AssetDatabase`/`CreateInstance`.

**AB2 — Client sync.** New `ContentCatalog.AbilityCatalogMessage` / `BuildAbilities()` / `ApplyAbilities()`,
registered alongside the existing item catalog handler in `GameNetworkManager`. `AbilityRegistry` gains
`LoadFrom(IEnumerable<AbilitySnapshot>)` (mirrors `ItemRegistry.LoadFrom`), and its `Awake` no longer does
`Resources.LoadAll` once retired (AB7).

**AB3 — Tags.** `ability_tags(tag_id TEXT PRIMARY KEY, display_name TEXT)` — flat, tiny, `ContentGrid`-able
as-is. An ability's own semantic `tags` list becomes a join table `ability_definition_tags(ability_id,
tag_id, sort_order)`; `CooldownLink.tag` becomes a plain `tag_id TEXT` FK column on the cooldown-links child
table (AB4) — no separate join needed there, a cooldown link has exactly one tag.

**AB4 — Cooldown links.** Child table `ability_cooldown_links(id, ability_id, sort_order, tag_id, duration)`.
Empty list (no rows) ⇒ ability uses the shared GCD, exactly as today.

**AB5 — Header table.** `abilities(ability_id TEXT PRIMARY KEY, display_name, description, targeting_type
INT, range REAL, cast_time REAL, mana_cost INT, anim_trigger TEXT)`. `animTrigger` was already a plain
string (no asset ref) — no asset-binding convention needed here, unlike mob `prefab_address` or item
`icon_address`.

**AB6 — Web editor shape.** `AbilityEditorWindow`'s existing sections map directly onto a `CrudModal`:
Identity / Targeting / Resource / Animation (all flat fields) → Tags (multi-select checkboxes or a
tag-id list against the `ability_tags` grid) → Cooldown Links (repeatable tag-dropdown + duration rows,
mirrors Mob Editor's faction-hits rows) → Effects (repeatable effect-type dropdown + amount/stat/factor
rows, ordered — mirrors Loot Editor's weighted rows). **Ability Tag Editor** is a second, much simpler
`ContentGrid`/`CrudModal` pair (two fields, no children) — same shape as the Faction Editor's flat pieces.

**AB7 — Retire the SO path + seed existing content.** Once verified, `AbilityRegistry`/`AbilityEditorWindow`
drop the `Resources.LoadAll`/asset-authoring path per the standing "retire the old field once proven"
principle. `DatabaseSeeder` seeds the 4 existing abilities faithfully from their asset YAML so nothing is
lost: **Kick** (`kick`, SingleTarget r10, animTrigger `Kick`, tag+cooldown-link `MartialAbility`/10s, one
`damage` effect base 8 / Str / 0.5), **Taunt** (read its asset — not yet inspected, grab exact fields during
implementation), **Fire Bolt** (`fire_bolt`, SingleTarget r20, 10 mana, animTrigger `Cast`, one `damage`
effect base 12 / Int / 0.5), **Minor Heal** (`minor_heal`, Self, 10 mana, animTrigger `Cast`, one `heal`
effect base 20 / Wis / 0.5). Seed the `MartialAbility` tag too.

**AB8 — Cross-item coupling with 2.10 (must be resolved in 2.9, not deferred).**
`ClassDefinition.startingAbilities` is `List<AbilityDefinition>` — a direct SO reference to the very asset
type 2.9 retires. `ClassDefinition` itself isn't migrating to DB until 2.10, so this can't just be left
broken in between. Recommend: as part of 2.9, change `ClassDefinition.startingAbilities` to `List<string>`
(ability ids) — `ClassDefinition` stays an SO for now (2.10's job), but decouples from the `AbilityDefinition`
asset type immediately. This is a **simplification, not a workaround**: `PlayerAbilities.SetRaceClass`
already treats `startingAbilities` as an id source (`ability.abilityId`) and discards the object reference
immediately — switching the field to `List<string>` removes a dereference, not adds one. Touches:
`ClassDefinition.cs` (field type), `PlayerAbilities.SetRaceClass` (drop the null/dereference checks, iterate
strings), `RaceClassEditorWindow.cs`'s Known Abilities section (legacy Unity editor — becomes a text-id list
UI instead of an object-field list; it's superseded by 2.10's web editor shortly anyway, so keep this
minimal), and `ClassContentSetup.cs`/`CharacterRosterSetup.cs` (any tooling that currently assigns
`startingAbilities` via asset refs switches to assigning ids).

## Schema (migration `0023_abilities.sql`)

```sql
CREATE TABLE abilities (
  ability_id     TEXT PRIMARY KEY,
  display_name   TEXT NOT NULL,
  description    TEXT NOT NULL DEFAULT '',
  targeting_type INT  NOT NULL DEFAULT 1,   -- 0=Self, 1=SingleTarget
  range          REAL NOT NULL DEFAULT 20,
  cast_time      REAL NOT NULL DEFAULT 0,
  mana_cost      INT  NOT NULL DEFAULT 0,
  anim_trigger   TEXT NOT NULL DEFAULT ''
);

CREATE TABLE ability_tags (
  tag_id       TEXT PRIMARY KEY,
  display_name TEXT NOT NULL
);

CREATE TABLE ability_definition_tags (
  id         SERIAL PRIMARY KEY,
  ability_id TEXT NOT NULL REFERENCES abilities(ability_id) ON DELETE CASCADE,
  tag_id     TEXT NOT NULL REFERENCES ability_tags(tag_id),
  sort_order INT  NOT NULL DEFAULT 0
);

CREATE TABLE ability_cooldown_links (
  id         SERIAL PRIMARY KEY,
  ability_id TEXT NOT NULL REFERENCES abilities(ability_id) ON DELETE CASCADE,
  sort_order INT  NOT NULL DEFAULT 0,
  tag_id     TEXT NOT NULL REFERENCES ability_tags(tag_id),
  duration   REAL NOT NULL DEFAULT 3
);

CREATE TABLE ability_effects (
  id             SERIAL PRIMARY KEY,
  ability_id     TEXT NOT NULL REFERENCES abilities(ability_id) ON DELETE CASCADE,
  sort_order     INT  NOT NULL DEFAULT 0,
  effect_type    TEXT NOT NULL,             -- 'damage' | 'heal' (more later, new columns as needed)
  base_amount    INT  NOT NULL DEFAULT 0,
  scaling_stat   INT  NOT NULL DEFAULT 0,    -- ScalingStatType enum
  scaling_factor REAL NOT NULL DEFAULT 0
);
```

## Unity changes

- `Assets/Scripts/Server/Content/AbilitySnapshot.cs` — plain-data mirrors of the 5 tables (header + 3
  child lists), same shape as `MobSnapshot`/`MobFactionHitSnapshot`.
- `Assets/Scripts/Server/Content/AbilityRepository.cs` — header query + 3 child queries, id-keyed dictionary
  assembly (copy `MobRepository`'s pattern exactly — it's the closest precedent: one header + one child list;
  this has one header + three).
- `AbilityEffect.cs` — becomes a plain abstract class (no `ScriptableObject`/`CreateAssetMenu`); new
  `AbilityEffectFactory.Build(AbilityEffectSnapshot)` replaces subclass-per-asset construction.
  `DamageEffect`/`HealEffect` become plain classes constructed by the factory from `effect_type`.
- `AbilityDefinition` — either stays a thin runtime-only class (no longer an SO) built by
  `AbilityRegistry.LoadFrom`, or is replaced outright by `AbilitySnapshot` + a small runtime wrapper.
  Decide the exact shape during implementation once AB1 is confirmed — functionally it just needs to keep
  serving `PlayerAbilities`/`HotbarUI`'s existing read surface (`abilityId`, `displayName`, `targetingType`,
  `range`, `manaCost`, `animTrigger`, `cooldownLinks`, `effects`) so those two files don't change.
- `AbilityRegistry.LoadFrom` + drop `Resources.LoadAll` (AB7).
- `ContentCatalog.cs` — add `AbilityCatalogMessage`/`BuildAbilities`/`ApplyAbilities`, same pattern as items.
- `GameNetworkManager.cs` — register/unregister the new handler, send on `OnServerReady` alongside items.
- `ContentLoader.cs` — new step loading abilities (after tags implicitly, since it's one repository call),
  exposing `ContentLoader.Abilities` for the catalog sync to read (mirrors `ContentLoader.Items`).
- `ClassDefinition.cs` / `PlayerAbilities.SetRaceClass` / `RaceClassEditorWindow.cs` — AB8 changes.
- Delete `AbilityEditorWindow.cs` + `AbilityTagEditorWindow.cs` once the web editors are verified (AB7).

## Implementation log (2026-07-17)

**AB1 simplified during implementation — checked the actual `ItemDefinition` precedent before writing
code, which the original draft hadn't done.** `ItemDefinition` (2.2) is **still a `ScriptableObject`**
after its DB migration — `ItemRegistry.Build(ItemSnapshot)` just calls `ScriptableObject.CreateInstance
<ItemDefinition>()` and fills its fields from the snapshot; it's simply never authored as an asset
anymore. The devplan's original AB1 assumed `AbilityEffect`/`AbilityDefinition`/`AbilityTag` had to stop
being `ScriptableObject`s (a plain-class + `AbilityEffectFactory` split) — unnecessary. Implemented the
simpler, precedent-matching version instead: `AbilityDefinition`, `AbilityTag`, `DamageEffect`, and
`HealEffect` all **stay exactly as they were** (same fields, same `Apply()` contract) — only
`[CreateAssetMenu]` was dropped (no longer meaningful once nothing should hand-author an instance) and
each gained a doc comment marking it runtime-only. `AbilityRegistry.Build(AbilitySnapshot)` constructs
them via `ScriptableObject.CreateInstance<T>()` from the snapshot, mirroring `ItemRegistry.Build` line
for line. Net effect: **zero changes needed to `PlayerAbilities.cs` or `HotbarUI.cs`** beyond AB8 — both
already treated `AbilityDefinition` as an id-keyed read surface with no asset-specific behavior.

Also found `RaceClassEditorWindow.cs`'s "Known Abilities" section needed **no change** — its
`EditorGUILayout.PropertyField(_classSO.FindProperty("startingAbilities"), …, true)` call uses Unity's
generic property drawer, which renders a `List<string>` (text fields) exactly as readily as it rendered
the old `List<AbilityDefinition>` (object-reference fields). Confirmed via reading the call site before
assuming a rewrite was needed.

**Cross-item coupling (AB8) resolved as planned**, plus one consequence found while executing it: the
three existing `ClassDefinition` assets (`Warrior.asset`, `Wizard.asset`, `Cleric.asset`) still had their
`startingAbilities` serialized as the *old* `List<AbilityDefinition>` YAML shape (asset-guid references
to the now-deleted `Kick.asset`/`FireBolt.asset`/etc.). A Unity field-type change doesn't migrate old
serialized data — on next load those lists would have silently gone empty (Unity discards YAML that
doesn't match the new field's serialized shape, no error). Hand-edited all three `.asset` files directly
to replace the object-reference YAML with the equivalent plain-string list (`kick`/`Taunt` for Warrior,
`minor_heal` for Cleric, `fire_bolt` for Wizard) so starting abilities survive the migration unbroken.

**Retired per AB7**: `AbilityEditorWindow.cs`, `AbilityTagEditorWindow.cs` (both purely
`ScriptableObject`/`AssetDatabase`-driven, incompatible with the new no-longer-asset-authored types), and
`ClassContentSetup.cs` (a one-time editor tool that authored Fire Bolt/Minor Heal/Kick's damage effect as
SO sub-assets — its job is now `DatabaseSeeder.SeedAbilities`, and it directly assigned
`ClassDefinition.startingAbilities` as object refs, which no longer compiles against the new field type).
Deleted the now-orphaned `Resources/Abilities/*.asset` (4 files) and
`ScriptableObjects/AbilityTags/MartialAbility.asset` — their exact data (verified by reading each asset's
YAML before deleting) is faithfully seeded into the DB by the new `DatabaseSeeder.SeedAbilities`, matching
the ids already referenced by `ClassDefinition.startingAbilities` and any already-saved character hotbars
(`kick`, `Taunt`, `fire_bolt`, `minor_heal` — exact case preserved, including `Taunt`'s inconsistent
capitalization and its original "Taunts the eneimy" typo, both left exactly as authored rather than
"fixed" during a pure data migration).

**Build verification**: `dotnet build` on `/api` — 0 errors, 0 warnings. `ng build --configuration
production` on `/web` — clean. **Could not compile-check the Unity side** — attempted a headless batch
build (`Unity.exe -batchmode -nographics -quit`) but it aborted immediately because the project was
already open in the user's own Editor instance (Unity refuses two simultaneous opens of one project);
verified instead via careful manual re-read of every touched/created file.

**In-editor verification (2026-07-17): ✅ passed.** One real snag along the way, not a code bug: after
`Tools/Database/Run Migrations` the `abilities` table existed but had 0 rows — `Run Migrations` only
applies schema, seeding is a separate step (`Tools/Database/Seed Database` or a Host start with
`SeedOnStart`), a previously-documented gap in this project's workflow (see the 2026-06-24 CLAUDE.md
entry), not specific to 2.9. Confirmed via `docker exec ueq_postgres psql` that migration 0023 was
applied (`schema_version` had it) but `abilities` was empty. After running `Tools/Database/Seed Database`,
the user confirmed Kick/Taunt/Fire Bolt/Minor Heal all resolve correctly and the ability system works
end to end. **2.9 closed.**
