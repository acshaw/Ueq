**Roadmap item:** M1 → 1.4 *(pulled ahead of 1.3 per the 2026-06-21 review decision O1 — character
persistence is built on a real account→character key, so accounts land first)*
**Status:** ✅ Done 2026-06-21 — verified in-editor via Multiplayer Play Mode (register / login / wrong-password / duplicate-username / already-online matrix all pass). Implemented ahead of 1.3 per decision O1.
**Depends on:** 1.1 (Postgres + `Database`/`MigrationRunner`) ✅, 1.2 (`PersistenceService` —

**Unblocks:** 1.3 (character-state persistence keyed by account→character), 1.5 (character

---

## Goal

Put the world **behind a login**: a player supplies credentials, the server authenticates them
against an `accounts` table before the connection is accepted, and the authenticated **account id is
attached to the connection** so everything spawned for that player knows which account it belongs to.
This is the identity foundation 1.3 deferred to — it produces the **account→connection→character
seam** that the character round-trip keys off.

Per roadmap 1.4: account table (hashed passwords), Mirror `NetworkAuthenticator` login handshake,
connection→account mapping, session token. **Transport stays unencrypted (KCP)** — hardened
auth + encryption is explicitly deferred to 5.3; passwords cross the wire in the clear at this hobby
stage (accepted risk, see Risks).

### Scope guardrails
- **In scope:** `accounts` schema + migration, an `AccountRepository`, dependency-free password
  hashing (PBKDF2), an `AccountAuthenticator : NetworkAuthenticator` doing an **async** credential
  check during the connect phase, in-client **register + login** UI, connection→account mapping via
  `conn.authenticationData`, single-login enforcement, and a lightweight session token.
- **Out of scope:**
  - **Character select/creation (1.5).** 1.4 logs you into an *account*; the existing default player
    still spawns. 1.5 adds the character list/creation on top of the account.
  - **Character-state persistence (1.3).** 1.4 only exposes the account id at spawn; actually saving
    per-character state is 1.3 (next).
  - **Transport encryption + hardened/rate-limited auth (5.3).** No TLS, no lockout/throttle beyond
    basics.
  - **Password reset / email / account management UI.** Not needed for trusted hobby users.
- **Hard rule:** the credential check is **server-authoritative and runs off the main thread** (DB
  I/O), reusing 1.2's load dispatch — the connect handshake must never block Mirror's tick.

## Approach

### 1. Schema — `accounts` (+ optional `sessions`, see O3)

```sql
CREATE TABLE IF NOT EXISTS accounts (
    account_id     BIGSERIAL   PRIMARY KEY,
    username       TEXT        NOT NULL UNIQUE,        -- stored lower-cased; compared case-insensitively
    password_hash  TEXT        NOT NULL,               -- PHC-style "pbkdf2$<iter>$<salt_b64>$<hash_b64>"
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at  TIMESTAMPTZ
);
```

The PHC-style single string keeps salt + iteration count + subkey together so the verifier is
self-describing and the work factor can rise later without a schema change. `username` is stored
lower-cased with a `UNIQUE` constraint so registration races resolve at the DB
(`INSERT … ON CONFLICT (username) DO NOTHING` → rows-affected tells us if the name was taken).

This is also where the **1.3 FK lands later**: `characters.account_id → accounts.account_id`. 1.4
creates the parent table; 1.3 adds the child.

### 2. Password hashing — PBKDF2, dependency-free (see O2)

Use `System.Security.Cryptography.Rfc2898DeriveBytes` (built into .NET Standard 2.1 — **no new
NuGet**, unlike BCrypt). `PasswordHasher`:
- `Hash(password)` → generate a 16-byte random salt, derive a 32-byte subkey with SHA-256 and a
  fixed iteration count (e.g. 100k), return `"pbkdf2$100000$<salt_b64>$<subkey_b64>"`.
- `Verify(password, stored)` → parse the fields, re-derive with the stored salt/iterations, compare
  in **constant time** (`CryptographicOperations.FixedTimeEquals`).

Adequate for the hobby stage; 5.3 can bump the work factor or swap to Argon2/BCrypt behind the same
two-method interface without touching the schema (the algorithm tag is in the stored string).

### 3. Async credential check during the connect phase (the core risk)

Mirror's `NetworkAuthenticator` handlers run on the **main thread**, but the credential check is
**blocking DB I/O** — so it goes off-thread and resolves the connection on the callback, exactly the
1.2 pattern. Flow (modeled on Mirror's `ChatAuthenticator`, but DB- and async-aware):

1. **Client** (`OnClientAuthenticate`) sends `AuthRequestMessage { username, password, bool register }`.
2. **Server** (`OnAuthRequestMessage`): add `conn` to a `_pending` set (ignore duplicate requests),
   then `PersistenceService.Instance.LoadAsync(conn2 => Authenticate(conn2, msg), outcome =>
   Resolve(conn, outcome))`. `Authenticate` runs on the pooled connection off-thread:
   - **register=true:** `INSERT … ON CONFLICT (username) DO NOTHING RETURNING account_id` in a tx;
     0 rows ⇒ `UsernameTaken`; else hash the password, return `Created(account_id)`.
   - **register=false:** `SELECT account_id, password_hash` by username; missing ⇒ `BadCredentials`;
     `PasswordHasher.Verify` fail ⇒ `BadCredentials`; else update `last_login_at`, return
     `Ok(account_id)`.
   Returns a plain `AuthOutcome { Code, AccountId }` — Unity-free, safe to cross the thread.
3. **Server** `Resolve` (back on the main thread): remove from `_pending`; on success stash identity
   in `conn.authenticationData`, send success `AuthResponseMessage`, `ServerAccept(conn)`; on failure
   send the error response and `ServerReject` after a short delay (so the message is delivered first,
   same as the Chat example). Guard against the connection having dropped mid-lookup (check
   `conn.isReady`/still-connected before sending).

Writes that aren't on the latency path (e.g. `last_login_at`) could alternatively go through
`EnqueueSave`, but folding them into the same off-thread `Authenticate` call keeps the outcome
atomic and is simpler — they're cheap.

### 4. Connection → account mapping + session token

On accept, set:
```csharp
conn.authenticationData = new AccountSession { AccountId = id, Token = Guid.NewGuid().ToString("N") };
```
- **`AccountId`** is the seam 1.3/1.5 read at spawn (`GameNetworkManager.OnServerAddPlayer` /
  player `OnStartServer`) to resolve the character key.
- **`Token`** is a per-session random id. For 1.4 it lives only in `authenticationData` (in-memory);
  O3 decides whether it's also persisted to a `sessions` table (needed only once we want
  reconnection-resume / auditing — not yet). Recommended minimal: in-memory token now.
- **Single-login enforcement:** a server-side `Dictionary<long, NetworkConnectionToClient>
  _onlineByAccount`. If an account is already online, reject the new login (`AlreadyOnline`) — or
  kick the old one (O4). Cleared on `OnServerDisconnect`.

### 5. Host login

The host's **local client authenticates too** (so the host's player also maps to an account). Two
ergonomic options (O5): require the host to log in via the same UI, or auto-login a seeded dev
account in Host mode for fast iteration. Recommended: **seed a `dev` account and auto-fill the login
form** so testing stays one click, while the real handshake still runs.

### 6. Client login UI

A pre-connect `LoginUI` panel (uGUI, built by `SceneSetup` like the other canvases) shown while
`!NetworkClient.active`: username + password fields, **Login** and **Register** buttons, an error
label, and a server-address field. On submit it stores the credentials on the `AccountAuthenticator`
(client instance) and calls `StartClient()`; the authenticator sends them in `OnClientAuthenticate`.
`GameNetworkHUD`'s connect buttons are gated behind successful login (Host/Server-only buttons stay
for dev). Auth response code drives either entering the world or showing the error.

### 7. Lifecycle wiring

- Migration `0004_accounts.sql` via the existing runner.
- `AccountAuthenticator` component on the NetworkManager GameObject (auto-assigns to
  `NetworkManager.authenticator` via its `Reset()`), registers/unregisters message handlers in
  `OnStartServer`/`OnStopServer` and `OnStartClient`/`OnStopClient`.
- `GameNetworkManager`: read `conn.authenticationData` in `OnServerAddPlayer` (store account id where
  the player can read it); clear `_onlineByAccount` in `OnServerDisconnect`.
- `Tools/Database/Create Account` editor menu for seeding (incl. the `dev` host account).
- **`roadmap.md`** updated when this lands: note 1.4 implemented **before** 1.3, with the devplan link.

## Test plan

1. `Tools/Database/Run Migrations` → applies `0004` (`schema_version` gains a row); re-run → none pending.
2. **Register:** start Server, client enters a fresh username/password, **Register** → account row
   created (verify in `psql`: `password_hash` is a `pbkdf2$…` string, never plaintext), client enters
   the world.
3. **Login:** restart client, **Login** with the same creds → accepted, world entered, `last_login_at`
   updated.
4. **Wrong password / unknown user** → rejected with a generic "invalid credentials" error
   (no user-enumeration leak); connection closed; UI shows the error.
5. **Duplicate registration** (username taken) → rejected via the `ON CONFLICT` path; existing account
   untouched.
6. **Single-login** → log the same account in from a second client → rejected `AlreadyOnline`
   (or old session kicked, per O4); freed after the first disconnects.
7. **Account id at spawn:** log a debug line in `OnServerAddPlayer` showing the mapped `account_id` —
   confirms the seam 1.3 will consume.
8. **Host:** Start Host → seeded `dev` account auto-login (O5) → host player maps to the dev account.
9. **Tick-safety:** the async check doesn't stall the server; several rapid connect attempts resolve
   without hitching.
10. **DB-down:** with Postgres stopped, the server already aborts at start (1.1); if it drops after
    start, a login attempt fails closed (reject, logged) rather than accepting unauthenticated.

## Resolved decisions (approved 2026-06-21 — all recommendations)
- **O1 → In-client register.** Login/Register toggle creates the account if the username is free.
- **O2 → PBKDF2 via built-in `Rfc2898DeriveBytes`.** No new NuGet; work factor/alg swappable later.
- **O3 → In-memory session token** in `conn.authenticationData` (no `sessions` table yet).
- **O4 → Reject the new login** when the account is already online.
- **O5 → Seed a `dev` account + auto-fill/auto-login in Host mode** (real handshake still runs).

## Resolved / carried decisions
- **Transport stays unencrypted (KCP)** — encryption + hardened auth deferred to **5.3**. Plaintext
  credentials on the wire are an accepted hobby-stage risk.
- **Async, server-authoritative credential check** reusing 1.2's `LoadAsync` — no main-thread DB block.
- **Raw Npgsql + hand-written SQL** (carried from 1.1/1.2).

## Risks
- **Plaintext-on-wire** (transport unencrypted) — accepted, 5.3 fixes. Don't reuse real passwords.
- **Connect-phase async** — the connection can drop while the DB lookup is in flight; `Resolve` must
  null/▸connected-check before sending and not leak `_pending`/`_onlineByAccount` entries. Covered by
  removing on disconnect and guarding the callback.
- **No throttle** — brute-force/spam connects aren't rate-limited at this stage (5.3). Generic error
  messages avoid username enumeration in the meantime.

## Done when

A client must register/log in before entering the world; credentials are verified against
`accounts` with hashed passwords through the async (non-blocking) handshake; the authenticated
**account id rides on the connection** and is readable when the player spawns (the seam 1.3
consumes); duplicate/invalid/already-online logins are handled; and Host testing stays one-click via
the seeded dev account.
