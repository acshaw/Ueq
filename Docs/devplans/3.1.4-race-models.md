## Why

Onboarding needs a character that *looks* like the race/class you rolled. Today the Player prefab
hard-parents a single Synty child (Knight) — everyone is a knight regardless of choice. This item makes the
in-world body reflect the character, and turns character creation into the real **gender → race → class**
cascade the assets support. It also introduces **gender** as a first-class character attribute (it has never
existed; the conversation system already reserved a `<gender>` substitution token with nothing to fill it).

## The design (settled)

**Gender is picked first** and gates the rest: gender → available races → available classes.
**Race drives the body mesh; class drives the (future) weapon prop.** Every legal combination maps to a
model we own — the matrix falls out of the assets:

| Gender | Race | Class → body model |
|---|---|---|
| **Male** | Human | Warrior → `SM_Chr_Warrior` (PolygonAdventure) · Wizard → `SM_Chr_Male_Wizard_01` |
| **Male** | Dwarf | Warrior → Rivals `Dwarf` · Cleric → Rivals `Dwarf` (one body, both classes) |
| **Female** | Human | Warrior → `SM_Chr_Female_Gypsy_01` · Wizard → `SM_Chr_Female_Peasant_01` · Cleric → `SM_Chr_Female_Peasant_02` |

Falls out of what we own: no male-human-Cleric (only a female cleric body), no female Dwarf (the Rivals dwarf
is male). All three source packs are Humanoid (`animationType: 3`, one shared avatar each) so existing Mixamo
locomotion + Kick retarget onto every body with no new animation work. So resolution is a small
**(gender, race, class) → prefab** lookup, dwarf collapsing its two classes to one body.

## Current state (grounding)

- `RaceDefinition` (SO, `Resources/Races`) = `raceName` + `xpModifier` + 7 stat mods. **No model ref, no
  gender/class-availability data.** `ClassDefinition` similar (`Resources/Classes`). `RaceClassRegistry`
  loads both by name from Resources (M2.10 swaps the backing store for the DB behind the same lookups).
- Character creation: `CharacterSelectController.BuildAndSendList` sends flat
  `CharacterListMessage.raceOptions/classOptions` = `RaceClassRegistry.AllRaceNames()/AllClassNames()`;
  `CharacterSelectPanel.BuildCreate` shows Race/Class **cycle buttons**; `CreateCharacterMessage` = `{name,
  race, cls}`; server validates race/class via the registry then `CreateIdentity(... raceName, className)`.
- Persistence: `characters` table has `actual_race`/`apparent_race` + a class column; **no gender column**.
- Client already knows race: `PlayerFactionScores.ActualRace` is a `[SyncVar]`. Class name is server-side on
  `PlayerExperience.CurrentClass` (confirm sync during impl).
- The Player prefab's model is a static Synty child with an Animator (correct Avatar) + `PlayerAnimator`
  driving the `PlayerLocomotion` blend tree; `PlayerAbilities` finds `PlayerAnimator` via
  `GetComponentInChildren` (so a runtime-built model child is discovered).
- Legacy IMGUI `CharacterSelectUI.cs` (disabled at runtime, still in project) reads
  `raceOptions/classOptions` — **must stay compiling** if the message shape changes.

## Decisions

### RM1 — Availability + model data home — **recommend: one authored `CharacterRoster` ScriptableObject in `Resources`**
A single asset = ordered list of `RosterEntry { Gender gender; string race; string cls; GameObject modelPrefab; }`
— the 7 legal tuples above. It is simultaneously (a) the create-form option source, (b) the server-side
validation whitelist, and (c) the client model resolver. Load via a `CharacterRosterRegistry` (mirrors the
`RaceClassRegistry` pattern; M2.10 can move it to the DB behind the same lookups).
*Alt rejected:* spread "allowed genders / allowed classes" across `RaceDefinition` — class availability
depends on the **(gender, race) pair** (male-human ≠ female-human class lists), which a flat per-race field
can't express. One explicit roster asset matches EQ's fixed matrix and is trivially web-authorable later.

### RM2 — Gender as a persisted attribute — **recommend: `Gender {Male, Female}` enum, persisted, next migration `0018`**
Add `gender` to: `CreateCharacterMessage`, `CharacterListEntry` (roster display), the `characters` table
(migration `0018_character_gender.sql`, default `Male` for existing rows), and
`CharacterRepository.CreateIdentity`/snapshot/load. Store as a short text/int. This finally lets the
`<gender>` conversation token resolve (nice free win — wire the token read in `NpcConversation`).

### RM3 — Sync (gender, race, class) to the client — **recommend: a synced identity trio consumed by `PlayerModel`**
The client model builder needs all three. Race already syncs (`ActualRace`); add a `[SyncVar] Gender` and a
synced class name (either on a small new component or alongside `ActualRace`). `CharacterPersistence` sets
them on spawn from the loaded snapshot.

### RM4 — In-world model swap — **recommend: new `PlayerModel` component, runtime-instantiate the SM_Chr prefab**
Strip the static Synty child from the Player prefab. `PlayerModel` (client) on start reads the synced
(gender, race, class) → `CharacterRosterRegistry` lookup → `Instantiate` the model prefab under a `ModelRoot`
child at local `(0,-1,0)` → set the Animator's `runtimeAnimatorController = PlayerLocomotion` → add/rebind
`PlayerAnimator`. **Instantiate the full `SM_Chr_*` prefab** (ships Animator + correct Avatar) rather than a
bare mesh — this is the lesson from the 2026-06-17/18 T-pose saga (bare mesh ⇒ missing avatar ⇒ T-pose).
Keep `_defaultRace/_defaultClass` (+ a default gender) as the fallback when no character context (host-dev).

### RM5 — Creation UI cascade — **recommend: Gender → Race → Class cycle buttons, filtered from the roster**
Send the roster entries in `CharacterListMessage` (replace flat `raceOptions/classOptions`).
`CharacterSelectPanel.BuildCreate` adds a **Gender** cycle first, then **Race** filtered to that gender, then
**Class** filtered to that (gender, race); resetting an earlier pick clamps the later ones to valid values.
Keep the plain cycle-button style — the styled picker + **live 3D preview is 3.1.6**, not here. Update the
legacy IMGUI `CharacterSelectUI` just enough to compile against the new message shape (it's retired/disabled).

### RM6 — Weapon props (axe / mace / staff) — **recommend: OUT of 3.1.4, fold into 3.1.5**
3.1.4 = bodies + gender/race/class gating + persistence only. Attaching a class weapon prop to a hand socket
is a small self-contained follow-up; do it with the class work in 3.1.5 (Warrior axe/sword, Cleric mace,
Wizard staff), where the caster props from the Fantasy Characters pack also live.

### RM7 — Asset authoring (editor step) — **recommend: create Human + Dwarf races + the roster asset**
Author `RaceDefinition` assets in `Resources/Races` for **Human** (likely exists) and **Dwarf** (new; stat
mods TBD — e.g. +STA/+STR, −AGI/−INT, user tunes in the Race & Class Editor), and the `CharacterRoster` asset
with the 7 entries + model-prefab refs. Race system stays extensible for a real Elf later (just add rows).
**Do not `git add` the gitignored Synty packs** — the roster references prefabs inside them; committing the
roster asset with those refs is fine (refs are GUIDs), but the packs themselves stay local until adopted.
