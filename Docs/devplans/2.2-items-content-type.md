# Devplan 2.2 — Items (the reference content vertical)

**Roadmap item:** M2 → 2.2 (first real content type; the shape every later vertical copies)
**Status:** 🟢 Approved (2026-06-24) — D1 (Mirror catalog sync) and D4 (retire Resources now) confirmed with the user; D2/D3/D5 as recommended. Implementing.
**Depends on:** 2.1 ✅ (the rails — `/api` + `/web` + `ContentLoader`/`AssetResolver` seams + migration runner)
**Unblocks:** 2.3 (quests), 2.4 (loot/XP), 2.5 (abilities), 2.6 (races/classes), 2.7 (mobs) — all copy this pattern

---

## Goal

Migrate **items** from `Resources/Items/*.asset` (ScriptableObjects) to **Postgres + a web Item Editor**,
loaded by the server at startup and distributed to clients at runtime. Items are the reference vertical
because they're the **most-connected** content type — inventory, loot, vendors, and equipment all key off
`itemId` — so proving the full pattern here de-risks every type that follows.

> Direction (locked 2026-06-20): content lives in Postgres, authored in web editors, loaded by the
> **server at startup**; the DB is the source of truth and shipping content needs no Unity rebuild.
> Migration is per-type and hybrid — items keep working off `Resources/` until this lands, then that
> path is retired (D4).

### The new problem 2.2 must solve (that 2.1 didn't)
`content_ping` only had to reach the **server**. Item data is needed on **clients** too (inventory slot
names, tooltips, equip stat lines) — and clients must **not** touch Postgres (no DB creds on clients; ties
to the eventual hosted model). So 2.2 introduces a **content-distribution path to clients**: the server
loads from the DB and **syncs the catalog to each client over Mirror** on connect. Built once here,
reused by every later content type that clients need to see (abilities, races, …). This is the bulk of
the non-copy work.

### Scope guardrails
- **In scope:** `items` table + migration; server-side `ItemSnapshot`/`ItemRepository`/`ContentLoader`
  step populating `ItemRegistry` from the DB; the **generic Mirror catalog-sync** so clients get items;
  web **Item Editor** (Angular) + API entity/controller; retire `ItemRegistry`'s `Resources` path (D4);
  optional `icon_address` to exercise the 2.1 Addressables convention against a real type (D2).
- **Out of scope:**
  - Other content types (loot/abilities/etc. — later M2 items, even though they'll reuse the sync).
  - Inventory/equip **gameplay** changes — item *behavior* is unchanged; only where definitions come from.
  - Auth on the web stack (still trusted-local, per 2.1).
  - Wiring icon sprites into the inventory UI visuals — the *column + resolver* land here; the UI art pass
    is deferred (inventory is still text today).
- **Locked principle (unchanged):** migrations own schema; the web API does data CRUD only.

## Approach

### Data flow (extends 2.1)
```
Angular Item Editor ─HTTP─▶ .NET API ─EF─▶ Postgres ◀─Npgsql─ Unity SERVER (ContentLoader @ OnStartServer)
                                            items table          │ builds ItemDefinition instances → ItemRegistry
                                                                 ▼
                                                      Mirror catalog sync on connect
                                                                 ▼
                                                       Unity CLIENT → ItemRegistry (same API)
```

### 1. Schema — `items` table (D5: string PK)
One row per item. Columns mirror `ItemDefinition` 1:1 (flat — no child tables; items have no
collections):
- `item_id TEXT PRIMARY KEY` — the stable, human-readable key already referenced everywhere
  (`InventorySlot.itemId`, equipment, loot, vendors). Set in the editor; treated as immutable once referenced.
- `display_name TEXT`, `description TEXT`, `max_stack_size INT`
- `is_equippable BOOL`, `equip_slot INT` (the `EquipSlot` enum 0–12)
- `bonus_str/sta/agi/dex/int/wis/cha INT`
- `weapon_base_damage INT`, `weapon_delay REAL`, `weapon_range REAL`, `weapon_category INT` (`WeaponCategory`)
- `buy_price INT`, `sell_price INT`
- `icon_address TEXT NULL` (D2 — Addressables address; null = no icon)
- `updated_at TIMESTAMPTZ DEFAULT now()`

Migration `0009_items.sql` (next free; created by the existing runner).

### 2. Unity server — load items from DB into the registry
- `ItemSnapshot` — plain struct mirroring the row (also JSON-serializable for the client sync).
- `ItemRepository.LoadAll(conn)` — hand-written Npgsql read (1.2 DAL convention).
- `ContentLoader.LoadAll()` gains an **items step**: read snapshots → build runtime `ItemDefinition`
  instances (`ScriptableObject.CreateInstance` + copy fields) → `ItemRegistry.Register`. The registry's
  `Get(itemId)` API is unchanged; only its *source* moves from `Resources.LoadAll` to the DB.

### 3. Client distribution — generic Mirror catalog sync (the new infra)
- `ContentCatalogMessage { string itemsJson }` (Mirror `NetworkMessage`) — server serializes the loaded
  `ItemSnapshot` list to JSON (Newtonsoft, already in the project).
- Server sends it to each client on connect/ready; client handler deserializes and populates its
  `ItemRegistry` with runtime `ItemDefinition` instances (same builder the server uses).
- **Host short-circuit:** when `NetworkServer.active` the registry is already populated — skip the rebuild.
- Designed generic: as later types migrate, the message carries their JSON too (or one message per type) —
  the serialize→send→rebuild shape is reused, not reinvented.

### 4. Asset binding (D2)
`icon_address` stores an Addressables address resolved through 2.1's `AssetResolver.LoadAsync<Sprite>`.
2.2 lands the column + the resolve call site (tooltip/slot can ask for the sprite); making the inventory
visually show icons is a later UI pass.

### 5. Web Item Editor (copy the 2.1 ping pattern, fleshed out)
- **API:** `Item` EF entity (mapping-only, onto `items`) + `ItemsController` CRUD, mirroring
  `ContentPing*`. `item_id` is the route key (string).
- **Angular:** `ItemService` + an Item Editor view — list on the left, a form on the right with sections
  matching the Unity Item Editor (Identity, Stackable, Equipment + slot, Stat Bonuses, Weapon Stats,
  Economy, Icon address). Replaces the ping smoke component as the app's first real screen.

### 6. Retire the Resources path (D4)
Once DB load + sync works, `ItemRegistry.Awake`'s `Resources.LoadAll<ItemDefinition>("Items")` is removed
(server loads from DB; clients from the sync). Existing `Resources/Items/*.asset` are migrated into the DB
first (one-time seed/import — see test plan) so nothing is lost.

## Schema / API changes
- **Migration:** `0009_items.sql` — the `items` table above.
- **API:** new `Item` entity + `ItemsController` (CRUD over `items`, `item_id` key).
- **Unity:** `ItemSnapshot`, `ItemRepository`, `ContentLoader` items step, `ContentCatalogMessage` +
  send/receive handlers, a shared `ItemDefinition` builder; `ItemRegistry.Awake` Resources load removed.

## Test plan
1. **Migrate existing items:** import current `Resources/Items/*.asset` into the `items` table (a one-time
   editor tool or hand-seed) so no item is lost when the Resources path is retired.
2. **API:** CRUD `items` via curl/Swagger; `item_id` string key works.
3. **Angular:** Item Editor lists/creates/edits/deletes; sections persist all fields.
4. **Server load:** host start → `ContentLoader` logs N items; `ItemRegistry.Get("…")` returns a DB-backed
   def (spot-check a vendor/loot/equip path still resolves names + stats).
5. **Client sync:** a non-host client (MPPM virtual player) sees correct item names/stats in inventory +
   tooltips — proving the catalog reached the client without DB access.
6. **Asset binding:** an item with an `icon_address` resolves a sprite via `AssetResolver` (log/echo; full
   UI display deferred).
7. **Regression:** loot drop → inventory → equip (stat bonus applies once) → vendor buy/sell, all against
   DB-backed items.

## Open decisions (recommendations first)
- **D1 — Client content distribution:** ✅ recommend **generic Mirror catalog sync** (server loads DB →
  JSON → message → client rebuilds registry). Alt: clients keep loading `Resources` (drift, defeats the
  migration); clients query DB (rejected — no client DB creds, breaks hosted model). This is the one piece
  of real new infrastructure; building it generically now pays off for every later type.
- **D2 — Icon binding now or later:** recommend **add `icon_address` column + resolver call site now**,
  defer the inventory-UI art. Validates 2.1's Addressables convention against a real type cheaply. Alt:
  omit icons entirely from 2.2 (less to test, but leaves the asset convention unproven on a real type).
- **D3 — Catalog sync granularity:** recommend **one `ContentCatalogMessage` per content type** (items
  now), not a single mega-message — keeps each type independent as the library grows. Alt: one combined
  message (simpler now, couples types later).
- **D4 — Retire Resources path:** recommend **remove it in this item** (after migrating existing assets to
  DB) so there's a single source of truth and no drift. Alt: keep `Resources` as a fallback (hybrid)
  one more milestone — safer rollback, but two sources to keep in sync.
- **D5 — Item PK:** recommend **`item_id TEXT` primary key** (the existing cross-system reference;
  human-readable, stable). Alt: surrogate `BIGSERIAL` + unique `item_id` (extra indirection for no gain —
  everything already references the string).

## Risks
- **Client-sync timing** — the catalog must arrive **before** the client renders inventory/tooltips that
  read it. Sequence the send on connect/ready and have UI tolerate a not-yet-populated registry briefly.
- **Runtime ScriptableObject instances** — building `ItemDefinition` via `CreateInstance` on load (server
  + client) instead of asset refs; make sure nothing relies on asset identity/`name` (spot-check
  equip/vendor/loot which currently look up by `itemId`, so should be fine).
- **Data migration fidelity** — moving existing `Resources/Items` into the DB must preserve every field
  exactly (stat bonuses, weapon stats, prices) or balance/equip breaks. Verify with the regression path.
- **Two readers, one schema** — API (EF mapping-only) and Unity (`ItemSnapshot`) both map the `items`
  columns by hand; a column add must touch both. (Known M2 type-drift risk; shared model lib is the
  eventual fix.)

## Implementation (2026-06-24)

Built; Unity-side awaits the editor (DB + API + Angular legs verified headless).

**DB / seed:**
- `0009_items.sql` — the `items` table (flat, `item_id TEXT` PK, `icon_address` nullable).
- `DatabaseSeeder.SeedStarterItems` — idempotent `ON CONFLICT DO NOTHING` insert of the 4 existing
  Resources items (`tunic`, `rat_paw`, `rat_ear`, `rat_whisker`) with their exact field values, so the
  game keeps working after the Resources path is retired. The web editor owns edits thereafter.

**Unity (compiles in-editor):**
- `ItemSnapshot` (shared plain data; no asmdefs so it's visible server + client) + `ItemRepository`
  (Npgsql read).
- `ItemRegistry` — `LoadFrom(snapshots)` builds runtime `ItemDefinition` instances; `Resources.LoadAll`
  **removed** (D4). `Get(itemId)` API unchanged. Added `IsPopulated`.
- `ContentLoader` — items step (populates the server registry + caches `Items` for the sync); the 2.1
  `content_ping` step dropped.
- `ContentCatalog` — `ItemCatalogMessage` (JSON via Newtonsoft) + server `BuildItems` / client
  `ApplyItems` (host short-circuits — shares the server registry).
- `GameNetworkManager` — registers the catalog handler in `OnStartClient`, sends it in `OnServerReady`
  (before player spawn), unregisters in `OnStopClient`.

**.NET API (`/api`, verified):** `Item` entity (mapping-only) + `Items` DbSet mapping + `ItemsController`
full CRUD keyed by `item_id`. **Verified end-to-end against Postgres** via curl: create (all fields incl.
`icon_address`), 409 on duplicate id, 400 on missing id, GET, PUT full update, 204 delete. *(Built to a
scratch dir + ran on port 5099 because the user's 2.1 API on 5144 was still running and locking `bin`.)*

**Angular (`/web`, verified build):** `ItemService` + a master/detail Item Editor (Identity, Equipment,
Stat Bonuses, Weapon, Economy, Icon sections); replaced the ping smoke screen (deleted
`content-ping.service.ts`). `ng build` succeeds.

**Legacy (harmless, defer to a 2.8 cleanup):** the 2.1 `content_ping` table, `ContentPingRepository`,
and the API's `ContentPingController` remain but are no longer used by the loader/app. The Unity
`ItemEditorWindow` still creates ScriptableObjects but those no longer load at runtime (DB is the source
now) — superseded by the web editor.

**Remaining (in-editor, user):**
1. ⚠️ **Restart your running API** — the one on `localhost:5144` (PID 35540) is the pre-items 2.1 build
   and is locking `bin`; Ctrl+C it and `dotnet run` again to get the items endpoints (and free the lock).
2. Reopen Unity → recompile the new scripts.
3. `Tools/Database/Run Migrations` → applies `0009` (`CREATE TABLE IF NOT EXISTS` no-ops since the API
   smoke test already created `items`; records version 9). Host start then seeds the 4 starter items.
4. **Host:** expect `[Content] Loaded 4 item(s)…`; confirm loot/inventory/equip(stat bonus once)/vendor
   still resolve names + stats (now DB-backed).
5. **Remote client (MPPM virtual player):** expect `[Content] Client received 4 item(s)…`; confirm
   inventory/tooltips show correct names/stats — proves the catalog reached the client without DB access.
6. **Web:** `cd web && npx ng serve` → `localhost:4200`; add/edit an item → restart Host → see the new
   count logged and the item usable in-game.

## Done when
Items are authored in the web Item Editor, stored in Postgres, loaded by the server at startup, and synced
to clients over Mirror; `ItemRegistry`'s `Resources` path is retired with existing items migrated into the
DB; loot/inventory/equip/vendor all work against DB-backed items on both host and a remote client. The
catalog-sync + asset-binding patterns are proven on a real type and ready for 2.3+ to copy.
