# 8.6 — Area population spawner (population zones)

**Status:** 🟡 Awaiting review.
**Roadmap item:** M8 → 8.6 (added 2026-09-20, after the point-based items 8.1–8.5 — a distinct spawning
model, not a variant of them).
**Pattern:** a new `IWorldPlacement` marker (`PopulationZone`) that *references* a `WanderRegion` for its
geometry rather than defining its own shape — plus a small, additive extension to `WanderRegion` itself
(a `Polygon` shape) so the geometry problem is solved once, for every consumer, not just this one.
**Scope note:** unlike 8.1–8.5, this item needs **no DB migration, no API change, and no Angular change**
for its first pass — see PZ6.

---

## Goal & why now

Requested directly: an irregularly-bounded area (e.g. "grassland east of the road, west of the shoreline,
north of the forest") that maintains a population ceiling (e.g. at most 10 wolves) rather than a fixed set
of discrete camps. Each death independently starts its own 2-5 minute countdown toward one replacement —
so sustained hunting pressure can genuinely drain the population toward 0, which is the intended behavior,
not a bug to guard against. This is a different mechanism from every other M8 item: those are all
point-based (`SpawnPoint`, one location, one respawn cycle per group); this is area-based (a shared
ceiling across a whole region, N independent replacement timers in flight at once).

Deliberately **out of scope**: density-aware "intelligent" wander that biases mobs toward filling the
space evenly. At the population sizes under discussion (≤10 in a real-sized field), plain independent
random wander — which `WanderBehavior` already does — reads as adequately spread in practice; building
real inter-mob distribution logic (repulsion fields, grid-fill heuristics) is disproportionate AI
investment for a mostly-invisible payoff at this scale. PZ5 below gives a cheap upgrade path if it's ever
actually needed.

## Current state (grounding)

- `WanderRegion` (3.1.11) supports **Box or Sphere only** (`RandomPointInVolume()`) — no polygon. This is
  the actual blocker for "east of the road, west of the shoreline, north of the forest": a box/sphere can
  only approximate an irregular natural boundary, either clipping part of the intended area or bleeding
  into the excluded parts (the road, the water).
- **`BoundedRegion.TryGetRandomPoint`** (`IWanderRegion.cs`) already does exactly "sample a raw point from
  the region, then `NavMesh.SamplePosition` snap it" — the full pipeline a population zone needs for
  placing a new spawn, not just for ongoing wander. **This item needs zero new sampling/snapping code** —
  it reuses `new BoundedRegion(region).TryGetRandomPoint(...)` verbatim for initial spawn placement.
- **`EnemyAI`'s leash/return already degrades correctly with no fixed per-mob home.** `EnterReturn()` calls
  `_movementBehavior.GetReturnAnchor(_spawnPoint)`; for a `BoundedRegion`, `GetReturnAnchor` returns
  `currentPos` ("reset in place"), ignoring `_spawnPoint` entirely. **Verified — zero `EnemyAI` changes
  needed.** A population-zone mob that disengages from combat just resumes wandering from where it is,
  exactly the semantics wanted (no walking back to a literal spawn coordinate it doesn't meaningfully have).
- `SpawnPoint.SpawnOne` already handles zone-scene assignment (`SceneManager.MoveGameObjectToScene` if the
  spawn point's own scene differs from the active scene) — the same one-line pattern a `PopulationZone`
  needs, since it's just as much a placed-in-a-zone-scene object.
- `SpawnTable`/`SpawnTableRegistry`/`MobRegistry` are fully reusable as-is for "what spawns" — no new
  content-authoring concept needed there.

## Decisions (recommendations in **bold**)

**PZ1 — Geometry: extend `WanderRegion` with a `Polygon` shape, don't invent a parallel type.**
**Add `Shape.Polygon`, sampled via rejection sampling within the polygon's XZ bounding box + a
point-in-polygon test (ray-casting/winding-number — correct regardless of convexity; a natural boundary
like this is very plausibly non-convex).** Vertices are **ordered child transforms**, the exact same
authoring convention `PatrolRoute` already uses (and the project's trail tools before that) — no new
gesture for the user to learn. Cap the rejection loop (e.g. 30 attempts) falling back to the polygon's
centroid on a degenerate/self-intersecting shape rather than looping forever. *Alt considered:*
triangulation-fan sampling (uniform-by-area, more "correct" statistically) — rejected for this scope;
ear-clipping a possibly-non-convex polygon is real geometry work for a difference nobody will perceive at
sub-30-vertex, sub-10-population scale. **Side benefit:** any future bounded `SpawnPoint` (not just
population zones) can use a `Polygon` `WanderRegion` too, for free.

**PZ2 — A new `PopulationZone` component, separate from `WanderRegion`, referencing it.** **`PopulationZone
: MonoBehaviour, IWorldPlacement, IReferencesOtherPlacements`** — mirrors how `SpawnPoint` already
references a `WanderRegion` by placement id (two-pass resolution, `_pendingWanderRegionPlacementId` →
`ResolveReferences`). Keeps "what area" (`WanderRegion`, now polygon-capable) decoupled from "how many
mobs live here and how they replenish" (`PopulationZone`) — the same separation of concerns already
established between `SpawnPoint` and `WanderRegion`, and it means one authored polygon could later be
shared by a population zone *and* an ordinary bounded `SpawnPoint` if ever wanted.

**PZ3 — Population maintenance model.** **Each death schedules its own independent respawn coroutine** —
not a periodic "check if under cap, top up" tick. On `OnMemberDied`: remove from `_live`, start
`RespawnAfterDelay()` (rolls `respawnBase ± respawnVariance`, e.g. 210s ± 90s for a literal 2-5 minute
range), then — if the zone is still active (PZ4) and still under `maxPopulation` when the timer fires —
spawn exactly one replacement at a fresh random point in the region. This is what makes "several players
can outpace the respawns and drain the population to zero" fall out naturally: nothing tops up faster than
one-slot-per-death-timer, so sustained kill pressure simply exceeds the refill rate. Initial fill (at
first activation) spawns up to `maxPopulation` immediately, each at its own independently-rolled point —
already naturally scattered, no staggering needed for correctness (a small optional stagger, spawning one
every 1-2s instead of all at once, is a one-line nicety if instant mass pop-in looks bad, not core to the
design).

**PZ4 — Activation gating.** **Mirror `SpawnPoint.ActivationCheck` exactly: a 5s proximity poll (any
player within some radius of the zone) gates both initial fill and whether a fired per-death timer is
allowed to actually spawn its replacement right now.** If a replacement timer fires while no player is
nearby, it just waits and re-checks on the next activation tick rather than spawning into an empty area —
consistent with the rest of the spawn system's "don't do simulation work where nobody is" philosophy.
**Consequence worth being explicit about:** a zone hunted to 0 and then abandoned by players will sit at 0
until someone returns — arguably correct (nobody's there to notice or care), but a real behavioral choice,
not an oversight. *Alt (if a true always-simulating ecosystem is wanted instead):* let per-death timers
fire unconditionally regardless of player proximity — simpler mentally, costs maintaining live
NavMeshAgent-driven mobs in zones nobody's visiting. Flagging both rather than picking silently, since it's
a real tradeoff between "the world feels alive even unobserved" and "don't spend CPU on empty areas,"
and this project has consistently chosen the latter everywhere else (`SpawnPoint` itself included).

**PZ5 — Distribution "fill evenly" upgrade path (not built now, per Goal).** If clustering ever becomes an
actual observed problem: the rejection-sampling loop PZ1 already has is the natural place to add one more
rejection criterion — "and not within `K` units of another currently-live zone member" — cheap to bolt on
later (a `_live` position check inside the existing retry loop) rather than a rewrite. Documented here so
a future session doesn't have to re-derive where this would go.

**PZ6 — Authoring: Unity-only for this pass, no DB/API/web work.** **`PopulationZone`'s config
(`spawnTableId`/`mobId`, `maxPopulation`, `respawnBase`/`respawnVariance`, the `WanderRegion` reference)
rides the existing generic `world_placements.data` JSONB blob exactly like `WanderRegion`/`PatrolRoute`
already do** — no new table, no new API entity, no new Angular editor needed for the sync/import round
trip to work (2.7.3's Stage A/B already handle "a new marker type implementing `IWorldPlacement`" as a
zero-other-code-change case, per its own WP1 design goal — this is close to a real test of that claim).
Web *editability* (the way `SpawnPoint`'s `spawnTableId`/`mobId` are dropdown-editable in the Placement
Editor, WP7) is explicitly **not** built in this pass — a `PopulationZone` row would show as read-only JSON
in the web Placement Editor, same treatment `PatrolRoute`/`WanderRegion` rows already get. Flag as a
fast-follow only if hand-tuning population/timer numbers from the web turns out to matter in practice.

**PZ7 — `SpawnTableEntry.groupSize` is ignored in this context.** A population zone fills **one slot per
roll**, regardless of an entry's authored `groupSize` (which means something different for a point-based
camp — "spawn this many together at once"). Worth stating explicitly in code comments so a future reader
doesn't wonder why it's unused here, rather than silently reinterpreting a field's meaning without a note.

## Files (once approved)

**New:** `Assets/Scripts/NPC/PopulationZone.cs` (the component itself — placement interface, activation
poll, per-death respawn scheduling, initial fill), a matching `IPlacementFactory` registration in
`PlacementFactories.cs`, drag-in prefab under `Assets/Prefabs/Zones/` (mirrors `WanderRegion`/`PatrolRoute`),
an Editor authoring helper analogous to `Tools/Zones/Add Patrol Waypoint` for adding polygon vertices
(could plausibly be the *same* tool generalized, since both are "append an ordered child transform" —
worth checking whether unifying them is cleaner than a parallel `Add Region Vertex` command).
**Modified:** `WanderRegion.cs` (`Shape.Polygon`, `RandomPointInVolume`'s rejection-sampling branch,
`CapturePlacementData`/`ApplyPlacementData` gain polygon vertices using the same scene-owned-position
convention `PatrolRoute` already established for its waypoints, `OnDrawGizmos` gains a closed-polyline
draw for the new shape).

## Test plan

1. Author an irregular (non-convex) polygon `WanderRegion` and a `PopulationZone` referencing it, table
   → wolves, `maxPopulation = 10`, respawn 210s±90s. Confirm initial fill spawns up to 10, all inside the
   polygon (spot-check a few obviously-outside-a-bounding-box points near polygon concavities never get
   used), none inside the excluded road/shoreline notches.
2. Kill several wolves in quick succession with multiple players → confirm population trends down, each
   killed wolf's replacement arrives independently ~2-5 minutes after *that* wolf's death, not in lockstep.
3. Kill wolves faster than the timers refill → confirm population can reach 0 and stays there under
   sustained pressure (the explicitly-expected behavior).
4. Combat/leash: aggro a wolf, kill something or disengage → confirm it resumes wandering from wherever it
   ended up, not walking back to a specific "home" point (PZ2/grounding claim, direct verification).
5. Placement sync round-trip: sync a scene with a polygon `WanderRegion` + `PopulationZone` to the DB
   (`Tools/Zones/Sync Placements to Database`), restart, confirm both re-resolve and the polygon's vertex
   *positions* survive untouched while non-spatial config still refreshes (same test shape 2.7.3 already
   runs for `PatrolRoute`/`WanderRegion`).

## Risks

- **Non-convex polygon degenerate cases** — a self-intersecting or near-zero-area authored shape could
  make rejection sampling spin; the capped-retry-then-centroid-fallback (PZ1) bounds this, but worth a
  console warning if the fallback is ever actually hit, so a bad authoring mistake is visible rather than
  silently producing a mob that always spawns dead-center.
- **PZ4's activation semantics are a real design choice, not a default to skip past** — flagged explicitly
  so it's confirmed rather than assumed; the "always simulating" alternative is a one-line change
  (drop the activation gate on the respawn-timer path) if wanted later.
- **Unifying the polygon-vertex authoring tool with `Tools/Zones/Add Patrol Waypoint`** is called out as
  worth checking, not decided here — if the existing tool is tightly coupled to `PatrolRoute` specifically
  rather than "append an ordered child to whatever's selected," a parallel command is the pragmatic
  fallback rather than forcing a shared-tool refactor into this item's scope.

## Done when

An irregular (non-box/sphere) area can be authored, a `PopulationZone` referencing it maintains a target
population via independent per-death respawn timers, can be driven to zero under sustained hunting
pressure, and mobs wander/leash correctly within the polygon with zero `EnemyAI` changes required.
