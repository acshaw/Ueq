# 4.1 — Server-Authoritative Movement Core

**Status:** ✅ Done — verified in-editor 2026-07-13. SA1–SA9 applied as recommended.

## Goal
Retire the current client-predicted-with-no-reconciliation movement hybrid and make the **server** the single
source of truth for player position/rotation — for *every* viewer, including the owning client's own screen.
This is the foundation M4 exists to lay before combat depth (5.1) and any PvP sit on trustworthy positions.
Deliberately **not** re-adding client prediction here (that's 4.2) — after 4.1 lands, the owner's own movement
will feel laggier (bound by round-trip time) than it does today. That is the accepted, temporary cost of doing
this in the right order: land pure authority first, then reintroduce prediction *with* reconciliation (4.3),
rather than patching the existing predict-no-reconcile hybrid in place.

## Current architecture (grounding — read `NetworkedPlayer.cs` + the vendored Mirror `NetworkTransformReliable`)

**Today's `Update()` in `NetworkedPlayer.cs`:**
```csharp
if (isLocalPlayer) { CollectInput(); ApplyLook(); ApplyMovement(); CmdSendInput(...); }
else if (isServer)  { ApplyMovement(); }
```
The owning client applies movement **locally and immediately** (`_cc.Move(...)` in `ApplyMovement()`), then
separately tells the server what input it used via `CmdSendInput`. The **server independently re-simulates**
the same input in its own `ApplyMovement()` call (different branch, own `CharacterController`/gravity
integration) — these two simulations can diverge on anything timing-sensitive (collisions with other
players being the case that surfaced it, 2026-07-05: pushing one player into another shows each side a
different, permanently-diverged result, and the *server's* copy — the authoritative one — is the wrong one
from the pusher's perspective, so range/targeting checks read off a phantom position). **There is no
correction step**: the owner's local prediction is never reconciled against the server's outcome.

**Why observers see the server's position at all today, despite `Player.prefab`'s `NetworkTransformReliable`
being configured `syncDirection: 1` (= `ClientToServer`):** this setting is effectively **dead** given how the
owner's copy is handled. `NetworkedPlayer.OnStartLocalPlayer` disables the local player's own
`NetworkTransform*` component outright on non-host clients (`if (!isServer) { ...b.enabled = false... }`), so
the owning client's NT never runs its send logic at all — the `ClientToServer` half of the contract is never
exercised. What actually reaches observers is that `NetworkTransformReliable.LateUpdate()` marks the component
dirty **whenever `isServer` is true**, unconditionally, regardless of `syncDirection` — so the *server's own*
transform (kept current by its independent `ApplyMovement()` call) is what gets broadcast to every observer.
In effect the game already behaves as `ServerToClient` for everyone except the owner, who instead renders
their own uncorrected local simulation. **`Enemy.prefab`'s `NetworkTransformReliable` is already the sane
default** (`syncDirection` left at its `ServerToClient` default — see `SceneSetup.AddEnemyNetworkTransform`'s
comment) — it's specifically the Player prefab that was flipped to `ClientToServer` as part of an earlier,
abandoned client-authoritative attempt, then partially undone by the runtime disable hack, leaving today's
confusing hybrid.

**The real technical obstacle to full authority (not just a config flip) — read `NetworkTransformBase.cs` /
`NetworkTransformReliable.cs` in `Assets/Mirror/Components/NetworkTransform/`:**
`NetworkTransformReliable.UpdateClient()` gates ALL snapshot-interpolation application on
`if (!IsClientWithAuthority)`, where `IsClientWithAuthority => isClient && authority` — a **raw connection-
ownership check that does not consult `syncDirection` at all**. That means even after (a) flipping
`syncDirection` to `ServerToClient` and (b) no longer disabling the component on the owner, the owning
client's own `UpdateClient()` would still skip applying incoming server snapshots to itself — Mirror's stock
component assumes "if you own it, you're driving it locally," which is exactly the assumption 4.1 needs to
remove for the owner. **This needs a small subclass**, not just a settings change (see SA3).

**Everything else already reads position/rotation generically and needs no change:** `PlayerAnimator` drives
its blend tree from `transform.position` delta each frame regardless of what set that position (already
proven — this is exactly how remote players animate correctly today); rotation already syncs via
`syncRotation = true` (3.0.1 fix, forced at runtime in `Awake`); `PlayerSitting`'s body-yaw-freeze and
auto-stand-on-move already run server-side inside `CmdSendInput`; zone transitions/respawn/`/unstuck` already
route through `NetworkTransformBase.ServerTeleport` (never a raw position set), which is untouched by this
devplan's changes.

## Decisions

### SA1 — Scope: authority only, no prediction — **CONFIRMED (per roadmap's own phased plan)**
4.1 makes the server the sole mover. The owner's own screen will lag input by roughly the round-trip time
plus Mirror's default interpolation buffer (typically ~2 send intervals) until 4.2 restores local prediction
correctly. This is a known, temporary UX regression — not a bug to chase during 4.1's own verification.

### SA2 — Unify `Update()`'s movement gate to `isServer`, drop the local-prediction call — **RECOMMEND**
```csharp
void Update()
{
    if (isLocalPlayer)
    {
        // target-loss cleanup (unchanged)
        CollectInput();
        ApplyLook();          // local-only camera/pitch — never needs to be authoritative
        CmdSendInput(_moveInput, _yaw, _sprint, _jumpQueued);
        _jumpQueued = false;  // consumed by sending, not by a local ApplyMovement anymore
    }
    if (isServer) ApplyMovement(); // the ONLY place movement is simulated now — host's own player included
}
```
This is a genuine simplification, not just a restriction: today's branchy `if (isLocalPlayer) {...} else if
(isServer) {...}` (two different call sites for the same method, one of which double-runs the exact same
input) collapses to one unconditional server-gated call that covers host + every remote-owned copy uniformly.
**Required companion fix in `CmdSendInput`:** the existing `if (jump && !isLocalPlayer) _jumpQueued = true;`
guard exists ONLY because host used to consume jump locally in the same frame before the Cmd handler ran; once
`ApplyMovement()` never runs locally for anyone, that guard must become unconditional (`if (jump) _jumpQueued =
true;`) or host's own jump will never register.

### SA3 — A small subclassed NetworkTransform so the owner also applies server snapshots — **RECOMMEND**
New `Assets/Scripts/Networking/ServerAuthoritativeTransform.cs : NetworkTransformReliable`, overriding the
`protected virtual void UpdateClient()` method to interpolate + apply snapshots unconditionally (drop the
`IsClientWithAuthority` skip — every client, owner included, is just an observer of server truth now). This
follows the project's own established precedent of subclassing a vendored Mirror component instead of editing
the package (`ZoneInterestManagement : SceneInterestManagement`, `Docs/devplans/3.0-zone-integration.md`).
Swap `Player.prefab`'s `NetworkTransformReliable` component for this subclass (same serialized fields —
`syncPosition`/`syncRotation`/interpolation/etc. all carry over unchanged, `Apply()`/`OnSerialize()`/
`ServerTeleport()` are inherited as-is).

### SA4 — Flip `syncDirection` to `ServerToClient` + delete the runtime owner-disable hack — **RECOMMEND**
`Player.prefab`'s NT `syncDirection` goes from `1` (`ClientToServer`, today effectively dead per the grounding
above) to `0` (`ServerToClient`, matching `Enemy.prefab`'s already-correct default) — makes the *serialized*
config match what actually happens, rather than relying on a runtime workaround to paper over a live-but-inert
misconfiguration. Remove the `OnStartLocalPlayer` block that finds-and-disables any `NetworkTransform*`
component by name (`Assets/Scripts/Networking/NetworkedPlayer.cs:113-123`) — with SA2/SA3 in place there's no
longer a local simulation for it to protect from being overwritten.

### SA5 — Rotation, sitting, zone teleports — **CONFIRM NO CHANGE NEEDED, VERIFY IN TEST PASS**
- Rotation: already server-set (`CmdSendInput`'s `transform.eulerAngles = ...` when not sitting) and already
  synced (`syncRotation = true`, forced in `Awake`) — `Apply()` is inherited unchanged by the SA3 subclass, so
  this should carry over with no code change; just re-confirm in testing (remote players still visibly turn).
- Sitting (3.1.7): `PlayerSitting`'s freeze/auto-stand is already invoked server-side from `CmdSendInput` —
  already "server-authoritative" by construction. The camera-height ease and seated free-look in `ApplyLook()`
  are purely local/cosmetic (camera is never networked) and need no change.
- Zone transitions / `/unstuck` / respawn / character-select spawn: all route through
  `NetworkedPlayer.ServerWarpTo` → `NetworkTransformBase.ServerTeleport(position, rotation)`, inherited
  untouched by the SA3 subclass — re-verify the round-trip still snaps cleanly (no interpolation-into-teleport
  smear) since that's exactly the failure mode `ServerTeleport` exists to prevent.

### SA6 — CharacterController on non-authoritative copies — **CONFIRMED, NO CHANGE**
On every copy except the server's own simulation, nothing calls `_cc.Move()` anymore (not even the owner, per
SA2) — the CC sits enabled but passive, which is exactly how remote-observer copies already behave today
(nobody calls `Move()` on a copy that's neither `isLocalPlayer` nor `isServer`). This is desirable, not
incidental: the capsule collider needs to stay live so raycasts/targeting/other players' physics still hit it.
Direct `transform.position` writes (what `NetworkTransformBase.SetPosition` does) don't fight an idle CC — no
enable/disable toggling needed on the per-frame interpolation path (unlike the one-shot teleport path, which
already toggles CC deliberately for a different reason — avoiding CC "correcting" a large instantaneous jump).

### SA7 — Enemy/mobs — **OUT OF SCOPE, UNCHANGED**
Mobs have no owning client to disagree with the server in the first place; `Enemy.prefab`'s NT is already
`ServerToClient` (the correct default) and unaffected by anything here.

### SA8 — Expected UX regression during 4.1's own testing — **ACKNOWLEDGE, DON'T CHASE**
The owner's movement will visibly lag input (RTT + interpolation buffer) after this lands — this is the
intended, temporary state per SA1, not a defect to fix inside 4.1. Note it for the record so 4.2/4.3's "done"
bar (own-movement feels responsive again) is judged against a known baseline, not confused with a regression.

### SA9 — Test plan
1. **Solo (Host):** walk/sprint/jump feel laggier than before (expected, SA8) but arrive at the correct final
   position; no jitter/rubber-banding at rest.
2. **Two clients (Server Only + 2 remote MPPM clients):** the core bug this closes — push one player into
   another; **all three views (both players' own screens + a third observer) must agree** on the resulting
   position, unlike today where the pusher's own screen disagrees with everyone else's.
3. Rotation still visible on remote clients (3.0.1 regression check).
4. Sitting: `/sit`, auto-stand on move/damage, seated free-look + camera height ease all still work.
5. Zone transitions (creslins⇄thornwood), `/unstuck`, death respawn, and login-into-persisted-zone all still
   teleport cleanly (no smear/rubber-band into the new position).
6. Jump works for the host's own player (SA2's required `CmdSendInput` fix) as well as for remote clients.

## Done when
A pushed/colliding player's position agrees across every client (owner + all observers) with no permanent
divergence; rotation, sitting, zone teleports, and respawn all still work exactly as before. The owner's
movement feeling laggier than pre-4.1 is expected and explicitly NOT a blocker — that's what 4.2 (client
prediction) + 4.3 (reconciliation) exist to fix next.

## Deferred / backlog seeds

## Implementation log (2026-07-12)
Implemented as SA1–SA9 recommended, code only — not compiled/tested in-editor (no Unity instance available
to this session; pending in-editor verification per this project's usual pattern).

- **NEW `Assets/Scripts/Networking/ServerAuthoritativeTransform.cs`** (SA3) — subclass of Mirror's
  `NetworkTransformReliable` overriding the virtual `UpdateClient()` to always interpolate + apply incoming
  snapshots, dropping the stock `IsClientWithAuthority` skip that otherwise exempts the owning connection.
  Only handles the non-fixed-update path (`useFixedUpdate = false`, this project's setting — the fixed-update
  buffer field is private on the base class and unreachable from a subclass); falls back to `base.UpdateClient()`
  if that flag is ever turned on. New guid `f26cbbf604a1223a7bc5516147c9547f`.
- **EDIT `Assets/Prefabs/Player.prefab`** — swapped the `NetworkTransformReliable` component's `m_Script` to
  the new subclass and flipped `syncDirection` from `1` (`ClientToServer`) to `0` (`ServerToClient`, matching
  `Enemy.prefab`'s already-correct default). All other serialized fields (interpolation, sensitivity,
  `syncPosition`, etc.) are inherited unchanged and carried over as-is (no new serialized fields on the
  subclass).
- **EDIT `Assets/Scripts/Networking/NetworkedPlayer.cs`**:
  - `Update()` restructured (SA2): the owner no longer calls `ApplyMovement()` locally — it only collects
    input, drives its own (cosmetic, unsynced) camera, and sends input via `CmdSendInput`. `ApplyMovement()`
    now runs from a single unconditional `if (isServer)` check, covering host's own player and every
    remote-owned copy uniformly (collapsing the old two-call-site branch).
  - `OnStartLocalPlayer` — removed the runtime block that disabled the owner's own NetworkTransform (SA4);
    no longer needed since the owner now renders through `ServerAuthoritativeTransform` like any observer.
  - `CmdSendInput`'s jump handling — dropped the `!isLocalPlayer` guard (SA2's required companion fix): that
    guard only existed to stop host's local `ApplyMovement()` from double-consuming a queued jump in the same
    frame; since `ApplyMovement()` never runs locally anymore, the guard would have silently swallowed host's
    own jumps. Found a related host-specific ordering subtlety while implementing: `_jumpQueued` must NOT be
    reset by the local `Update()` branch when `isServer` is true (host shares one field/instance between its
    "local player" and "server" code paths in the same frame) — only remote (non-host) clients reset their
    own local copy after sending, since their own `ApplyMovement()` never runs to do it for them; host leaves
    the reset to `ApplyMovement()`'s existing consume-then-clear, which now runs later in the same `Update()`.
  - Updated two now-stale comments (the `Awake()` `syncRotation` note, and the `OnStartLocalPlayer` disable
    site) to reflect the new model instead of describing the retired one.
- **EDIT `Assets/Scripts/Editor/SceneSetup.cs`** — `CreatePlayer()`'s NetworkTransform-adding code (used by
  `Tools/Rebuild Player Prefab (Fresh)`) now prefers `ServerAuthoritativeTransform` over the stock Mirror type
  (falls back if not yet compiled), so a from-scratch rebuild doesn't silently regress this fix.
  `Tools/Patch Player Prefab`'s component list doesn't touch NetworkTransform at all, so the routine
  incremental-patch path was never at risk.
- **EDIT `Assets/Scripts/PlayerAnimator.cs`** — doc-comment accuracy only (referenced the retired component
  by name; now correctly notes the owner renders through the same synced transform as everyone else).
