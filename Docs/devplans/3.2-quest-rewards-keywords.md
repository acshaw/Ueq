# 3.2 — Quest Turn-ins & Rewards via Keywords

**Status:** 🟡 Draft — awaiting review. Decisions Q1–Q7: **Q1 decided** (fold 2.8 in, ship self-contained),
**Q2 decided** (quests are repeatable; anti-farm is the item-side LORE flag, 3.2.1), Q4 revised (turn-in
included), **Q7 decided** (no partial collection); Q3/Q5/Q6 carry recommendations.
Delivers the first full quest transaction over dialogue: say the right keyword to a satisfied NPC → the NPC
**accepts required items/coin** and **grants a reward** (XP / items / currency / faction), all-or-nothing. No quest
UI — objectives are inferred from dialogue, exactly per the design doc's emergent-quest model.

## Why
The conversation system (2.4) can already gate keyword responses by faction and dispatch keyword events to NPC
components — but nothing *grants* anything yet. This closes the loop: a keyword becomes a claimable reward,
turning dialogue into progression. It's the runtime the roadmap earmarked under 3.2.

## The 2.8 question (read first — decision Q1)
The roadmap splits this as **2.8 = quest data model + Quest Editor** (authoring) and **3.2 = runtime granting**.
But grounding it in code shows the design has **no separate quest entity**: quests are emergent (the doc's
"players infer objectives from dialogue and environmental clues; no explicit quest UI or quest-giving"). A "quest
reward" is really just *a faction-gated, usually one-time reward bundle fired by a conversation keyword* — there is
nothing to track as an "objective." So a dedicated quest content type would be a heavier abstraction than the
design calls for. **Recommendation (Q1): fold the reward bundle into the conversation keyword and ship 3.2
self-contained**, absorbing the slim, actually-needed slice of 2.8. A separate Quest Editor with multi-step
objective chains is only worth building if/when quests outgrow single-keyword rewards — reclassify 2.8 as that
future generalization.

## Current state (grounding)
- **`NpcConversation`** (Conversation/) — on a keyword match it runs `MeetsFactionRequirement` (per-keyword
  faction/standing gate, already live), delivers the response, applies session unlocks, and calls
  `_dispatcher.DispatchConversationKeyword(player, keyword)`. **The gate runs *before* dispatch**, so any reward
  handler is automatically faction-gated for free.
- **`IOnConversationKeyword`** (`NPC/NpcEvents.cs`) — `OnConversationKeyword(NetworkIdentity player, string
  keyword)`. `VendorApplicator` is the working reference implementation (opens a shop on the `wares` keyword).
- **`ConversationKeyword`** (Conversation/) — DB-backed (2.4) with `Keyword`, `Response`, faction gate
  (`RequiredFactionId`/`RequiredStanding`), `UnlocksKeywords`, `RequiresUnlock`. **No reward fields yet** — this is
  where the bundle would attach. Authored in the web **Conversation Editor**; loaded via
  `ConversationRepository`/`ConversationRegistry`.
- **Grant primitives already exist:** `PlayerExperience.AddXp(int)` (level-up chat included),
  `PlayerInventory.AddItem(itemId, qty)` + `AddCurrency(...)`, `PlayerFactionScores.ModifyScore(faction, delta)`.
  `MobKillReward : IOnDeath` is the reference for "grant + Reward-channel chat feedback."
- **Anti-repeat gap:** keyword unlocks are **session-scoped, not persisted** (design doc). So a reward attached
  naively to a keyword is **farmable** — say it again, get it again. Fixing this needs new per-character state.
- **Persistence pattern** to copy: normalized per-character child tables (inventory/equipment/faction scores)
  loaded on login + saved via the async persistence queue. Last migration = **0018** (gender) → next is **0019**.

## The turn-in is part of the transaction (design input, 2026-07-10)
A quest is usually "**bring me X (or pay me N coin) → receive Y**." So the NPC **accepting items/coin from the
player** is the *requirement/cost* side of the same keyword transaction as the reward — not a separate feature.
Folding it in makes 3.2 deliver real quests ("hand over 5 wolf pelts → 500 XP + a Rusty Key") instead of
free rewards. The consume primitives already exist (`PlayerInventory.HasItem`/`RemoveItem`/`SpendCurrency`),
symmetric with the grant side. This absorbs the core of the old roadmap 3.3 (player→NPC item hand-off).

## Scope
1. **Quest transaction on a conversation keyword** — DB + Conversation Editor, two symmetric sides:
   - **Requirements (cost, consumed on claim):** required items (id+qty) + required coin.
   - **Reward (granted on claim):** XP, currency, items (id+qty), faction hits (faction+delta).
   - Every transaction is **repeatable** (Q2) — no completion flag, no `rewardId`.
2. **Runtime transaction** — a `KeywordRewardApplicator : IOnConversationKeyword` (sibling to `VendorApplicator`)
   that, on the matched (faction-gated) keyword, **validates + consumes the requirements, then grants the reward**,
   with Reward-channel chat feedback. All-or-nothing: if the player lacks the required items/coin, nothing is
   consumed or granted and they get a "you don't have what I asked for" line.

**Out of scope:** one-time / non-repeatable quests + completion tracking (Q2 — quests are repeatable; a one-time
layer is a purely additive future addition, no current need); the **LORE item flag** that limits reward
stockpiling (roadmap **3.2.1**, item-system feature — 3.2 gets it free via `AddItem`); partial/collection turn-ins
accumulated across visits (Q7 — a turn-in is single all-at-once); multi-step objective chains / a dedicated Quest
Editor (future 2.8 generalization); any quest UI; non-transaction item-gives that only fire a script event with no
reward (a thin remainder of old 3.3 — see the roadmap note).

## Decisions (Q1–Q6)

**Q1 — Scope/sequencing (the headline).** *Recommend:* **fold the reward bundle into the conversation keyword and
ship 3.2 self-contained** (no separate 2.8 quest content type first). The design has no objective-tracking entity,
so a keyword-attached reward *is* the quest. Reclassify roadmap 2.8 as "future: dedicated multi-step quest
authoring, if needed." *(Alt: build 2.8 first as a standalone quest entity referenced by keyword id — heavier,
and premature for single-keyword rewards.)*

**Q2 — Anti-repeat. [DECIDED 2026-07-11 — quests are repeatable; anti-farm is item-side (LORE), EQ1-style.]**
No completion tracking, no `character_completed_rewards` table, no migration, no `PlayerQuestLog`. Every quest
transaction can be re-run as often as the player can supply the turn-in cost. The **farming lever is the item
system, not the quest system**: a **LORE** item (max one in possession — roadmap **3.2.1**) can't be stockpiled, so
a LORE reward item is self-limiting; 3.2 grants through `PlayerInventory.AddItem`, so it inherits LORE enforcement
with zero quest-side code. **Known + intended:** LORE limits *item* stockpiling only — XP/coin from a repeatable
quest is deliberately farmable, bounded by the effort to gather the required items (the EQ1 model). **Extensibility:**
one-time quests are an additive future layer (add a `rewardId` + `repeatable=false` + a completion table then) that
leaves repeatable quests untouched; not built now (no current need).

**Q3 — Reward contents.** *Recommend:* **XP + currency + items + faction hits** (all four have grant primitives;
items + faction hits reuse the loot-table / mob-faction-hit child-table shapes already built). Currency reuses the
PP/GP/SP/CP normalization in `PlayerInventory.AddCurrency`.

**Q4 — Item / coin requirement (turn-in). [REVISED per 2026-07-10 design input]** *Recommend:* **include it in
3.2** as the requirement side of the transaction — required items (id+qty) + required coin, validated and consumed
before the reward is granted (all-or-nothing). This absorbs the core of old roadmap 3.3 (player→NPC hand-off) so a
keyword can express a real turn-in quest. Uses existing `HasItem`/`RemoveItem`/`SpendCurrency`. *(A non-reward
item-give that only fires a script event — a thin remainder of 3.3 — stays future/optional.)*

**Q5 — Authoring surface.** *Recommend:* **extend the web Conversation Editor** with a per-keyword "Reward"
section (XP, currency, item rows, faction-hit rows, rewardId, repeatable). One place, mirrors the existing
loot/faction-hit editors. *(No separate Quest Editor — see Q1.)*

**Q6 — Feedback.** *Recommend:* **Reward-channel chat on grant** ("You receive 500 experience." / "You receive a
Rusty Key.") mirroring `MobKillReward`, plus a short NPC/System line when a one-time reward was already claimed.

**Q7 — Partial collection. [DECIDED 2026-07-10 — NOT included.]** A turn-in is a **single, all-at-once
hand-off**: the player must have the *entire* required item/coin cost present at the moment they say the keyword,
or the transaction is refused (nothing consumed). There is **no** server-side accumulation of "3 of 5 pelts
turned in so far" across visits — no partial-progress state to author, persist, or display. (A player naturally
"collects" by holding the items in their own inventory until they have the full set, then turns in once.)

## Design detail — the transaction path
1. Player says a keyword to an NPC they're targeting and satisfy the faction gate.
2. `NpcConversation.HandleMatch` delivers the response and dispatches the keyword.
3. `KeywordRewardApplicator.OnConversationKeyword(player, keyword)` resolves the matched keyword's transaction
   bundle from the NPC's `ConversationKeywordSet` (via `ConversationRegistry`, keyed by the NPC's
   `conversationSetId`).
4. **Requirement check (validate BEFORE consuming anything):** does the player have every required item at qty +
   the required coin, *and* will the reward items fit? If not → send the appropriate refusal line ("you don't have
   what I asked for" / "make room first") and stop (consume nothing, all-or-nothing).
5. **Consume:** `RemoveItem` per required item, `SpendCurrency` for required coin.
6. **Grant:** `AddXp` / `AddCurrency` / `AddItem` per reward item / `ModifyScore` per faction hit; send
   Reward-channel chat.

The **faction gate needs no new code** — it already runs in `NpcConversation` before dispatch. **Ordering matters:**
validate the *whole* transaction (has-cost AND reward-fits) before consuming anything, so we never take the turn-in
and then fail to hand back the reward. Every transaction is repeatable (Q2) — no completion state to check or write.

## Build stages (each verifiable, commit-able)
1. **Full transaction runtime.** `KeywordRewardApplicator` + transaction-bundle schema (requirements + reward)
   wired through DB → repository/registry; validate → consume → grant + Reward chat. *Verify: a keyword with an
   item/coin cost consumes it and grants the reward, faction-gated; a player lacking the cost (or too full for the
   reward) is refused with nothing consumed; re-running it works again.*
2. **Editor + authoring.** Conversation Editor transaction section (requirements + reward rows, mirroring the
   loot/faction-hit editors), and author one demo turn-in on a seeded NPC keyword. *Verify end-to-end from the web
   app → in-game.*

*(No persistence stage — Q2 makes quests repeatable, so there's no completion state to store.)*

## Done when
Saying a faction-gated keyword to an NPC runs a full quest transaction — the NPC **accepts required items/coin**
and **grants a XP/item/currency/faction reward** with chat feedback, all-or-nothing, repeatable; multi-step quests,
one-time-completion tracking, and a dedicated Quest Editor remain additive future work. (Stockpiling of item rewards
is limited separately by the LORE flag, roadmap 3.2.1.)
