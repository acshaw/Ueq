# 5.12 — Sky & Day/Night Cycle (with Lunar Phases)

Status: 🟠 Implemented — pending in-editor verification (2026-08-05). All decisions DC1–DC10
approved and implemented; first real in-editor test (2026-08-05) found one genuine bug (moon
tracked the sun's arc instead of the opposite — fixed, see the Implementation log) and one design
call reversed by the user (DC9/clouds cut entirely — the procedural fallback looked bad and no
owned Synty pack had a real cloud prop). See the Implementation log at the bottom of this file.

## Goal

A server-authoritative day/night cycle — rotating sun, gradient sky, shifting ambient light —
plus a slower lunar phase cycle, rendering identically for every connected client regardless of
which zone they're in. This is a global rendering/atmosphere system, not zone content, so it
doesn't belong to any single zone's decoration pass (7.1–7.3).

## Grounding (read before implementing)

- **Current lighting state**: `SampleScene.unity`'s `RenderSettings` block points
  `m_SkyboxMaterial` at Unity's built-in `Default-Skybox` material, `m_AmbientMode: 0` (Skybox —
  ambient derives from the skybox), and `m_Sun: {fileID: 0}` (no sun explicitly assigned to
  RenderSettings). One `Directional Light` exists in-scene (`m_Type: 1`, intensity 2). No
  day/night or sky script of any kind exists in the codebase today.
- **Zone architecture is the one fact that shapes this whole design**: zones are
  additively-loaded scenes at large world-space offsets (`creslins_field`=0, `thornwood`=+5000,
  `grukmars_deep`=+10000 — see `ZoneCatalog.cs`/`ZoneManager.cs`), all served by one process, with
  the base scene (`creslins_field`) always active. A `Directional Light`'s effect depends only on
  its **rotation**, never its position — so one global sun rig, living in the always-loaded base
  scene, lights every zone correctly regardless of that zone's offset. No per-zone duplication of
  sun/sky objects is needed.
- **Established art direction**: this project has repeatedly chosen flat/matte/stylized rendering
  over realism (the custom `Ueq/LowPolyTerrain` faceted shader, solid-color Synty-palette terrain
  layers with smoothness forced to 0 via alpha, "vinyl-looking" gloss treated as a bug to fix
  every time it appeared). A photoreal procedural sky (URP Physically Based Sky, atmospheric
  scattering) would be a stylistic mismatch — recommend a small custom stylized gradient skybox
  shader instead.
- **Existing synced-clock precedent**: 4.2's movement reconciliation already leans on Mirror's
  shared `NetworkTime.time` rather than inventing a new synced clock — this devplan reuses that
  same mechanism instead of a per-frame `SyncVar`.
- **Server-only singleton precedent**: `ZoneManager` and `ChatManager` both live on the
  `NetworkManager` GameObject in the base scene and persist across zone loads. `WorldClock`
  follows the same placement.
- **Resources-loaded tunable-config precedent**: `XpTableDefinition` and
  `CombatTierDamageConfig` are both ScriptableObjects loaded from `Resources/` at runtime with an
  in-code fallback if the asset is absent. `WorldClockSettings` follows the same shape — this is a
  single global tunable, not per-item authored content, so it does **not** get a DB/web editor
  (per the roadmap's "pure data vs. asset bindings" principle, this is closer to a Unity rendering
  config than authored game content).

## Decisions

**DC1 — Clock authority & sync mechanism.** RECOMMEND: new `WorldClock` (`NetworkBehaviour`
singleton on the NetworkManager GO, alongside `ZoneManager`/`ChatManager`). Server picks a
`dayLengthSeconds` from `WorldClockSettings` and a start reference tied to `NetworkTime.time` at
boot. Rather than syncing a `dayFraction` SyncVar every frame (bandwidth churn for no real
benefit), sync the two constants `(serverStartTime, dayLengthSeconds)` once — on server start for
already-connected observers, and via a targeted message to each client on connect — and have
every client (including the server's own client view, for host) compute `dayFraction` locally
from `NetworkTime.time`. Zero ongoing traffic, exact lockstep with the server, and a late-joining
client shows the correct current time immediately instead of resetting to dawn.

**DC2 — Day length.** RECOMMEND: configurable real-minutes-per-in-game-day on
`WorldClockSettings` (Resources-loaded SO), not real-time-locked. Suggest defaulting to something
short enough to actually see a cycle during normal play (e.g. 45–60 real minutes per in-game day)
— tunable without recompiling.

**DC3 — Sky visual.** RECOMMEND a small custom shader, `Ueq/StylizedSky` — a horizon→zenith color
lerp sampled from a `Gradient` keyed across time-of-day (dawn orange → day blue → dusk
orange/purple → night navy), no clouds or atmospheric scattering. Simpler and matches the
project's established flat/matte look better than URP's Physically Based Sky. **Implementation
caution**: the skybox material must be `Instantiate()`d into a runtime instance before `WorldClock`
mutates its properties every tick, or the shared `.mat` asset gets edited on disk in the Editor —
same class of gotcha already hit and fixed elsewhere in this project (e.g. runtime terrain layer
texture assignment).

**DC4 — Sun behavior.** RECOMMEND rotating the existing Directional Light's transform around its
local X axis across `dayFraction` (`angle = dayFraction * 360 - 90`, so noon points straight
down), with `Light.intensity`/`Light.color` driven by curves — dim and warm at dawn/dusk, near-zero
(or a very dim cool "moonlight" floor) at night. Also RECOMMEND switching
`RenderSettings.ambientMode` from Skybox to Flat or Trilight and driving ambient color directly
from the same time-of-day gradient, rather than relying on skybox-derived ambient (which needs
periodic `DynamicGI.UpdateEnvironment()` calls to refresh — an ongoing real-time-GI cost this
project has no other use for).

**DC5 — Moon visual. DECIDED (user, 2026-08-04): procedural, no textures.** A quad or low-poly
disc mesh, mounted on a rig rotating opposite the sun (rigidly opposite is simpler than an
independent moonrise/moonset rate and reads fine for a stylized game). Phase rendering uses a
small custom shader (`Ueq/ProceduralMoon`) drawing the disc as a flat-shaded circle with a shadow
overlay whose position/curvature sweeps across it as `lunarFraction` advances — the standard
two-circle "moon phase widget" technique (a lit disc + a masking ellipse/circle whose horizontal
offset goes from fully-covering at new moon, to centered/no-coverage at full moon, sweeping from
one side to the other across waxing/waning). This gives a smooth continuous phase for free instead
of the originally-considered 8-discrete-texture-swap approach, and needs **zero art assets** —
consistent with DC9's reuse-first/no-download posture and this project's prior lesson on
texture-style mismatches (the ambientCG-vs-Synty terrain incident). `lunarCycleDays` stays a
tunable on `WorldClockSettings` (suggest 7–10 in-game days).

**DC6 — Gameplay hook. DECIDED (user, 2026-08-04): cosmetic only for this pass.** The moon's
phase only changes its visual appearance. `WorldClock` exposes a public, server-readable
`CurrentLunarPhase` (enum or 0–1 float) as a static read hook, so a future content item (e.g. a
7.x zone-population devplan) can opt a specific spawn table into a full-moon condition later
without this devplan reaching into `SpawnTable`/`SpawnPoint` at all. No gameplay system changes
in this pass.

**DC7 — Per-zone opt-out.** RECOMMEND adding `usesDayNightCycle` (bool, default `true`) to
`ZoneDefinition` (`ZoneCatalog.cs`) now, even though nothing needs it yet — cheap to add while
touching the file, and it's the obvious future home for Grukmar's Deep (7.3, an underground
dungeon, currently just a flat unbuilt scaffold) to opt out and keep static dungeon lighting
instead of an incongruous outdoor sky cycle underground.

**DC8 — Persistence across server restarts.** RECOMMEND time-of-day resets to a fixed dawn on
every server boot (simplest — no new schema, no new save state). Revisit only if it turns out to
matter in practice; not worth a `world_state` table for this pass.

**DC9 — Clouds. DECIDED (user, 2026-08-04): fold into this pass. ⛔ CUT (user, 2026-08-05): the
procedural puff-cluster fallback ("a handful of overlapping flat-shaded rounded shapes") looked
bad in the first real in-editor test ("atrocious") and no owned Synty pack turned up a real cloud
prop to use instead — `CloudField.cs` deleted, `WorldClockSceneSetup` no longer wires it (and
self-cleans a leftover `CloudField` GameObject from an earlier run). Revisit only with real cloud
art (owned or newly acquired), not another procedural attempt.** Original text below, kept for
context on the (now unused) design: Unlike the sun (rotation-only,
position-independent — see Grounding) and the skybox (camera-relative by definition), clouds are
real 3D geometry with a position, so they can't be anchored to zone world-space coordinates the
way the sun/sky rig is: a cloud field parked at the base scene's origin wouldn't visually follow a
player standing 5000+ units away in Thornwood. RECOMMEND a **client-side-only, non-networked**
`CloudField` component that recenters on the local camera — a fixed pool of N cloud instances
drifting along a wind direction, each wrapped back around when it drifts past a radius (the same
"recenter around the viewer" trick used for any effectively-infinite decorative layer). Purely
decorative: no server authority, no sync needed — nobody notices or cares if two clients' clouds
sit in slightly different positions, same as nobody would notice desynced dust motes. Visual
approach: RECOMMEND drifting low-poly cloud **meshes/billboards**, matte-shaded to match style,
over a shader-noise volumetric cloud layer — the latter reads soft/realistic and would clash with
the flat/matte call already made for the sky and terrain. Check owned Synty packs (Nature Biomes,
Adventure, Generic, Prototype, Dungeon) for existing cloud props before authoring new ones — same
reuse-first approach already used for terrain tree painting (`TerrainTreePalette`); if none exist,
a handful of overlapping flat-shaded rounded shapes is cheap to hand-author. **Scope cut**: no
rain/storm/weather state machine, no cloud shadows cast on terrain — just an ambient drifting
layer for this pass.

**DC10 — Stars. DECIDED (user, 2026-08-04): fold into this pass.** Folds cheaply into the same
`Ueq/StylizedSky` shader from DC3 rather than a separate object or system — a noise/hash-based
star field (pseudo-random bright points generated from the view direction, not a texture),
faded in only as the sun's intensity drops toward night and dimmed near the horizon so they don't
read as clipping through terrain silhouettes. Zero new art assets, same as DC5/DC9. A cheap
sin-based twinkle is a nice-to-have, not required for this pass.

## Build stages

1. **Clock core (no visuals)** — `WorldClock` + `WorldClockSettings`, `NetworkTime`-anchored
   `dayFraction`/`lunarFraction` calc, synced via the one-time constants per DC1. Verify via a
   debug log ticking identically on host + a remote MPPM client.
2. **Sun** — rotate the existing Directional Light, intensity/color curves.
3. **Sky + stars** — `Ueq/StylizedSky` shader + runtime material instance, `WorldClock` driving
   its gradient sample; ambient mode switched to Flat/Trilight, ambient color driven alongside;
   the DC10 noise-based star field is the same shader/material, so it lands in this stage too.
4. **Moon** — disc mesh on the opposite-sun rig, driven by the `Ueq/ProceduralMoon` shader (DC5)
   sampling `lunarFraction` — no texture authoring/sourcing step to wait on.
5. **Clouds** — `CloudField` client-side pool + recenter-on-camera logic (DC9); source or author
   cloud prop meshes (check owned Synty packs first).
6. **Per-zone flag** — `usesDayNightCycle` on `ZoneDefinition` (DC7); `WorldClock`/sky renderer
   no-ops (or forces a fixed dark ambient) when the player's current zone has it disabled.
7. **Debug tooling** — `Tools/World Clock Debug` EditorWindow: a time-of-day scrub slider +
   jump-to-time buttons (dawn/noon/dusk/midnight) + a lunar-phase scrub, so testing doesn't
   require sitting through a real 45–60 minute cycle. Real practical need, not a nice-to-have.

## Test plan

- **Compressed-day solo test**: set a short day length via the debug window, watch a full
  cycle — sun rotates, sky gradients through dawn/day/dusk/night, ambient shifts, stars fade in
  at night and out at dawn, moon phase visibly and smoothly advances across several cycles (scrub
  the debug window's lunar-phase slider through a full cycle and confirm the terminator sweeps
  the correct direction — new → waxing crescent → first quarter → waxing gibbous → full → waning
  gibbous → last quarter → waning crescent → new).
- **Cross-zone simultaneity**: two MPPM clients, one in `creslins_field`, one in `thornwood` (or
  wherever the current MVP zones are) — confirm both see identical sun angle/sky color/ambient at
  the same real moment, despite the 5000-unit offset. This is the direct validation of the
  "directional light is position-independent, one global clock is correct" assumption underlying
  the whole design.
- **Late join**: a client connecting mid-cycle shows the correct current time immediately, not a
  reset-to-dawn — validates the `NetworkTime`-anchored calc over a naive
  "start counting from my own `OnStartClient`" approach.
- **Host restart**: time resets to dawn per DC8 — confirm this is the actual (accepted) behavior,
  not an unintended reset mid-testing.
- **Cloud recentering**: walk/run far enough (or cross a zone transition) that the `CloudField`
  recenters around the camera — confirm the recenter is visually seamless (no pop/jump in the
  cloud layer) and that clouds render correctly regardless of which zone's world offset the
  player is standing at.

## Risks / open items

- DC3's runtime skybox material instancing is the one implementation detail most likely to bite
  if skipped — must confirm the Editor's `.mat` asset is untouched after a Play session; the same
  applies to DC5's `ProceduralMoon` material instance.
- DC5's two-circle phase-shading math is the one real implementation risk in the moon — getting
  the terminator sweep direction/curvature right (which side "waxes" vs. "wanes") needs a visual
  check against a known reference (a real moon-phase calendar) rather than trusting the math
  blind; cheap to get subtly backwards on a first pass.
- DC9's cloud prop meshes are still an asset-sourcing gap (this one isn't shader-avoidable the way
  moon/stars are, since clouds are genuine 3D geometry) — check owned Synty packs first (Stage 5);
  if nothing suitable is found, hand-authoring a few simple shapes is the fallback, not a blocker.
- Grukmar's Deep (DC7's intended consumer) isn't built yet (7.3, still an unbuilt flat scaffold),
  so the per-zone opt-out can't be end-to-end tested against a real dungeon zone this pass — but
  Thornwood already exists and can serve as a synthetic test zone for the flag itself (see the
  Implementation log's ZoneClientHelper note below).

## Verification round 1 (2026-08-05)

User ran it with a local host + an MPPM client, day length dialed to 2 real minutes
(`Assets/Resources/WorldClockSettings.asset` → `dayLengthMinutes: 2`, hand-edited directly since
the asset already existed by the time this was requested — Unity had picked up the new scripts and
the user had already run `Tools/World Clock/Setup Scene` between sessions). Two real findings:

1. **Clouds looked bad ("atrocious").** No owned Synty pack had a cloud prop, so `CloudField` was
   always falling back to its procedural puff-cluster (a few overlapping matte spheres) — which
   didn't read as clouds. **User's call: cut DC9 entirely rather than iterate on the procedural
   fallback.** `CloudField.cs` deleted; `WorldClockSceneSetup.cs` no longer creates/wires a
   `CloudField` and now self-cleans a leftover one from the earlier run (`RemoveAnyLeftoverCloudField`)
   so re-running the tool fixes the scene's now-dangling "missing script" reference. Revisit only
   with real cloud art, not another procedural attempt.

2. **Real bug: the moon tracked the sun's arc instead of the opposite one** — visible overhead
   during the day, hidden at night (exactly backwards). Root cause: `MoonRig`'s pivot rotation used
   `sunAngle + 180`, on the assumption that adding 180° to the sun's angle formula would place the
   moon on the opposite side of the sky. That assumption doesn't hold, because the sun's angle
   formula defines a Directional Light's **ray-travel direction** (`forward = down` correctly means
   "sun is up" at noon), while the same angle applied to `MoonRig`'s pivot defines a **position
   offset** for a real visible disc (the disc sits along the pivot's forward direction, so
   `forward = down` places the disc *below* the camera). Those two uses of "forward" are inverses
   of each other by construction — reusing the sun's own angle formula *unmodified* already puts
   the moon on the opposite side of the sky; adding +180 on top double-flips it back onto the sun's
   own side. Verified by hand at all three cardinal points (noon, midnight, dawn) before committing
   the fix. **Fixed**: `MoonRig.LateUpdate()` now uses the exact same `f * 360f - 90f` formula as
   `SunDriver`, no offset — the class doc comment on `MoonRig.cs` has the full derivation for future
   reference. This fix applies automatically on recompile; no `Setup Scene` re-run needed for it.

**Both fixes are code-only, not yet re-verified in-editor** (this response happened without an
active Unity session). **NEXT (user, in Editor): recompile → re-run `Tools/World Clock/Setup Scene`
once to clean up the leftover `CloudField` GameObject → re-test: moon should now be up at night /
hidden during the day, opposite the sun. Then resume the remaining NEXT steps above (5–7).**
