# 8.4 — Spawn-pool exclusivity (rotating pops)

**Status:** 🟡 Awaiting review.
**Roadmap item:** M8 → 8.4
**Pattern:** a new marker type implementing `IWorldPlacement`, the exact same shape `PatrolRoute`/
`WanderRegion` already use — a `SpawnPoint` cross-references it via `IReferencesOtherPlacements`, same
two-pass resolution `patrolRoute`/`wanderRegion` already go through.

---

## Goal & why now

Several `SpawnPoint`s sometimes need to share one "only one of us is ever live at a time" pool — the
classic case is a boss/named encounter with 2-3 possible spawn locations in a room, where exactly one is
occupied and killing it causes the *next* pop to potentially appear somewhere else in the room, not
necessarily back at the same spot. Today every `SpawnPoint` is fully independent — nothing coordinates
across points.

## Current state (grounding)

- `SpawnPoint` implements `IWorldPlacement` (placement sync, 2.7.3) and `IReferencesOtherPlacements`
  (cross-references `patrolRoute`/`wanderRegion` by `PlacementId`, resolved in a second pass by
  `ResolveReferences` after every placement in the zone is indexed).
- Activation (`ActivationCheck`, every 5s) and spawning (`DoSpawn`) are both fully local to one
  `SpawnPoint` — proximity check, `_live` list, `_respawnPending` flag are all per-instance state with no
  shared coordination point.
- `WanderRegion`/`PatrolRoute` are the two precedents for "a plain scene MonoBehaviour, referenced by id,
  that several `SpawnPoint`s can point at" — but those are *shared config* (many points can point at the
  same route/region and each spawns independently); a pool is different in kind — it's *shared exclusivity
  state* across points, not shared config.

## Decisions (recommendations in **bold**)

**SP1 — New marker type: `SpawnPool`.** **A new scene MonoBehaviour implementing `IWorldPlacement`**
(own `PlacementId`, `MarkerType = "SpawnPool"`), holding no spatial data of its own (it's a coordination
object, not a placed thing with a meaningful transform) — just a `List<NetworkIdentity> Live` (server-only,
not persisted) and a small API: `bool TryClaim(SpawnPoint who)`, `void Release(SpawnPoint who)`. A
`SpawnPoint` gets an optional `SpawnPool pool` field, resolved the same two-pass way as
`patrolRoute`/`wanderRegion` (`CapturePlacementData` stores `spawnPoolPlacementId`; `ResolveReferences`
looks it up).

**SP2 — Where the gate applies.** **`SpawnPoint.DoSpawn()` checks `pool == null || pool.TryClaim(this)`
before proceeding** — if the pool is already claimed by a *different* point, `DoSpawn` silently returns
(no warning — this is expected, normal contention, not a misconfiguration). Proximity/activation logic
(`ActivationCheck`) is **completely unchanged** — every pooled point still polls its own radius
independently; the pool only gates the *spawn* step, not the *activation* step. On the group's last member
dying, the owning point calls `pool.Release(this)` before its own `RespawnAfterDelay` logic runs.

**SP3 — Who spawns next.** **Recommend: whichever pooled point's `ActivationCheck` next finds
`_live.Count == 0 && !_respawnPending` AND wins the `TryClaim` race** — i.e., don't pick a specific "next"
point deterministically; let normal proximity polling decide, and the pool only ever prevents *more than
one* from succeeding at once. This keeps SP2 genuinely simple (a claim/release gate, no scheduling logic)
and naturally produces "shows up somewhere in the room, not necessarily the same spot" — the actual goal —
without needing a round-robin or weighted-random picker. *Alt considered:* the pool itself picks the next
point (round-robin or random) and tells it to spawn — more deterministic, but adds real scheduling logic
for a benefit (control over *which* point specifically) nobody's asked for yet; reject unless SP3's
simpler approach turns out to feel too random in practice.

**SP4 — Respawn timing with a pool.** **Each pooled `SpawnPoint` keeps its own respawn timer, unaffected
by the pool** — the pool only gates *which* point's spawn attempt wins, not *when* an attempt happens.
A pool of 3 points each on the same table/timer will naturally show one "up" at a time with normal
per-point respawn pacing; a design that wants the *pool* to have one shared timer (rather than N
independent ones racing) is a heavier feature not built here — flag if that's actually wanted.

## Files (once approved)

**New:** `Assets/Scripts/Placement/SpawnPool.cs` (`IWorldPlacement`, `TryClaim`/`Release`, no config
fields to capture/apply beyond a placeholder empty `CapturePlacementData`/`ApplyPlacementData` — it has no
authored data, only runtime claim state), a matching entry in `PlacementFactories.cs`'s registry (WP1's
"a brand-new marker type needs zero other code changes" — this is the test of that claim), drag-in prefab
under `Assets/Prefabs/Zones/` mirroring `WanderRegion`/`PatrolRoute`'s existing prefab treatment.
**Modified:** `SpawnPoint.cs` (`pool` field + `_pendingSpawnPoolPlacementId` + `CapturePlacementData`/
`ApplyPlacementData`/`ResolveReferences` gain the pool reference; `DoSpawn`/`OnMemberDied` gain the
claim/release calls), `PlacementMaterializer.cs` if `SpawnPool` needs to participate in the two-pass
non-referencing-types-first ordering (it doesn't reference anything itself, so it's a "pass 1" type like
`WanderRegion`).

## Test plan

1. Place 3 `SpawnPoint`s in one small area, all referencing the same `SpawnPool`, each on the same table.
   Confirm only ever one has a live mob at a time, and confirm (over several kill/respawn cycles) that the
   *next* pop can land at a different one of the 3 (not deterministically the one that just died).
2. Kill the live pop → confirm `Release` frees the pool → confirm one of the 3 (any of them, per SP3) can
   claim the next spawn.
3. A `SpawnPoint` with no pool reference behaves exactly as today (regression check).
4. Placement sync round-trip: sync a scene with a `SpawnPool` + 3 referencing `SpawnPoint`s to the DB,
   restart, confirm the pool reference re-resolves correctly (mirrors the existing `patrolRoute`/
   `wanderRegion` reference test already in the 2.7.3 test plan).

## Risks

- **Claim/release races under concurrent activation** — two pooled points polling in the same 5s tick
  could both attempt `TryClaim` near-simultaneously; `TryClaim` must be a genuinely atomic check-and-set
  (trivial single-threaded on Unity's main thread/server tick, but worth stating explicitly so the
  implementation doesn't accidentally introduce a check-then-act gap across a `Server` RPC boundary that
  doesn't actually exist here — everything's server-local, so this is lower-risk than it sounds, just
  worth confirming during implementation).
- **`SpawnPool` participating in placement sync with zero real spatial/config data** is a slightly odd fit
  for a system designed around "captures this object's config as JSON" — its `CapturePlacementData` is
  essentially `{}`. Not a blocker (the interface tolerates an empty payload fine), but worth a one-line
  comment explaining why, so a future reader doesn't think something was forgotten.

## Done when

Multiple `SpawnPoint`s can reference one `SpawnPool`; at most one member of the pool has a live spawn at
any time; killing the live one frees the pool for any member (not necessarily the same one) to spawn next.
