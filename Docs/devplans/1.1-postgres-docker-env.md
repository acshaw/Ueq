## Goal

Stand up PostgreSQL in Docker locally and give the **Unity server process** everything it needs to talk to it: a connection, a versioned migration runner, a `schema_version` ledger, and a seed entry point. No gameplay data yet — this item only proves "the server boots, connects, migrates, and seeds." Character tables arrive in 1.3+; **DB-backed content tables arrive in M2.** This item is the shared DB/migration foundation for both (its own scope here is unchanged — just `schema_version`).

Scope guardrails:
- **In scope:** Docker Compose, Npgsql in Unity, connection config, migration runner + first migration, seed hook, server-start wiring, editor convenience menu.
- **Out of scope:** character/account schema (1.3/1.4), the async save queue + repositories (1.2), any client-side anything.

## Approach

### 1. Docker Compose (repo root)

`docker-compose.yml` with one `postgres` service:
- `postgres:16` image, named volume `ueq_pgdata` for durability, `5432:5432`, a `healthcheck` (`pg_isready`).
- Credentials/db from a root **`.env`** (gitignored): `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB=ueq`.
- Commit **`.env.example`** with safe placeholders.
- `docker compose up -d` is the only command needed to get a DB.

### 2. Npgsql in Unity (the only real integration risk)

The Unity **server** process uses **Npgsql** (the .NET Postgres driver) directly.

- **Recommended:** add **NuGetForUnity** and install **Npgsql 6.x** through it. NuGetForUnity resolves Npgsql's transitive deps (`System.Threading.Tasks.Extensions`, `System.Runtime.CompilerServices.Unsafe`, `Microsoft.Extensions.Logging.Abstractions`, etc.) into `Assets/Packages/`, which is what makes this painless vs. hand-dropping DLLs.
- **Why 6.x:** it targets `netstandard2.0`, which Unity's scripting runtime supports cleanly. Newer Npgsql (8/9) leans on .NET 8 targets that are riskier under Unity.
- **Player Settings:** confirm **API Compatibility Level = .NET Standard 2.1** (or .NET Framework) and **Scripting Backend** is whatever we already ship; verify a `NpgsqlConnection.Open()` actually links in the editor before building anything on top.
- All Npgsql usage lives behind our own thin wrapper so the rest of the codebase never references Npgsql types directly — keeps the driver swappable.

### 3. Connection config (server-only, secrets out of git)

`DatabaseConfig` resolves a connection string in this order:
1. Environment variable `UEQ_DB_CONNSTRING` (full string), else
2. individual env vars (`UEQ_DB_HOST/PORT/NAME/USER/PASSWORD`), else
3. a gitignored **`db.config.json`** at the project root for editor convenience.

Commit **`db.config.example.json`**. Real config is never committed. Editor reads file/env; standalone server reads env (set by the host/AWS later).

### 4. Migration runner (homegrown, dependency-light)

- Migrations are plain **`.sql` files in `Assets/StreamingAssets/Database/Migrations/`**, named `0001_*.sql`, `0002_*.sql`, … (StreamingAssets so they ship verbatim with a standalone server and are readable via `Application.streamingAssetsPath` in both editor and build).
- `MigrationRunner`:
  1. Ensures a `schema_version` table exists.
  2. Reads applied versions from it.
  3. Applies each higher-numbered file **in a transaction**, recording `(version, name, applied_at)` on success.
  4. Idempotent — re-running applies nothing.
- First migration **`0001_init.sql`**: creates the `schema_version` ledger only (no game tables yet). Confirms the whole pipeline end-to-end with nothing to get wrong.

### 5. Seed entry point (dev only)

`DatabaseSeeder.Seed()` — a stub hook that runs after migrations **only in dev** (guarded by config flag `seedOnStart`, default true locally). Empty for now; future content seeds plug in here. Keeps the "seed as we go" workflow ready without committing to seed content yet.

### 6. Server wiring

`GameNetworkManager.OnStartServer` → `Database.InitializeServer()`:
- resolve config → open a connection → run pending migrations → run seed (if dev) → log success/failure.
- On failure: log a clear error and (decision below) either abort server start or continue without DB. Recommend **abort with a loud error** so we never silently run unpersisted.
- Guarded so it only ever runs server-side.

## Schema / API changes

**New DB objects (via `0001_init.sql`):**
```sql
CREATE TABLE schema_version (
    version     INTEGER     PRIMARY KEY,
    name        TEXT        NOT NULL,
    applied_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**New C# (all server-only, namespace e.g. `Ueq.Server.Database`):**
- `DatabaseConfig` — connection-string resolution + dev flags.
- `Database` — connection factory + `InitializeServer()`.
- `MigrationRunner` — apply/track migrations.
- `DatabaseSeeder` — `Seed()` stub.
- Editor: `DatabaseTools` — `Tools/Database/Test Connection`, `Tools/Database/Run Migrations`, `Tools/Database/Reset (drop & recreate)` (dev).

No public gameplay API changes; no client changes.

## Test plan

1. `docker compose up -d` → `docker compose ps` shows postgres healthy.
2. `Tools/Database/Test Connection` → logs "connected to ueq@localhost".
3. `Tools/Database/Run Migrations` → applies `0001`; `schema_version` has one row. Re-run → "no pending migrations."
4. Start a host/server in the editor → `OnStartServer` logs the same connect+migrate+seed sequence.
5. Stop docker → server start logs a loud, clear DB-unavailable error (verifies the failure path).
6. `Tools/Database/Reset` then re-run → clean rebuild from scratch.

## Resolved decisions

- **Data access = raw Npgsql, hand-written SQL.** Not an ORM. EF Core rejected (heavy/AOT-hostile under Unity). Dapper (micro-ORM on top of Npgsql) deferred — revisit in 1.2 only if row→object mapping gets tedious; default is to stay on bare Npgsql.

## Risks / open questions (please weigh in)

- **D1 — Npgsql integration method:** NuGetForUnity (recommended, handles transitive deps) vs. manually vendoring DLLs into `Assets/Plugins/`. I'd go NuGetForUnity unless you object to adding it.
- **D2 — Npgsql version vs Unity runtime:** planning on **Npgsql 6.x (netstandard2.0)** + verifying **API Compatibility Level = .NET Standard 2.1**. If our project is on a different compat level/backend, I'll adjust the pinned version. This is the one thing I want to smoke-test before building anything else.
- **D3 — Migration tooling:** homegrown runner over `.sql` files (recommended — zero extra deps, full control) vs a library like DbUp. Homegrown is plenty for our scale.
- **D4 — DB-unavailable behavior:** **abort server start** (recommended) vs. start anyway without persistence. Abort prevents silent data loss.
- **D5 — Migrations location:** `StreamingAssets/.sql` (recommended, ships with standalone server, real `.sql` for tooling) vs. embedded C# strings. StreamingAssets is cleaner to author.
