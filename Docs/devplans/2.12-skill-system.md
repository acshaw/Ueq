# 2.12 — Weapon Skill System

**Status:** ✅ Done — verified in-editor 2026-07-15.

**Written in tandem with `5.1-combat-threat-overhaul.md`** (user's call) — 5.1's Step 1 hit roll needs an
attacker/defender weapon-skill value that doesn't exist anywhere in the codebase today, so this devplan
exists to produce exactly that, scoped tightly to what 5.1 consumes rather than the full EQ-classic skill
system the roadmap originally sketched (rise-on-use, Dodge/Parry/Block skill gating, a Skill Editor). Per the
`docs/eventide_combat_pipeline.md` design, avoidance (Dodge/Parry/Riposte) is stat-driven (Agility/Dexterity),
not skill-gated — so that original "skill-gated avoidance" scope doesn't apply anymore; this devplan only
covers weapon skill.

## Goal
Give every player (and every mob) a weapon-skill value the combat pipeline can read for Step 1's Skill
Differential modifier (§2.8 of the design doc): net value = attacker weapon skill − defender weapon skill,
perfect-square weight transfer, capped at ±5.

## Grounding — current state
- **No skill concept exists anywhere.** Grepped `Assets/Scripts` for skill/proficiency fields — none.
  `CharacterStats.cs` has STR/STA/AGI/DEX/INT/WIS/CHA only (all derived from race+class+equipment, never
  persisted as raw earned progression — see below).
- **`WeaponCategory` already exists** (`PlayerAutoAttack.cs:5`, enum `{Might, Finesse}`), tied to
  `ItemDefinition.weaponCategory` and driving the existing STR-vs-DEX weighting in
  `PlayerAutoAttack.ComputeDamage()`. Decided (user): weapon skill is scoped to this same 2-value split — one
  Might skill, one Finesse skill per character — not a granular per-weapon-type tree.
- **Persistence pattern**: `CharacterRepository.cs` upserts flat scalar columns on `characters` (name, xp,
  currency, current HP/mana, position, zone) plus four delete-all-reinsert child tables (inventory,
  equipment, faction scores, hotbar). Critically, `CharacterSnapshot.cs` does **not** persist STR/AGI/etc. at
  all — those are pure derived values reconstructed from race+class+equipment at load (`CharacterStats.
  SetRaceClass`). Weapon skill is different in kind: it's **earned through play** (use-based progression, like
  XP), not derivable from level+race+class — so unlike the RPG stats, it genuinely needs to persist.
- **Mob authoring**: mobs are fully DB-backed (migration `0012_mobs.sql` mirrors `MobDefinition` 1:1; API
  `MobsController.cs`; Angular `mob-editor.ts`/`mob.service.ts`). `MobDefinition.cs` has no weapon-category or
  skill-equivalent field today. User decided (for 5.1) that mobs get their combat data **authored per-mob in
  the Mob Editor**, not derived automatically from `mobLevel` — this devplan follows that same posture for the
  mob's skill-equivalent value.
- **Latest migration**: `0020_conversation_rewards.sql` — next is `0021`.

## Decisions

### SK1 — Data model: two explicit skills, new component — **RECOMMEND**
New `PlayerWeaponSkills : NetworkBehaviour` (sibling to `CharacterStats`), `[SyncVar] int _might`,
`[SyncVar] int _finesse`, public `Might`/`Finesse` accessors + `int For(WeaponCategory cat)`. Matches
`CharacterStats`' existing shape (explicit named fields, not a generic dictionary) — appropriate given the
count is fixed at exactly 2 by the earlier granularity decision.

### SK2 — Persistence: flat columns on `characters` — **RECOMMEND**
Two new int columns, `might_skill` and `finesse_skill` (default 0), migration `0021_weapon_skills.sql`. A
flat-column addition, not a new child table — the fixed cardinality (exactly 2, never more) doesn't warrant
the `character_faction_scores`-style key/value child-table pattern. `CharacterSnapshot`/`CharacterRepository`
gain the two fields; `PlayerWeaponSkills.LoadState`/an equivalent hook restores them at login (mirrors how
`CharacterStats` — no, mirrors how `Health`/`PlayerMana` restore *current* values, since this is genuinely
persisted state, not derived).

### SK3 — Starting value + cap formula — **RECOMMEND, values flagged tunable**
Start both skills at 0. Cap: `skillCap(level) = 5 + 5 × (level − 1)` — a literal reading of the design doc's
"skill cap increases by 5 per level" (§2.8), giving level 1 cap = 5, level 20 cap = 100, level 50 cap = 250.
Exposed as two tunable constants (base + per-level), not hardcoded inline, since the doc doesn't commit to a
specific base value — this is a best-guess starting point pending playtesting, same posture as the doc's own
"tuning parameter" callouts elsewhere.

### SK4 — Rise-on-use mechanic — **RECOMMEND, not specified by the design doc, designed fresh here**
The design doc only says skill is an input to the pipeline — it doesn't say how skill increases. Simplest
defensible first pass: on every attack swing while `current < cap`, a flat 8% chance to gain +1 (server-side,
in the same swing-resolution path 5.1 builds). No decay-as-you-approach-cap curve for now — that's a real
EQ-classic refinement worth adding later if flat-rate leveling feels wrong in practice, not something to
design blind before there's a working pipeline to feel it against.

### SK5 — Mob skill-equivalent: authored per-mob — **DECIDED (per 5.1's mob-data question)**
`MobDefinition` gains `weaponCategory` (Might/Finesse) and `weaponSkill` (int) fields, exposed in the Mob
Editor (migration adds `weapon_category`/`weapon_skill` columns to `mobs`, `MobsController`/Angular follow).
A mob's skill value is a flat authored number, not use-based progression — mobs don't "train," they're just
data.

### SK6 — Pipeline read seam — **RECOMMEND**
`5.1`'s Step 1 needs `int AttackerSkill` / `int DefenderSkill` for any combatant (player or mob). Add a small
static/extension resolver — e.g. `CombatSkill.Of(GameObject combatant, WeaponCategory cat)` — that checks for
`PlayerWeaponSkills` first, falls back to `MobApplicator.Definition.weaponSkill` for mobs. Keeps 5.1's roll
code combatant-agnostic (same code path resolves skill regardless of attacker type), consistent with the
"mobs get the full pipeline" decision.

### SK7 — Skill Editor (roadmap's original ask) — **DEFERRED, not built here**
The roadmap originally scoped 2.12 as "Skill system + Skill Editor." Given the actual data is now just 2
per-character ints + 2 per-mob fields (no longer a rich skill tree), a dedicated Skill Editor tool isn't
warranted — the Race & Class Editor / Mob Editor already cover the authoring surface needed (skill cap
constants, mob weapon skill values). If weapon-skill granularity ever expands beyond Might/Finesse, revisit.

## Done when
A player's Might/Finesse skill persists across relog, rises gradually while swinging a weapon of that
category (capped by level), and both a player's and a mob's skill values are readable by 5.1's Step 1 roll
code via one shared resolver.

## Deferred / backlog seeds
- Rise-on-use decay curve (chance decreasing as skill nears cap) if flat-rate leveling feels off in practice.
- A richer per-weapon-type skill tree, if 2-category granularity proves too coarse later.
- A dedicated Skill Editor, only if skill data outgrows what the Race & Class / Mob Editors already cover.
