## Goal

Give the server a safe, reusable way to **read and write Postgres without ever stalling Mirror's
main-thread tick**. 1.1 proved we can connect + migrate at startup; 1.2 builds the runtime plumbing
that everything persisted will go through:

- a **background write path** (async save queue) so DB writes happen off the server tick,
- a **load path** that runs the DB read off-thread and hands the result back **on the main thread**,
- **connection/transaction helpers** and a **repository convention** for hand-written Npgsql,
- a **graceful flush** on server stop so queued writes are never lost.

No character/account schema yet — that's 1.3. 1.2 is the *machinery*, proven against a throwaway
table so it's independently testable (same philosophy as 1.1's `schema_version`-only first cut).

### Scope guardrails
- **In scope:** the `PersistenceService` (worker + queue + load dispatch + flush), job/snapshot
  abstractions, a repository base/convention, transaction helpers on `Database`, a DAL self-test
  (throwaway table + editor menu), server-lifecycle wiring.
- **Out of scope:** the character schema and a real `CharacterRepository` (1.3); accounts/login
  (1.4); **save *policy*** — *when* to autosave / save-on-disconnect (1.6). 1.2 only provides the
  mechanism; call sites come later.
- **Hard rule:** server-authoritative. The DAL is a server-only component; the client never
  references it and never opens a connection.

## Approach

### 1. Threading model — why a background worker at all

Mirror's server logic and all `NetworkBehaviour` code run on Unity's **main thread**. Npgsql calls
are **blocking I/O**; running them inline would freeze the tick (hitching, timeouts) under any real
write volume. So DB I/O moves off-thread, with one inviolable rule:

> **The worker thread only ever touches plain snapshots + Npgsql — never Unity/Mirror objects.**

Anything entity-specific (a character's stats, inventory, position) is copied into a **plain-data
snapshot on the main thread** at enqueue time. The worker serializes that snapshot to SQL. Load
results are marshaled **back to the main thread** before any Unity object is touched.

### 2. `PersistenceService` (server-only `MonoBehaviour` singleton)

The single owner of all runtime DB access. Created on server start, destroyed (after flushing) on
server stop. Responsibilities:

- **Write queue:** a `BlockingCollection<ISaveJob>` drained by **one dedicated worker thread**
  (`BlockingCollection` blocks when empty — no busy-wait). Each job opens a pooled connection and
  runs its writes in a transaction.
- **Load dispatch:** `LoadAsync<T>(Func<NpgsqlConnection,T> read, Action<T> onLoaded)` runs `read`
  off-thread (thread pool, so a big write backlog can't delay a player-join load) and posts
  `onLoaded` to the **main-thread callback queue**.
- **Main-thread pump:** a `ConcurrentQueue<Action>` of continuations drained in `Update()`, so load
  results (and write-error notifications) resume on the main thread.
- **Graceful flush:** on `StopWorker()` (called from server stop / `OnApplicationQuit`),
  `CompleteAdding()` then **drain the remaining queue synchronously** and join the thread, so no
  pending write is dropped on shutdown.

### 3. Job + snapshot abstractions

- `ISaveJob` — `void Execute(NpgsqlConnection conn)`. The worker wraps each `Execute` in a
  transaction (begin/commit, rollback+log on throw). Concrete jobs in 1.3 carry an entity snapshot.
- `DelegateSaveJob` — adapts an `Action<NpgsqlConnection>` for ad-hoc writes and the self-test.
- **Coalescing (key-based, optional per DA2):** an `IKeyedSaveJob { string CoalesceKey }`. When a
  new keyed job is enqueued, it **replaces** any still-pending job with the same key (e.g.,
  `"character:42"`), so rapid repeat saves of one entity collapse to the latest snapshot instead of
  piling up. Implemented as a small pending-map guarding the queue.

### 4. Repository convention (raw Npgsql, no ORM)

Repositories are hand-written classes operating on a connection — no base class machinery beyond a
marker for consistency:

- `IRepository` (marker) + a documented shape: `Upsert(NpgsqlConnection conn, TSnapshot s)` and
  `TSnapshot Load(NpgsqlConnection conn, <id>)`, using parameterized commands only.
- `Database.RunInTransaction(Action<NpgsqlConnection, NpgsqlTransaction> body)` — a helper for
  multi-statement units of work (a 1.3 character spans several tables in one tx).
- Concrete repositories (e.g., `CharacterRepository`) are 1.3; 1.2 ships the convention + the
  self-test repo only.

### 5. DAL self-test (independent verification)

- Migration **`0002_dal_smoke.sql`** — a throwaway `dal_smoke (id TEXT PK, payload TEXT, updated_at
  TIMESTAMPTZ)` table, used only to prove the pipeline. (Dropped in a later migration once 1.3's real
  tables exist, or left as a harmless scratch table — decision DA3.)
- `Tools/Database/DAL Self-Test` — enqueues N writes through `PersistenceService`, triggers a flush,
  then loads them back and asserts the values round-tripped (incl. a coalescing check: enqueue the
  same key twice quickly, assert only the latest persisted). Logs pass/fail, cleans up its rows.

### 6. Server-lifecycle wiring

- `GameNetworkManager.OnStartServer` (already calls `Database.InitializeServer()`): after a
  successful DB init, **create the `PersistenceService`** (and `DontDestroyOnLoad` its GameObject).
- `GameNetworkManager.OnStopServer`: **flush + stop** the worker, then destroy the service.
- Guarded so it only ever exists server-side.

   draining to completion before the worker stops (no "lost N writes").

## Resolved decisions
- **Raw Npgsql, hand-written SQL + repositories** (carried from 1.1 — no ORM; Dapper still on the
  table only if mapping gets tedious in 1.3).
- **Server-only**, single `PersistenceService` owns all runtime DB access.

## Open decisions (please weigh in)
- **DA1 — Worker model:** dedicated `Thread` + `BlockingCollection` (recommended — predictable,
  no busy-wait, easy clean shutdown) vs. `Task`/thread-pool only. I lean dedicated thread for writes.
- **DA2 — Write coalescing:** key-based dedup keeping the latest snapshot (recommended — prevents
  queue blowup under autosave/on-change in 1.6) vs. plain FIFO (every enqueue writes). Coalescing is
  a bit more code now but pays off the moment save policy lands.
- **DA3 — Self-test table lifetime:** throwaway `dal_smoke` dropped by a later migration once 1.3's
  real tables exist (recommended) vs. keep it as a permanent generic scratch/kv table.
- **DA4 — Load result marshaling:** explicit main-thread callback queue drained in `Update()`
  (recommended — robust, no reliance on Unity's `SynchronizationContext`) vs. `async/await` relying
  on the captured sync context.
- **DA5 — Worker write-failure handling:** log + **bounded retry** (e.g., 2 retries w/ backoff) then
  surface to the main thread and drop (recommended) vs. log-and-drop immediately vs. block the queue.
