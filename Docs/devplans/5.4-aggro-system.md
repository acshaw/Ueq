# 5.4 — Aggro System

**Status:** ✅ Done 2026-07-26 — AG1–AG5 reviewed one at a time then built, then verified in-editor by the
user after three more real fixes surfaced during that verification (see "Verification log" below). AG1 grew
substantially into a full player-triggered Consider system; AG4 was redesigned twice, ending on a
threat-status model (Active/Dead/Zoned) that preserves damage history for 5.3's kill-credit purposes while
still correctly excluding departed players from live retargeting.

## Verification log (2026-07-26)

User ran the full build/test plan across two real fixes rounds before confirming everything works:

1. **Consider always showed the generic fallback text.** Root cause: the `consider_text` seed used `ON
   CONFLICT (name) DO NOTHING`, so it silently never populated on the threshold rows that already existed
   in the dev DB from before this session — the exact idempotency trap already correctly avoided for Taunt's
   effect, just missed here. Fixed to a backfill-if-blank `ON CONFLICT ... DO UPDATE ... WHERE consider_text
   = ''`, which fills in without ever clobbering a future web-authored edit.
2. **HP panes showed "Player" instead of the real character name.** A genuinely pre-existing, unrelated bug
   (nothing to do with 5.3/5.4) — `Nameplate` had **never been added to the Player prefab at all**, in
   either `Tools/Patch Player Prefab`'s list or the from-scratch `CreatePlayer()` builder (confirmed by
   grepping the actual prefab file: zero references, versus `Enemy.prefab` which has it correctly). Every
   `GetComponent<Nameplate>()` on a player has always returned `null`, so `CharacterPersistence.ApplyName`'s
   `_nameplate?.SetLabel(name)` has always silently no-op'd. Fixed by adding `Nameplate` to both. A first
   attempted fix (a lazy re-check in `PlayerFrame.Update()`, assuming a SyncVar-arrival timing race) was
   solving the wrong problem — kept anyway as legitimate defense-in-depth now that the component actually
   exists.
3. **"How does a Cleric heal a groupmate if players can't be targeted?"** — correctly identified as a real
   gap, not a non-issue: extended `Targetable` to players (with a friendly/green highlight distinct from the
   hostile/red used for mobs, and a lazy renderer re-resolve since a player's body is built at runtime by
   `PlayerModel`, after `Awake`). Made ability casting (`CmdCastAbility`) read the server's own authoritative
   target instead of a client-supplied one, unifying click-targeting and F-key group-targeting onto one path
   for the first time. Necessary companion fix: broadened the same-party-only friendly-fire guard (GP6) into
   a blanket **no-PvP rule** (`Health.TakeDamage` backstop + `PlayerAutoAttack`'s proactive message) — before
   this change targeting a player at all was physically impossible, so nothing had ever exercised
   player-vs-player damage outside a party; enabling targeting for the first time would otherwise have
   quietly opened a real, unintended PvP damage path in a game with no PvP design anywhere.

**User confirmed everything works end to end after these fixes.**

## Why

Retitled from "Group threat/aggro tuning" (2026-07-26) — that framing wrongly presumed a working base
threat/aggro system already existed to tune. It doesn't: today's is the 1:1-damage-mirror placeholder
retired from 3.4, folded into 5.1's scope note but never itself devplanned. This is that real system.

Scoped tightly on purpose, matching the instinct that just retired 5.6/5.7 as premature: this is **the
missing mechanism**, not a role-balance pass. No tank-stance/threat-multiplier system, no player-facing
threat meter, no touching the core per-hit damage-to-threat formula — those all want real playtesting data
first, which doesn't exist yet.

## Current state (grounding — verified against the real code)

- **`EnemyAI._threatList`** (`Dictionary<NetworkIdentity, int>`) is genuinely just "cumulative damage dealt
  per attacker." `AddThreat(player, amount)` is called from exactly two places: `OnAttacked` (every point of
  damage becomes threat, 1:1) and `NpcFaction.OnAggroStanding` (a flat `BaseAggroThreat` on initial hostile
  perception). No decay, no other source.
- **`NpcFaction.OnPerceived`** (`Assets/Scripts/Faction/NpcFaction.cs`) is the real, working perception entry
  point — evaluates the player's faction standing and routes to `OnAggroStanding` (real: calls `AddThreat`),
  `OnWarningStanding`, or `OnFriendlyStanding`. **The latter two are bare `Debug.Log` calls with `// TODO`
  comments** — no standing is player-visible today except by getting attacked.
- **`FactionThreshold`** (`Assets/Scripts/Faction/FactionThreshold.cs`) is currently just `{Name,
  MinScore}` — no text field to hang a player-facing message on. The shared threshold ladder is DB-backed
  (`faction_thresholds`, migration `0013`) and editable via the web Faction Editor (2.6) — consistent with
  this project's "no content without a tool" principle, any new authored text should live there too, not in
  a C# switch keyed on threshold name (which would silently break if a threshold is renamed).
- **`C` is a completely unbound key** — free to use.
- **No social aggro.** The only NPC-to-NPC threat code (`NpcEventDispatcher.PerceptionTick`) handles
  *mutually hostile factions* perceiving each other (e.g. a rat and a guard), not "an ally of my faction
  joins the fight I'm already in" — the design doc's actual social-aggro spec. `FactionDefinition` already
  models ally/hostile relations (2.6) via `IsHostileWith` — confirmed there's no `IsAllyWith`-driven combat
  broadcast anywhere.
- **Threat never expires except via a threatening player's own death** (`SubscribeToPlayerDeath` →
  `RemoveFromThreatList`). `EnterReturn()` (the leash-and-walk-home path) has **never** cleared
  `_threatList` — not something 5.3 touched, a pre-existing gap. A mob's grudge against a player who simply
  ran away currently persists indefinitely across repeated pulls.
- **`Taunt` has zero effects** — confirmed in `DatabaseSeeder.cs`: `kick`/`fire_bolt`/`minor_heal` each get a
  `SeedAbilityEffect` call, `Taunt` doesn't. It has an empty `animTrigger` too. It's a real hotbar slot
  (Warrior's second starting ability) that mechanically does nothing beyond consuming its cooldown today.
- **Ability effects today**: only `DamageEffect` and `HealEffect` exist as concrete `AbilityEffect`
  subclasses (per the original ability-system design — "new mechanic = new `AbilityEffect` subclass, no
  existing code touched"). A threat-manipulating effect needs a new subclass, not a variant of an existing
  one.

## Decisions

### AG1 — Consider system (revised during review — a full player-triggered mechanic, not an automatic ping)
**Redesigned after discussion**: rather than an automatic one-time chat ping on perception (the original
idea), this is the classic "consider" mechanic — a player actively presses **C** (or right-clicks a live,
non-corpse target) while targeting a mob/NPC to learn its disposition, on demand, any time. **Decided:
consider-only, no automatic ping at all** — matches how this already works in the reference genre, and
avoids two overlapping notification mechanisms doing similar jobs.
- **Trigger**: `C` key while a target is set (mirrors the existing hotkey-poll pattern — `PlayerAutoAttack`'s
  `digit1Key`, `PlayerSitting`'s `digit0Key` — suppressed while chat is open, same as those). **Also**:
  right-click on a live (non-corpse) `Targetable` — purely additive, since RMB on a live mob currently does
  nothing at all (today's RMB handling only checks for `Corpse`/`PlayerCorpse`).
- **Output**: a chat line (System or a new dedicated channel — see AG1b below), reusing existing
  `ChatManager` delivery. No new UI surface.
- **Text is data-driven, not hardcoded**: `FactionThreshold` gains a `considerText` field (migration adds
  `faction_thresholds.consider_text`), authored per-threshold in the web Faction Editor alongside `Name`/
  `MinScore` — so renaming or adding a threshold tier never silently breaks the message. A new server-side
  `CmdConsider(NetworkIdentity target)` resolves the target's `NpcFaction.EvaluatePlayer(...)` (the exact
  same evaluation `OnPerceived` already uses) and sends back the matched threshold's `considerText`.
- This also **subsumes AG2's original concern** for the *informational* gap — a player can now consider a
  friendly NPC to learn its disposition on demand, so `OnFriendlyStanding`'s stub no longer needs to be
  treated as an urgent player-facing hole. What it doesn't cover is *NPC-initiated* unprompted greeting
  speech, which stays a separate, smaller, Conversation-System-flavored item (AG2 below).

**AG1a — Message channel — DECIDED: new `ChatChannel.Consider`** (distinct color/filter) rather than reusing
System — considers will be frequent/exploratory (players will consider lots of things while scouting), and
bundling them into System chat would drown out actual system messages. Same pattern as 5.3's `Group` channel
addition.

**AG1b — Default consider text per tier**: needs real authored strings for the 9 existing thresholds (KOS →
Ally) before this is usable — will seed sensible defaults (e.g. KOS: "would attack you on sight"; Ally:
"looks upon you as a true friend") via `DatabaseSeeder`, fully re-editable per-faction afterward in the
Faction Editor exactly like every other seeded default in this project.

### AG2 — Friendly/greeting perception branch — **DECIDED: OUT of this item's scope**
`OnFriendlyStanding`'s stub covers *NPC-initiated* unprompted speech (an NPC saying hello as you walk up).
Discussed at length during review: hostile perception already has a real mechanism (aggro → `AddThreat`),
and now that AG1 (Consider) gives players an on-demand way to learn any NPC's disposition, the friendly/
neutral case is no longer an urgent information gap — what's left is a genuinely separate design problem
(multiple players passing the same NPC shouldn't each re-trigger an identical greeting line; needs real
per-NPC or per-player-NPC rate-limiting, most naturally built on the Conversation System's existing session/
cooldown machinery rather than a new bespoke mechanism). That's real design work deserving its own devplan,
not a fold-in here — see Deferred/backlog seeds.

### AG3 — Social aggro — **DECIDED, refined during review**
When a mob's `EnemyAI` transitions **into** `Combat` state (not every tick — an edge trigger, mirroring how
perception itself already edge-triggers via `_perceivedPlayers`), broadcast to nearby eligible `NpcFaction`
components within a radius; each eligible ally adds threat against the *same* target directly (`AddThreat`,
skipping its own independent perception check) rather than running a fresh perception scan — matches the
design doc's explicit "not a separate perception check" framing.
- **Toggle**: new `bool socialAggroEnabled` on `MobDefinition` (Mob Editor), **default false/opt-in** — ships
  with zero behavior change to any existing mob; authors deliberately enable it for organized groups (guard
  patrols, goblin warbands), leave solitary wildlife untouched.
- **Radius**: new `float socialAggroRadius` on `MobDefinition`, only meaningful when the toggle is on —
  authored per-mob (a tight dungeon room and an open field call for very different ranges) but **defaults to
  a sensible common value** (e.g. 20 units) so an author enabling the toggle doesn't also have to think about
  the number unless they want to customize it.
- **Responder eligibility**: same faction, **or** a faction the aggroing mob's faction is allied with
  (`FactionDefinition.IsAllyWith`, already built for 2.6, confirmed in code) — no new authored relation data
  needed, reuses the existing ally/hostile lists. A fully independent "which factions respond" list per mob
  was considered and set aside as unneeded authoring surface for a case the relation table already covers;
  cheap to add later if a real need for divergence from a mob's own faction relations ever comes up.

### AG4 — Threat lifecycle: unified departure cleanup, no chase leash — **DECIDED, substantially redesigned during review**
Grounded against the real code before deciding, since two of the three behaviors discussed already exist:
- **Player death → removed from every mob's threat list**: already works (`SubscribeToPlayerDeath`/
  `RemoveFromThreatList`, per-mob `Health.OnDied` subscription).
- **Player zones out → removed from that mob's threat list + reassessment**: already works
  (`EnemyAI.PruneZonedOutThreats`, WR7, per-frame scene comparison).
- **"Resume whatever it was doing before" once the threat list empties**: already works
  (`EnterReturn` → `_movementBehavior.Resume()`, built in 3.1.11 — patrol resumes its route, wander resumes
  roaming, stationary returns to post).

**Redesigned twice during review** — first to a unified reverse-index push, then again once a real fairness
question surfaced: should a group member who dies (or zones out) mid-fight still count toward their group's
eventual kill credit (5.3, GP5)? **Decided: yes, their damage contribution should be preserved**, which means
a threat entry needs a *status* (is this a live combat threat?) separate from its *damage total* (does this
count toward who gets credit?) — collapsing them into "present in the dict = both" (the original plan) can't
express that distinction.

**Final data model**: `_threatList` becomes `Dictionary<NetworkIdentity, ThreatEntry>`, where `ThreatEntry =
{int Damage, ThreatStatus Status}` and `ThreatStatus = {Active, Dead, Zoned}`.
- **`AddThreat`** only ever creates/updates `Active` entries (a dead or zoned identity can't act, so this
  path is never realistically hit for them again until a genuinely new encounter).
- **`GetTopThreat`/retargeting** only considers `Status == Active` entries — a dead or zoned player is never
  re-targeted and never keeps a mob engaged. This replaces the old `Health.IsDead` check on read.
- **A per-player reverse-index** (new server-only `NetworkedPlayer` field: which `EnemyAI`s currently have
  this player threat-listed, populated by `AddThreat`) lets a departing player proactively tell every mob
  that has them to flip their status — `Dead` from `HandlePlayerDeath` (character survives, respawns
  elsewhere, so this must be explicit), `Zoned` from the zone-transition point (`SetZone`). **Replaces** the
  current per-mob `OnDied` subscription and the per-frame `PruneZonedOutThreats` scan — one push at the
  moment of departure, and a nice side benefit of removing a per-frame per-mob dictionary scan.
- **5.3's `ResolveCreditedGroup` sums `Damage` across every entry regardless of status** — a dead or zoned
  member's contribution still counts toward their group winning the majority-damage contest. Their personal
  XP share is still separately gated by 5.3's existing same-zone/in-range filter (GP4), so this doesn't let a
  departed player collect a reward — it just makes which *group* gets credit accurate.
- **The whole dictionary is cleared once `ReturnLoop` completes** (the mob fully disengages, back to Idle) —
  otherwise stale `Dead`/`Zoned` entries would leak into a completely unrelated future encounter. This is
  the original "clear on Return" idea from the first pass at this decision — it looked redundant once the
  reverse-index made `Active` cleanup prompt, but it's genuinely needed again now that non-`Active` entries
  are deliberately kept around (for credit) rather than removed outright.
- **`Disconnected` deliberately left out as its own status for now** — until true linkdead persistence exists
  (deferred, see below), a disconnect already behaves like "identity destroyed," which every read path here
  is already null-safe against. Slots in cleanly as a third status later if that feature is ever built.

**No chase-distance leash** — considered during review and explicitly rejected: chasing/being led ("training
to zone") is an intentional accepted design choice here, not a bug. A mob will keep chasing a fleeing-but-
alive, same-zone target indefinitely, same as today — this item doesn't change that.

**Disconnect needs no special aggro-side handling.** Confirmed in code: `GameNetworkManager.
OnServerDisconnect` already destroys the player's character via Mirror's default behavior (`base.
OnServerDisconnect` → `DestroyPlayerForConnection`) — there's no "linkdead" body persisting in the world
today. True EQ1-style linkdead persistence (character stays in world, uncontrolled, still killable, to
prevent disconnect-as-escape) was discussed and is a genuinely separate, bigger character-lifecycle/
networking feature — not aggro-system work, since the aggro code's job is identical either way (react
correctly to "this identity is gone" or "present and killable," both already handled). Flagged as its own
deferred idea, not designed or built here.

### AG5 — Give Taunt (and future threat abilities) a real effect — **DECIDED: new `ThreatEffect` AbilityEffect subclass**
New `AbilityEffect` subclass (`ThreatEffect`) — flat amount or multiplier added directly via
`EnemyAI.AddThreat`, following the same "one subclass per mechanic" pattern `DamageEffect`/`HealEffect`
already established (no changes needed to `PlayerAbilities.TryCast` or the effect-application loop). Wire it
onto the existing `Taunt` ability (currently effect-less) via the web Ability Editor — a flat, generous bonus
(e.g. enough to reliably overtake the current top threat) rather than a proper "threat multiplier / tank
stance" system, which is explicitly out of scope here (AG-scope note above).

## Build / test plan
1. **AG1 (Consider)**: target a mob at each of several standings (aggro/warning/friendly) → press `C` →
   confirm the correct per-threshold `considerText` appears on the Consider channel, not spammed on repeat
   presses beyond what the player does; right-click a live mob produces the same result; right-click on a
   corpse still loots (unaffected); consider suppressed while chat is open.
2. **AG3**: place two same-faction mobs near each other; aggro one via combat; confirm the second joins
   without needing its own separate proximity-perception trigger on the player.
3. **AG4**: aggro a mob solo, die mid-fight (no group) → confirm the mob stops targeting the (now-respawned)
   player and, once no `Active` entries remain, resumes its prior behavior (patrol/wander/post); same test
   zoning away instead of dying; confirm a mob actively chasing a fleeing-but-alive same-zone target keeps
   chasing indefinitely (no leash — intentional). **Group scenario (the actual point of the redesign)**: two
   grouped players fight a mob, one dies (or zones) partway through, the other lands the killing blow →
   confirm the group still receives full credit (5.3's XP split + loot rights) reflecting *both* members'
   damage, not just the survivor's — and confirm the mob resumed correctly (fully disengaged and returned)
   for a completely separate, later, unrelated encounter, not carrying stale entries into it.
4. **AG5**: cast Taunt on a mob currently fighting someone else; confirm it retargets to the taunter.
5. Regression: solo pulls, faction-gated conversation warnings still work correctly with the new
   `ThreatEntry`/status data shape (any code reading `_threatList` as a raw damage dictionary needs updating
   for the wrapped-value change, not just 5.3's `ResolveCreditedGroup`).

## Done when
A player can consider any targeted mob/NPC (C key or right-click) and get an accurate, per-faction-tier
message on demand; same-faction allies join an in-progress fight within their mob-authored social radius
(when enabled); a player's death or zone-departure flips their threat status (not deleting their damage
history) so mobs stop treating them as a live threat while still crediting their contribution at eventual
kill time, and those mobs correctly resume their prior behavior once no live threats remain; Taunt actually
taunts. No chase-distance leash (training is intentional), no automatic perception ping, no new non-chat UI,
no threat-multiplier/tank-stance system, no continuous decay tuning, no linkdead-persistence work.

## Deferred / backlog seeds
- **NPC-initiated unprompted greeting speech (AG2)** — a real, separate item, not a quick stub-fill. Needs a
  deliberate anti-spam design (per-NPC and/or per-player-NPC cooldown so a crowded area doesn't repeat the
  same line for every passer-by) — most naturally reusing the Conversation System's existing session/
  cooldown state rather than inventing a new mechanism. Discussed 2026-07-26; deliberately not designed here.
- **True linkdead persistence on disconnect (AG4)** — EQ1-style: character stays in the world, uncontrolled,
  still killable, rather than being destroyed immediately (today's behavior) — to prevent disconnect being
  used as a consequence-free escape. A real, separate character-lifecycle/networking feature; discussed
  2026-07-26 but not designed or built here since the aggro system needs no special handling either way.
- Continuous in-combat threat decay (AG4) — revisit once there's real group-tanking playtesting data.
- Heal/buff-generated threat — blocked on group-targetable abilities (5.3's GP9, itself deferred); no live
  trigger path exists yet since only self-heals are castable today.
- Tank stance / threat-multiplier role system — real class-role balance work, wants playtesting data first,
  same reasoning that retired 5.6/5.7.
- Player-visible threat meter/UI — not requested, not clearly needed yet.
