# 8.2 — Named/rare spawn behavior

**Status:** 🟡 Awaiting review — scope narrowed 2026-09-20 (see note below).
**Roadmap item:** M8 → 8.2
**Pattern:** extends `spawn_table_entries` (2.7.2) with one field; the "named" identity itself (better
stats/loot) needs **no new schema at all** — a named is just its own `MobDefinition` row, which the
content system already supports.

**Scope narrowed 2026-09-20:** asked the user before implementing whether the spawn announcement should be
server-wide or zone-scoped — answer was **no announcements at all for this item**. Named/rare mobs are a
day-to-day camp-variety mechanic (a rarer roll with better loot), not an event; the user wants
server/zone-wide "X has appeared!" broadcasts reserved for a **future raid/event-mob system**, not spun up
here for an ordinary named. **NR3/NR4 (announcement scope + chat channel) are dropped entirely** — 8.2 is
now just the independent respawn-pace override. The announcement concept isn't lost — noted in CLAUDE.md's
Deferred/Backlog list for whenever raid/event mobs get scheduled.

---

## Goal & why now

The classic EQ pattern — a camp that's usually a placeholder trash mob, rarely a tougher named with better
loot — is *almost* fully covered by a low-weight `SpawnTableEntry` today: give the named mob its own
`MobDefinition` row (its own stats/loot table/xpReward — already fully supported, no new capability
needed there) and a weight of, say, 1 against the trash's 20. What's actually still missing is **its own
respawn pace**, independent of the camp's normal timer — a named shouldn't pop back in as fast as the
trash it replaces.

## Current state (grounding)

- `SpawnPoint._respawnTimer` is set **once per `DoSpawn()` call, from the table's single `defaultTimer`**
  — every entry in a table currently respawns on the same pace regardless of which one rolled.
  `SpawnPoint` doesn't track *which entry* was rolled past the moment it resolves `def`/`groupSize` — it
  discards that after `SpawnOne` is called, so there's no hook today for a per-entry respawn override even
  if the data existed. Re-confirmed accurate after 8.1's rewrite of `DoSpawn()` (the `entry` local is still
  discarded the same way, now alongside the new eligibility-filter logic) — nothing there drifted.
- Loot/XP/stats richness for a "named" needs zero new plumbing — `MobDefinition.lootTableId`/`xpReward`/
  `atk`/`ac`/`maxHealth` are all already independent per mob id (M2.5/2.7/5.1.5/Mitigation).

## Decisions (recommendations in **bold**)

**NR1 — What "named" actually adds.** **One new field on `SpawnTableEntry`: an optional respawn override
(`RespawnBaseSeconds`/`RespawnVariance`, nullable — null = fall back to the table's `defaultTimer`,
unchanged behavior for every entry that doesn't set one).** Nothing else — the mob being "better" is
already just authoring a richer `MobDefinition` for that entry's `mob_id`, no code change. (Announcement
dropped per the scope-narrowing note above.)

**NR2 — Where the respawn override is read.** `SpawnPoint.DoSpawn()` must **remember which entry it
rolled**, not just the resolved `MobDefinition`, so `OnMemberDied`'s respawn-delay lookup can prefer the
entry's override over the table default. **Recommend:** `DoSpawn()` stores the rolled `SpawnTableEntry`
reference itself in `_lastRolledEntry` alongside the existing `_respawnTimer`; `RespawnAfterDelay()` checks
`_lastRolledEntry?.RespawnBaseSeconds` first. For the `mobId` (non-table) path, there's no entry to
override from — unaffected, keeps its existing `_respawnTimer = null` (300s default) behavior.

**NR5 — Web authoring.** One new pair of fields per entry row in the Spawn Editor: an optional "Respawn
override (s) — leave blank to use the table's timer" pair of number inputs (base/variance), mirroring the
table-level timer fields' own layout.

## Schema

```sql
ALTER TABLE spawn_table_entries
    ADD COLUMN IF NOT EXISTS respawn_base_seconds    REAL,   -- null = use the table's default timer
    ADD COLUMN IF NOT EXISTS respawn_variance        REAL;   -- null = use the table's default timer
```

## Files (once approved)

**Modified:** `SpawnTable.cs` (`SpawnTableEntry` gains the two respawn-override fields), `SpawnTableRepository.cs`/
`SpawnTableRegistry.cs` (read them; build a per-entry `SpawnTimer` only when an override is present),
`SpawnPoint.cs` (remember the rolled entry; prefer its timer over the table default in
`RespawnAfterDelay`), migration `00NN_named_rare_spawns.sql`, API entity/controller + Angular
service/editor (two new entry fields).

## Test plan

1. Author a table with a weight-20 trash entry and a weight-1 named entry (`RespawnBaseSeconds = 1800`).
   Kill the named → confirm the camp's next respawn happens on ~1800s, not the table's normal (much
   shorter) default — and that a subsequent trash-mob respawn on the same point still uses the table
   default (the override is per-roll, not sticky).
2. A table with no override entries behaves exactly as before (regression check).

## Risks

- **Respawn-override bookkeeping** — `_lastRolledEntry` must be cleared/ignored correctly across the
  `mobId`-only spawn path (no entry exists there) and across a table swap (editing a live point's
  `spawnTableId` mid-session) — worth an explicit null-check rather than assuming the field is always fresh.

## Done when

A spawn table entry can be given its own respawn pace, authored in the web Spawn Editor, with zero effect
on entries that don't opt in.

## Deferred (not part of this item)

Spawn announcements ("X has appeared!", server- or zone-wide) — the user wants this reserved for a future
raid/event-mob system rather than firing for every ordinary named/rare roll. Noted in CLAUDE.md's
Deferred/Backlog list. When that system gets scheduled, this devplan's dropped NR3/NR4 (SendAll vs. a new
zone-scoped `ChatManager.SendZone`, a new `ChatChannel.Spawn` value + the two `ChatUI.cs` switch arms it
needs) are the starting design, not thrown away — just not needed for plain named/rare mobs.
