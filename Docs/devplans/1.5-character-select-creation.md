# Devplan 1.5 — Character select + creation (first-run)

**Roadmap item:** M1 → 1.5
**Status:** ✅ Done 2026-06-21 — verified in editor + MPPM: select panel appears for both host (`dev`)
and a freshly-registered Player 2 account; create/enter/delete all work; duplicate-name and
short-name rejection, one-character-per-account block, created-character persist round-trip, and
account isolation all pass; no `_defaultRace` fallback warning in the normal flow. (Hotbar display
oddity during testing was the known UI-wiring quirk — cosmetic, resolved by Setup All + scene save;
1.7 replaces that procedural UI.)

> **Implementation notes (deviations from the plan, all minor):**
> - Result message is `CharacterActionResult` (plan sketched `CharacterCreateResult`) — used for
>   create/enter/delete failures; success just spawns (no message).
> - The off-thread list read returns `CharacterRepository.CharacterRow` (raw); the controller derives
>   `level` on the main-thread callback (level math touches the Resources XP table, so it can't run
>   off-thread).
> - Removed the hardcoded `Nameplate.SetLabel("Player")` from `NetworkedPlayer.OnStartServer` — with
>   `CharacterPersistence` ordered before `NetworkedPlayer`, it would clobber a freshly-created
>   character's name. Name is now owned by `CharacterPersistence.ApplyName`.
> - `PlayerFactionScores.Initialize` now `_scores.Clear()`s first, so re-seeding on creation (chosen
>   race) is clean.
> - Delete does a combined delete-then-relist on the load path (one off-thread op) to avoid a
>   write-queue-vs-read race when refreshing the list.
> - Server handlers' lifecycle is driven by `GameNetworkManager.OnStartServer/OnStopServer`
>   (`CharacterSelectController.OnServerStarted/OnServerStopped`).
**Depends on:** 1.1 ✅, 1.2 ✅, 1.4 ✅ (account→connection seam), **1.3 (character persistence — load/save
round-trip + `CharacterPersistence`/`CharacterRepository`/`RaceClassRegistry`)** — pending its in-editor
verification, but the API it exposes is what 1.5 builds on.
**Unblocks:** 1.6 (multi-character, save policy/polish)

---

## Goal

Replace the hardcoded default-character spawn with a real first-run flow: **log in → see your
character (or none) → create one (name / race / class) → enter the world.** Creation seeds the
character through the existing `SetRaceClass` path (base stats, racial faction defaults, starting
abilities) and **retires the prefab `_defaultRace`/`_defaultClass` test path** as the source of truth.

This turns the account (1.4) into something that *owns a character* the player chose, and makes the
1.3 persistence round-trip start from a real creation event instead of a prefab default.

### Scope guardrails
- **In scope:** deferring player spawn until a character is chosen (`autoCreatePlayer = false` + an
  explicit enter-world handshake); a character-list + creation UI shown after auth and before spawn;
  server-side create/enter (and minimal delete) message handlers; seeding a new character via
  `SetRaceClass` + racial faction defaults + the chosen name; applying the name to the nameplate +
  chat identity; and sending the available race/class options to the client.
- **Out of scope:**
  - **Multiple characters per account (1.6).** 1.5 stays **one character per account** — the 1.3
    `UNIQUE(account_id)` constraint is unchanged; the "list" shows 0 or 1 (see D1). 1.6 relaxes the
    constraint and turns the list into N slots.
  - **Save cadence / clean-logout polish (1.6).** 1.5 persists a new character via the 1.3
    save-on-stop/disconnect path (plus one immediate save right after creation so it survives).
  - **DB-backed race/class content + rich creation data (M2.6).** Race/class stay ScriptableObjects
    resolved by `RaceClassRegistry`; 1.5 sends their names/display info, nothing richer.
  - **Polished uGUI creation screen, character preview/3D model, appearance customization.** IMGUI
    for now (D3); art/polish is later.
- **Hard rule (carried):** server-authoritative. The client only *requests* create/enter; the server
  validates ownership + input and decides what spawns. DB work stays off the main thread (1.2).

## Approach

### 1. Flow (deferred spawn)

Today `autoCreatePlayer = true`, so Mirror auto-spawns the player the instant auth succeeds. 1.5 sets
**`autoCreatePlayer = false`** and inserts a selection step between auth and spawn:

```
LoginUI (1.4)  ──auth ok──▶  CharacterSelectUI (1.5)         server
                                  │  request list  ──────────▶ ListByAccount(account) [off-thread]
                                  ◀───────── CharacterListMessage { entries[], raceOptions[], classOptions[] }
        ┌── list empty ──▶ Create form (name / race / class) ─▶ CreateCharacter ─▶ validate ─▶ spawn(new)
        └── has a char ──▶ Select + [Enter] ───────────────────▶ EnterWorld{charId} ─▶ validate ─▶ spawn(existing)
                                                          (optional) Delete{charId} ─▶ DeleteByAccount
                                  ◀──── player spawned (NetworkServer.AddPlayerForConnection) ────
```

The host's local client goes through the same screen (after the 1.4 host-as-dev auto-login). A dev
convenience (D3) can auto-enter when the account already has exactly one character.

### 2. Creation model — **"create = enter"** (D2, recommended)

A brand-new character is spawned **directly** and persisted by an immediate post-init save, reusing
1.3's *no-saved-character* branch instead of pre-inserting a half-populated row:

- Client submits `CreateCharacterMessage { name, race, class }`.
- Server validates (name rules + optional uniqueness, race/class exist in `RaceClassRegistry`, account
  has no character yet in 1.5), then stashes a **pending creation** on the connection and calls
  `NetworkServer.AddPlayerForConnection`.
- The spawned player's `CharacterPersistence.OnStartServer` sees the pending creation → runs
  `InitializeNewCharacter(name, race, class)` (below) → calls `Save()` immediately, which **creates**
  the row via the existing `Upsert`.

This avoids a "new but uninitialized" row shape (and the sentinel/branch logic that a pre-inserted
row would force on the load path) — the *no row* case already means "fresh character," we just feed it
the chosen race/class/name instead of the prefab defaults. (Rejected alternative: insert a minimal row
at creation and detect "new" on load via a sentinel column — more schema + branching for no 1.5
benefit. Revisit in 1.6 if create-without-enter is wanted for multi-slot management.)

### 3. `CharacterPersistence` changes (modifies the 1.3 component)

`OnStartServer` chooses a path from the connection's `AccountSession`:

- **Pending creation present** → `InitializeNewCharacter(name, race, cls)`:
  - `_exp.LoadState(0, race, cls)` (base stats, max HP/mana, known abilities + default hotbar),
  - `_faction.Initialize(race.raceName)` (seed racial faction defaults for the *chosen* race; sets
    Actual/ApparentRace),
  - apply the **name** → `Nameplate.SetLabel(name)` + `gameObject.name = name` (chat identity),
  - `_health.ResetToFull()` + set mana to max,
  - **keep Mirror's spawn-point position**; `SetBindPoint(transform.position)`,
  - `_loaded = true`, then `Save()` (creates the row immediately).
- **Existing selection** → the 1.3 load path unchanged (`LoadAsync(Load(account)) → ApplySnapshot`).
  Applies the saved name to the nameplate/`gameObject.name` too (1.3 currently leaves it "Player" —
  this is the line that fixes it).

`ApplySnapshot` gains one line: after `RefreshMax`, apply `s.Name` to nameplate + `gameObject.name`.
No sentinel/HP-fill branch is needed because new characters never reach `ApplySnapshot` (they go
through `InitializeNewCharacter`).

### 4. Connection state (the seam)

Extend `AccountSession` (already on `conn.authenticationData`) with selection state the server sets
before spawning and `CharacterPersistence` reads on spawn:

```csharp
public long SelectedCharacterId;          // existing character chosen to enter (1.6 keys load off this)
public PendingCharacter PendingCreation;  // non-null = create-and-enter a new character
// PendingCharacter { string Name, Race, Class; }
```

For 1.5 (one char/account) the existing load still keys off `AccountId`; `SelectedCharacterId` is
recorded now as the seam 1.6 will load by. Cleared/irrelevant after spawn.

### 5. Message protocol + server handlers

New `NetworkMessage` types (one file, `CharacterSelectMessages.cs`):
`CharacterListRequest {}`, `CharacterListMessage { CharacterListEntry[] entries; string[] raceOptions;
string[] classOptions; }`, `CreateCharacterMessage { name, race, class }`,
`EnterWorldMessage { long characterId }`, `DeleteCharacterMessage { long characterId }` (D7), and a
`CharacterCreateResult { bool ok; string error; }` for create/enter validation feedback.
`CharacterListEntry { long id; string name, race, cls; int level; }`.

**`CharacterSelectController`** (server, MonoBehaviour on the NetworkManager GameObject — D6):
- `OnStartServer`: `NetworkServer.RegisterHandler` for the four request messages.
- `CharacterListRequest` → `PersistenceService.LoadAsync(conn => repo.ListByAccount(accountId), …)` →
  send `CharacterListMessage` (entries + `RaceClassRegistry` option names).
- `CreateCharacter` → validate input (name length/charset, race/class exist, no existing char in 1.5,
  optional name-uniqueness D4); on fail send `CharacterCreateResult{false, …}`; on pass set
  `PendingCreation` on the session and `NetworkServer.AddPlayerForConnection(conn, Instantiate(playerPrefab))`.
- `EnterWorld` → verify the `characterId` belongs to this account (cheap query) → set
  `SelectedCharacterId` → `AddPlayerForConnection`.
- `DeleteCharacter` (D7) → `repo.DeleteByAccount`/by-id (children cascade) → resend the list.

**`CharacterSelectUI`** (client, IMGUI — D3): registers the `CharacterListMessage` /
`CharacterCreateResult` handlers; visible while `NetworkClient.isConnected && localPlayer == null`;
renders the list (Enter/Delete) or the create form (name field + race/class dropdowns from the sent
options); sends the request on first show and the create/enter/delete messages on button press.

### 6. `autoCreatePlayer` + spawn wiring

- Scene/`SceneSetup`: set `NetworkManager.autoCreatePlayer = false`; add `CharacterSelectController`
  to the NetworkManager GameObject next to `LoginUI`/`AccountAuthenticator`/`GameNetworkHUD`.
- The server spawns the player **only** via `AddPlayerForConnection` from the controller, so
  `GameNetworkManager.OnServerAddPlayer` (account-id log, 1.4) still runs on the real spawn.
- The existing player prefab + `NetworkStartPosition` placement is reused (new characters keep that
  spawn position; returning characters get teleported to their saved position by 1.3's load).

### 7. Retiring the default path (D5)

`PlayerExperience._defaultRace`/`_defaultClass` (and `PlayerFactionScores.defaultRace`) stop being the
normal source — every spawn now arrives via create (chosen race/class) or load (saved race/class).
Recommended: keep the serialized fields as an **explicit dev-only fallback** (used only if a player
somehow spawns with neither a pending creation nor a saved row), with a `Debug.LogWarning` when that
path fires, so it's obvious it shouldn't happen in the real flow.

## Schema / API changes

- **Schema:** none required for the core flow (1.3's `characters` already has `name`). **D4 (optional):**
  `0006_character_name_unique.sql` — a *partial* unique index `ON characters (lower(name)) WHERE name <> ''`
  (partial so 1.3's empty-name test rows don't collide; new characters always have a name).
- **`CharacterRepository`** (new reads/method):
  - `List<CharacterListEntry> ListByAccount(conn, accountId, tx=null)` — id/name/race/class/total_xp
    (level computed from XP).
  - `bool NameExists(conn, string nameLower, tx=null)` — only if D4 = enforce.
  - `DeleteById(conn, characterId, tx=null)` — if D7 keeps delete distinct from `DeleteByAccount`.
- **`AccountSession`** — `SelectedCharacterId` + `PendingCreation` fields (+ `PendingCharacter` type).
- **`CharacterPersistence`** — branch in `OnStartServer`; new `InitializeNewCharacter`; name applied in
  both paths.
- **New types:** `CharacterSelectMessages.cs`, `CharacterSelectController.cs`, `CharacterSelectUI.cs`.

## Resolved decisions (approved 2026-06-21 — all recommendations accepted)
- **D1 — Characters per account → ONE in 1.5** (keep `UNIQUE(account_id)`); multi-character is 1.6.
- **D2 — Creation model → CREATE = ENTER.** A new character spawns immediately and reuses 1.3's
  *no saved character* branch (fed the chosen race/class/name), persisted by an immediate post-init
  save. No pre-inserted/sentinel row. *(Forward note: the eventual creation flow is
  race→class→location→name; the location step plugs into `InitializeNewCharacter`'s
  position/bind seam — see [[project_creation_flow_intent]] — but is out of scope here, gated on M3
  zones.)*
- **D3 — UI tech → IMGUI** (matches `LoginUI`; intentionally throwaway — the polished version is part
  of the 1.7 UI refactor).
- **D4 — Character name uniqueness → ENFORCE** via `0006_character_name_unique.sql` (case-insensitive
  partial unique index `ON characters (lower(name)) WHERE name <> ''`). DB index is the real guard;
  the create form does a friendly pre-check for UX (same two-layer pattern as 1.4 usernames).
- **D5 — `_defaultRace`/`_defaultClass` → RETIRE from the normal flow, keep as a *warned* dev
  fallback** (logs a warning if it ever fires, so it can't silently mask a broken creation flow).
- **D6 — Server handler home → DEDICATED `CharacterSelectController`** on the NetworkManager GO
  (sibling to `AccountAuthenticator`/`LoginUI`).
- **D7 — Delete in 1.5 → INCLUDE a minimal, confirmed delete** (two-click confirm). With D1's
  one-character rule + creation blocked when one exists, delete is the only in-game way to re-roll.

## Risks
- **Spawn-flow regressions:** flipping `autoCreatePlayer` off means *nothing* spawns until the handshake
  works — a bug leaves the player stuck on the select screen. Mitigate with the dev auto-enter path and
  clear client-side error surfacing (`CharacterCreateResult`).
- **Pending-creation lost on early disconnect:** if the client disconnects between `CreateCharacter`
  and spawn, no row is written — acceptable (nothing was entered). The immediate post-init `Save()`
  closes the normal-case gap.
- **Name application timing:** `gameObject.name`/nameplate must be set server-side after spawn; the
  nameplate SyncVar propagates to clients, but `gameObject.name` is server-local (only chat uses it) —
  fine, but don't rely on it client-side.
- **Race/class option drift:** the client form must only offer what `RaceClassRegistry` actually has
  (Human/Warrior today) — drive the dropdowns from the server-sent option lists, never hardcode.

## Done when

A player logs into an account, and — if they have no character — creates one by name/race/class and
enters the world as that character (correct stats/abilities/faction/name), which persists and reloads
on the next login; an existing character is shown and entered directly; creation is server-validated;
and the prefab `_defaultRace`/`_defaultClass` path no longer drives normal spawns.
