## Goal

Get the content-authoring stack (`/web` Angular SPA + `/api` .NET backend + Postgres) reachable somewhere
other than localhost, with automated build validation on every push and automated deployment on merge —
so the user's brother (no SE background, out of state) can use the web editors without either of them
running `ng serve`/`dotnet run` by hand. Explicitly **not** the Unity dedicated game server (that's
5.10/6.2 — separate infrastructure, no coupling). Pulls roadmap **6.1** ("Deployed Postgres on AWS")
forward; sequenced right after 5.10 since both are pre-M6 infra de-risking work done ahead of schedule on
the user's call, not gated on M5's gameplay-depth items landing first.

## Grounding (read before designing)

- **The user already runs one AWS app** (`family-cookbook`, a sibling Angular+Postgres project) — read its
  `DEPLOY-AWS.md` in full. Its shape: Angular → **S3 + CloudFront**; Express API → **Lambda + API Gateway**;
  DB → **Aurora DSQL** (IAM-authenticated, no VPC needed); GitHub Actions deploys via **OIDC** (a
  `github-actions-deploy` style IAM role assumed per-run — zero long-lived AWS secrets in GitHub, just a
  role ARN). The OIDC identity provider (`token.actions.githubusercontent.com`) is **already registered on
  this AWS account** — CD6 below reuses it via a second, Ueq-scoped role rather than re-registering it.
- **Aurora DSQL is not a safe target for Ueq's schema.** This session's own 2.11 work built + verified an
  export/import tool (`ContentExportImport.cs`) that explicitly depends on `pg_get_serial_sequence`/
  `setval` to reset auto-increment ids after a bulk reload, and all 25 of Ueq's existing migrations lean on
  standard `BIGSERIAL`. DSQL's Postgres-compatibility has real gaps in exactly this area. Moving to it would
  risk a real schema/tooling rework for a payoff (no VPC networking) that doesn't apply once we're not
  putting the API on Lambda anyway (see CD1). **Use plain Postgres, not DSQL** — the identical engine Ueq
  already runs locally in Docker.
- **Access model is fundamentally different from `family-cookbook`.** That app is a public family site with
  no access restriction. Ueq's web tool is a **private admin/content-authoring surface** for exactly two
  known people (the user + their brother) — the user already chose **IP allowlisting** as the access
  control mechanism for this (prior turn in this session). A public CDN (CloudFront) is designed for open
  reach; IP-restricting it needs an AWS WAF IP-set or a CloudFront Function, which is more moving parts than
  just firewalling one box directly. This is why CD3 below deliberately departs from copying
  `family-cookbook`'s S3+CloudFront pattern verbatim — different access model, different right answer.
- **No auth exists in the web/API stack today** (a 2.1-era decision: "no auth, trusted users only"). IP
  allowlisting is doing the entire access-control job here — get the Lightsail firewall rule right, since
  there's no login screen behind it.
- **Migrations only run from the Unity Editor** (`Tools/Database/Run Migrations`, or automatically at Host
  process start via `Database.InitializeServer()`). The `/api` .NET project has no migration-running
  capability of its own — it only ever reads from tables the Unity side already created. This matters for
  CD8: there is no "the CI pipeline auto-migrates the deployed DB" story today without new engineering.
- Lightsail cost/spec grounding (see prior turn): the **$10/mo tier** (2 vCPU, 1 GB RAM, 40 GB SSD, 2 TB
  transfer) is the target size — the $5 tier's 0.5 GB RAM is too tight once a future Unity dedicated server
  process joins Postgres + the API on the same box. Lightsail supports AWS Systems Manager (SSM) via a
  documented one-time step (attach the default Lightsail SSM instance role in the console) — this is what
  makes CD6's no-SSH-key deploy mechanism possible on Lightsail specifically, not just raw EC2.

## Decisions

**CD1 — Hosting shape: one Lightsail instance, three co-located processes.** A single $10/mo Lightsail
instance (Ubuntu) runs: (1) Postgres via Docker (the existing local `docker-compose.yml`, bound to
`127.0.0.1` only — never exposed to any inbound firewall rule), (2) the `/api` .NET backend published for
`linux-x64` and run as a systemd service (`ueq-api.service`, Kestrel bound to localhost, not directly
internet-facing), (3) Caddy (see CD4) serving the built Angular app as static files and reverse-proxying API
calls to the local Kestrel process. A fourth process — the Unity dedicated game server — is **reserved
headroom, not built now**; see CD9.

**CD2 — Database: plain Postgres via Docker, not Aurora DSQL.** Same engine, same `docker-compose.yml`
shape as local dev. Zero schema-compatibility risk against the 25 existing migrations or the 2.11 export/
import tool. Bound to localhost only.

**CD3 — Frontend + API both served directly off the one box via Caddy, not S3+CloudFront+API Gateway.**
Deliberate departure from `family-cookbook`'s pattern (see Grounding) — the two apps have different access
models, and copying the CDN pattern here would fight against the IP-allowlist decision rather than serve
it. Caddy serves the Angular `dist/` build as static files under `/` and reverse-proxies `/api/*` (or a
distinct path) to the local Kestrel process — one server, one firewall rule, one place to reason about
access.

**CD4 — TLS via Caddy's automatic HTTPS.** Caddy (single binary, automatic Let's Encrypt cert issuance +
renewal, minimal config) instead of the more traditional nginx + certbot two-system combination — fewer
moving parts for a single small box. **Correction after verifying against AWS's own CLI/docs (the original
draft assumed Lightsail auto-assigns a public DNS hostname the way EC2 does — it doesn't; `get-instance`
only returns a public IP, no hostname field at all):** since Let's Encrypt issues certificates for domain
names, not bare IPs, this needs *some* resolvable hostname. Use **sslip.io** — a free wildcard-DNS service
where `<public-ip>.sslip.io` automatically resolves to that IP with no registration or purchase — as a real,
Let's-Encrypt-valid hostname with zero cost, closest to the original "no domain needed" intent. A real
custom domain (~$12/yr) remains a fine optional upgrade later, just not required to ship this.

**CD5 — Access control: app-level auth (JWT + invite-coded registration), not IP allowlisting. SSH still
closed entirely.** **Revised 2026-07-19 — superseded the original IP-allowlist plan.** Both the user's and
their brother's home IPs turned out to be dynamic, making a firewall allowlist a recurring manual-fix chore
every time an ISP rotated either address — genuinely cumbersome, not a one-time setup cost. Considered
Tailscale (a private mesh VPN — solves the dynamic-IP problem by authenticating identity instead of
network location) as an alternative; **the user chose real application-level auth instead**, reasoning it's
a small lift given the game server already has a working, tested password-hashing scheme to reuse (1.4's
`PasswordHasher.cs`).

Implemented: a new `web_admins` table (migration `0026_web_admins.sql`, separate from the game's `accounts`
table — different concern), a `PasswordHasher.cs` ported byte-for-byte into the `/api` project (same
PBKDF2/PHC-string scheme, not shared code but deliberately identical rather than inventing a second one), a
new `AuthController` (`/api/auth/register`, `/login`, `/logout`, `/me`), and a session mechanism: a signed
JWT in an **HttpOnly cookie** (not a bearer header — the JwtBearer middleware is configured to pull the
token out of the cookie via `OnMessageReceived`), validated on every request via a **global**
`AuthorizeFilter` (`AddControllers(o => o.Filters.Add(new AuthorizeFilter()))`) so a future new controller
can't accidentally ship unauthenticated — only the auth endpoints themselves opt out via
`[AllowAnonymous]`.

**Registration is self-service in the Angular app (mirroring the game's own register flow) but gated by a
shared invite code** (`UEQ_WEB_INVITE_CODE` env var, compared via `CryptographicOperations.FixedTimeEquals`)
— without this, an open registration endpoint on a content-authoring tool would let anyone who finds the
URL create an account and start editing game content, which would defeat the entire point of adding auth.
Two secrets resolve via a new `AuthConfig.cs` (mirrors `DatabaseConfig`'s env-var-first pattern): `UEQ_WEB_
JWT_SECRET` (signs/validates sessions) and `UEQ_WEB_INVITE_CODE`, both required in Production, with an
insecure fixed fallback in Development only so `dotnet run` works locally with no setup.

**CD3's original reasoning (avoid fighting a CDN's public-by-design reach with WAF/a CloudFront Function)
is now moot** — auth replaces IP-restriction as the access-control layer, so a CDN would no longer need any
special IP-blocking mechanism. Kept CD1/CD3 (single Lightsail box + Caddy) unchanged anyway: no new reason
emerged to prefer S3+CloudFront, and switching now would be pure extra churn for no concrete benefit at
this traffic scale. **Net effect on CD5's firewall config**: 80/443 open to everyone (`0.0.0.0/0`), not
IP-restricted — the login/invite-code gate is the real barrier now. Port 22 (SSH) stays closed entirely,
unrelated to this change — manual admin access via Lightsail's browser-based SSH.

**Verified via a real end-to-end curl-based test against a throwaway Postgres + the actual built API
(not just compiled)**: unauthenticated request to `/api/items` → 401; register with a wrong invite code →
401; register with the correct invite code → 200 + session cookie set; duplicate username → 409; `/api/
auth/me` with the cookie → 200 + username; `/api/items` with the cookie → 200; logout → subsequent `/me` →
401; login with wrong password → 401; login with correct password → 200, and the resulting cookie
authorizes `/api/items` again. Every case behaved exactly as designed.

**CD6 — Deploy mechanism: GitHub OIDC → S3 artifact bucket → SSM, no stored SSH key.** On push to the
main branch: build the API (`dotnet publish -c Release -r linux-x64 --self-contained false`) and the web
app (`ng build --configuration production`), zip each, and upload both to a new small private S3 bucket
(`ueq-deploy-artifacts`) using a **new IAM role scoped to the Ueq repo** (reuses the AWS account's existing
GitHub OIDC provider registration from `family-cookbook`, mirroring its `gh-trust.json` pattern with a
different `sub` condition). The same role then calls `aws ssm send-command`, targeting the one Lightsail
instance, to run a small deploy script already present on the box: pull the latest zips from S3, unpack,
`systemctl restart ueq-api`, reload Caddy. Requires enabling AWS Systems Manager on the Lightsail instance
once (attach the default Lightsail SSM instance role via the console — a supported, documented Lightsail
feature). Net effect: **zero long-lived secrets in GitHub, zero open SSH port** — matches the
`family-cookbook` app's "no stored AWS keys" ethos even though the underlying transport (SSM vs. Lambda's
native IAM invoke) is different because we're deploying to a stateful VM, not a serverless resource.

**CD7 — CI (build validation): runs on every push/PR, no AWS credentials involved.** A separate, always-on
workflow: `dotnet build` (`/api`), `ng build` (`/web`), plus a migration-order sanity check — spin up a
throwaway `postgres:16` GitHub Actions service container and apply every file in
`Assets/StreamingAssets/Database/Migrations/*.sql` in filename order via a plain `psql -f` loop. This
validates the migrations execute cleanly from empty; it doesn't need to exercise Unity's
`MigrationRunner.cs` bookkeeping (`schema_version` incremental-apply logic), since CI's database is always
starting from empty — exactly the case that logic exists to handle, so a simpler ordered-apply loop proves
the same thing for CI's purposes. This half of the pipeline needs no AWS access and should catch a broken
migration or a build break before it's anywhere near deploy.

**CD8 — Applying schema migrations to the deployed DB stays manual, not automated, in this devplan.**
The `/api` project has no migration-running code of its own (Grounding) — only the Unity Editor does. For
now, applying a new migration to the AWS-hosted Postgres is the same playbook already rehearsed and
verified this session for the 2.11 round-trip test: temporarily point `db.config.json`/env vars at the
target DB, run `Tools/Database/Run Migrations` from the local Editor, then (for a first-time cutover)
`Tools/Database/Import Content...` from a local export to carry over existing content. A portable,
non-Unity migration runner would let CD6 auto-apply migrations as part of every deploy — flagged as a
reasonable future item if the manual step becomes a real friction point, but it's new engineering scope
beyond "stand up CI/CD for what already exists," so it's not built here.

**CD9 — Room reserved for the future Unity dedicated server, not built now.** When 5.10 (headless build
spike) and 6.2 (dedicated server + hosting) land, the game server becomes a fourth process on this same
box: its own systemd unit, its own UDP firewall rule (Mirror/KCP's transport — distinct from the TCP 80/443
Caddy handles). Whether it stays co-located here or splits onto dedicated capacity is explicitly a **6.5**
(load testing) decision made from real data, not decided in this devplan.

**Correction: one real Angular source change was required, found while writing the runbook, not
anticipated at draft time.** All 24 web service files hardcoded `http://localhost:5144/api/...` as an
absolute URL (no `environment.ts` split existed anywhere in this project, `angular.json` had no
`fileReplacements`). Deployed as-is, every browser visiting the site would try to reach `http://
localhost:5144` on *its own machine*, not the server — completely broken, not just a CORS issue. Fixed:
new `web/src/environments/environment.ts` (dev, `apiBase: 'http://localhost:5144'`) /
`environment.production.ts` (prod, `apiBase: ''`), wired into `angular.json`'s production configuration via
`fileReplacements`; all 11 files with a functional hardcoded base URL (`ability.service.ts`,
`ability-tag.service.ts`, `class.service.ts`, `conversation.service.ts`, `item.service.ts`,
`faction.service.ts` [2 URLs], `loot.service.ts`, `mob.service.ts`, `race.service.ts`, `spawn.service.ts`,
`vendor.service.ts`, `xp.service.ts`) now build their base from `` `${environment.apiBase}/api/...` ``. In
production this resolves to a **relative** `/api/...` path, which rides through Caddy's same-origin
reverse proxy for free — sidesteps the API's hardcoded `localhost:4200`-only CORS policy entirely, no API
change needed. The 12 `*-editor.ts` files' dev-only error-hint strings ("is the .NET api project running on
http://localhost:5144?") were deliberately left alone — informational text for a connection-refused
fallback, not a functional URL, low value to make environment-aware. Verified: `ng build --configuration
production` succeeds, and the built bundle was directly inspected (`grep`) to confirm a relative `/api/
items` string is present and zero occurrences of the functional `localhost:5144/api/...` pattern remain.

## Risks / open questions

- **Resolved (2026-07-18):** the original draft assumed Lightsail auto-assigns a public DNS hostname —
  verified against AWS's own docs/CLI reference that it doesn't (only a public IP). Fixed via `sslip.io`
  (CD4); no purchase or account needed, real Let's Encrypt validation.
- **Resolved (2026-07-18):** verified Lightsail's actual SSM integration mechanism against AWS's docs —
  it's **not** an EC2-style IAM instance profile attachment (Lightsail doesn't support that). It's a
  Systems Manager **hybrid activation** (the same mechanism used for on-premises/non-EC2 machines):
  `aws ssm create-activation` returns an activation code + ID, which get passed to the SSM Agent install/
  register command on the instance. Exact commands are in `docs/DEPLOY-AWS.md`. This resolves the
  devplan's original uncertainty flag — the mechanism is now fully specified, not just "documented to
  exist somewhere."
