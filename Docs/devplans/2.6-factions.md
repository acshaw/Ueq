## Goal

Migrate factions to Postgres + a web **Faction Editor**, and populate `FactionRegistry` (today an empty stub) so the **already-wired** faction gates go live:

## What "a faction" is, in data

Three related server-only shapes (all currently ScriptableObjects):

1. **Shared named-threshold table** — the `KOS … Ally` ladder with `MinScore` cutoffs. **One shared table** for all factions (cluster decision DC4; today every faction's `ThresholdTable` already points at the single `DefaultThresholds.asset`).
2. **Factions** — a stable id, a display/score name, and NPC-to-NPC **ally/hostile** relation lists.
3. **Race → faction default scores** — a new character's starting standing per race (seeds `PlayerFactionScores` at character creation; also used as the substituted score under illusion).

### Faithful seed data (mapped from the existing assets)

Thresholds (`DefaultThresholds.asset`): `KOS -10000, Threatening -750, Dubious -500, Apprehensive -100, Indifferent 0, Amiable 100, Kindly 500, Warmly 750, Ally 1100`.

Factions (asset `m_Name` → `FactionName`): `CityGuards → "City Guards"`, `Vermin → "Vermin"`, `QeynosGuards → "Qeynos Guards"`.

Relations: **CityGuards ⇄ Vermin hostile** (mutual). QeynosGuards: none.

Race defaults:
| Faction | Human | Troll | Dwarf |
|---|---|---|---|
| CityGuards | 0 | -5000 | 500 |
| Vermin | -1000 | -10000 | -10000 |

> ✅ **The id-vs-name trap — resolved by re-keying to `faction_id` now (DF2, decided 2026-06-26).** `mobs.faction_id` and `conversation_keywords.required_faction_id` already use the asset **id** (`"CityGuards"`); the inconsistency is that `PlayerFactionScores` keys its score dictionary — and 1.3 persistence stores scores — by **`FactionName`** (`"City Guards"`). Rather than carry both keys forever, **everything moves to `faction_id`**: `FactionDefinition` gains a `FactionId`, score lookups key off it, and the `character_faction_scores.faction_name` column is **renamed to `faction_id`** with existing dev rows migrated in `0013` (`City Guards→CityGuards`, `Qeynos Guards→QeynosGuards`; `Vermin` unchanged). `faction_name` survives only as a display label.

## Schema — `0013_factions.sql` (schema only; seeded idempotently by `DatabaseSeeder`)

```sql
-- The single shared named-threshold ladder (DC4). One row per standing.
CREATE TABLE IF NOT EXISTS faction_thresholds (
    name        TEXT PRIMARY KEY,         -- "Indifferent"
    min_score   INT  NOT NULL,            -- inclusive lower bound
    sort_order  INT  NOT NULL             -- low standing → high standing
);

-- A faction. faction_id = stable key (matches mobs.faction_id / required_faction_id AND the score key).
-- faction_name = display label only (DF2: scores re-keyed to faction_id).
CREATE TABLE IF NOT EXISTS factions (
    faction_id    TEXT PRIMARY KEY,        -- "CityGuards"
    faction_name  TEXT NOT NULL DEFAULT '',-- "City Guards"
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- NPC-to-NPC ally/hostile lists (for social aggro / guards-respond, future 3.4).
CREATE TABLE IF NOT EXISTS faction_relations (
    faction_id        TEXT NOT NULL REFERENCES factions(faction_id) ON DELETE CASCADE,
    other_faction_id  TEXT NOT NULL,       -- not FK'd: tolerate self-ref ordering / soft refs
    relation          TEXT NOT NULL CHECK (relation IN ('ally','hostile')),
    PRIMARY KEY (faction_id, other_faction_id, relation)
);

-- Starting standing a race has with a faction (seeds new characters; illusion substitute).
CREATE TABLE IF NOT EXISTS race_faction_defaults (
    race        TEXT NOT NULL,             -- "Troll"
    faction_id  TEXT NOT NULL REFERENCES factions(faction_id) ON DELETE CASCADE,
    score       INT  NOT NULL,
    PRIMARY KEY (race, faction_id)
);
```

## Unity (server-only)

- **`FactionSnapshot`** (plain DTO) + **`FactionRepository`** — one `LoadAll(conn)` that returns the thresholds, the factions, their relations, and the race defaults (a small bundle struct, since `FactionRegistry` builds them together).
- **`FactionRegistry`** (extend the existing stub) — `LoadFrom(bundle)` builds runtime instances in **three passes** (factions reference each other, so relations are wired after all factions exist):
  1. Build the shared `FactionThresholdTable` via `ScriptableObject.CreateInstance`, thresholds ordered by `sort_order`.
  2. Build each `FactionDefinition` (`CreateInstance`): `FactionName = faction_name`, `ThresholdTable = shared table`, empty relation lists. Index by `faction_id`.
  3. Wire `AlliedFactions`/`HostileFactions` (resolve `other_faction_id` → built instances) and build a runtime `RaceDefaultsTable` whose `Defaults` reference the built `FactionDefinition` instances.
  - Keep `Get(faction_id)` (exists); add `RaceDefaults` (built table) and `Thresholds` (shared table) accessors. Same "build a runtime SO instance per row" trick `MobRegistry`/`ConversationRegistry` already use, so every existing consumer (`NpcFaction`, `PlayerFactionScores`, `MobDefinition.faction`) is unchanged in type.
- **`PlayerFactionScores`** — prefer the DB race defaults: `var rd = FactionRegistry.RaceDefaults ?? raceDefaults;` in both `Initialize` and `GetEffectiveScore`. Keeps the serialized SO as a headless/no-DB fallback (matches the hybrid pattern). **Score keying re-keyed to `FactionDefinition.Key` (= `faction_id`) per DF2** — `_scores`, seeding, and export/load all use it; the `character_faction_scores` column is renamed in `0013`.
- **`MobRegistry.Build`** — no change (already resolves `def.faction = FactionRegistry.Get`). It just needs factions loaded first.
- **`ContentLoader.LoadAll`** — insert the **factions step before the mobs step** (mobs resolve their faction at build time). New order: items → vendors → conversations → **factions** → mobs. Log `[Content] Loaded N faction(s)`.
- **`DatabaseSeeder`** — `SeedFactions(conn)` (idempotent `ON CONFLICT DO NOTHING`), seeding the thresholds + 3 factions + relations + race defaults above. Called from `Seed()`.

## Decisions (recommendations in **bold**)

- **DF1 — Threshold model.** **Keep the single shared table (DC4).** All factions reference one ladder; add per-faction tables only if a faction ever needs a different curve. Schema above reflects this (no `threshold_set_id` on `factions`).
- **DF2 — Score key. ✅ DECIDED 2026-06-26: re-key everything to `faction_id` now** (user: "bite the bullet… I don't want to deal with that later"). `FactionDefinition` gains a `FactionId` (the registry sets it on each built instance; a `Key` property falls back to `FactionName` so blank-id SO assets still work in the headless fallback). `PlayerFactionScores._scores`, race-default seeding, and `ExportScores`/`LoadState` all key off `FactionId`. Persistence: `0013` renames `character_faction_scores.faction_name → faction_id` and migrates the 3 seeded dev values. `faction_name`/`FactionName` is now purely a display label.
- **DF3 — Retire the SO path?** **Retire it to a fallback, don't delete the classes.** `FactionDefinition`/`FactionThresholdTable`/`RaceDefaultsTable` remain the in-memory runtime types (the registry builds instances of them). Stop relying on the `Resources`/serialized assets as the source on the server; keep the serialized refs on `NpcFaction`/`PlayerFactionScores` as a headless/no-DB fallback (the `??` chains already exist).
- **DF4 — Thresholds editable in the web app?** **Yes — editable.** Tuning standing cutoffs is real balance/content work; a read-only seed-only table would force code/DB edits for tuning.
- **DF5 — Wire mob/conversation faction dropdowns now?** **Yes.** Closing the "(2.6)" placeholders in the Mob + Conversation editors is the natural completion of this item and makes the gates authorable end-to-end.

## Risks

- **Id-vs-name mismatch (DF2)** — the headline risk. Runtime `FactionDefinition.FactionName` must equal `faction_name`, and race-default seeding into `_scores` must key by `FactionName`, or player standings silently read as 0/Indifferent. Covered by test 3–4.
- **Load order** — factions **must** precede mobs in `ContentLoader`, or `MobRegistry.Build` resolves `faction = null` and aggro stays off.
- **Two-pass relations** — build all factions before wiring ally/hostile (they reference each other).
- **Persistence continuity** — don't rename existing factions; 1.3 saved scores are keyed by `FactionName`.
