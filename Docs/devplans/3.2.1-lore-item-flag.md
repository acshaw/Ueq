# 3.2.1 — LORE Item Flag (anti-stockpile)

**Status:** ✅ Done — verified in-editor 2026-07-11 (L1–L6 as recommended). See the implementation log at the end. An
item-system feature, not quest-specific: a **LORE** item (EQ1-style) can be possessed **at most once** — any
attempt to acquire a second is refused. The anti-farm lever for the repeatable quests in 3.2 (Q2): a LORE reward
item can't be stockpiled, so 3.2 stays balanced on the item side while inheriting the enforcement for free through
`AddItem`.

## Why
3.2 makes quest turn-ins repeatable (design decision Q2). LORE is how repeatable quests avoid becoming item
farms — you can hand a quest in as often as you can supply the cost, but you can never hold two copies of a LORE
reward. It's a general item property (affects loot, vendor buys, quest rewards, future trades), so it lives in the
item system and every acquire path respects it. Note it limits **item** stockpiling only — repeatable XP/coin is
intentionally farmable, bounded by the turn-in cost (the EQ1 model, per 3.2 Q2).

## Current state (grounding)
- **`ItemDefinition`** (`Inventory/`) — DB-backed (2.2), synced to clients via `ItemCatalogMessage`. Add a
  `lore` flag here + the DB column + the synced field.
- **`PlayerInventory.AddItem(itemId, qty)`** (`Inventory/`) — **the single choke point** every acquire funnels
  through, returns `bool` (false if it couldn't fit). Possession = inventory slots; equipped items live in
  `PlayerEquipment` (`SyncList<string> _slots`, `GetItemId(slot)`).
- **Acquire paths (all call `AddItem`):**
  - **Loot** — `Corpse`/`PlayerCorpse` loot-all + `NetworkedPlayer.CmdTakeLootSlot` use the safe pattern
    `if (inv.AddItem(...)) source.RemoveSlot(...)` — the item only leaves the corpse if it was added. So a
    LORE-aware `AddItem` makes loot self-correct: a dupe just stays on the corpse.
  - **Vendor buy** — `NetworkedPlayer.CmdBuyItem` **charges first** (`SpendCurrency`) then `AddItem`, refunding if
    add fails. Needs a pre-check so a LORE dupe is refused **before** charging (and with the right message).
  - **Quest reward** — 3.2's `KeywordRewardApplicator` grants via `AddItem`; its "reward fits" validation should
    call the same pre-check so a LORE dupe refuses the whole transaction (nothing consumed).
- **⚠️ Internal moves must NOT be LORE-blocked** — `PlayerEquipment.TryUnequip` calls `inv.AddItem(itemId)`
  **while the item is still in the equip slot** (add, *then* clear the slot); `TryEquip` returns the swapped-out
  item + refunds via `AddItem`. If `AddItem` enforced LORE unconditionally it would see the still-equipped copy,
  refuse, and **trap the LORE item on the character forever**. Enforcement therefore must be **opt-in**, off by
  default, so these internal shuffles are untouched.

## Scope
1. **`lore` flag** on `ItemDefinition` + DB `items.lore` column + client sync + Item Editor checkbox.
2. **Possession-aware acquire guard** on `PlayerInventory`: a `CanAcquire(itemId, qty)` pre-check and an opt-in
   `AddItem(itemId, qty, enforceLore)` (default `enforceLore = false`), both refusing a **second** LORE item
   (counting inventory **and** equipped copies).
3. **Wire the three external acquire paths** to enforce: loot (flip the existing `AddItem` calls to `enforceLore:
   true`), vendor buy (pre-check before `SpendCurrency`), quest reward (3.2's validation). Internal equip moves
   stay on the default (no enforcement).
4. **Refusal feedback** — a clear message on a blocked acquire; loot dupe stays on the corpse, buy isn't charged.

**Out of scope:** other item flags (NODROP/MAGIC/etc. — sibling flags to add if needed); player-to-player **trade**
enforcement (no trade system exists yet — note it as a required check when trade lands); bank/shared storage (none
yet).

## Decisions (L1–L6)

**L1 — Enforcement mechanism.** *Recommend:* a `PlayerInventory.CanAcquire(itemId, qty)` pre-check **plus** an
opt-in `AddItem(itemId, qty, bool enforceLore = false)`. External acquires opt in (pre-check where they consume the
source first, e.g. buy; `enforceLore: true` on the `AddItem` call as the backstop); internal equip moves keep the
default. **Default false is deliberate** (per the grounding ⚠️): a forgotten enforcement = a farmable dupe, which is
far less harmful than a forgotten *disable* trapping an item on unequip. *(Alt: enforce inside `AddItem`
unconditionally — rejected, it breaks unequip/swap.)*

**L2 — Possession scope.** *Recommend:* count a LORE item as possessed if it's in **any inventory slot OR any
equipment slot** (`PlayerInventory` consults `PlayerEquipment`). Corpses/vendor stock/loot windows don't count
(not yet the player's). *(Bank/trade are future and out of scope.)*

**L3 — Which acquire paths now.** *Recommend:* **loot, vendor buy, quest reward.** Trade doesn't exist yet — add a
one-line note so whoever builds trade wires the same `CanAcquire` check.

**L4 — LORE + stackable.** *Recommend:* **LORE implies max-one, overriding stack size.** The acquire guard blocks a
second regardless of `maxStackSize`; the Item Editor warns/prevents `lore` + `maxStackSize > 1` (contradictory).

**L5 — Feedback.** *Recommend:* a System/`SendSystemMsg` line on a blocked acquire — e.g. "You can only carry one
{item}." Loot: the dupe stays lootable on the corpse (no consume); buy: refused before charging.

**L6 — Client display.** *Recommend:* **sync the `lore` flag to clients** (it rides the existing
`ItemCatalogMessage`) so the item's data is complete client-side. An actual "LORE" tag in the item tooltip/UI is a
small optional follow-up (the inventory tooltip system is still backlog) — not required for enforcement, which is
fully server-side.

## Design detail — the guard
```
// server-side, PlayerInventory
bool PossessesLore(itemId):  itemId in any inventory slot OR PlayerEquipment holds it
bool CanAcquire(itemId, qty): (item not LORE OR !PossessesLore(itemId)) AND it will fit
AddItem(itemId, qty, enforceLore=false): if (enforceLore && item is LORE && PossessesLore(itemId)) return false; else <existing add>
```
- **Loot:** `if (inv.AddItem(id, q, enforceLore: true)) source.RemoveSlot(...)` — dupe stays on the corpse.
- **Buy:** `if (!inv.CanAcquire(id)) { "You can only carry one …"; return; }` **before** `SpendCurrency`; then
  `AddItem(id, 1, enforceLore: true)`.
- **Quest reward (3.2):** the transaction's pre-validation calls `CanAcquire` for each reward item, so a LORE dupe
  refuses the whole turn-in (consume nothing); grant uses `AddItem(..., enforceLore: true)`.

## Done when
An item flagged LORE can be held at most once across inventory + equipment; loot/vendor/quest-reward acquires of a
second are refused with feedback and no loss; equipping/unequipping/swapping a LORE item is unaffected; the flag is
authorable in the Item Editor and syncs to clients. This is what keeps 3.2's repeatable item-reward quests from
becoming farms.
