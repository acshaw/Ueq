## Why
3.1.4 shipped the gender→race→class create cascade behind a deliberately minimal UI: cycle-buttons and a
full-form teardown (`Rebuild()`) on every click. It works but reads as a prototype, and there's no way to
see the character you're making. 3.1.6 is the convergence point of the 3.1 tracks — it turns the functional
shell (3.1.1–3.1.3) + the identity model (3.1.4–3.1.5) into a real character-creation screen: a **live 3D
preview** of the selected (gender, race, class) body, proper **arrow selectors**, and the **class weapon
props** deferred from 3.1.5 (grip-aligned live in that preview — the reason they waited for this item).

## Scope
1. **Live 3D preview** — a RenderTexture-backed character viewport in the create (and optionally roster) screen
   that shows the exact Synty body for the current selection, idling, slowly turning.
2. **Create-form UX** — replace cycle-buttons with ◀ / ▶ arrow selectors; kill the per-click full-form
   flicker by updating in place instead of tearing the form down.
3. **Class weapon props** (moved from 3.1.5, CS6/CS7) — attach a class weapon to the body's right hand
   (Warrior sword / Wizard staff / Cleric sceptre), grip offsets tuned live in the preview.

Out of scope: deeper appearance customization (faces/hair/armor tiers = modular/Sidekick, roadmap 4.8);
select/create screen art beyond inheriting the existing `MenuUI` rounded styling.

## Current state (grounding)
- `CharacterSelectPanel` (`Assets/Scripts/UI/Screens/`) builds the create form in `BuildCreate()`; every
  gender/race/class change calls `Rebuild()` → `ClearContent()` destroys all rows below the title and
  re-adds them (the flicker; the name field is preserved via `_pendingName` as a workaround). Options come
  from `_list.createOptions` (a `CreateOption[]` synced in `CharacterListMessage`); client-side filters
  `Genders`/`RacesFor`/`ClassesFor` drive the cascade. The server re-validates the tuple on create.
- `CharacterRosterRegistry.GetModel(gender, race, cls)` → the Synty body prefab for a tuple (already used
  by `PlayerModel`). `AllOptions()` feeds the create form.
- `PlayerModel` instantiates that prefab under a `ModelRoot` mount, assigns `locomotionController`, adds
  `PlayerAnimator` — the exact recipe the preview reuses (a body idles at `Speed = 0`).
- `UIScreenManager.BuildMenuCamera()` makes a `cullingMask = 0` menu camera (renders nothing). The preview
  needs its own camera + staging, isolated from both the menu and the (not-yet-loaded) world.
- `ClassDefinition` (`className`, stats, HP/mana) — where per-class weapon-prop data will hang (CS7).
- `Gender` enum; race = `RaceDefinition.raceName`; class = `ClassDefinition.className`.

## Decisions

### Strand 1 — Live 3D preview

**PV1 — Rendering approach — recommend: RenderTexture + dedicated preview camera + `RawImage`.**
A small staging setup (root + one directional light + a camera) renders the selected body to a
`RenderTexture`; a `RawImage` in the create card shows it. This isolates the preview from the ScreenSpace
overlay canvas and needs no scene geometry. The alternative (a world-space character in front of the menu
camera) couples preview framing to the UI layout and fights the overlay canvas — rejected.
*Get right:* create the RT at a sane size (e.g. 512×768, `matchWidthOrHeight` aware), release it on panel
hide, and gate the whole preview when `SystemInfo.supportsRenderTextures` is false (fall back to no preview,
form still works).

**PV2 — Staging location + pose — recommend: offset staging root on a dedicated `CharacterPreview` layer.**
Place the staging root far from world origin (e.g. `(0, -5000, 0)` — clear of any zone) so it never
collides with menu or gameplay objects; put the body + light on a dedicated layer and set the preview
camera's `cullingMask` to only that layer (and every other camera to exclude it). Drive an **idle** pose by
assigning the same `PlayerLocomotion` controller with `Speed = 0` (reuses `PlayerModel`'s wiring; no new
clip). Slow auto-yaw on the staging root; **click-drag to rotate** is a cheap add if it falls out easily,
else defer.

**PV3 — Preview rebuild — recommend: a standalone `CharacterPreview` component, swap body on selection change.**
Factor the body-instantiation recipe out of `PlayerModel` into a shared helper (or a lightweight
`CharacterPreview` MonoBehaviour) so the preview and the in-world model don't drift. On each selection
change, destroy the old body + instantiate `CharacterRosterRegistry.GetModel(...)` under the staging root —
**not** tied to the form's teardown (UX1 removes that). Show the class weapon prop here too once WP lands.

### Strand 2 — Create-form UX

**UX1 — Selector widget — recommend: ◀ / ▶ arrow selectors, built once, updated in place.**
Replace each cycle-button with a `◀ [Value] ▶` row (a label flanked by two arrow buttons). Restructure
`CharacterSelectPanel` so the create form's widgets (name field, 3 selector rows, Create/Back buttons,
error text) are **built once** in `OnShow`/`BuildCreate`; changing a selection mutates label text +
dependent selector ranges + the preview, with **no `ClearContent()`**. This removes the flicker and makes
the `_pendingName` workaround unnecessary (the name field is never destroyed). Keyboard nav (arrows +
Enter, matching the existing Tab/Enter/Esc shell) is a natural add. Roster ↔ create switching can still
rebuild (it's a screen change, not per-interaction).

**UX2 — Layout — recommend: two-column card — preview left, selectors + name + Create right.**
Preview viewport on one side, the selector stack + name + Create/Back on the other. Inherit the `MenuUI`
rounded button/field styling from 3.1.3. Keep the persistent "Character Select" heading.

**UX3 — Roster preview — recommend: optional, do it if cheap.**
Ideally selecting an existing character in the roster also previews its body (the preview machinery is
already there). Nice-to-have; ship create-form preview first, add roster preview only if it's a small
delta.

### Strand 3 — Class weapon props (from 3.1.5 CS6/CS7)

**WP1 — Prop data location — recommend: on `ClassDefinition` (`weaponPropPrefab` + grip offset).**
Add `GameObject weaponPropPrefab`, `Vector3 gripPositionOffset`, `Vector3 gripEulerOffset` to
`ClassDefinition` (class name is already synced; the class drives the weapon). Resolve at model-build time
via `RaceClassRegistry` (class lookup by name). Attach in the shared body helper by parenting the prop to
`Animator.GetBoneTransform(HumanBodyBones.RightHand)` (rig-independent across all Humanoid packs) and
applying the grip offset. Props: Warrior `SM_Wep_Sword_01`, Wizard `SM_Prop_WizardStaff_01`, Cleric
`SM_Prop_Sceptre_01` (no mace in any owned pack).

**WP2 — Don't double up — recommend: verify the Synty bodies ship no held weapon first (in-editor check).**
Some Synty premades already hold a weapon. Before wiring props, eyeball each roster body in the preview; if
one already carries a weapon, either leave its `weaponPropPrefab` empty or strip the built-in mesh. This is
a quick visual check the preview makes trivial.

**WP3 — Grip authoring — recommend: serialized offsets tuned by eye in the preview.**
The live preview is exactly where hand alignment is easy — expose the grip offsets on `ClassDefinition` and
adjust until the grip looks right. No custom tooling unless it proves fiddly.
