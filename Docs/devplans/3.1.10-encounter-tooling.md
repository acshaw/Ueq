# 3.1.10 — Encounter Tooling + Starter-Zone Population

**Status:** ✅ Done — verified in-editor 2026-07-11 (all stages: mob-body catalog, patrol runtime, placement
tooling, starter content). Extended the 3.1 onboarding vertical: the starter zone was shaped + dressed (3.1.9) but
**empty of life**. This added the missing runtime piece (waypoint patrol) + in-scene placement tooling, then
populated Creslin's Field with basic encounters. (A Host-only placeholder-cube bug was found + fixed during verify.)

## Why
A new player entering a beautifully-dressed but lifeless field is poor onboarding. Most of what a "living zone"
needs is **already built** (see grounding) — the only true gaps are **waypoint patrol** (guards on the road)
and **ergonomic in-scene placement**. Build those two, then author the content.

## Scope
0. **Mob body pipeline** — decouple a mob's *art* from its networked prefab so adding a mob body is "drop a Synty
   prefab in a folder + name it," not "build a whole new networked Mirror prefab." Mirrors `PlayerModel`:
   `MobModel` (client) instantiates a plain body prefab from `Resources/MobModels/<modelId>` under a `ModelRoot`;
   `modelId` rides a `SyncVar` set server-side from the `MobDefinition`. **This unblocks Stage 3.**
1. **Patrol runtime** — `PatrolBehavior` (an `INpcMovementBehavior`) so an NPC walks an ordered route instead of
   random-wandering; interrupts for combat and resumes its beat on return. **No `EnemyAI` changes.**
2. **Placement tooling** — `Tools/Zones/Place Encounter` (drop a configured `SpawnPoint`) + a `PatrolRoute`
   authoring flow (drag-in prefab + "Add Waypoint", gizmo labels + connecting lines, snap-to-navmesh), matching
   the existing `ZonePortal`/`ZoneWaypoint` + `ZoneMarkerGizmos` pattern.
3. **Population (content)** — author **3 wilderness mob types** (web Mob Editor + Spawn Editor), place **static +
   weighted-random** spawns, and **one road guard patrol** in Creslin's Field.

**Out of scope:** roaming/ambient area spawners (user confirmed "random encounter" = weighted mob *type* at a
fixed point, which `SpawnTable` already does); real threat/social aggro (that's **3.4**); populating the *other*
zones (**3.6**).

## Current state (grounding — most of this already exists)
- **Spawn system (DB-backed):** `SpawnPoint` (Combat/) — proximity activation (`activationRadius`), group
  spawning, per-mob respawn on last-member death, ground+navmesh snap. Precedence: `spawnTableId` (weighted
  `SpawnTable` + group size + `SpawnTimer`) → `mobId` (single named mob). Placed as plain scene GameObjects.
- **Mob AI:** `EnemyAI` (Idle → Chase → Combat → Return; server-authoritative NavMeshAgent + mob NetworkTransform
  syncs to clients). Movement is delegated through `INpcMovementBehavior { Startup/Suspend/Resume }`, resolved via
  `GetComponent<INpcMovementBehavior>()` in `Awake` **and re-read in `OnStartServer`** (after `SetDefinition`).
  `WanderBehavior` is the only implementation today. **`EnemyAI` never names Wander — it calls the interface,** so
  a `PatrolBehavior` sibling is a drop-in with zero AI edits. On combat: `Suspend()`; on return-to-spawn:
  `Resume()`. Leash anchor = `_spawnPoint` (mob's spawn position).
- **Content authoring:** DB `MobDefinition` via web Mob Editor (loot/XP/faction-hits), `SpawnTable`/`SpawnTimer`
  via web Spawn Editor. A **City Guard** mob + **Giant Rat** are already seeded; Fantasy Rivals pack is a mob
  goldmine (Troll/Ork/golems/etc.) for wilderness models.
- **Aggro:** faction-driven (`NpcFaction.OnPerceived` → KOS/Threatening → `AddThreat` → Chase) already works, so
  hostile wilderness mobs function **today**. 3.4 only deepens it (threat tables, social aggro, decay).
- **Marker tooling pattern to mirror:** `ZoneEntry`/`ZonePortal` = plain MonoBehaviours drawing `OnDrawGizmos`;
  `ZoneMarkerGizmos` uses `[DrawGizmo]` + `Handles.Label` for scene-view text; drag-in prefabs in
  `Assets/Prefabs/Zones/`; `TrailBuilder`/path tools already use an ordered **child-empty waypoint** convention.

## Decisions (recommendations to confirm)

**E1 — How a spawned mob becomes a patroller.**
→ **Recommend:** add an optional `PatrolRoute patrolRoute` field to `SpawnPoint`. When set, after `Instantiate`
and before `NetworkServer.Spawn`, the spawn path **swaps** the mob's `WanderBehavior` for a `PatrolBehavior`
seeded with the route (see E3). Null = wander, exactly as today. Reuses all existing spawn/respawn/group logic and
keeps the single shared Enemy prefab (matches the "one prefab, differ by data" philosophy). `OnStartServer`'s
interface re-read then picks up `PatrolBehavior`.
*Alt:* a separate guard prefab variant (more prefabs to maintain; rejected).

**E2 — Route data model.**
→ **Recommend:** `PatrolRoute` scene MonoBehaviour whose **ordered child transforms** are the waypoints (same
convention as the existing trail/path tools, so authors already know it). Fields: `loop` (loop vs ping-pong) and
a default `pausePerPoint`; optional per-waypoint pause via a tiny `PatrolWaypoint` marker. Exposes `Vector3[]
Points` (child positions) for injection.

**E3 — How the route reaches the mob at runtime.**
→ **Recommend:** the route is a **scene object**, so it can't be a serialized ref on a network prefab. The
`SpawnPoint` (which holds the `PatrolRoute` ref, E1) injects `route.Points` into the spawned `PatrolBehavior` via
a `SetRoute(points)` call before spawn — the same "configure-before-Spawn" seam as `MobApplicator.SetDefinition`.

**E4 — Placement tooling shape.**
→ **Recommend two menu items + gizmos:**
- `Tools/Zones/Place Encounter` — instantiates a `SpawnPoint` prefab at the scene-view focus (or spawn), selects
  it for immediate inspector edit (`spawnTableId`/`mobId`, `activationRadius`). `SpawnPoint` already draws its
  activation-radius gizmo; add a `[DrawGizmo]` `Handles.Label` showing its `spawnTableId`/`mobId` (mirror
  `ZoneMarkerGizmos`).
- `PatrolRoute` drag-in prefab + `Tools/Zones/Add Patrol Waypoint` — appends a child waypoint at the scene pivot,
  **snapped to the navmesh** (`NavMesh.SamplePosition`); gizmos draw the ordered polyline + `⚑ n` labels (+ a
  loop-closing segment when `loop`).

**E5 — Patroller return-from-combat behavior.**
→ **Recommend:** `EnemyAI` already returns to `_spawnPoint` then `Resume()`s. `PatrolBehavior.Resume()`
re-acquires the **nearest** waypoint and continues the loop (a guard that fought walks back onto its beat rather
than snapping). Spawn stays the leash anchor — no change to leash/return.

**E6 — Group patrols.**
→ **Recommend MVP:** individual patrollers. A `SpawnTable` with `groupSize > 1` on a route = each member walks
the same route (existing XZ jitter offsets them). Formation/escort behavior deferred.

**E7 — Content scope for Creslin's Field.**
→ **Recommend:** 3 wilderness mobs authored via the **existing web tools** (Mob Editor + Spawn Editor; models from
Fantasy Rivals) — e.g. a weak melee, a ranged/caster, a tougher "named". Place: a few **static** single-mob posts
+ one or two **weighted `SpawnTable`** points (the "random encounter") along the interior; **one road guard
patrol** reusing the seeded **City Guard** on a `PatrolRoute` down the south road. Actual DB authoring is
user-side in-editor; this plan delivers the code + tools + a seed/wire pass.

**E8 — Mob body resolution model.**
→ **Recommend:** keep the **single shared networked `Enemy` prefab** and attach the visual at runtime, mirroring
`PlayerModel`. New `MobModel` (client MonoBehaviour): reads a synced `modelId`, `Resources.Load<GameObject>(
"MobModels/" + modelId)`, instantiates it under an auto-created `ModelRoot`, wires an animator. Body prefabs are
**pure art** — no `NetworkIdentity`, no `spawnPrefabs` registration, no per-mob networked prefab. Adding a mob
body = drop a Synty prefab in `Assets/Resources/MobModels/`. Generalize `CharacterModelFactory` with a
`BuildFromPrefab(mount, prefab, controller, driveLocomotion)` path so player + mob share the instantiate/animator
wiring (can't drift). `MobDefinition.prefab`/`prefab_address` stays only for genuinely distinct *networked*
archetypes (if any ever need different net components) — not for art.

**E9 — How `modelId` reaches the client.**
→ **Recommend:** `MobDefinition` is server-only, so add a `[SyncVar] string _modelId` on the Enemy (owned by
`MobModel` or alongside `Nameplate`, which already syncs the label this way). Server sets it in `OnStartServer`
from `MobApplicator.Definition.modelId`; the client `MobModel` polls the SyncVar (as `PlayerModel` polls its
identity) and (re)builds when it resolves. **Convention default:** blank `modelId` → fall back to the mob id, so
naming the art prefab to match the mob id needs no explicit field; an explicit `modelId` lets many mobs share one
body (e.g. 5 rat variants → one `giant_rat` model).

**E10 — Authoring: folder convention + web dropdown.**
→ **Recommend both, staged:** add a `model_id` column + Mob Editor field (migration). Ship the **folder
convention** first (`Resources/MobModels/`, resolved by name) — the big ergonomic win, usable immediately. Then a
`Tools/Content/Refresh Mob Model Catalog` scans the folder and publishes the model-name list to the API so the
Mob Editor's Model field becomes a **dropdown** (the web tool can't read Unity's asset folders directly — the
catalog endpoint is the bridge). Result: drop art in the folder → pick it from a dropdown (or name-match).

## Build stages (each verifiable independently)

   `BuildFromPrefab`, migration for `model_id` + Mob Editor field, and the catalog-refresh tool + dropdown (E10).
   Migrate the seeded **Giant Rat**/**City Guard** to a `modelId`. *Commit-able alone.* Verify: change a mob's

   aggros/fights → kills or leashes → returns to spawn → **resumes the beat**; confirmed on a remote MPPM client
   (mob NetworkTransform already syncs).
2. **Placement tooling** — `Tools/Zones/Place Encounter`, `PatrolRoute` prefab + `Add Patrol Waypoint`, gizmo

3. **Population** — author 3 wilderness mobs + tables, place static + weighted spawns + the road patrol, rebake
   navmesh, SAVE + commit. Verify: walk the zone → encounter each mob type, the weighted point rolls different
   types across respawns, the guard patrols the road, all synced on a second client.

## Implementation log

### Stage 0 — Increment A (mob body pipeline, convention-based) — code done, pending in-editor verify (2026-07-09)
Delivered the runtime + folder convention with **zero DB/API/Angular changes** (usable immediately; the explicit
`model_id` column + web dropdown are Increment B). Files:
- **`CharacterModelFactory.cs`** — factored out `public static GameObject BuildFromPrefab(parent, prefab,
  controller, driveLocomotion)` (instantiate + Animator wiring, no roster/class coupling); `Build` (player path)
  now calls it then attaches the class weapon prop. **No player behavior change.**
- **`Combat/MobModel.cs`** (new, `NetworkBehaviour`) — mirrors `PlayerModel`: `[SyncVar] _modelId` set in
  `OnStartServer` from `MobApplicator.Definition` (explicit `modelId`, else the mob id by convention), client
  builds the body in `OnStartClient`/hook via `Resources.Load("MobModels/"+id)` under an auto `ModelRoot`, wires
  the shared locomotion controller. Hides the placeholder cube's `MeshRenderer` on success (collider kept for
  targeting); a missing model leaves the cube + warns (visible "missing art" marker).
- **`Combat/MobDefinition.cs`** — added `string modelId` (blank = convention); reworded `prefab` (now only for
  distinct *networked* archetypes, not art).
- **`Editor/SceneSetup.cs`** — `MobModel` added to `CreateEnemy` + `PatchEnemyPrefab` component lists; new
  `WireMobModel(root)` assigns `Assets/Animations/PlayerLocomotion.controller` (Synty mob bodies are Humanoid →
  retarget it) in both paths.
- **`Assets/Resources/MobModels/README.md`** (new folder) — drop-zone for body prefabs + convention docs.

**Verify (user, in editor):** recompile → `Tools/Patch Enemy Prefab` → re-save `Assets/Prefabs/Enemy.prefab`
(gains `MobModel` + wired controller) → drop a Synty body prefab named exactly like a mob id (e.g. `Giant
Rat.prefab`) into `Assets/Resources/MobModels/` → spawn that mob → the Synty body shows (placeholder cube hidden)

## Risks / notes

  the 3.0.1 persisted-navmesh fix applies).
