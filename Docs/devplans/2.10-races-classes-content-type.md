# 2.10 — Races & Classes (DB-backed content type)

Status: ✅ Done — verified in-editor 2026-07-18 (RC1–RC10 all as recommended)

## Goal

Migrate `RaceDefinition` / `ClassDefinition` (currently ScriptableObject assets under
`Resources/Races/` + `Resources/Classes/`) to Postgres + a web **Race Editor** and **Class Editor**,
built on 2.1.1's `ContentGrid`/`CrudModal`. Copies the 2.9 shape (client sync required, header table stays
a runtime `ScriptableObject` built via `CreateInstance` from a DB snapshot) more closely than the 2.3–2.7
server-only cluster, since races/classes are read on the client too (see RC1).

## Grounding (read before designing)

- `RaceDefinition` (SO): `raceName`, `xpModifier`, 7 flat stat modifiers (str/sta/agi/dex/int/wis/cha).
  Flat, tiny — same shape as `ability_tags`.
- `ClassDefinition` (SO): `className`, `xpModifier`, 7 base stats, 5 HP-formula fields, 6 mana-formula
  fields (incl. `ManaStatType` enum), 2 `CombatTierTable` structs (7 floats each — Level 1 and Level 20,
  `CombatResolver` interpolates between them by character level, 5.1.1), `startingAbilities`
  (`List<string>` ability ids since 2.9's AB8), and a **weapon-prop cosmetic** block (`weaponPropPrefab`
  GameObject + `gripPositionOffset`/`gripEulerOffset` Vector3s, 3.1.6) — the one genuine asset reference
  left on the class. Read the current live data in all 5 asset files before drafting this — see the exact
  values transcribed under **Seed data** below (Warrior's base stats are all 75, notably different from
  Wizard/Cleric's ~10 baseline + one bumped stat — preserved verbatim, not a typo to "fix" here).
- **`RaceClassRegistry` is read on the client, not just the server** — confirmed by grep, not assumed:
  `CharacterModelFactory.cs` and `CharacterPreview.cs` (both client-side — the 3.1.6 create-form preview
  and in-world weapon-prop attachment) call `RaceClassRegistry.GetClass(cls)`. This puts 2.10 in the same
  bucket as 2.2 (items) and 2.9 (abilities) — needs `ContentCatalog` client sync — not the server-only
  bucket (2.3–2.7). Server-side readers: `CharacterPersistence.cs`, `CharacterSelectController.cs`.
- `RaceClassRegistry.GetRace`/`GetClass` lazily load from `Resources/Races`/`Resources/Classes`; swapping
  the backing store is meant to be transparent to callers (its own doc comment says so).
- **Persistence needs no schema change** — `CharacterSnapshot.RaceName`/`ClassName` are already plain
  strings (confirmed in `CharacterSnapshot.cs`); `RaceClassRegistry`'s backing-store swap is invisible to
  the save/load path.
- `CharacterRoster` (SO, 3.1.4 RM1) is a **separate** asset — one authored (gender, race, class) → Synty
  body-prefab lineup, used for character-creation validation + client body resolution
  (`CharacterRosterRegistry`). Its own doc comment: *"Lives at Resources/CharacterRoster.asset... M2.10
  can move the backing store to the DB"* — permissive, not mandated (see RC5).
- `MobModelCatalog`/`MobModelRegistry` (3.1.10) is the established precedent for "a DB row needs to
  reference a Unity prefab that lives in-place inside a gitignored Synty pack folder (not under
  `Resources/`)": a hand-maintained Unity SO holding direct prefab references keyed by a plain string id,
  which itself is never DB-migrated — only the string id is DB-authored (on `MobDefinition.modelId`,
  itself still a runtime `ScriptableObject`, not a DB row directly). The same shape fits `weaponPropPrefab`
  (RC4).
- Three now-obsolete one-time editor authoring tools write directly to `RaceDefinition`/`ClassDefinition`
  SO assets and will not compile/make sense once those types stop being asset-authored: `CombatTierSetup.cs`
  (`Tools/Combat/Seed Class Combat Tables` — writes the two `CombatTierTable`s), and
  `CharacterRosterSetup.cs`'s `EnsureRace`/`EnsureClass` helpers (its roster-building half stays, per RC5).
  Both were themselves the origin of the current live data, useful for confirming the numbers are correct.
- `RaceClassEditorWindow.cs`'s "XP Table" tab is **already stale** — 2.7 migrated the real XP curve to the
  DB with its own web `xp-editor.ts`; this tab still points at the pre-2.7 `Resources/XpTable.asset`,
  which `PlayerExperience.SetTable` no longer reads. Retiring this whole window (RC9) loses nothing live.

## Decisions

**RC1 — Client sync (confirmed necessary, not a judgment call).** New
`ContentCatalog.RaceCatalogMessage`/`ClassCatalogMessage` (or one combined message — recommend two,
matching one-message-per-type precedent) + `RaceRegistry`/`ClassRegistry` gain `LoadFrom`, wired into
`GameNetworkManager` alongside items/abilities. `RaceDefinition`/`ClassDefinition` **stay
`ScriptableObject`s**, built via `CreateInstance` from a DB snapshot — the same AB1 simplification 2.9
landed on (mirrors `ItemRegistry`/`AbilityRegistry`), so `CharacterModelFactory`/`CharacterPreview`/
`CharacterPersistence`/`CharacterSelectController` need zero changes to their read surface.

**RC2 — Header table shape.** `races` (flat, 9 columns) and `classes` (flat, ~30 columns: identity/xp/7
base stats/5 HP fields/6 mana fields/14 combat-tier floats) + one child table
`class_starting_abilities(class_id, ability_id, sort_order)` FK'd to `abilities.ability_id` (2.9 already
exists, so this is a real, enforced reference — classes must load after abilities, already the natural
order). Mirrors `Mob`'s already-large flat table as precedent for a wide single-entity row.

**RC3 — Combat tier columns.** 14 flat float columns (`tier_l1_miss` … `tier_l1_crippling`,
`tier_l20_miss` … `tier_l20_crippling`) — same naming shape as `mobs.tier_*` (5.1.1), just doubled for the
two levels the class table interpolates between.

**RC4 — Weapon prop moves off `ClassDefinition` onto `CharacterRoster` (recommend).** `weaponPropPrefab` /
`gripPositionOffset` / `gripEulerOffset` are pure Unity-asset wiring (a GameObject reference + tuning
vectors) with no numeric/text "content" value a web form adds — and they'd otherwise be the *only* asset
reference left on an entity that's meant to become clean DB rows. Recommend: add a small
`List<ClassWeaponProp> classWeaponProps` to the already-Unity-asset `CharacterRoster` (RC5), keyed by
`className` (string), carrying the same 3 fields. `CharacterModelFactory`/`CharacterPreview` swap their
one call site from `RaceClassRegistry.GetClass(cls).weaponPropPrefab` to
`CharacterRosterRegistry.GetWeaponProp(cls)`. **Alternative if you'd rather keep it simple:** leave
`weaponPropPrefab` as a `GameObject` field that just doesn't get DB-synced (client-only, resolved locally
same as today, unset on the server-built instance) — smaller diff, but leaves one dangling asset-authored
field on an otherwise-fully-migrated type. Flagging as a real choice, not a forced one.

**RC5 — `CharacterRoster` stays a Unity asset, not migrated to the DB.** It's prefab-wiring (which Synty
body goes with which tuple), not text/numeric content — mirrors the `MobModelCatalog` precedent, which
also never moved to DB despite mobs being fully DB-migrated. `CharacterRosterSetup.cs`'s roster-building
half is kept (just drops its `EnsureRace`/`EnsureClass` calls, since races/classes now come from the DB
seed, not from this tool creating placeholder assets).

**RC6 — Retire per the standing principle.** Delete `RaceClassEditorWindow.cs` (superseded by the web
editors; its XP Table tab was already dead per Grounding), `CombatTierSetup.cs` (its job becomes DB
seeding), and `CharacterRosterSetup.cs`'s `EnsureRace`/`EnsureClass` methods (keep `Build`/`Entry`/
weapon-prop wiring if RC4 is accepted). Delete the 5 now-orphaned SO assets (`Human.asset`, `Dwarf.asset`,
`Warrior.asset`, `Wizard.asset`, `Cleric.asset`) once their exact data is seeded into the DB.

**RC7 — Seed data (faithfully migrated, exact current values — see below).** `DatabaseSeeder.SeedRaces`
+ `SeedClasses`, following the 2.9 `SeedAbilities` idempotent-header-then-children shape. Must run **after**
`SeedAbilities` (child FK to `abilities`).

**RC8 — Web editor shape.** **Race Editor**: flat `ContentGrid`/`CrudModal`, Identity + XP + Stat
Modifiers sections (9 fields, no children) — closest precedent is the Ability Tag Editor's simplicity.
**Class Editor**: a bigger form mirroring the legacy window's own section order (Identity → XP → Base
Stats → HP Formula → Mana Formula → Combat Tier Table [two mini-grids, Level 1 / Level 20] → Starting
Abilities [ordered ability-id dropdown rows, same row/add/remove pattern as the Ability Editor's cooldown
links]). If RC4 is accepted, weapon-prop fields do **not** appear here (they move to a small addition on
whatever authors `CharacterRoster` — still Unity-side, no web UI for it, matching precedent that prefab
wiring stays in-editor).

**RC9 — `PlayerAbilities`/character-creation regression risk.** `SetRaceClass` already reads
`cls.startingAbilities` as `List<string>` (post-2.9 AB8) — no change needed here. Character creation
(`CharacterSelectController`) resolves race/class by name string via `RaceClassRegistry` — no change
needed beyond the registry's backing-store swap.

**RC10 — No persistence/schema migration for characters.** Confirmed via Grounding — `RaceName`/
`ClassName` are already plain strings on `character` rows. Nothing to touch there.

## Schema (migration `0024_races_classes.sql`)

```sql
CREATE TABLE races (
  race_id      TEXT PRIMARY KEY,   -- = race_name (matches the current SO convention, RaceDefinition has no separate id)
  race_name    TEXT NOT NULL,
  xp_modifier  REAL NOT NULL DEFAULT 1,
  str_mod INT NOT NULL DEFAULT 0, sta_mod INT NOT NULL DEFAULT 0, agi_mod INT NOT NULL DEFAULT 0,
  dex_mod INT NOT NULL DEFAULT 0, int_mod INT NOT NULL DEFAULT 0, wis_mod INT NOT NULL DEFAULT 0,
  cha_mod INT NOT NULL DEFAULT 0
);

CREATE TABLE classes (
  class_id        TEXT PRIMARY KEY,  -- = class_name
  class_name      TEXT NOT NULL,
  xp_modifier     REAL NOT NULL DEFAULT 1,
  base_str INT NOT NULL DEFAULT 10, base_sta INT NOT NULL DEFAULT 10, base_agi INT NOT NULL DEFAULT 10,
  base_dex INT NOT NULL DEFAULT 10, base_int INT NOT NULL DEFAULT 10, base_wis INT NOT NULL DEFAULT 10,
  base_cha INT NOT NULL DEFAULT 10,
  class_base_hp INT NOT NULL DEFAULT 15, hp_per_level INT NOT NULL DEFAULT 4,
  sta_cap INT NOT NULL DEFAULT 255, base_sta_ratio REAL NOT NULL DEFAULT 0.23, sta_growth_rate REAL NOT NULL DEFAULT 0.15,
  mana_stat_type INT NOT NULL DEFAULT 0,
  class_base_mana INT NOT NULL DEFAULT 0, mana_per_level INT NOT NULL DEFAULT 0, mana_cap INT NOT NULL DEFAULT 0,
  base_mana_ratio REAL NOT NULL DEFAULT 0.23, mana_growth_rate REAL NOT NULL DEFAULT 0,
  tier_l1_miss REAL NOT NULL DEFAULT 17.5, tier_l1_glancing REAL NOT NULL DEFAULT 40, tier_l1_hit REAL NOT NULL DEFAULT 30,
  tier_l1_solid REAL NOT NULL DEFAULT 10, tier_l1_good REAL NOT NULL DEFAULT 2.5,
  tier_l1_critical REAL NOT NULL DEFAULT 0, tier_l1_crippling REAL NOT NULL DEFAULT 0,
  tier_l20_miss REAL NOT NULL DEFAULT 2, tier_l20_glancing REAL NOT NULL DEFAULT 13, tier_l20_hit REAL NOT NULL DEFAULT 20,
  tier_l20_solid REAL NOT NULL DEFAULT 35, tier_l20_good REAL NOT NULL DEFAULT 25,
  tier_l20_critical REAL NOT NULL DEFAULT 3, tier_l20_crippling REAL NOT NULL DEFAULT 2
);

CREATE TABLE class_starting_abilities (
  id         SERIAL PRIMARY KEY,
  class_id   TEXT NOT NULL REFERENCES classes(class_id) ON DELETE CASCADE,
  ability_id TEXT NOT NULL REFERENCES abilities(ability_id),
  sort_order INT  NOT NULL DEFAULT 0
);
```

*(If RC4 is accepted, `weaponPropPrefab`/grip offsets never enter the DB at all — they stay Unity-side on
`CharacterRoster`, no schema for them here.)*

## Implementation log (2026-07-18)

Implemented essentially as designed — RC1–RC10 all landed as recommended, with one architectural
simplification found while implementing RC1: **no separate `RaceRegistry`/`ClassRegistry`
`MonoBehaviour` classes were created.** The devplan's Unity-changes section proposed mirroring
`AbilityRegistry`'s scene-singleton (`.Instance`) shape, but `RaceClassRegistry` was already a plain
**static** class with its own lazy-load cache (`_races`/`_classes` dictionaries + `EnsureLoaded()`) —
there was no scene GameObject to begin with, and introducing one would have meant also wiring a new
`SceneSetup.CreateRaceRegistry`/`CreateClassRegistry` step for no functional benefit. Instead,
`RaceClassRegistry` itself gained `LoadRaces`/`LoadClasses` (push-based, replacing the old lazy
`Resources.LoadAll` pull) and two small private `BuildRace`/`BuildClass` methods (the same
`CreateInstance`-from-snapshot pattern as `AbilityRegistry.Build`). `ContentCatalog.ApplyRaces`/
`ApplyClasses` call these directly — no `.Instance == null` guard needed since the class is static and
always "available." This also meant the old `RaceClassRegistry.Invalidate()` method (used only by the
pre-DB `CharacterRosterSetup.cs` to force a Resources reload) had no equivalent need in the push model
and was dropped; its one call site was removed along with the code it used to invalidate.

**RC4 (weapon prop → `CharacterRoster`) executed with one extra finding beyond the devplan's grounding:**
`CharacterPreview.cs` doesn't just attach the weapon prop via `CharacterModelFactory` — it **also**
directly reads `ClassDefinition.gripPositionOffset`/`gripEulerOffset` every `Update()` frame, specifically
so a developer can live-tune the grip alignment by editing the Inspector value while watching the running
preview (a real, intentional workflow feature from 3.1.6, not incidental). Preserved it: `CharacterPreview`
now re-queries `CharacterRosterRegistry.GetWeaponProp(_cls)` fresh each frame instead of caching a
`ClassDefinition` reference at `Show()` time — since `ClassWeaponProp` is a struct read live off the
still-Unity-asset `CharacterRoster`, editing its Inspector value during Play still reflects immediately,
exactly as before. Also proactively hand-edited `Resources/CharacterRoster.asset`'s YAML to populate the
brand-new `classWeaponProps` list with the exact 3 prefab guids that were previously on
`Warrior`/`Wizard`/`Cleric.asset` (all grip offsets zero, matching current live data) — a purely additive
field, so no data-loss risk existed here the way it did for 2.9's `startingAbilities` type change, but
doing it now means the weapon props don't silently vanish until someone remembers to re-run `Tools/
Character/Build Character Roster`.

`CharacterRosterSetup.cs` was trimmed rather than deleted (RC6) — its `EnsureRace`/`EnsureClass` methods
(which used to stamp placeholder `RaceDefinition`/`ClassDefinition` SO assets) are gone, but its
roster-building role continues, now also wiring `classWeaponProps` via a new `MergeWeaponProps` helper
that preserves any hand-tuned grip offsets already present on the roster rather than clobbering them on
re-run (mirrors the pre-existing "don't clobber a hand-tuned setup" guard the old `ClassContentSetup.cs`
had for the single-prefab-field version).

**Build verification**: `dotnet build` (API, built to a scratch output dir since the live API was running
and had the binary locked) — 0 errors, 0 warnings. `ng build --configuration production` (web) — clean.
A repo-wide grep confirmed zero dangling references to the retired `weaponPropPrefab`/
`RaceClassEditorWindow`/`CombatTierSetup`/`RaceClassRegistry.Invalidate`. **Could not compile-check the
Unity side directly** (project open in the user's own Editor, as with 2.9) — did a careful manual
brace-balance + read-through pass on every touched file instead.

**In-editor verification (2026-07-18): ✅ passed.** One transient snag, not a code bug: the user hit a
404 on `GET /api/classes` while smoke-testing — the live API process was still running the pre-2.10
build (only the scratch-dir build above had picked up `ClassesController`/`RacesController`); restarting
the API resolved it immediately. User confirmed "everything works" after that. **2.10 closed.**
