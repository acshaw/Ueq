# 8.1 — World Clock: full calendar system (Age / Year / Month / Week / Day)

**Status:** 🟡 Awaiting review — implementation-reviewed 2026-09-20 (see the addendum near the end).
**Roadmap item:** M8 → **8.1**, restructured 2026-09-20 into an umbrella over **8.1.1–8.1.6** (same
pattern as 3.1's sub-items) — the original single-item scope (day/night + lunar-phase spawn gating) is now
just 8.1.4, one consumer of a much bigger foundational piece. The original standalone devplan for that scope
(`8.1-time-gated-spawns.md`, TG1-TG4) was folded into 8.1.4 below and deleted — nothing was checked in yet,
so there was no reason to keep two files for one roadmap sub-item.
**Pattern:** extends `WorldClock` (5.12) from a cosmetic, session-relative day/night+lunar cycle into a
persistent, server-authoritative calendar (Age → Year → Month → Week → Day), reusing its existing
sync-once-from-`NetworkTime` architecture rather than replacing it.

---

## Goal & why now

The game is deliberately built around **ages/cycles** as a narrative structure. The user wants a full
calendar exposed by `WorldClock`: day-of-week, week-of-year, month-of-year, year, and **age** (all servers
start on the 1st Age). The stated math, chosen so units divide evenly:

- **Week = 7 days**
- **Month = 4 weeks = 28 days** — deliberately equal to the lunar cycle
- **Year = 13 months = 52 weeks = 364 days**
- **Age** — an even larger unit above Year; count starts at 1 for every server.

## Real gap found while grounding — this drives the whole restructure

Read `WorldClock.cs`, `GameNetworkManager.cs`, and the `world_clock_settings` migration/repository directly
before designing anything. Two concrete findings:

**(1) `WorldClock` has no persistence across server restarts.** `ServerInitialize()` unconditionally sets
`_startNetworkTime = NetworkTime.time` on every boot — the clock's phase reference resets to zero every
single server start. This is invisible today: day/night is cosmetic, nobody tracks "which specific day is
it," so a fresh cycle every boot looks the same as a continuous one. **It is not survivable for a
calendar/age system** — without a fix, every server restart (routine deploys, crashes, dev iteration)
would silently reset the world to Age 1 / Year 1 / Day 1, which defeats the entire point of a persistent
age-based calendar. This has to be fixed first (8.1.1); everything else in this plan depends on it.

**(2) The DB's current lunar cycle default doesn't match the stated 28-day premise.** `0028_world_clock_settings.sql`
sets `lunar_cycle_days REAL NOT NULL DEFAULT 8` (an 8-day cycle, from 5.12 — no documented reason, just the
original default), not 28. This needs to change as part of this work — a **value change, not an
architecture change**, but flagging it explicitly since "since we have a 28-day lunar cycle" is the load-
bearing premise behind the whole month-length choice, and the live config currently says otherwise.
**Recommend:** set it to 28. A nice side effect once 8.1.1's unified epoch lands: a 28-day lunar cycle
anchored to the same epoch as the calendar day-count means the moon phase and day-of-month stay in sync
with zero extra bookkeeping **within a given age** — day 14 of the month is a full moon, because both are
the same modulo-28 computation against the same start point. **Caveat found during implementation review
(see CAL6a, Risks):** since `DayOfMonth` becomes age-relative but the moon's own cycle deliberately stays
on the eternal epoch (so it doesn't visually jump when an age changes), an age transition that doesn't land
on a lunar-cycle boundary permanently shifts that alignment for the new age — "day 14 = full moon" isn't
literally forever, it's "forever within an age, then possibly a few days off after the next age begins."
Flagged as an accepted cosmetic quirk, not fixed — see Risks.

## 8.1.1 — Persistent calendar epoch *(foundation)*

**Current state:** `_startNetworkTime` (a `double`, in `NetworkTime.time`'s domain — which itself resets
per server process, it is not wall-clock time) is the single reference point `DayFraction`/`LunarFraction`
already compute from. `ServerSetHour` (the existing `/set-time` backend) already rewrites this same field
by subtracting an offset — i.e., "shift the epoch" is already this file's established technique, not a new
one.

**CAL1 — What gets persisted.** **A single accumulated value: `calendar_elapsed_seconds` (double), counting
simulated seconds since the world's Day 1 — advancing only while a server process is actually running.**
On boot: `_startNetworkTime = NetworkTime.time - calendar_elapsed_seconds`. On save: persist
`NetworkTime.time - _startNetworkTime` (current elapsed seconds). Exactly the same arithmetic
`ServerSetHour` already does, just persisted instead of thrown away.
*Alt considered:* a **wall-clock epoch** (persist a real UTC timestamp marking "Day 1 began," derive
elapsed time from `DateTime.UtcNow - epoch` regardless of whether the server was running) — simpler (one
timestamp, no periodic writes needed), and arguably more "alive" (the world keeps aging while offline,
EVE-Online-style). **Rejected for now:** it means a multi-day server outage causes the calendar to silently
jump forward by however long the server was down — possibly skipping a full-moon window (8.1.4) or several
days entirely with nobody able to observe it happen. The uptime-accumulated model avoids surprise jumps and
matches how the rest of this system already thinks about time (`NetworkTime` itself is uptime-relative, not
wall-clock). Revisit only if "the world ages while the server's down" becomes a wanted feature in its own
right — it's a bigger, deliberate design choice, not a free upgrade.

**CAL2 — Where the persist calls go.** **Piggyback on infrastructure that already exists at exactly the
right call sites** — no new lifecycle wiring needed:
- `GameNetworkManager.AutosaveTick()` (1.6, currently `SaveAllCharacters()` only, every 90s) also calls a
  new `WorldClock.ServerPersistCalendar()`.
- `GameNetworkManager.OnStopServer()` calls it once more before shutdown, in the same place character saves
  are flushed (mirrors the existing "save everything, then flush" ordering already there).
- **Write mechanism: a direct synchronous `UPDATE world_clock_settings SET calendar_elapsed_seconds = …,
  age = … WHERE id = 1`**, matching `WorldClockSettingsRepository`'s existing synchronous-read style
  (already how this table is read at boot, no complaints) — **not** routed through 1.2's async
  `PersistenceService` write queue, which is designed around the `ISaveJob`/per-character convention. A
  90-second, single-row settings write has no latency profile worth the extra machinery.

**CAL11 — Real bug this item would otherwise inherit: `ServerSetHour` (the existing `/set-time` backend)
currently destroys the whole-day count.** Found while reviewing for implementation, not while originally
drafting this — re-read the live code:
```csharp
public static void ServerSetHour(int hour) {
    ClearDebugOverrides();
    float targetFraction = Mathf.Clamp(hour, 0, 23) / 24f;
    _startNetworkTime = NetworkTime.time - targetFraction * _dayLengthSeconds;
}
```
This rewrites `_startNetworkTime` from **only** the target fraction-of-day, discarding whatever whole-day
count was previously implied. Harmless today (nothing reads whole days yet). **After 8.1.1, this becomes a
real corruption bug** — every `/set-time` call would silently reset `TotalElapsedDays` to 0, wiping out
accumulated Age/Year/Month/Week progress via what looks like a harmless testing command. **Must fix as part
of 8.1.1**, preserving the current day count and only rewriting the fraction:
```csharp
public static void ServerSetHour(int hour) {
    ClearDebugOverrides();
    long currentDay = TotalElapsedDays; // capture BEFORE rewriting _startNetworkTime
    float targetFraction = Mathf.Clamp(hour, 0, 23) / 24f;
    double newElapsedSeconds = currentDay * _dayLengthSeconds + targetFraction * _dayLengthSeconds;
    _startNetworkTime = NetworkTime.time - newElapsedSeconds;
}
```
No urgency to also force an immediate persist here (unlike `ServerSetAge`) — losing up to 90s of a
deliberate hour-of-day test to an unclean crash is a non-issue, same reasoning as CAL2's risk note.

**Schema** (extends the existing singleton `world_clock_settings` row, same table fog fields were added to
in migration 0029):
```sql
ALTER TABLE world_clock_settings
    ADD COLUMN IF NOT EXISTS calendar_elapsed_seconds  DOUBLE PRECISION NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS age                        INT NOT NULL DEFAULT 1,
    ADD COLUMN IF NOT EXISTS age_started_elapsed_days   BIGINT NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS age_starting_year_display  INT NOT NULL DEFAULT 1372;
```
(`age_started_elapsed_days`/`age_starting_year_display` back CAL6/CAL7 — see 8.1.3/8.1.6. Defaults produce
Age 1, "Year 1372" with no extra seeding step, matching the user's stated starting year.)
Also update the seeded/default `lunar_cycle_days` to `28` (see the grounding note above) — a data change
in `DatabaseSeeder.SeedWorldClockSettings` + the migration's own default, not a schema change.

## 8.1.2 — Calendar unit derivation (read API)

**CAL3 (revised after implementation review — see CAL6a below) — Two elapsed-day counts, not one.** 8.1.1
folds the persisted elapsed time directly into `_startNetworkTime`, so every peer can already derive total
elapsed days independently, exactly the way `DayFraction` already works today:
```csharp
public static long WorldElapsedDays => (long)Math.Floor((NetworkTime.time - _startNetworkTime) / _dayLengthSeconds);
```
`WorldElapsedDays` is the **eternal, never-resets** count — it's what `DayFraction`/`LunarFraction` already
use (unchanged, still purely time-of-day/moon-phase, continuous across an age change — see CAL6a) — but per
CAL6a it is **not** what the calendar-display units below use.

**CAL4 — Indexing convention: internal math 0-based, exposed API 1-based.** Reads as `Day 1 of Month 1 of
Year 1` at the start of any age (matches how a human reads a calendar), computed off `AgeElapsedDays`
(CAL6a), not `WorldElapsedDays`:
```csharp
const int DaysPerWeek = 7, WeeksPerMonth = 4, MonthsPerYear = 13;
const int DaysPerMonth = DaysPerWeek * WeeksPerMonth;      // 28
const int DaysPerYear  = DaysPerMonth * MonthsPerYear;     // 364

static long AgeElapsedDays => WorldElapsedDays - _ageStartedElapsedDays;      // CAL6a

public static int DayOfWeek   => (int)(AgeElapsedDays % DaysPerWeek) + 1;           // 1-7
public static int DayOfMonth  => (int)(AgeElapsedDays % DaysPerMonth) + 1;          // 1-28
public static int WeekOfYear  => (int)((AgeElapsedDays / DaysPerWeek) % (MonthsPerYear * WeeksPerMonth)) + 1; // 1-52
public static int MonthOfYear => (int)((AgeElapsedDays / DaysPerMonth) % MonthsPerYear) + 1;                  // 1-13
public static int Year        => _ageStartingYearDisplay + (int)(AgeElapsedDays / DaysPerYear);               // CAL7
```
(`DayOfMonth` wasn't in the original draft of this section — added for 8.1.6's `/time` command, which needs
"day N of the month," not just "day N of the week.") `WeekOfMonth` (1-4) is one more cheap one-liner if
wanted later — not building it speculatively since nobody's asked for it yet.

**Not in scope:** naming the days/months (e.g. lore-flavored names instead of raw numbers). That's a
content/presentation concern for later — the engine exposes numbered units; nothing here blocks adding
display names on top whenever that's designed. (Unlike `LunarPhase`'s New/Full/Waxing names, which are
astronomically-conventional and were cheap to hardcode, day/month names would be setting-specific lore this
devplan shouldn't invent.)

## 8.1.3 — Age tracking

**CAL5 — Age is a manually-set, persisted value with no auto-advance.** Unlike the calendar units below,
Age is **not derived from elapsed time** — nothing was specified about how long an age lasts, and ages in
this kind of setting are typically lore/event-driven (a cataclysm, a war's end), not fixed-duration.
Persisted as the `age` column added in 8.1.1, changed only via an explicit server-authoritative call.

**CAL6 — Decided: a new Age resets Year back to 1** ("Second Age, Year 1," not "Second Age, Year 9,412").

**CAL6a — Revised after implementation review, per the user's explicit confirmation: a new Age resets the
*entire calendar display* — Day/Week/Month/Year all restart at 1 — but leaves time-of-day completely
untouched** (if it's mid-afternoon when the age turns over, it's still mid-afternoon a moment later, just
now "Day 1 of Month 1"). This falls out naturally from keeping two genuinely separate concepts, not one:
- `WorldElapsedDays`/`DayFraction`/`LunarFraction` (CAL1/CAL3) — the **eternal** epoch. Never touched by an
  age change. This is *why* time-of-day survives untouched: `DayFraction` is a modulo *within* a single day
  and never references the age anchor at all.
- `_ageStartedElapsedDays` (new) — **which `WorldElapsedDays` value the current age began on.** Every
  calendar-*display* unit (`DayOfWeek`/`DayOfMonth`/`WeekOfYear`/`MonthOfYear`/`Year` — all of CAL4, not
  just `Year`) is computed off `AgeElapsedDays = WorldElapsedDays - _ageStartedElapsedDays`, so the instant
  `ServerSetAge` stamps a fresh anchor, every one of them reads back as 1 — a full, clean reset — while
  `DayFraction` (a completely separate computation) is untouched.

**CAL7 — Display year is not the same as internal year 1, 2, 3, ….** Confirmed by the user (8.1.6): the
game's year *display* starts at **1372**, not 1 — "Year 1372" is Age 1's first year. This isn't a hardcoded
constant; it's `age_starting_year_display`, a second field stamped alongside `age_started_elapsed_days`
whenever the age changes, so a future age can start its own display-year count wherever makes sense
lore-wise (not necessarily 1372 again, and not necessarily 1). Seeded default for the world's initial state:
`age = 1`, `age_started_elapsed_days = 0`, `age_starting_year_display = 1372`.
```csharp
[Server]
public static void ServerSetAge(int age, int startingYearDisplay)
{
    _age                     = age;
    _ageStartedElapsedDays   = WorldElapsedDays;   // CAL6a — stamps the reset point for Day/Week/Month/Year
    _ageStartingYearDisplay  = startingYearDisplay;
    ServerPersistCalendar(); // immediately — don't wait for the 90s tick, this is a rare/deliberate action
}
```
(`Year`'s actual formula lives in CAL4 now, alongside the other calendar units it's computed the same way
as — `AgeElapsedDays / DaysPerYear` plus the display offset — rather than repeated here.)

**CAL3 correction:** the original draft claimed only `Age` needed a new sync field. **That was wrong once
CAL6a made every calendar unit age-relative** — `WorldClockSyncMessage` now needs **three** new fields:
`int age`, `long ageStartedElapsedDays`, `int ageStartingYearDisplay`. Still small/cheap (three primitives,
one more one-time push, same "zero ongoing sync traffic" property), just not literally zero as first
stated — flagging the correction explicitly rather than leaving the earlier wrong claim standing.

`age`, `age_started_elapsed_days`, and `age_starting_year_display` are all added to the same `ALTER TABLE`
as `calendar_elapsed_seconds` in 8.1.1's schema (below), and ride the same sync/persist path together.

## 8.1.4 — Calendar-aware spawn conditions *(the original 8.1 scope, extended)*

*(2026-09-20: this section now holds the full content of the original `8.1-time-gated-spawns.md` — folded
in directly and that file deleted, since none of these devplans were checked in yet and there was no reason
to keep two files for one roadmap sub-item. TG1–TG4 below are unchanged from the original draft; only the
last two condition fields are new.)*

**Goal:** 5.12 built `WorldClock.CurrentLunarPhase` and `DayFraction` specifically as read hooks for "a
future content item (e.g. a 7.x spawn table) to opt into a full-moon condition later, without this devplan
touching `SpawnTable`/`SpawnPoint` at all" (DC6's own comment) — nothing consumed them until now. Lets a
spawn table entry be conditionally eligible based on day/night, lunar phase, day-of-week, or month, so
camps can have night-only undead, day-only critters, a full-moon-only rare, or (new, from the werewolf/
inn-NPC discussion) an inn patron who only shows up on a specific day — all server-authoritative and
already synchronized for free.

**Current state (grounding):**
- `SpawnTableEntry` (`SpawnTable.cs`, runtime) = `{ MobDefinition mob, int weight, int groupSize }`.
  `SpawnTable.Roll()` sums weights across all entries and picks one — no concept of "ineligible right now".
- DB: `spawn_table_entries` has `mob_id, weight, group_size, sort_order` (`0016_spawn_tables.sql`); the web
  Spawn Editor's entry rows are mob dropdown + weight + group size (`spawn.service.ts`/`spawn-editor.ts`).
- `SpawnPoint.DoSpawn()` calls `table.Roll()` once per activation/respawn; if it returns null (or the
  resolved mob has no prefab), `SpawnPoint` logs a warning and returns without spawning.

**TG1 — Condition shape.** **Two independent, nullable-by-default enum fields per entry**: `TimeCondition`
(`Any` / `DayOnly` / `NightOnly`) and `LunarCondition` (`Any` / `FullMoonOnly` / `NewMoonOnly`). Covers the
two classic patterns (day/night creatures, a full-moon rare) without building a generic phase-range query
language nobody's asked for. Day/night boundary: `DayFraction` in `[0.25, 0.75)` = day, else night — matches
the star-visibility boundary 5.12 already settled on (`starHideStart = 0.25`), so "day" means the same
thing to a player as it already does visually.
*Alt considered:* a raw min/max `DayFraction` range per entry (more general, but nobody has a concrete
need past day/night + full/new moon — reject until one shows up).

**TG2 — Where the filter applies.** **`SpawnTable.Roll()` filters to currently-eligible entries first, then
weights among survivors** (not a post-hoc reroll-if-ineligible loop — cleaner and avoids weight bias toward
whichever entry happens to be checked first). Requires `Roll()` to read `WorldClock` directly — an
acceptable static-singleton reach-in, matching how `SkyDriver`/`MoonRig` already read `WorldClock` freely.

**TG3 — All-entries-filtered-out behavior.** **`Roll()` returns null, exactly like an empty table today** —
`SpawnPoint` already handles that path (warns, doesn't spawn). *Real risk, not just a design nicety:*
`SpawnPoint.ActivationCheck` runs every 5s and calls `DoSpawn()` again whenever `_live.Count == 0 &&
!_respawnPending` — a point whose only entries are `NightOnly` would call `DoSpawn()` → get null → warn,
**every 5 seconds all day**, every day, for any point with a player nearby. **Recommend:** distinguish "table
resolved to nothing because everything's condition-filtered right now" (quiet, expected, no warning) from
"table resolved to nothing because it's genuinely empty/misconfigured" (warn, as today) — `Roll()` should
report *which* case happened (e.g. return a small result struct or an out bool `anyEntriesExist`) so
`SpawnPoint` can log-once-and-stay-quiet for the former. Doesn't need a real backoff/pending-timer (no
CPU concern at a 5s poll interval) — just stop the log spam.

**TG4 — Web authoring.** **New `<select>`s per entry row** in the Spawn Editor (Time condition, Lunar
condition, and now Day-of-week/Month), same dropdown-of-fixed-options style as `movementType`/
`socialAggroEnabled` elsewhere in this app. No new lookup table needed — these are small fixed enums, not
DB-driven lists.

**TG5 (new) — the two calendar-axis conditions this item adds beyond the original TG1-TG4:**
- **`DayOfWeekCondition`** — `Any` or a specific day (1-7), read against the now-age-relative
  `WorldClock.DayOfWeek` (8.1.2).
- **`MonthCondition`** — `Any` or a specific month (1-13), read against `WorldClock.MonthOfYear`.

(Not adding an `AgeCondition` in this pass — no concrete use case yet, unlike the other four axes which all
came from the werewolf/inn-NPC discussion. Easy to add later with the same shape if one shows up.) This is
exactly the gap flagged in the werewolf/inn-NPC discussion: the inn-patron rotation ("some NPCs only spawn
on certain days") wasn't representable because `WorldClock` had no day-of-week concept at all. It is now,
and this closes that gap directly.

**Schema:**
```sql
ALTER TABLE spawn_table_entries
    ADD COLUMN IF NOT EXISTS time_condition     TEXT NOT NULL DEFAULT 'Any',
    ADD COLUMN IF NOT EXISTS lunar_condition    TEXT NOT NULL DEFAULT 'Any',
    ADD COLUMN IF NOT EXISTS day_of_week_condition INT  NULL,  -- 1-7, NULL = Any
    ADD COLUMN IF NOT EXISTS month_condition       INT  NULL;  -- 1-13, NULL = Any
```
`time_condition`/`lunar_condition` stored as text (`'Any'|'DayOnly'|'NightOnly'` /
`'Any'|'FullMoonOnly'|'NewMoonOnly'`) — matches how `mobs.aggro_max_standing`/`warning_max_standing` are
already stored (named-standing strings), keeps a raw `SELECT * FROM spawn_table_entries` human-readable.
`day_of_week_condition`/`month_condition` stored as nullable ints instead (`Any` = `NULL`) since they're
numeric ranges (1-7/1-13), not small fixed enums — no reason to invent string constants for them.

**Files:** `SpawnTable.cs` (`SpawnTableEntry` gains all four condition fields; `Roll()` filters + the TG3
quiet-empty distinction), `SpawnTableRepository.cs`/`SpawnTableRegistry.cs` (read the new columns),
`SpawnPoint.cs` (use the "quiet" signal from `Roll()` instead of always warning), migration
`00NN_spawn_time_conditions.sql` (can ride in the same migration file as 8.1.1's `world_clock_settings`
changes, or its own — implementation's call), `api/Models/SpawnTable.cs` + `ContentDbContext.cs` +
`SpawnTablesController.cs` (new fields, nested DTO), `web/src/app/spawn.service.ts` + `spawn-editor.ts`
(four dropdowns per entry row).

**Test plan:**
1. Author a table with one `NightOnly` entry and one `DayOnly` entry, both weight 1. Stand at the point at
   noon (or use `Tools/World Clock Debug`/`/set-time`) → only the day entry ever rolls. Flip to night → only
   the night entry rolls.
2. A table where every entry is `NightOnly`, checked at noon: confirm no spawn, and confirm the console is
   NOT spammed every 5s (TG3).
3. Full-moon entry: scrub `Tools/World Clock Debug`'s lunar slider to Full → entry becomes eligible; move
   off Full → ineligible again.
4. A table with no condition-restricted entries behaves exactly as before (regression check).
5. Author a spawn entry restricted to `DayOfWeekCondition = 3`; confirm it only rolls on day 3 of the
   (age-relative) week cycle, and that a full server restart doesn't reset which day it currently is — the
   actual regression test for 8.1.1, the whole reason this got restructured.

**Risks:**
- **`Roll()` reaching into `WorldClock` statics** couples a previously-pure data class to networking state
  — acceptable here (server-only call site, `SpawnPoint.DoSpawn` already runs `[Server]`-only), but worth
  a one-line doc comment on `SpawnTable.Roll()` noting it's no longer side-effect-free/testable in isolation.
- **Day/night boundary drift** — if a future 5.12 follow-up changes `starHideStart`, TG1's hardcoded
  `[0.25, 0.75)` boundary won't automatically follow. Low risk (that boundary is design-locked, not
  actively iterated), but worth a shared constant if it ever needs to change once.

**Done when:** a spawn table entry can be restricted to day-only, night-only, full-moon-only, new-moon-only,
a specific day-of-week, or a specific month, authored in the web Spawn Editor, and `SpawnPoint` correctly
excludes ineligible entries at roll time with no warning-log spam when a table is temporarily
all-ineligible.

## 8.1.5 — Web + debug tooling

**Web (World Clock Editor):** **found while reviewing for implementation — Age should be read-only here,
not editable.** `WorldClockSettingsController`'s own doc comment confirms this whole settings row is
"read at boot... a web edit takes effect the next time the server (re)starts" — fine for day-length/lunar-
cycle tuning, but `/set-age` (8.1.6) is explicitly designed to apply **live and immediately**. Exposing an
editable Age field in the web editor too would create two different-latency paths to the same value — edit
it in the browser and nothing visibly happens until a restart, which reads as broken. **Recommend:** show
Age/Year/Month/Week/Day **read-only** in this editor (a status readout, not a form field) and keep
`/set-age` as the sole way to actually change it. Day-length/lunar-cycle/fog fields keep their existing
edit-then-restart behavior unchanged — only Age avoids that pattern, because a live command for it already
exists and a second, slower path to the same value is a genuine footgun, not a convenience.

**Testing command:** extend the existing `/set-time`-style pattern (`ChatUI.cs`'s plain string-equality
chain, `WorldClock.ServerSetHour`) with a **`/set-age <age> <startingYear>`** command wired to the new
`ServerSetAge(age, startingYearDisplay)` (see CAL7). A full `/set-date` (jump to an arbitrary day/month/year)
is more work for less testing value than `/set-age` (age changes are rare/deliberate; day/month/week already
cycle naturally and quickly at the default day length, 50 min/day → a full 28-day month in under 24 real
hours) — **recommend deferring a full date-jump command unless testing turnaround actually needs it.**

**`Tools/World Clock Debug` (Editor window):** the existing day/lunar sliders are explicitly **process-
local, cosmetic overrides that never touch the network** (see the window's own doc comment) — that
mechanism doesn't fit calendar state, which is now server-authoritative and persisted. **Recommend:** add a
plain read-only label showing the live Age/Year/Month/Week/Day under the existing sliders (no new scrub
control) — enough to verify 8.1.1-8.1.4 visually without building a second, differently-scoped debug
surface. A real "jump the calendar forward" tool, if wanted, would need to be server-authoritative (like
`/set-age`), not an addition to this process-local window.

## 8.1.6 — `/time` command + editable calendar display names

Player-facing (not a "Testing:" command like `/set-time`/`/set-age`): shows both the real-world date/time
and the full in-game date/time, in the exact formats given:

- **Real world:** `9/20/2026 10:24 am`
- **In-game:** `Fast Day, 3rd Day of the Harvest Moon in the Year 1372 of the 1st Age`

Parsed apart, the in-game string is five pieces: **`{DayOfWeekName}`**, **`{Ordinal(DayOfMonth)} Day of
the {MonthName}`**, **`in the Year {Year}`** (CAL7's display year, not the raw internal count), **`of the
{Ordinal(Age)} Age`**.

**CAL8 — Day-of-week and month names are DB-backed content, not hardcoded strings.** The user explicitly
wants to rename them later without a rebuild ("in case I find a typo or come up with better names") — same
"no content without a tool" standing principle as everything else on this roadmap. Two small fixed-
cardinality tables (7 rows / 13 rows always — the calendar math fixes the count, so this isn't an open-
ended CRUD list like Factions or Items):
```sql
CREATE TABLE IF NOT EXISTS world_clock_day_names (
    day_index SMALLINT PRIMARY KEY CHECK (day_index BETWEEN 1 AND 7),
    name      TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS world_clock_month_names (
    month_index SMALLINT PRIMARY KEY CHECK (month_index BETWEEN 1 AND 13),
    name        TEXT NOT NULL
);
```
Seeded with placeholder names for all 7/13 slots (`DatabaseSeeder`), with day 1 = "Fast Day" and month 10 =
"Harvest Moon" per what the user's already named — the rest need names from the user whenever convenient,
not invented here.

**Web editor:** extends the same World Clock Editor page 8.1.5 already adds the Age field to — two small
fixed-row sections (7 text inputs for day names, 13 for month names), **not** the generic
`ContentGrid`/`CrudModal` (there's nothing to create or delete, only rename — same reasoning 2.1.1's
AF9/AF10 used to give Faction's shared-thresholds ladder its own small form instead of forcing it onto the
generic grid).

**CAL9 — Names sync to clients on the existing `WorldClockSyncMessage`, not a new message type.** 20 short
strings (7+13) is trivial payload added to the one-time push `WorldClockSyncMessage` already delivers on
connect — a second message type/registry (like `AbilityCatalogMessage`) would be the "proper" content-sync
shape, but is unjustified machinery for a fixed 20-string list that only ever changes via a deliberate admin
edit. `WorldClock` caches the arrays alongside its other synced statics, read the same way `CurrentLunarPhase`
already is.

**CAL10 — `/time` needs no server round trip at all.** Unlike `/set-time`/`/set-age` (state-mutating, must
be `[Command]`s), `/time` only *reads* state every client already has locally after connecting: real-world
`DateTime.Now`, and `WorldClock`'s calendar fields — all already either synced once (`age`, the name
arrays) or purely derived client-side from that sync (`Year`/`MonthOfYear`/`DayOfMonth`/`DayOfWeek`, per
CAL3). **Recommend: resolve and print `/time` entirely client-side in `ChatUI.cs`**, appended straight to
the local chat window like a local echo — no `Cmd`/`Rpc`, no server load, works instantly even spammed.
```csharp
static string Ordinal(int n) => (n % 100 is 11 or 12 or 13) ? $"{n}th"
    : (n % 10) switch { 1 => $"{n}st", 2 => $"{n}nd", 3 => $"{n}rd", _ => $"{n}th" };

string realWorld = DateTime.Now.ToString("M/d/yyyy h:mm tt").ToLowerInvariant();
string gameTime  = $"{WorldClock.DayOfWeekName}, {Ordinal(WorldClock.DayOfMonth)} Day of the " +
                   $"{WorldClock.MonthName} in the Year {WorldClock.Year} of the " +
                   $"{Ordinal(WorldClock.Age)} Age";
```

## Risks

- **CAL2's write cadence (90s) means up to 90 real seconds of elapsed calendar time can be lost on an
  unclean crash** (not a clean `OnStopServer` shutdown) — acceptable; the same risk profile 1.6's character
  autosave already accepts, and losing at most 90 seconds of a 50-minute in-game day is a rounding error,
  not a real gap.
- **Blast-radius change for `/set-time`:** today, `/set-time` only affects the current session (nothing
  persists `_startNetworkTime`); after 8.1.1, it mutates the **persisted world calendar** — a deliberate
  test command now has permanent, shared effect. Not a problem, but worth the user knowing the stakes
  changed, since it wasn't true before this item.
- No DB/API/web risk beyond the usual — this follows the exact migration/repository/controller/editor shape
  already used for `world_clock_settings`'s existing fields (fog, day length, lunar cycle).
- **Lunar-phase/day-of-month drift across an age transition (found during this review, see the CAL1
  caveat):** because `DayOfMonth` resets per-age but the moon's own cycle deliberately doesn't (so it never
  visually jumps), an age that begins off a lunar-cycle boundary permanently shifts "day 14 = full moon"
  for that age by however many days off-boundary the transition happened to land. **Accepted as a cosmetic
  quirk, not fixed** — forcing alignment would mean either snapping the moon's visible phase at age
  transitions (contradicts why it's kept eternal) or delaying exactly when `/set-age` takes effect until a
  lunar boundary (unwarranted complexity for a rare, deliberate GM action). Worth knowing about, not worth
  solving now.

## Done when

A server can be stopped and restarted and the in-game Age/Year/Month/Week/Day/moon-phase all continue
exactly where they left off (not reset), every client reads the same values, a spawn-table entry can be
gated on day-of-week or month, Age can be advanced (with its own starting Year display, and a **full clean
reset of Day/Week/Month/Year while time-of-day stays untouched** — CAL6a) via an explicit server-
authoritative call, `/set-time` no longer disturbs the day/week/month/year count (CAL11), `/time` prints
both the real-world and in-game date/time in the exact specified formats with zero server round trip, and
every day/month name is renameable from the web editor without a rebuild — with 8.1.4's original day/night +
lunar-phase spawn-gating behavior (TG1-TG4) fully preserved and unaffected by everything else added here.

## Implementation-review addendum (2026-09-20)

Reviewed this whole devplan against the live code once more before implementation, per the user's request.
Found and resolved three things, none of which were caught in the original draft:
1. **CAL11** — a real bug the plan would have inherited: `ServerSetHour` (`/set-time`) discards the whole-
   day count, which would silently corrupt Age/Year/Month/Week after 8.1.1. Fixed in the design.
2. **CAL6a** — `Year`'s age-relative reset (CAL6) was inconsistent with Day/Week/Month staying globally
   cyclic. Asked the user directly; **confirmed: full reset of the whole calendar display on a new Age,
   time-of-day explicitly untouched.** All of CAL4 now derives from `AgeElapsedDays`, not the eternal
   `WorldElapsedDays`; `WorldClockSyncMessage` needs three new fields, not one (correcting CAL3's original
   claim).
3. **Web editor Age field** — found `WorldClockSettingsController`'s existing "apply on next restart"
   convention would conflict with `/set-age`'s "apply immediately" design if both edited the same field;
   recommended Age/Year/Month/Week display read-only in the web editor, `/set-age` as the sole live path.

Also documented (not fixed, accepted as-is): an age transition that doesn't land on a lunar-cycle boundary
permanently offsets "day 14 = full moon" for that age, since the moon's phase deliberately stays on the
eternal epoch while the calendar display resets. Cosmetic, not functional — see Risks.
