# 5.1.1 — Combat Pipeline: Hit Roll

**Status:** ✅ Done — verified in-editor 2026-07-15. HR2's data gap resolved: Cleric/Wizard ship as
budget-ratio-scaled placeholders (`Tools/Combat/Seed Class Combat Tables`), swap for real hand-authored
tables later with no code change.

**First of four sibling devplans** (5.1.1 Hit Roll → 5.1.2 Avoidance → 5.1.3 Damage → 5.1.4 Mitigation),
numbered to match `docs/eventide_combat_pipeline.md`'s own Step 1/2/3/4 labels. **Build order deviates from
that numbering, deliberately** — this project builds 5.1.1 → **5.1.3** → **5.1.2** → 5.1.4, per the design
doc's own §6.3 recommendation (validate Hit Roll + Damage end-to-end before the more complex Avoidance
waterfall goes in; Mitigation ships as a stub last). Written in tandem with `2.12-skill-system.md` — Hit
Roll's Skill Differential modifier (HR4) reads 2.12's weapon-skill values directly.

## Scope (shared across all four 5.1.x devplans)
- **Melee/physical auto-attack only** for this whole 5.1 effort. Spell/ability damage keeps its current
  formula; physical abilities (Kick, etc.) route through this pipeline later, as part of 5.1's separate
  ability-kit expansion (roadmap, not yet devplanned).
- **Symmetric** — player-attacks-mob and mob-attacks-player both run the full pipeline. Mobs get their combat
  data **authored per-mob in the Mob Editor** (this devplan), not derived from `mobLevel`.
- Threat/aggro overhaul is explicitly out of scope for 5.1.1–5.1.4 — it's a separate follow-on devplan,
  sequenced after all four of these land, so it generates off *real* damage numbers instead of the current
  1:1 placeholder.

## Grounding — what this replaces
- **`PlayerAutoAttack.ComputeDamage()`** (`Assets/Scripts/Combat/PlayerAutoAttack.cs:129-156`) — the entire
  bell-curve hit-tier formula is replaced. `EffectiveDamage`/`EffectiveDelay`/`EffectiveRange`/`EffectiveCat`
  (reading the equipped `ItemDefinition`) are unchanged.
- **`EnemyAI.CombatLoop()`** (`Assets/Scripts/Networking/EnemyAI.cs:168-186`) — currently flat guaranteed
  damage (`TakeDamage(_attackDamage, ...)`), no roll at all. Becomes a call into the same shared roll code.
- **`MobDefinition.cs`** has `attackDamage`/`attackInterval`/`attackRange` but no weapon category, skill, or
  hit-tier data — this devplan adds it (HR5).
- **`CharacterStats.cs`** STR/AGI/DEX/etc. accessors, unchanged; consumed by the Stat Contribution formula
  (§2.10 of the design doc).

## Decisions

### HR1 — Table representation — **RECOMMEND**
A `CombatTierTable` type: 7 weights (Miss, Glancing, Hit, SolidHit, GoodHit, Critical, Crippling), matching
the design doc §2.2's weighted-table shape. Whether stored as raw `/340` weights or normalized 0–1 fractions
is an implementation detail — recommend raw weights (matches the doc's own numbers directly, no conversion
bugs from copying its tables in).

### HR2 — Class/level table authoring — **DECIDED: block on real hand-authored per-class tables**
`ClassDefinition` gains a Level 1 baseline `CombatTierTable` (new fields, authored in the Race & Class Editor
— extends its existing HP/Mana-formula-fields pattern), seeded from design doc §2.5's numbers
(Warrior/Cleric/Wizard given verbatim).

**Gap, resolved:** the doc gives a full Level 1→20 progression curve for **Warrior only** (§2.11) — other
classes have no target table. A budget-ratio-scaled derivation from Warrior's curve was worked out and shown
to be internally consistent (weight-conserving), but rests on two unproven assumptions (level-20 budget
ratios matching level-1 ratios; linear scaling of a delta the doc's own cost model treats as nonlinear) — **user's
call: no shortcut, hand-author Cleric's and Wizard's own Level 1→20 target tables** rather than derive them.
5.1.1 implementation is blocked on that authored data — the `CombatTierTable`/roll-resolution code (HR1, HR6)
and the mob-side plumbing (HR5) can proceed without it, but the Race & Class Editor's per-class progression
fields won't have real numbers to seed until the user supplies Cleric/Wizard's tables (same format as §2.11:
Level 1 %, Level 20 %, or the full per-level curve if available).

### HR3 — Level Differential modifier — **RECOMMEND**
Implements design doc §2.7's Fibonacci-threshold futility model (1→2→3→5→8→13→21 level bands, more level
increments needed for "full futility" as the band widens; asymmetric — disadvantage hurts faster than
advantage helps). Exact weight-transfer magnitudes per band are named as tuning parameters in the doc itself
("set conservatively, adjust through playtesting") — implement with a first-pass magnitude, exposed as
tunable constants, not hardcoded inline.

### HR4 — Skill Differential modifier — **RECOMMEND**
Implements §2.8's perfect-square scaling (±1→1, ±2→4, ±3→9, ±4→16, ±5+→25 weight units, capped), reading
attacker/defender weapon skill via 2.12's `CombatSkill.Of(combatant, category)` resolver. Weight moves
Miss→Glancing→Hit (negative) or Crippling→Critical→GoodHit (positive), per the doc.

### HR5 — Mob combat data: authored per-mob in the Mob Editor — **DECIDED (this session's Q&A)**
`MobDefinition` gains: `weaponCategory` (Might/Finesse), `weaponSkill` (int — feeds HR4, shared with 2.12's
SK5), and **7 raw hit-tier weight fields** (mirroring `CombatTierTable`) authored directly per mob. Recommend
defaulting a newly-created mob's 7 fields to the Warrior Level 1 table (§2.5) so authors start from a valid
table, not blank/zeroed weights. New migration (next after 2.12's `0021`, so `0022_mob_combat_fields.sql`)
adds the columns to `mobs`; `MobsController.cs`/EF model/Angular `mob-editor.ts` gain the corresponding
fields — mirrors the exact migration→API→Angular pattern already used for every other mob field (e.g.
`0015_mob_faction_hits.sql`'s precedent).

### HR6 — Weighted roll resolution — **RECOMMEND**
Standard weighted pick: sum the (possibly-transferred) weights after all modifiers apply, roll uniform
`[0, total)`, walk cumulative tier boundaries to find the resulting tier. Pure, stateless, unit-testable in
isolation — matches the design doc's own §6.3 recommendation to validate this step standalone first. Position
Modifier (design doc §2.9, rear-attack reliability) is included here too since it's part of the same
per-swing modifier chain, but note it's recalculated fresh every swing (not cached).
