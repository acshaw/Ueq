# 6.4 — Build Pipeline / Client Distribution

Status: 🟠 Implemented — pending AWS-side upload + real-machine verification

## Implementation log (2026-07-26)

**BP6 revised during review**: the user pushed back on "no launcher" — a real (auto-updating)
launcher is genuinely on their agenda, not a nice-to-have. Scoped it to the smaller of two tiers
discussed: a simple auto-launcher that always re-downloads the full client zip when it detects a
version change (no delta/binary-diff patching — that's a much bigger systems project, deferred
until it's an actual pain point, not built speculatively). BP1–BP5 implemented as originally
drafted.

Implemented:
1. **`Assets/Scripts/BuildInfo.cs`** — plain runtime `ScriptableObject`, `Resources.Load`-able by
   both client and server. `Current` returns `""` if never stamped (Editor Play testing) — treated
   as "don't enforce," not "reject everyone."
2. **`ServerBuildTools.cs`**: new `Tools/Build/Stamp New Build Id` — stamps `Assets/Resources/
   BuildInfo.asset` **and** a sibling `C:\Builds\Ueq\version.txt` (the launcher's own check, since
   it never runs Unity code) with one UTC-timestamp id. Deliberately a separate, explicit step, not
   auto-run inside each build method — stamping on every build call would give the client and
   server built moments apart two *different* ids, breaking the very check this exists for. Each
   build method calls a new `EnsureBuildInfoStamped()` guard (auto-stamps once if nothing exists
   yet, so a fresh clone can't silently ship with no id forever).
3. **`AccountAuthenticator.cs`** (BP3): `AuthRequestMessage.clientBuildId`, new
   `AuthCode.VersionMismatch`, checked **first** in `OnAuthRequest` — before the pending-connection
   guard, before any DB work — comparing against `BuildInfo.Current`. Message names a download URL
   read from a new `UEQ_DOWNLOAD_URL` env var (falls back to a generic message if unset, rather
   than a broken link).
4. **New `launcher/Ueq.Launcher/`** — a small self-contained .NET WinForms app (`net10.0-windows`,
   `PublishSingleFile`, no runtime prerequisite for the recipient). `MainForm.cs`: on load, GETs
   `/downloads/version.txt`, compares to a local marker (`%LOCALAPPDATA%\UeqGame\version.txt`); if
   different (or nothing installed yet), downloads `/downloads/UeqClient.zip` with a progress bar,
   extracts over the previous install, updates the marker, launches `Ueq.exe`. Offline-tolerant: if
   the version check itself fails (no internet) but a working copy is already installed, launches
   it anyway with a warning rather than hard-blocking on a transient network hiccup.
5. **`deploy/Caddyfile`**: new `/downloads/*` static handle — uses `handle_path`, not `handle`
   (worth noting: `handle` doesn't strip the matched prefix before `file_server` looks on disk,
   which would have looked for a nonexistent nested `downloads/downloads/...` path — caught and
   fixed before it ever shipped).
6. **`deploy/deploy.sh`** / **`.github/workflows/deploy.yml`**: extended with the same
   optional/tolerant `CLIENT_URL`/`VERSION_URL` pattern as 6.2's `GAMESERVER_URL` (presign always
   succeeds even before the first manual S3 upload; a 404 is a skip, not a failure). Explicitly
   **not** using `tar` here despite 6.2's lesson — that bug was Windows→Linux (`unzip` choking on
   `Compress-Archive`'s backslash paths); this artifact is Windows→Windows (the launcher's own .NET
   `ZipFile.ExtractToDirectory` on the recipient's machine, and this Linux box never unzips it
   itself, just serves the raw bytes), so `.zip`/`Compress-Archive` is correct here.
7. **`docs/DEPLOY-AWS.md`** gained **§15**: one-time `UEQ_DOWNLOAD_URL` env var, the
   stamp→build→zip→upload release flow, one-time launcher publish+handoff, and a verify checklist
   (fresh install works; a deliberately mismatched client gets a clear rejection, not a silent
   desync; re-running the launcher after that self-heals).

Ran the full local half already: stamped a build id (`20260726T063947Z`), rebuilt both the Linux
server and Windows client with it embedded (both `Result: Succeeded, 0 errors`), published the
launcher (`dotnet publish`, self-contained single-file, ~116 MB — expected for a bundled .NET

**Not yet done — needs the user's own terminal** (same AWS-TLS-validation limitation as every prior

and end-to-end verification with a real second machine (ideally the brother's own, per the devplan's

## Goal

Make it fast and low-friction for the user's brother (no SE background, can't build the client
himself — the whole reason a web content-admin exists instead of Unity ScriptableObjects) to get a
runnable client whenever there's something new to test. Today that means an ad-hoc manual file
transfer every time. The actual driver, per the user: **speed up content-development iteration
between the two of them**, not "ship the game to the public."

Explicitly scoped DOWN from the roadmap's older "launcher / patcher" framing (`CLAUDE.md`'s
retained Phase 6c language: "version check on launch, delta patching," "push client updates
without full re-download"). That's real infrastructure for an unknown/growing player base. At
2 known users who can just be told "hey, new build, redownload," it's premature — see BP6.

## Grounding

- **6.2 already proved the pattern to reuse**: build locally in the Editor (no Unity CI — same
  reasoning as DH7: licensing/setup overhead isn't worth it for a solo/two-person project), upload
  through the existing zero-long-lived-secrets S3-presign/SSM `deploy.sh` pipeline.
- **Caddy already serves static files** for the Angular web app (`deploy/Caddyfile`, `root * /var/
  www/ueq-web` + `file_server`) — a `/downloads/*` path on the same instance is zero new
  infrastructure, not a new service/account (itch.io, Dropbox, etc.) to depend on.
- **A real, repeated pain this project has hit multiple times**: client and server builds falling
  out of sync produces *confusing* symptoms, not a clear error — Mirror scene-object hashing
  desyncs into "Spawn scene object not found" warnings (first hit 5.10), and 6.2's own
  verification session would have been faster to diagnose with a real version check instead of
  reasoning it out from log lines. There's currently **zero version/build check anywhere** in the
  connect handshake (confirmed via grep — no `version` reference in `GameNetworkManager.cs`).
- **`AccountAuthenticator.AuthRequestMessage`** (`Assets/Scripts/Server/Auth/AccountAuthenticator.cs`)
  is already the first message exchanged after connecting, before any DB lookup — the natural,
  minimal-change integration point for a build-id check.
- **6.2's own zip-vs-tar lesson applies in reverse here**: that bug was Windows→Linux (PowerShell's
  `Compress-Archive` backslash paths broke Linux's `unzip`). This artifact is Windows→Windows (the
  brother's own machine), where `.zip` is the *right* choice — Windows Explorer's native "Extract
  All" only understands `.zip`, not `.tar.gz`, and the brother is exactly the non-technical
  audience that matters for this call.

## Decisions

**BP1 — Host the download on the same Caddy instance already serving `/web`, not a new service.**
New `/downloads/` path in `deploy/Caddyfile`, serving a static directory the deploy pipeline
populates. Reject itch.io/Dropbox/Google Drive: real options, but each is a new external
dependency/account to manage for zero benefit over infrastructure that's already paid for, running,
and HTTPS-terminated.

**BP2 — Distribution format: plain `.zip`, built via PowerShell `Compress-Archive`.**
Windows→Windows this time (unlike 6.2's gameserver artifact), so the backslash-path issue that
broke Linux's `unzip` doesn't apply — Windows's own zip handling (Explorer, `Expand-Archive`) is
consistent either way. `.zip` over an installer (Inno Setup, etc.) — an installer is more polish
but pure overhead at 2-user scale; double-click-extract-and-run is a perfectly normal ask here.

**BP3 — A build-id check in the existing auth handshake, rejecting mismatches with a clear message
before any DB work.**
Add `clientBuildId` to `AuthRequestMessage`; the server compares it to its own build id and, on
mismatch, responds with a new `AuthCode.VersionMismatch` + a message naming the download URL,
before running the (more expensive) credential lookup. Turns the exact class of bug that has
repeatedly cost real debugging time this project (client/server desync from a forgotten rebuild)
into an immediate, actionable message instead of a confusing runtime symptom — cheap to add (one
string field, one early comparison) given the message plumbing already exists.

**BP4 — Build id = an auto-generated timestamp stamped at build time, not a manually-bumped
version number.**
A small `IPreprocessBuildWithReport` writes the current UTC timestamp into a `Resources/BuildInfo`
asset every time `ServerBuildTools`'s build methods run; both the client and server builds get one
stamped from the *same build session* when built together (the established rule already requires
rebuilding both together on any scene/code change, so this doesn't add a new discipline — it
automates detecting when that rule was skipped). Rejected: relying on `PlayerSettings.bundleVersion`
(currently a static `"0.1.0"`, per `ProjectSettings.asset`) — it requires remembering to bump it by
hand before every build, which is exactly the kind of manual step a 2-person team will eventually
forget, defeating the point.

**BP5 — Deploy mechanism: extend the same `deploy.sh`/`deploy.yml` S3-presign/SSM pipeline 6.2 just
built, not a new one.**
`client.zip` uploaded to S3 manually/locally after each build (same as `gameserver.tar.gz` — no
Unity CI), `deploy.yml` presigns it alongside the others, `deploy.sh` places it at
`/var/www/ueq-downloads/UeqClient.zip` (stable, memorable link: `https://<hostname>/downloads/
UeqClient.zip`).

**BP6 — Scope boundary: no launcher app, no auto-update/patching, no delta downloads.**
The client's version-mismatch message (BP3) names the download URL; a human clicks it and
re-downloads manually. This is the "launcher/patcher" work the roadmap's older phase language
described — genuinely worth building if/when there's an actual unknown-sized player base making
manual redownloads painful, not for two people who already talk to each other. Revisit if this
starts to feel like friction.

## Approach

1. `IPreprocessBuildWithReport` (or extend `ServerBuildTools.cs` directly) stamps a `BuildInfo`
   asset with a UTC timestamp before each build.
2. `AccountAuthenticator`: add `clientBuildId` to `AuthRequestMessage`, a server-side comparison
   against its own stamped `BuildInfo`, new `AuthCode.VersionMismatch`.
3. `deploy/Caddyfile`: new `/downloads/*` static handle.
4. `deploy/deploy.sh` / `.github/workflows/deploy.yml`: extend to presign/deploy `client.zip`
   alongside `web.zip`/`api.zip`/`gameserver.tar.gz`.
5. Build client + server together locally, zip the client with `Compress-Archive`, upload to S3,
   push to trigger the deploy (mirrors 6.2's exact real-world sequence).
6. Verify: an intentionally mismatched (old) client gets a clear rejection message, not a silent
   desync; a matching client connects normally; the brother can reach and extract the download URL
   without help.

## Test plan

- Build client + server together; connect — succeeds normally.
- Rebuild only the server (bump its `BuildInfo` without rebuilding the client) and connect with the
  stale client — clear `VersionMismatch` rejection naming the download URL, not a silent desync or
  confusing runtime symptom.
- `https://<hostname>/downloads/UeqClient.zip` downloads and extracts cleanly on a plain Windows
  machine (ideally the brother's own, to confirm zero-friction for the actual target user).

## Risks / open questions

- The build-id stamp only catches mismatches at the *client/server* boundary — it says nothing
  about whether the brother is looking at stale *content* (DB-authored data), which is a separate,
  already-solved problem (content loads fresh from the DB at connect, no client-side caching of it).
- Exposure posture: `/downloads/*` is public, unauthenticated, same as the open game port and API —
  consistent with this project's existing "hobby-scale, gate by not being discoverable" posture, not
  a new kind of exposure. Worth restating since it's a new URL, not because it's meaningfully riskier
  than what already exists.
