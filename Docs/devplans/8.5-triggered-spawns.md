# 8.5 — Event/quest-triggered spawns

**Status:** 🟡 Awaiting review.
**Roadmap item:** M8 → 8.5
**Pattern:** deliberately scoped to the trigger *mechanism* only, mirroring how 5.12 shipped
`WorldClock.CurrentLunarPhase` as a pure read hook with no consumer — wiring a real quest/script system to
call it is future work, out of scope here.

---

## Goal & why now

Every spawn today happens via proximity (`ActivationCheck` polling `activationRadius`) or a respawn timer
after death. Some content wants a spawn that happens on an explicit event instead — a quest turn-in
summons an escort NPC, a scripted encounter pops only after some other condition. This item adds the
trigger mechanism to `SpawnPoint`; it does **not** build the quest/script system that would call it — the
project's own conversation/quest model is still keyword-reward-only (no quest UI, 3.3 NPC item-giving is
still on hold per roadmap M3), so there's no real caller to wire up yet. Building a speculative caller
would be designing against a system that doesn't exist.

## Current state (grounding)

- `SpawnPoint.ActivationCheck` (every 5s): if a player is in range and `_live.Count == 0 &&
  !_respawnPending`, calls `DoSpawn()`. This is the *only* path that ever calls `DoSpawn()` today, aside
  from `RespawnAfterDelay` after a death.
- `NpcEventDispatcher` already has a clean dispatch API other systems call into (`DispatchConversationKeyword`,
  `DispatchFactionChanged`, etc.) — the established pattern for "an external system tells an NPC-side
  component something happened," which this item's trigger method should match in shape even though a
  `SpawnPoint` isn't itself an NPC (it has no `NpcEventDispatcher`).
- Every other piece of `SpawnPoint` (table/mobId resolution, group jitter, movement behavior application,
  respawn timer) is orthogonal to *how* a spawn attempt gets started — none of it needs to change.

## Decisions (recommendations in **bold**)

**ET1 — Mechanism.** **A `SpawnMode` enum field (`Proximity` / `Triggered`, default `Proximity`) +
a new public server method `ServerTrigger()`.** `ActivationCheck` early-returns without polling proximity
at all when `spawnMode == Triggered` (no wasted `Physics.OverlapSphere` calls for a point that will never
self-activate). `ServerTrigger()` runs the exact same `DoSpawn()` a proximity activation would have —
100% code reuse of table/mobId resolution, group spawning, movement setup.

**ET2 — Does a triggered spawn ever auto-respawn?** **No, by default — `respawnAfterTrigger: bool = false`
gates it.** A `Triggered` point's death handler (`OnMemberDied`) checks this flag: if false (default), a
triggered spawn is genuinely one-shot per trigger call — it needs `ServerTrigger()` called again to
produce another spawn, even after its previous instance died. If `true`, once triggered, it behaves like a
normal timed camp from then on (auto-respawns via `RespawnAfterDelay` same as `Proximity` mode) — covers
"starts dormant until a quest flag flips, then behaves like a normal camp forever after," a real and
different use case from "pops exactly once per explicit call." Not defaulting to `true` because a
one-shot scripted encounter is the more common/expected meaning of "triggered" and silently letting it
auto-respawn would be a surprising default.

**ET3 — Debug/test entry point, since there's no real caller yet.** **A `/trigger-spawn <placementId>`
chat command (or an Editor `Tools/Zones` menu item taking a scene selection)** — recommend the chat
command, since it exercises the exact server-side code path a future real caller would use (a server-side
command handler calling `ServerTrigger()`), rather than an Editor-only path that might diverge. Gated the
same way other debug commands in this project are (presumably an admin/dev-only check — mirror whatever
`/unstuck`/`/set-time` already do for authorization, don't invent a new convention).

**ET4 — Placement sync.** **No new fields needed beyond `SpawnMode`/`respawnAfterTrigger` on the existing
`CapturePlacementData`/`ApplyPlacementData`** — this is config, not a new marker type or cross-reference,
so it rides the same JSON blob `spawnTableId`/`activationRadius`/etc. already go through.

## Files (once approved)

**Modified:** `SpawnPoint.cs` (`SpawnMode` enum + field, `respawnAfterTrigger` bool, `ServerTrigger()`
public method, `ActivationCheck` early-return for `Triggered`, `OnMemberDied`'s auto-respawn gated by
`respawnAfterTrigger`, both fields added to `CapturePlacementData`/`ApplyPlacementData`), `ChatUI.cs`
(gains a `/trigger-spawn <placementId>` string-equality check alongside the existing `/unstuck`/`/set-time`
arms at ~line 193, dispatching to a new `[Command]` — confirmed this file's exact dispatch shape: a plain
`if (raw.Equals("/unstuck", ...))`-style chain per command, not a dictionary, so the new arm follows the
same pattern verbatim), a new `[Command] CmdTriggerSpawn(string placementId)` on whichever component
`CmdUnstuck()` lives on (likely `NetworkedPlayer` — confirm at implementation time) that resolves the
placement id to a live `SpawnPoint` (needs a placement-id → GameObject lookup at the zone level; check
whether `PlacementMaterializer`'s indexing already exposes one before building a new one), web
Spawn/Placement editor gains a mode toggle if `SpawnPoint` config becomes web-editable for this field
(currently `SpawnPoint`'s non-spatial config is Unity-Inspector-only per the Placement Editor's
read-only-except-`spawnTableId`/`mobId` design, WP7 — confirm whether `SpawnMode` should join those two as
a web-editable field or stay Inspector-only).

## Test plan

1. Set a point to `Triggered`, `respawnAfterTrigger = false`. Confirm it never spawns from proximity alone
   (stand next to it, wait past the normal activation interval). Call `ServerTrigger()` → spawns once. Kill
   it → confirm it does **not** auto-respawn. Trigger again → spawns again.
2. Same setup with `respawnAfterTrigger = true`: after the first trigger + death, confirm it now respawns
   on its own timer without needing another explicit trigger.
3. A point left on `Proximity` (default) behaves exactly as today (regression check).
4. Placement sync round-trip: sync a `Triggered` point to the DB, restart, confirm its mode/flag persist.

## Risks

- **Placement-id → live-`SpawnPoint` lookup doesn't obviously exist yet** — every other consumer of
  `PlacementId` (the sync/import tools, `ResolveReferences`) works from a *zone load-time* index, not a
  live runtime one a chat command could query on demand. This may need a small new server-side registry
  (placementId → `SpawnPoint` instance, populated in `OnEnable`/`Awake`) rather than assuming one already
  exists — check `PlacementMaterializer`/`ZoneManager` for anything reusable before building a new one.
- **`ActivationCheck` early-return correctness** — must not accidentally also skip the death-driven
  `_live.RemoveAll(x => x == null)` pruning that currently happens at the top of every tick; that pruning
  should probably still run for a `Triggered` point (its own group could still despawn via other means),
  just skip the proximity-poll-and-auto-spawn part specifically.
- **No real caller yet (by design, ET-scope)** — this item ships a mechanism nothing calls in practice
  until a future quest/script item exists. Worth the user's explicit confirmation that shipping the
  mechanism ahead of its consumer (unlike the other four M8 items, which are each usable standalone the
  moment they're built) is still wanted now rather than when the first real trigger use case shows up.

## Done when

A `SpawnPoint` can be set to `Triggered` mode, spawns only via an explicit `ServerTrigger()` call (testable
via a debug chat command), and optionally reverts to normal timed auto-respawn after its first trigger.
