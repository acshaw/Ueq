# 3.1.11 — Mob Wander Regions (leashed / free-range / bounded)

**Status:** ✅ Done — verified in-editor 2026-07-11 (WR1–WR7 all as recommended). See the implementation log at the
end. Extends the 3.1.10
movement-behavior system. Generalizes idle wandering from "always tethered to the spawn point" into a
**region-driven** model so a mob can roam a spawn-anchored bubble (today), the whole zone, or an authored
bounded area — chosen per encounter, no new spawn "types."

## Why
Today every wander mob is tethered to a `wanderRadius` sphere around its exact spawn point (`WanderBehavior`).
That's right for a camp of rats but wrong for a wolf that should range a valley, or a herd that should roam a
meadow that isn't centered on where any one member spawned. The user wants **spawn-leashed wandering to stay an
option** alongside **free-range** and **free-range-within-boundaries**.

**Key reframe:** these are not three parallel systems. They're **one wander behavior sampling a swappable
region.** Leash = "region is a sphere at my spawn point"; bounded = "region is this authored shape"; free-range =
"region is the whole zone." Building it region-first is *less* code than three spawn modes and reuses the
`INpcMovementBehavior` seam 3.1.10 already established.

**Explicit non-goal (user):** no chase leash, ever. Chasing stays unbounded (mob pursues until the target dies or
disconnects). Regions constrain **idle wander only** — never aggro/chase.

## Scope
1. **Region abstraction** — a small "where may I roam" source that yields a random navmesh point:
   - `SpawnAnchoredRegion` — sphere of `wanderRadius` around the mob's spawn point (today's behavior).
   - `BoundedRegion` — an authored box/sphere volume placed in the scene (a `WanderRegion` marker).
   - `ZoneRegion` — the mob's whole zone navmesh (free-range).
2. **Wander behavior generalized** — `WanderBehavior` samples its region instead of hard-coding the spawn sphere.
   Backward compatible: no region assigned → `SpawnAnchoredRegion` (identical to current behavior).
3. **`WanderRegion` scene marker + authoring** — drag-in prefab with a box/sphere gizmo, referenced by a new
   `SpawnPoint.wanderRegion` field (mirrors the Stage-1 `SpawnPoint.patrolRoute` wiring), plus a
   `Tools/Zones/New Wander Region` placement tool + gizmo labels (matches `PatrolRoute`/`ZoneMarkerGizmos`).
4. **`EnterReturn` tweak for roamers** — a free-range/bounded mob shouldn't trudge all the way back to its spawn
   point after a kill. Roamers reset **where they stand** (or at the nearest point of their region); leashed mobs
   keep the current walk-home-and-heal.
5. **Disengage on target-left-zone (WR7)** — a mob whose target zones out currently keeps chasing across the zone
   boundary; make `EnemyAI` treat "target in a different scene" as target-loss and route it through the existing
   reassessment/return chain. Reuses (1)–(4); no fresh perception scan (that's 3.4).

**Out of scope:** arbitrary polygon regions (box + sphere MVP only); any change to chase/aggro; per-region
faction or social behavior; roaming *spawners* (the spawn point stays fixed — only the mob's wander area moves).

## Current state (grounding)
- **`WanderBehavior`** (`Assets/Scripts/NPC/`) — `INpcMovementBehavior`. On `Startup()` captures
  `_spawnPoint = transform.position` + reads `wanderRadius`/`wanderPauseMin`/`Max` (from `MobDefinition` or
  serialized fallback), then `WanderLoop` repeatedly picks `RandomNavPoint(_spawnPoint, _radius)` and walks there.
  `RandomNavPoint` = `origin + Random.insideUnitSphere * radius` → `NavMesh.SamplePosition(..., radius, AllAreas)`.
- **`EnemyAI`** (`Assets/Scripts/Networking/`) — drives movement only through `INpcMovementBehavior`
  (`Startup/Suspend/Resume`), re-resolved in `OnStartServer`. `_spawnPoint` (its own copy) is the **Return**
  anchor: after a target dies/leaves, `EnterReturn()` → `TrySetDestination(_spawnPoint)` → `ReturnLoop` walks home,
  and on arrival `_health.ResetToFull()` + `Resume()`. **`ChaseLoop` has no distance leash** (returns only on
  `_currentTarget == null`) — matches the "no chase leash" goal; nothing to change there.
- **`SpawnPoint`** (`Assets/Scripts/Combat/`) — Stage 1 added a `patrolRoute` field + `ApplyPatrol` (swap
  `WanderBehavior` → `PatrolBehavior`, seed the route) in `SpawnOne`, after `SetDefinition`, before
  `NetworkServer.Spawn`. A `wanderRegion` field + `ApplyWanderRegion` follows the exact same shape.
- **`PatrolRoute`** (`Assets/Scripts/NPC/`) — the pattern to mirror for `WanderRegion`: a scene component holding
  authoring data + gizmos; `EncounterTools`/`EncounterGizmos` place it + label it.

## Design detail — the region seam
A minimal interface keeps `WanderBehavior` clean and makes the three modes interchangeable:

```
interface IWanderRegion { bool TryGetRandomPoint(out Vector3 point); }
```

- `SpawnAnchoredRegion(spawn, radius)` → sample in a sphere at spawn (today's `RandomNavPoint`).
- `BoundedRegion(WanderRegion marker)` → sample inside the marker's box/sphere, project to navmesh.
- `ZoneRegion(mob)` → sample the mob's zone navmesh (see WR3 for how "the zone" is bounded).

`WanderBehavior.Startup` builds the region: if `SpawnPoint` handed it a `WanderRegion` → `BoundedRegion`; else if
the region is flagged free-range → `ZoneRegion`; else `SpawnAnchoredRegion` (default = unchanged). `WanderLoop`
calls `region.TryGetRandomPoint(...)` instead of `RandomNavPoint(_spawnPoint, _radius)`.

## Decisions (WR1–WR6)

**WR1 — One behavior + pluggable region, vs. three behaviors.**
*Recommend:* generalize `WanderBehavior` around `IWanderRegion` (one behavior, three region classes). Rationale:
the three "modes" differ only in *where* they sample; the loop/pause/suspend/resume logic is identical. Three
separate `INpcMovementBehavior` classes would duplicate that. (Patrol stays its own behavior — it's genuinely
different: ordered waypoints, not random sampling.)

**WR2 — Boundary shape: box + sphere (MVP) vs. polygon.**
*Recommend:* box **and** sphere only. Both are trivial to author (a marker with a size/radius + a wire gizmo),
trivial to sample, and cover the vast majority of "roam this area" needs. Arbitrary polygons need real tooling
(vertex editing, point-in-polygon) — defer until a specific encounter demands it.

**WR3 — What bounds "free-range"?**
*Recommend:* free-range = **the mob's zone**, not the literal global navmesh. The navmesh is one global mesh with
each zone offset ~5000u apart, so an unbounded sample could teleport a mob into another zone. Implement
`ZoneRegion` as a large box centered on the zone's authored bounds (derivable from the zone ground/terrain
extents, or a per-zone `WanderRegion` sized to the zone). **Consequence:** "free-range" and "bounded" share the
same sampling code — free-range is just a boundary the size of the zone. Less to build; call it out so we don't
pretend there's a separate free-range path.

**WR4 — Where the mode is authored: `SpawnPoint` vs. `MobDefinition`.**
*Recommend:* `SpawnPoint` (scene), via a `wanderRegion` field + a free-range toggle — mirroring `patrolRoute`.
Rationale: roam area is a *placement* concern (this wolf, in this valley), not an intrinsic property of the mob
*type* (the same wolf could be a spawn-camp guard elsewhere). Keeps `MobDefinition.wanderRadius` as the default
leash radius when no region is set. *(Alt: a mode enum on `MobDefinition` if you want the type to carry it — flag
if preferred.)*

**WR5 — `EnterReturn` for roamers: walk home vs. reset in place.**
*Recommend:* **reset in place** for free-range/bounded mobs (heal + `Resume()` where they stand, or at the nearest
region point if they ended up outside it); keep **walk-home-and-heal** for spawn-leashed mobs. Rationale: a roamer
marching across a valley back to an arbitrary spawn point after every kill looks broken. This needs `EnterReturn`
to know the mob's mode — pass a "return anchor" (spawn point for leashed, current/region for roamers) from the
region into `EnemyAI`, or query the movement behavior. Smallest surface: the region exposes a
`GetReturnAnchor(currentPos)` that `EnterReturn` targets instead of the hard-coded `_spawnPoint`.

**WR6 — Authoring tooling scope.**
*Recommend:* a `WanderRegion` drag-in prefab (box/sphere gizmo + `Handles.Label`), a `Tools/Zones/New Wander
Region` menu (snap-to-navmesh placement like `EncounterTools`), and a `SpawnPoint` inspector field to reference
it — all mirroring the 3.1.10 `PatrolRoute` tooling. No new web-editor work (regions are scene placement, like
routes/portals).

**WR7 — Disengage when the target leaves the mob's zone (zone-integration correctness — rides along here).**
*Problem:* today a mob only drops a target when the target **dies** (`OnDied` → `RemoveFromThreatList` → reassess)
or its object is **destroyed** (`_currentTarget == null` in Chase/Combat → `EnterReturn`, i.e. camp/disconnect).
When a player **zones**, the player object isn't destroyed — `MoveGameObjectToScene` relocates it ~5000u away in
another scene — so `_currentTarget` stays non-null and `ChaseLoop` keeps pathing toward the far-off position; the
mob runs to the zone edge / gets stuck and never disengages. `EnemyAI` has **no scene awareness of its target.**
*Recommend:* treat "target's scene ≠ my scene" as target-loss and route it through the **existing** reassessment:
in the Chase/Combat guard (and when pruning the threat list), if `_currentTarget.gameObject.scene !=
gameObject.scene` → `RemoveFromThreatList(_currentTarget)`; also drop any threat-list entries whose player left
the mob's scene. That reuses `GetTopThreat()` → `SwitchTarget` (another player already fighting it, same scene)
or `EnterReturn()` (→ walk home / reset in place per WR5, then `Resume()` wander/patrol). **Explicitly NOT
included:** a fresh perception scan for a brand-new bystander who never had threat — that's the aggro/perception
rework in **3.4**. So "find a new nearby target" here means "next player already on my threat list in my zone,"
not "re-scan the area." *This is a genuine zone-integration bug; it's implemented here only because it touches the
same `EnterReturn`/target-loss code WR5 reworks. Cross-referenced from roadmap 3.0.1.*

## Build stages (each verifiable, commit-able)
1. **Region seam + generalized wander (no authoring yet).** `IWanderRegion` + `SpawnAnchoredRegion`;
   `WanderBehavior` samples the region; default path byte-for-byte matches today. *Verify: existing wander mobs
   behave identically.* (Pure refactor — safe commit point.)
2. **Bounded region + marker + `SpawnPoint` wiring.** `BoundedRegion` + `WanderRegion` component/prefab +
   `SpawnPoint.wanderRegion` + `ApplyWanderRegion`. *Verify: a mob assigned a box/sphere region wanders inside it,
   ignoring its spawn point.*
3. **Free-range (`ZoneRegion`) + `EnterReturn` roamer tweak (WR3, WR5).** *Verify: a free-range mob roams the zone
   and, after a kill far from spawn, resets in place instead of trudging home; a leashed mob still walks home.*
4. **Placement tooling + gizmos (WR6).** `Tools/Zones/New Wander Region` + labels. *Verify: place a region in-scene,
   point a `SpawnPoint` at it, spawn, watch it honor the bounds.*
5. **Disengage on target-left-zone (WR7).** Scene-mismatch → target-loss in Chase/Combat + threat-list prune.
   *Verify (multi-client): aggro a mob, zone out through a portal; the mob disengages and resumes its idle behavior
   (wander-in-cage / patrol / walk-home) instead of running to the zone edge. A second same-zone attacker is picked
   up from the threat list; a bystander who never attacked is not (that's 3.4).*

## Done when
A designer can, per encounter, choose spawn-leashed (default, unchanged), free-range (zone), or bounded (drop a
box/sphere region) wandering via `SpawnPoint`; roamers reset sensibly after combat; a mob disengages when its
target zones out and resumes the correct idle behavior; chase is untouched (still no leash); existing wander camps
are unaffected.
