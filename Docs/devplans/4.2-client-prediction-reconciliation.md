# 4.2 — Client-Side Prediction + Reconciliation

**Status:** ✅ Done — verified in-editor 2026-07-13. Decisions PR1–PR10 confirmed 2026-07-13 (PR3 revised from
the original scalar recommendation to a struct, per user — swimming and levitation are confirmed near-term
movement modes, not hypothetical, and both will need a vertical-control input + likely a movement-mode flag;
doing the input's shape-change once now beats extending `CmdSendInput`'s flat scalar list twice). A
post-verification hardening pass (explicit CC-vs-CC de-penetration) was added and verified — see the
Hardening section below.

**Absorbs roadmap 4.3 (reconciliation + smoothing) and 4.4 (integration + regression) — see PR1.** Written
before 4.1 has been verified in-editor, at the user's request; PR6's threshold and any smoothing/blending
are deliberately left as tunable rather than fixed numbers (see PR6), to be set from what testing actually
shows rather than guessed now.

## Goal
Restore instant-feeling local movement for the owning client (lost as an accepted, temporary cost of 4.1) —
but this time **with** a correction mechanism, so a misprediction snaps back to the server's authoritative
outcome instead of diverging forever (the original 4.1-era bug). The server remains the single source of
truth for every gameplay-affecting decision (damage, range, targeting, etc.) exactly as 4.1 left it —
prediction is purely a client-side *rendering* technique layered on top, never trusted for anything else.

## Why 4.2 and 4.3 are one devplan (PR1)
Client-side prediction without reconciliation is exactly the bug 4.1 fixed — you cannot design "predict
locally" in isolation from "how do we correct it," because the correction scheme dictates the wire format
(sequence numbers, what the server acks back, what the client needs to have kept around to replay). Planning
them separately risks reworking 4.2's input protocol once 4.3's real requirements surface. **4.4's stated
scope is a regression pass with no independent design content** ("player-vs-player collision agrees on every
screen... MPPM multi-client + host verification") — folded into this devplan's Test plan / Done when instead
of a fourth near-empty file. `roadmap.md` will mark 4.3 and 4.4 as merged into 4.2 (same precedent as
2.8→3.2 and 3.4→5.1 — closed as absorbed, not implemented standalone, not renumbered).

## Grounding — current state after 4.1
- **`NetworkedPlayer.Update()`:** owner calls `CollectInput()` → `ApplyLook()` (purely local/cosmetic — never
  networked, never needs prediction) → `CmdSendInput(_moveInput, _yaw, _sprint, _jumpQueued)`. Movement itself
  (`ApplyMovement()`) runs from a single `if (isServer) ApplyMovement()` — the server is the *only* place it
  executes, host's own player included.
- **`ApplyMovement()`** reads instance fields (`_moveInput`, `_yaw`, `_sprint`, `_jumpQueued`,
  `_verticalVelocity`) and `Time.deltaTime` implicitly, then calls `_cc.Move(...)`. **This needs to become a
  pure step function taking an explicit `dt`** (PR2) — reconciliation replays several historical inputs
  back-to-back in one frame, and each one must use the `dt` that was *actually* elapsed when it was
  originally captured, not the current frame's `Time.deltaTime`.
- **`ServerAuthoritativeTransform : NetworkTransformReliable`** (4.1) makes *every* client, owner included,
  apply incoming server snapshots — that was the right call for 4.1 (the owner had zero local movement code,
  so without it the owner's own view wouldn't move at all) but is now the wrong call for 4.2: once the owner
  predicts + reconciles its own transform again, it must stop consuming NT snapshots (the corrected position
  comes from the reconciliation loop below, not raw interpolation) — see PR7.
- **Found while designing this (not yet a bug in practice, but worth knowing):** with `ServerAuthoritativeTransform`
  active, the owner's `transform.eulerAngles.y` currently has two writers in the same frame —
  `ApplyLook()` (always ran locally, immediately, even during 4.1 — rotation was never actually gated behind
  `isServer`) and the NT's snapshot-applied rotation (since `syncRotation = true`) — whichever of the two
  `Update()`s (NetworkedPlayer's vs. ServerAuthoritativeTransform's) happens to run later that frame wins,
  which Unity doesn't guarantee between components. In practice `ApplyLook()` overwrites every frame anyway,
  so this likely only ever shows as an imperceptible single-frame jitter, not a lasting problem — but it
  resolves cleanly as a side effect of PR7 (the owner stops consuming snapshots at all once prediction is
  back), so no separate fix is needed.
- **`PlayerSitting`** (`_sitting`, a plain `[SyncVar] bool`) is entirely independent of position/rotation —
  server-authoritative already, drives the Animator bool from the synced flag on every client. Nothing here
  changes.

## Decisions

### PR2 — Extract a deterministic step function — **DECIDED**
Refactor `ApplyMovement()` into `void SimulateMovement(Vector2 move, float yaw, bool sprint, bool jump, float
dt)`, operating only on its parameters + the persistent `_verticalVelocity`/CC state — no reads of
`Time.deltaTime` or the mutable `_moveInput`/`_yaw`/`_sprint`/`_jumpQueued` fields inside it. This ONE method
is called from three places: the server's per-frame simulation (unchanged in spirit from 4.1, just renamed/
reshaped), the owner's immediate local prediction (PR4), and the owner's replay-after-correction loop (PR6).
Using the same code for all three is what makes prediction agree with the server in the common case — two
different implementations would practically guarantee drift.

### PR3 — Wire format: new `PlayerInputCmd` struct — **DECIDED (revised from the original scalar recommendation)**
Introduce a `PlayerInputCmd { Vector2 move; float yaw; bool sprint; bool jump; uint seq; float dt; }` struct
and change `CmdSendInput` to take one `PlayerInputCmd` parameter instead of four-then-six loose scalars.

**Why the reversal:** the original recommendation (extend `CmdSendInput` with two more scalars, skip the
struct) was right for a scalars-only future. It's wrong now that swimming and levitation are confirmed
near-term additions — both will need at least a vertical-control input and likely a movement-mode flag
(walking/swimming/levitating) so the server knows which `SimulateMovement` variant to run. Bolting that onto
a flat scalar param list would push `CmdSendInput` past 8 parameters; doing the struct now means reshaping
the input model once instead of twice (once here, again in a few weeks for swim). The struct is scoped to
**exactly today's fields** — not pre-guessing swim/levitation's shape, just building the extensible vehicle
they'll land in.

**Risk, named honestly:** this project has hit Weaver-auto-serialization trouble with a custom struct before
— `InventorySlot` (`Assets/Scripts/Inventory/InventorySlot.cs`), a struct of plain `string`+`int` fields,
needed a hand-written `InventorySlotSerializer` (`WriteInventorySlot`/`ReadInventorySlot` extensions) rather
than relying on Weaver auto-gen. That precedent is suggestive, not proof — `InventorySlot` is used inside a
`SyncList<InventorySlot>`, and Mirror's Weaver has historically been less reliable auto-generating
`SyncList` payload serializers specifically than plain `[Command]` parameter serializers (input-cmd structs
on Commands are in fact a common, well-trodden Mirror pattern for predict/reconcile movement generally).
Failure mode is cheap regardless: if Weaver can't auto-generate `PlayerInputCmd`'s serializer, it's a
**compile-time** weave error, not a silent runtime bug, fixed by copying the same manual
`NetworkWriter`/`NetworkReader` extension pattern already proven in `InventorySlotSerializer`.

### PR4 — Client-side prediction — **DECIDED**
On the owner, each `Update()`: after `CollectInput()`, assign the next `_inputSeq`, capture `dt =
Time.deltaTime`, build a `PlayerInputCmd{move, yaw, sprint, jump, seq, dt}` (PR3), call
`SimulateMovement(cmd.move, cmd.yaw, cmd.sprint, cmd.jump, cmd.dt)` **locally, immediately** (instant visual
feedback — no round-trip wait), record `{cmd, resultingPosition, resultingYaw}` into a small ring buffer
(`List<PredictedInput>`, trimmed as acks arrive — see PR6), then send the same `cmd` via `CmdSendInput`.

### PR5 — Server processing + acknowledgment — **DECIDED**
Server's `CmdSendInput(PlayerInputCmd cmd)` handler calls the same `SimulateMovement(...)` (using the
CLIENT-reported `cmd.dt`, not its own frame delta — this is what makes replay reproducible) and tracks
`_lastProcessedSeq`. Add a new
`[TargetRpc] RpcAckMovement(NetworkConnectionToClient target, uint seq, Vector3 position, float yaw, float
verticalVelocity)` sent **only to the owning connection**, at the existing NT sync cadence (not on every
single Command — that's redundant; observers already get position via the ordinary NT sync path, this ack is
purely for the owner's own reconciliation). Carries `verticalVelocity` too, not just position/yaw, so a
replay after correction resumes from the exact physical state the server had (gravity/jump arc), not just a
teleported position.

### PR6 — Reconciliation — **DECIDED, threshold left tunable**
On receiving `RpcAckMovement`: discard buffered inputs with `seq <= acked seq` (server has processed them);
compare the client's OWN recorded `resultingPosition` at that sequence against the server's reported
`position`. If the error is within a small tolerance (serialized field, default placeholder ~0.15m — **tune
empirically from PR10's real MPPM testing, not guessed now**; note the field is a runtime-editable Inspector
value either way, so this default is low-stakes regardless of what it starts at), do nothing visible —
the buffer replay below already corrects it silently. If it exceeds tolerance: set
`transform.position/verticalVelocity` to the server's reported state, then replay every remaining buffered
input (in order, each with its own recorded `dt`) via `SimulateMovement(...)` to catch back up to "now."
**Popping on a large correction is accepted for this pass** — smoothing/blending the visual correction over a
few frames is a clean, isolated follow-up if testing shows it's actually noticeable; not designing it
speculatively now (avoid solving a problem we haven't observed).

### PR7 — Revert the owner's NetworkTransform to stock, retire the 4.1 stopgap — **DECIDED**
Once the owner drives (and now correctly reconciles) its own transform again, Mirror's *stock*
`NetworkTransformReliable.UpdateClient()` behavior — skip snapshot application for
`IsClientWithAuthority` — is exactly right again (that's precisely what "the owner is trusted to drive
itself" is supposed to mean, now backed by real reconciliation instead of 4.1-era's "trust forever, never
correct" bug). Recommend: swap `Player.prefab`'s NetworkTransform component back to plain
`NetworkTransformReliable` (`syncDirection` stays `ServerToClient` — still correct, the server is still sole
authority, only the *rendering* delivery mechanism for the owner changes) and delete
`ServerAuthoritativeTransform.cs` (its only purpose was bridging the 4.1-only gap where the owner had zero
local movement code — that gap no longer exists). Revert the matching `SceneSetup.CreatePlayer()` preference
added in 4.1. Non-owner observers are completely unaffected either way — they never had authority, so they
were always going through normal snapshot interpolation and still are.

### PR8 — Known, accepted limitation: predicting collision against other players — **ACKNOWLEDGE**
The client predicts against whatever it currently sees other entities doing, which isn't necessarily what the
server saw at the exact moment it processed that input (the original push-divergence scenario). Reconciliation
now corrects this quickly instead of diverging forever, but a brief prediction blip during player-vs-player
contact is expected, standard behavior for predict/reconcile netcode generally — not a defect to chase in this
devplan's own testing.

### PR9 — Sitting, zone teleports, respawn — **CONFIRMED NO CHANGE**
`PlayerSitting` is an independent `[SyncVar]`, untouched by any of this. Zone transitions / `/unstuck` /
respawn / login-into-persisted-zone all route through `ServerWarpTo` → `NetworkTransformBase.ServerTeleport`
— inherited unchanged whether the component is `ServerAuthoritativeTransform` or stock
`NetworkTransformReliable` (PR7). Worth an explicit check in testing: a `ServerTeleport` while the owner has
buffered-but-unacked predicted inputs should discard/reset the local prediction buffer (a teleport isn't
something to "reconcile" against — it's a hard authoritative override), so `ServerWarpTo`'s existing
`TargetRpcRespawn`/`ServerTeleport` path should also clear `_pendingInputs` client-side.

### PR10 — Test plan (absorbs old 4.4)
1. **Solo (Host):** movement/jump/sprint feel **responsive again** (instant local feedback restored, unlike
   4.1's interim laggy state) — this is the headline "done" signal versus 4.1's accepted regression.
2. **Two/three clients (Server Only + 2 remote MPPM):** push-collision test from 4.1 — all views should still
   agree on the *eventual* result; a brief visible correction during the actual contact moment is acceptable
   (PR8), a *permanent* divergence is not (that's the regression bar).
3. Inject artificial latency if Mirror's version here has a latency-simulation component (nice-to-have,
   otherwise just test over the real MPPM/network conditions available) to confirm reconciliation actually
   fires and corrects rather than only being exercised in the near-zero-latency host/LAN case.
4. Rotation, sitting (`/sit`, auto-stand, seated free-look + camera ease), zone transitions, `/unstuck`, death
   respawn, login-into-persisted-zone — full re-verification pass (this is 4.4's original scope).
5. Confirm a mid-flight zone teleport correctly discards the pending-input buffer (PR9) instead of replaying
   stale pre-teleport inputs on top of the new position.
6. Jump still works for both host and remote clients (carry over 4.1's check).

## Hardening — explicit de-penetration (PR8 follow-up, 2026-07-13)
**Root cause identified by inspection** (not directly observable — no Unity instance this session):
`CharacterController.Move()`'s collision resolution against ANOTHER CharacterController isn't a pure function
of net displacement; it's sensitive to exact per-call step timing. Specifically, `if (_cc.isGrounded)
_verticalVelocity = -2f;` reflects that PROCESS's own contact state at that instant — pushing into another
capsule can make `isGrounded` flicker differently between the client's and server's independent simulations,
nudging the vertical component of that step's `Move()` call just enough for one capsule to ride over the
other's rounded cap while the other stays blocked. The client and server don't tick in lockstep either (client
= once per rendered frame, server = once per arrived Command), compounding it. This is the same class of
issue the devplan's own backlog already named ("a fixed-timestep simulation tick, if variable-dt replay ever
shows determinism issues in practice — bigger and more invasive than anything here, not worth doing
speculatively") — a full fixed-timestep rework is the structural fix but a materially bigger undertaking than
4.2 itself.

**Scoped fix instead: explicit post-move de-penetration**, added as the last step inside `SimulateMovement`
itself (so it runs identically for prediction/server/replay, not a special case) — `ResolvePlayerOverlap()`
broad-phases nearby colliders via `Physics.OverlapSphere` around the CC's center, filters to other
`NetworkedPlayer`s specifically (CC.Move()'s own sweep already handles static world geometry fine — mobs and
terrain aren't in scope here), and for any overlapping other player's CharacterController, computes a
push-out vector via `Physics.ComputePenetration` (Unity's `CharacterController` IS a `Collider` under the
hood, so this works directly) and nudges `transform.position` out along it. Even if one step's implicit sweep
lets a sliver of interpenetration through, the very next `SimulateMovement` call (every input, i.e. every
frame) detects and corrects it — converging reliably regardless of which side's sweep behaved differently at
the contact instant, rather than relying purely on CC.Move()'s own (here, unreliable) resolution.
