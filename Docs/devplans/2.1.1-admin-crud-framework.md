# Devplan 2.1.1 — Generic admin CRUD framework

**Roadmap item:** M2 → 2.1.1 (inserted after 2.1, sequenced **before** 2.9/2.10/2.11)
**Status:** ✅ Done 2026-07-16 — all 7 editors (Item, Mob, Vendor, Loot, Faction, Conversation, Spawn)
retrofitted onto `ContentGrid`/`CrudModal` and browser-verified against the live API/DB; XP and
Faction's thresholds panel handled per AF9/AF10. AF1–AF10 all as recommended, AF2 decided with the
user before drafting.
**Depends on:** 2.1 (the Angular/API rails), 2.2–2.7 (the 7 existing bespoke editors this retrofits)
**Unblocks:** 2.9 (Abilities), 2.10 (Races & Classes), 2.11 (Seed/export) — built on the framework
directly instead of becoming three more one-off components; also the natural home for an icon
column once item icons are visually wired (5.9.1)

---

## Goal

Replace the 7 hand-built, structurally-identical Angular editors (Item / Vendor / Conversation /
Faction / Loot / Mob / Spawn — XP is the one exception, see AF9) with **one reusable pattern**: a
full-width, searchable/filterable/sortable **index grid** per content type, and a shared **CRUD modal
shell** that each type's existing (bespoke) form content renders inside. Not a fully generic
form-rendering engine — the real structural variance across types (Loot's three weighted child
lists, Conversation's nested per-keyword quest-transaction sub-panel, Vendor's ordered item-id
dropdown list) makes that a much bigger, more speculative build than the payoff justifies right now.

### Scope guardrails
- **In scope:** a generic `ContentGrid` component (columns, client-side search, click-to-sort), a
  shared `CrudModal` shell (title, Save/Delete, inline error, backdrop), a small per-type column
  schema colocated in each type's existing `*.service.ts`, and retrofitting all 7 row-based editors
  onto it.
- **Out of scope:**
  - **The .NET API / DB schema** — every controller already exposes the same
    `GET all / GET one / POST / PUT / DELETE` shape keyed by a string id (confirmed by reading
    `ItemsController.cs` against the others); nothing here needs an API change (AF1).
  - **A generic form-schema renderer** — form *content* stays bespoke per type (AF4).
  - **XP** (single shared table, no id-keyed rows) and **Faction's shared-thresholds sub-panel**
    (same shape — one ordered list, not per-row CRUD) — both explicitly excluded, not retrofitted
    (AF9/AF10).
  - **Server-side paging/filtering** — everything here is dev-authored data (dozens of rows per
    type, not thousands); revisit only if a type's row count genuinely grows into that range.

## Approach

### 1. Layout model (AF2 — ✅ decided with the user)
**Full-width grid + modal form.** The index becomes a real table with room for multiple sortable
columns; clicking a row (or "+ New") opens the CRUD form in a modal overlay on top of the grid. No
routing is introduced — still one view per left-nav tab in `app.ts`, just restructured inside it.

### 2. `ContentGrid<T>` — the generic index grid
A standalone component, roughly:
```ts
@Input() rows: T[] = [];
@Input() columns: GridColumn<T>[] = [];
@Input() searchFields: (keyof T)[] = [];
@Output() rowClick = new EventEmitter<T>();
```
```ts
interface GridColumn<T> {
  header: string;
  accessor: (row: T) => string | number;
  sortable?: boolean;   // default true
  kind?: 'text' | 'icon'; // 'icon' resolves+shows a small thumbnail (AF7)
}
```
Renders a `<table>`: a search box filtering rows client-side (case-insensitive substring match
across `searchFields`, AF6), clickable column headers toggling ascending/descending sort, and a row
click emitting the full row object. No pagination (AF6).

### 3. `CrudModal` — the shared form shell
A standalone component wrapping whatever form markup a type projects into it:
```ts
@Input() open = false;
@Input() title = '';
@Input() isNew = false;
@Input() error: string | null = null;
@Output() save = new EventEmitter<void>();
@Output() delete = new EventEmitter<void>();
@Output() close = new EventEmitter<void>();
```
Renders a backdrop + centered panel: `{{ title }}` heading, `<ng-content>` for the type's existing
per-section form markup (Identity/Stat Bonuses/etc. — unchanged from today), an inline error banner,
and a Save + (if `!isNew`) Delete button row — the same interaction each editor already has, just
factored out of 7 copies into one component + one shared stylesheet constant (mirrors the
`DOC_STYLES` precedent in `doc-styles.ts`).

### 4. Per-type column schema (AF5)
Each type's existing `*.service.ts` (which already holds the interface + `emptyX()` + the HTTP
service) gains one small exported constant, e.g.:
```ts
export const ITEM_GRID_COLUMNS: GridColumn<Item>[] = [
  { header: 'Icon', accessor: i => i.iconAddress ?? '', kind: 'icon' },
  { header: 'ID', accessor: i => i.itemId },
  { header: 'Name', accessor: i => i.displayName },
  { header: 'Equippable', accessor: i => (i.isEquippable ? 'Yes' : 'No') },
];
export const ITEM_SEARCH_FIELDS: (keyof Item)[] = ['itemId', 'displayName'];
```
Kept next to the type's data model rather than a new central registry file — matches the existing
one-file-per-type convention (interface + factory + service already live together).

### 5. Retrofit order (AF8)
One type at a time, each independently buildable/testable, not a big-bang rewrite:
1. **Item** — closest to "just fields," plus it already has the `iconAddress` field to prove the
   icon-column kind (AF7) against real data.
2. **Mob** — the largest form (6 sections), good stress test for the modal's scroll/height.
3. **Vendor**, **Loot** — nested child-row editors (ordered item-id list; three weighted lists);
   the child-row markup itself is untouched, only the outer index/detail chrome changes.
4. **Faction** — the retrofit also has to carve out the shared-thresholds sub-panel as its own
   small page (AF10), since it isn't a per-row entity.
5. **Conversation** — the most structurally complex (nested per-keyword quest-transaction
   sub-panel); do this last once the pattern is proven on six simpler cases.
6. **Spawn** — same shape as Vendor/Loot, quick once the pattern exists.

Suggested gut-check: after step 1 (Item), pause and confirm the modal interaction actually feels
right in practice before carrying it through the other six — cheap to back out of one type, more
friction to redo six.

### 6. Explicit exceptions (AF9, AF10)
- **XP** stays a standalone page — it's a single shared level curve with no id-keyed rows to
  select/filter (`PUT` replaces the whole array), so there's nothing for a grid to index. It can
  optionally pick up the shared button/error styling for visual consistency, not the grid or modal.
- **Faction's shared-thresholds panel** is the same shape as XP (one shared ordered list, not
  per-row CRUD) — gets its own small page/modal reusing `CrudModal`'s chrome, not shoehorned into
  the faction grid.

None. The .NET API and Postgres schema are untouched — this is a pure Angular-side rework (AF1).

`web/src/app/shared/admin-styles.ts` (shared CSS constant, mirrors `doc-styles.ts`).
**Modified:** `item-editor.ts`+`item.service.ts`, `mob-editor.ts`+`mob.service.ts`,

## Test plan
1. `ng build` clean after each retrofit step (7 separate checkpoints, not one at the end).
2. Per type: search box filters rows across the declared search fields; clicking a sortable column
   header toggles ascending/descending; "+ New" opens an empty modal; clicking a row opens it
   pre-filled; Save/Delete behave exactly as today (including the existing 409/validation error
   messages); cross-reference dropdowns that read a sibling service (Vendor↔Items, Loot↔Items,
   Conversation↔Factions+Items) still populate correctly from inside the modal.
3. Item's icon column (AF7): a row with a non-empty `iconAddress` renders *something* in the icon
   cell (even a placeholder/broken-image is fine at this stage — real sprite resolution is 5.9.1);
   an empty `iconAddress` renders no icon cleanly.
4. No Unity/DB/API regression expected (out of scope) — skip the Unity/API regression sweep for
   this item.

## Open decisions (recommendations first)
- **AF1 — API scope:** **Angular-only; no API/schema changes.** Every controller already exposes an
  identical `GET all / GET one / POST / PUT / DELETE` shape (verified against `ItemsController.cs`),
  so the generic grid can talk to any of them via each type's existing service with zero backend
  changes. Server-side query/paging support is a separate future item, only if warranted by data
  volume later.
- **AF2 — Layout model:** ✅ **DECIDED — full-width grid + modal form**, no new routing.
- **AF3 — Grid technology:** **hand-rolled** `ContentGrid` component, not a third-party grid library
  (ag-Grid/PrimeNG/Angular Material Table). Matches the app's existing low-dependency, hand-styled
  convention (every editor today is plain inline CSS, no UI kit); dataset sizes don't need a heavy
  grid library's virtualization/pagination features. *Alt considered: a real grid library — more
  built-in features (column resize, multi-sort) but a new dependency + learning curve for a benefit
  this app's data volume doesn't need.*
- **AF4 — Form genericity:** **not** a generic schema-driven form renderer — only the index/list side
  is generalized; each type's detail form keeps its existing bespoke markup, just moved inside the
  shared `CrudModal` shell. **Not a one-way door:** the same per-type schema object built here for
  grid columns could later drive a generic form renderer for the flatter types (Item, Mob's
  non-list sections) without redoing the grid work, if that ever seems worth it. *Alt considered: a
  full field-schema engine covering nested repeatable groups (Loot/Conversation) — bigger, more
  speculative build for unclear payoff across only ~8–11 types.*
- **AF5 — Schema location:** a small exported column-schema constant colocated in each type's
  existing `*.service.ts`, not a new central registry file.
- **AF6 — Search/filter/sort:** **client-side only**, over the already-fetched `getAll()` array; no
  pagination. Revisit if a type's row count ever grows into the hundreds+.
- **AF7 — Icon column:** the grid supports an optional `kind: 'icon'` column that resolves+shows a
  thumbnail when declared. Item already has an unused `iconAddress` field from 2.2 — this is a cheap
  add-on now, independent of 5.9.1 (which is about wiring icons into actual in-game UI, not authoring).
- **AF8 — Retrofit order:** Item → Mob → Vendor/Loot → Faction (+ its thresholds carve-out) →
  Conversation (most complex, last) → Spawn. Each step independently buildable/verifiable.
- **AF9 — XP exception:** stays a standalone page — no id-keyed rows, nothing to grid.
- **AF10 — Faction thresholds exception:** same shape as XP (one shared ordered list) — its own
  small page/modal, not part of the faction grid.

## Risks
- **Regression per retrofit** — 7 working editors get touched one at a time; mitigate by keeping
  each type's retrofit a separable, independently `ng build`-and-click-tested step rather than one
  big rewrite commit.
- **Modal UX is a genuine interaction change** from today's always-visible side-by-side layout —
  the AF8 gut-check after Item is there specifically to catch "this feels wrong" early, before
  carrying the pattern through six more types.
- **Cross-reference data fetching** (Vendor needs Items, Loot needs Items, Conversation needs
  Factions+Items) currently lives in each editor's own `ngOnInit`; moving the form markup into a
  projected modal doesn't change where that data comes from, but double-check each retrofit keeps
  fetching it (easy to accidentally drop when restructuring a component).

Ran a full Playwright pass across all 6: grid columns/rows correct for each, row-click opens the right

the per-row "✕" remove buttons, which also carry `class="danger"` — an early test assertion falsely

**One real debugging detour, resolved as a test-script bug, not an app bug:** the first attempts read
grid columns immediately after a nav click and got scrambled results (e.g. Spawns' tab briefly showing
Loot's columns) — traced to `ng serve`'s rebuild lag and, separately, to `waitForSelector('app-content-grid
table')` being satisfied instantly by the *previous* tab's still-present table during the Angular
`@switch` transition. Fixed by waiting on each editor's own `<h1>` toolbar text before reading anything.
A second false alarm: `[name]="'kw'+i"` (and the same pattern on Mob/Loot's other repeatable rows) never
renders an actual `name` DOM attribute — Angular's `NgModel` directive claims the `name` Input for its
own form-control bookkeeping, so the binding never reaches the raw element. This is pre-existing
behavior (identical in the original, un-retrofitted editor), not something introduced here; the fix was
in the *test*, switching to structural selectors (`.kwword`, `.txcol label:has-text(...)`) instead of
`input[name=...]`.
