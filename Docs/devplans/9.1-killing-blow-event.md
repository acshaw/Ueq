# 9.1 — Killing-blow notification event

**Status:** 🟡 Awaiting review.
**Roadmap item:** M9 → 9.1
**Pattern:** a new NPC script-event interface, symmetric to the existing `IOnDeath` — fired on the
**attacker's** dispatcher instead of the victim's, from the same single chokepoint `IOnDeath` already
fires from. No schema/DB/API/web changes — pure Unity, same shape as `IOnAggroLost`/`IOnTimer`.

---

## Goal & why now

Came up while scoping `EnemyAI` disengage options for a "full-moon zone-sweeper werewolf that terrorizes
the village" scenario. Of the three disengage options originally proposed (return to spawn / fall back to
previous wander-or-patrol state / trigger an event), the first two are **already built**:
`INpcMovementBehavior.GetReturnAnchor` (3.1.11/WR5) picks spawn-walk-home vs. reset-in-place per movement
type, and `Suspend()`/`Resume()` already hands control back to whatever wander/patrol behavior the mob has
once it reaches that anchor. Nothing new needed there.

The third — "trigger an event" — has a real extensibility point already (`IOnAggroLost`), but it doesn't
cover the concrete example that prompted this: *a tower guard kills the werewolf and should react to
having scored the kill* ("I must tell the queen of this werewolf spotting!"). `IOnAggroLost` fires on
every disengage cause alike (kill, target fled, disconnected, zoned) with no arguments — a listener can't
tell "I won" from "I gave up," let alone identify what was killed. The event that actually fits — "my
attack just scored a kill" — doesn't exist on the attacker's side at all today; `IOnDeath` only fires on
the **victim's** own dispatcher.

## Current state (grounding)

- `Health.TakeDamage(int amount, NetworkIdentity attacker)` (`Health.cs:78`) is the single chokepoint for
  all damage and death, regardless of source (auto-attack, abilities, riposte counters, environment). On
  the frame HP hits 0 it fires `OnDied?.Invoke(attacker)` — the attacker is known right here, once, at the
  exact moment of death.
- `NpcEventDispatcher.OnStartServer` subscribes to `_health.OnDied`; `OnHealthDied(NetworkIdentity
  attacker)` (`NpcEventDispatcher.cs:81`) fans out `IOnDeath` to every component on the **dying entity's
  own GameObject** (`_death` array, populated via `GetComponents<IOnDeath>()` in `Awake`). `attacker` is
  already passed through, just never used to look anything up on the attacker's side.
- No symmetric fan-out exists on the attacker. Player-vs-mob kill credit (XP/loot) goes through a
  completely separate path (`MobKillReward` reading `EnemyAI.ResolveCreditedGroup`, threat-based, group-
  aware) — not an event-interface listeners can hook into, and not relevant here (see KB3).
- `NpcEventLogger.cs` is the existing debug/test listener pattern — a `MonoBehaviour` implementing every
  NPC event interface, logging each to console, plus a `[ContextMenu]` damage-test button. Natural place
  to verify this lands correctly.

## Decisions (recommendations in **bold**)

**KB1 — Interface shape.** **`IOnKillingBlow { void OnKillingBlow(NetworkIdentity victim); }`** in
`NpcEvents.cs`, alongside the other event interfaces — mirrors `IOnDeath(NetworkIdentity attacker)`'s
shape (single identity argument), just naming the other party in the exchange.

**KB2 — Dispatch site.** **Extend `NpcEventDispatcher.OnHealthDied`**, right after the existing
`foreach (var l in _death) l.OnDeath(attacker);` line: resolve `attacker?.GetComponent<NpcEventDispatcher>()`
and, if found, call a new `DispatchKillingBlow(netIdentity)` on it (`netIdentity` here is the *victim's*
own identity — the dispatcher whose `Health` just died). Same call-site pattern as every other
`Dispatch*` method already on this class (`DispatchAggroLost`, `DispatchConversationStart`, …). Victim-side
`IOnDeath` fan-out keeps firing first, unchanged — this is a pure addition after it, not a reorder.

**KB3 — Scope: NPC/mob attackers only, not players.** **No special-casing needed — it falls out for
free.** Players have no `NpcEventDispatcher` component, so `attacker?.GetComponent<NpcEventDispatcher>()`
naturally returns null for a player kill and nothing fires. Player kill-credit (XP/loot via
`MobKillReward`) is untouched — this event is additive and only ever fires for an NPC/mob landing a kill
(on another mob, or on a hostile NPC per the existing NPC-to-NPC hostility perception in
`NpcEventDispatcher.PerceptionTick`). This matches the actual use case (a guard killing a werewolf) and
avoids scope creep into the player-credit system, which already works and is unrelated.

**KB4 — Don't also widen `IOnAggroLost`'s signature.** **Leave `IOnAggroLost` exactly as it is.** It would
be possible to fold "did I win" context into it instead of adding a new interface, but nothing has ever
needed extra context from it before, and changing a signature every existing/future listener must match is
a bigger footprint than adding one new interface. Revisit only if a second real need for aggro-lost context
shows up.

**KB5 — Single killing blow, not threat-based group credit.** **`victim` names only the literal attacker
passed into the fatal `TakeDamage` call** — i.e., whoever landed the finishing hit, same meaning `attacker`
already carries everywhere else in the codebase (`OnAttacked`, riposte damage, etc.). This is deliberately
*not* `EnemyAI.ResolveCreditedGroup`'s threat-weighted multi-attacker credit (that's a separate, XP/loot-
specific concept) — the use case is "the guard's own sword killed it," not "the guard's raid group gets
credit."

## Files (once approved)

**Modified:** `NpcEvents.cs` (new `IOnKillingBlow` interface), `NpcEventDispatcher.cs` (`_killingBlow`
array cached in `Awake`, new `DispatchKillingBlow(NetworkIdentity victim)` method, one new call in
`OnHealthDied`), `NpcEventLogger.cs` (implement `IOnKillingBlow` for console-log verification, same
pattern as its other nine interfaces).

**None:** no migration, no API, no Angular — this is a pure Unity C# event, same footprint class as
`IOnAggroLost`/`IOnTimer`.

## Test plan

1. Attach `NpcEventLogger` (extended per above) to a mob with an `EnemyAI`. Have it land a killing blow on
   another mob (or a hostile NPC, via the existing NPC-to-NPC hostility aggro) — confirm
   `[NpcEventLogger] <guard>: Killing blow on <victim>` logs exactly once, at the moment of the kill.
2. A player killing a mob — confirm nothing new fires (no `NpcEventDispatcher` on the player) and
   `MobKillReward`'s existing XP/loot path is unaffected (regression check).
3. Confirm the victim's own `IOnDeath` listeners (`Corpse`, `MobKillReward`, `EnemyAI.OnDeath`) still fire
   in their existing order — zero behavior change to the existing fan-out.
4. Null-attacker case (environmental damage, no `attacker` passed to `TakeDamage`) — confirm no exception,
   nothing fires (the `attacker?.` guard covers this).

## Risks

- Low — additive only, one new call site in an already-well-understood chokepoint (`OnHealthDied`), no
  change to any existing dispatch order or timing.
- `NpcEventDispatcher` keeps growing as a many-interfaces god-dispatcher (11 event types after this) — an
  existing, already-accepted shape (see the design doc's "NPC events are interface-based... discovered via
  `GetComponents`" decision), not a new risk this item introduces.

## Done when

An NPC/mob component can implement `IOnKillingBlow(NetworkIdentity victim)` and reliably fires exactly
once, on the **attacker's own** dispatcher, at the moment that attacker's hit drops the victim's health to
0 — verified via a guard-vs-mob kill logged through `NpcEventLogger`, with zero change to existing
victim-side death events or player kill-crediting.

## Note for future consumers

This item only builds the notification hook, not any concrete reaction. The werewolf/guard "announce it to
the queen" behavior — and anything else that reacts to a kill (rally nearby allies, drop a flag for a
future quest system, etc.) — is a separate `IOnKillingBlow`-implementing component, built when that content
actually needs it. Same treatment as 5.12's lunar-phase hook and 8.5's spawn trigger: build the seam now,
build the consumer later.
