# Devplan 2.3–2.7 — NPC content cluster (vendors, conversations, mobs, factions, loot)

**Roadmap items:** M2 → 2.3 vendors, 2.4 conversations, 2.5 mobs, 2.6 factions, 2.7 loot (re-sequenced cluster)
**Status:** 🟢 Approved (2026-06-24) — DC1–DC4 as recommended. Implementing vertical-by-vertical, starting with 2.3 vendors.
**Depends on:** 2.2 ✅ (items in DB — vendors/loot reference them) + the 2.1 rails (API/Angular/`ContentLoader`/`AssetResolver`)
**Goal of the cluster:** author **mobs, conversations, vendors, factions, and loot tables in the Angular app**, stored in Postgres, loaded by the server at startup — so a complete **web-authored vendor NPC (and then a full hostile mob)** can be tested in-game with no Unity ScriptableObject authoring.

## Build & test order (the important part)
Ordered to reach a **testable web-authored shopkeeper fastest**, then complete the rest:

1. **2.3 Vendor inventories** — `vendor_inventories` + items child; web editor; server load. (refs items ✅)
2. **2.4 Conversations** — `conversation_sets` + keywords (+ unlock lists); web editor; server load.
3. **2.5 Mobs (slice)** — `mobs` table (all `MobDefinition` fields) + web editor showing identity +
   conversation + vendor refs first; server load into a new `MobRegistry`; `SpawnPoint.mobId` resolves
   from it. **▶ TEST: author a talking shopkeeper end-to-end in the browser, spawn it, say "wares".**
4. **2.6 Factions** — `factions` (+ relations, race defaults, the shared threshold table); web editor;
   server load. Wire mob `faction_id` + conversation `required_faction`.
5. **2.7 Loot tables** — `loot_tables` (+ item/drop-count/coin-tier children); web editor; server load.
   Wire mob `loot_table_id`. **▶ TEST: a full hostile mob — aggro by faction, fight, loot on death.**

The mob editor (2.5) is authored once with all sections; the faction/loot dropdowns light up as 2.6/2.7
land. Each vertical is a copy of the 2.2 pattern.

## Client distribution — mostly NOT needed (simpler than items)
- **Factions, loot, conversations, vendor stock** are read on the **server only** (standing/aggro calc,
  loot roll on death, keyword matching, shop validation). **No catalog sync** — they never populate a
  client registry.
- **Vendor shop UI** is the one place a client sees vendor data: on shop-open the **server sends the
  stock list** (item ids + prices) to that client via the existing open-shop path (extend
  `VendorApplicator`/`VendorUI` to carry the list rather than read a local SO). Item *display* still
  comes from the client's item registry (2.2 catalog).
- **Mobs** reach clients only as **spawned `NetworkIdentity` objects** — name/level/health ride existing
  SyncVars (Nameplate/Health), not a catalog. The mob's **visual prefab** is referenced by a registered
  spawnable-prefab id/address (most mobs share the Enemy prefab; `MobApplicator` configures it), resolved
  on the server via `AssetResolver` — see risks.

## Schemas (grounded in the current ScriptableObjects)

### 2.3 `vendor_inventories` (+ `vendor_inventory_items`)
- `vendor_id TEXT PK`, `display_name TEXT`.
- child `vendor_inventory_items(vendor_id FK, item_id TEXT, sort_order INT)` — references `items`.

### 2.4 `conversation_sets` (+ `conversation_keywords` + `conversation_keyword_unlocks`)
- `set_id TEXT PK`, `display_name TEXT`.
- `conversation_keywords(id BIGSERIAL, set_id FK, keyword TEXT, mode INT, is_opener BOOL, ends_conversation
  BOOL, requires_unlock BOOL, response TEXT, required_faction_id TEXT NULL, required_standing TEXT NULL)`.
- `conversation_keyword_unlocks(keyword_id FK, unlocked_keyword TEXT)` — the `UnlocksKeywords` list.

### 2.5 `mobs` (flat; refs by id)
All `MobDefinition` fields: `mob_id TEXT PK`, `display_name`, `mob_level`, `prefab_address TEXT`
(spawnable-prefab id), combat (`max_health, attack_damage, attack_interval, attack_range`), movement
(`movement_type INT, move_speed, wander_radius, wander_pause_min/max`), AI (`perception_radius,
base_aggro_threat`), faction (`faction_id TEXT NULL, aggro_max_standing TEXT, warning_max_standing TEXT`),
`conversation_set_id TEXT NULL`, `loot_table_id TEXT NULL`, `xp_reward INT`, vendor
(`vendor_id TEXT NULL, vendor_open_keyword TEXT`).

### 2.6 `factions` (+ relations + race defaults + thresholds)
- `factions(faction_id TEXT PK, faction_name TEXT)`.
- `faction_relations(faction_id FK, other_faction_id FK, kind INT)` — kind = allied|hostile (the two lists).
- `faction_thresholds(name TEXT, min_score INT, sort_order INT)` — the EQ-style named bands (KOS…Ally);
  currently one shared table.
- `faction_race_defaults(race TEXT, faction_id FK, score INT)` — race-seeded starting standings.

### 2.7 `loot_tables` (+ children)
- `loot_tables(loot_table_id TEXT PK, display_name TEXT)`.
- `loot_table_items(loot_table_id FK, item_id TEXT, weight INT)`.
- `loot_table_drop_counts(loot_table_id FK, count INT, weight INT)`.
- `loot_table_coin_tiers(loot_table_id FK, min_copper INT, max_copper INT, weight INT)`.

Migrations `0010`–`0014` (one per vertical), created by the existing runner; existing SO assets seeded
idempotently in `DatabaseSeeder` so nothing breaks when each Resources path is retired.

## Per-vertical Unity work (the 2.2 pattern, repeated)
For each type: a plain `…Snapshot` + `…Repository` (Npgsql read), a `…Registry` (server, `Get(id)`),
a `ContentLoader` step, retire the `Resources`/SO load path, and an API entity/controller + Angular
editor. Server-only types skip the Mirror catalog sync. Cross-references resolve **by id** through the
registries (e.g. `MobRegistry` resolves `faction_id`→`FactionRegistry.Get`).

**Spawn (2.5):** `SpawnPoint`/`SpawnTable` gain a `mobId` string; on spawn, resolve the `MobDefinition`
from `MobRegistry`, instantiate the referenced spawnable prefab, and `MobApplicator.SetDefinition` as today.

## API / Angular
- **API:** one EF entity + controller per top-level type (children mapped as owned/related collections or
  separate endpoints). Mapping-only, no EF Migrations (D4 from 2.1). Keyed by the string id.
- **Angular:** one editor screen per type, plus a simple left-nav to switch between Items / Vendors /
  Conversations / Mobs / Factions / Loot. Editors with children (conversations, loot, factions) get
  add/remove rows. Mob editor uses dropdowns populated from the other content endpoints (faction,
  conversation set, vendor, loot table, item).

## Test plan (incremental)
- After **2.5 slice:** author vendor + conversation + mob (vendor) in the browser → `SpawnPoint` by mob
  id → in-game: target/hail, say "wares", shop opens, buy/sell works (items resolve via 2.2 registry).
- After **2.7:** author a faction, a hostile mob with loot → it aggros by standing, fights, drops loot on
  death; faction standing changes on kill.
- Each vertical: API CRUD (curl) + Angular build + server `[Content] Loaded N …` log + existing SO data
  seeded.

## Open decisions (recommendations)
- **DC1 — one cluster devplan vs five:** this single devplan covers 2.3–2.7 (they're one pattern). Each
  roadmap item links here. Alt: split per item (more review overhead for near-identical plans).
- **DC2 — mob prefab binding:** reference a **registered spawnable prefab by id** (small fixed set; most
  mobs share the Enemy prefab, configured by data). Alt: resolve arbitrary prefabs via Addressables +
  register as spawnable at runtime (heavier; defer until a mob actually needs a unique mesh).
- **DC3 — vendor stock to client:** server **pushes the stock list on shop-open** (keeps vendor data
  server-only). Alt: sync a vendor catalog to clients (unnecessary — shop is a momentary view).
- **DC4 — faction thresholds:** keep the **single shared threshold table** (current behavior) as one DB
  table, not per-faction. Alt: per-faction thresholds (no current need).

## Risks
- **Scope** — five verticals + cross-references; biggest M2 chunk. Mitigate by the slice-first order so a
  testable shopkeeper lands at step 3, before factions/loot.
- **Mob prefab / Mirror spawnable** — Mirror spawns by registered assetId; a DB `prefab_address` must map
  to a registered spawnable prefab. Fine while mobs share the Enemy prefab; unique meshes need runtime
  registration (DC2, deferred).
- **Cross-reference integrity** — a mob referencing a missing faction/loot/vendor/conversation id must
  degrade gracefully (null ref = no faction/loot/etc., logged) rather than fail the load.
- **Retiring SO paths** — each type's existing `Resources`/SO load is removed only after its assets are
  seeded into the DB; verify the seeded data matches the SO fields exactly.

## Verification log — 2026-06-26 (✅ shopkeeper passed; 2.3–2.5 verified)

In-editor end-to-end test **passed**: web-authored Merchant (prefab `Enemy`, conversation `GuardKeywords`,
vendor `Merchant`) spawned via a `SpawnPoint` with `mobId = Merchant`; in game, targeting + saying "wares"
opened a shop showing the DB-backed **Tunic**. This validates the full cluster in one path — **2.2 client
item-sync** (the Tunic resolves on the client via the catalog sync), **2.3 vendors** (stock pushed on open),
**2.4 conversations** (keyword heard, response delivered), and **2.5 mobs** (`MobRegistry` + `SpawnPoint.mobId`).

Two real fixes were needed to get there (both committed to the seed path so they don't recur):

1. **`Enemy` prefab lacked `VendorApplicator`.** The DB design has most mobs (incl. the Merchant) share the
   `Enemy` prefab and differ only by `vendorId`, but `Tools/Patch Enemy Prefab` didn't add the vendor
   component — so "wares" delivered the conversation line but no shop opened. Fix: added `VendorApplicator`
   (+ ensured `NpcConversation`) to the patch list in `SceneSetup.PatchEnemyPrefab`. It's inert on
   non-vendor mobs (acts only on the `wares` keyword and reads its `vendorId` from the mob definition).

2. **Seeded `wares` keyword had `ends_conversation = true`.** Sharp edge in `NpcConversation.HandleMatch`:
   it dispatches `IOnConversationKeyword` (vendor opens shop) and then, if `EndsConversation`, immediately
   runs `EndConversation` → `DispatchConversationEnd` (vendor **closes** the shop) + says the `closingLine`
   ("Farewell."). Net: shop opened and closed in the same call; the player saw "What would you like?" then
   "Farewell." with no window. **Rule: a vendor-open keyword must have `ends_conversation = false`.** Fixed
   the live `GuardKeywords` row (UPDATE) and the `DatabaseSeeder.SeedConversations` default. *(Future hint:
   the web Conversation Editor could warn when a keyword both opens a vendor and ends the conversation.)*

Status: **2.2, 2.3, 2.4, 2.5 ✅** (marked in `roadmap.md`). Next: 2.6 factions — wires `FactionRegistry`
(currently an empty stub) so the mob `faction_id` + conversation `required_faction` gates go live.
