# 5.10 — Dedicated Server Build Spike

Status: ✅ Done (2026-07-25). DS1–DS5 all confirmed working end to end: a real headless server
and a real standalone client, two separate processes, full register→login→spawn→target→combat→
loot loop. Two independent root causes were found and fixed along the way (the additive-scene
crash → prefab rework; the HUD-binding silent failure → self-heal fallback). See Findings below
for the full diagnostic trail — this was a long spike, worth reading before touching the client
screen-flow/HUD code again.

## Review log (2026-07-23)

Confirmed: DS2 runs the full ranked protocol in order (not skipping straight to disabling
Norton); DS5's "real client" bar is a loopback (`127.0.0.1`) test between two separately-built
Standalone processes, not a second physical LAN device; DS3 implemented immediately rather than
waiting on DS2 (it turned out to need no new code at all — see below).

## Goal

Prove that a real standalone/dedicated Unity build of Ueq can boot headless, connect to
Postgres, and accept real (non-Editor) client connections — the one open question sitting in
front of **6.2** (dedicated server + hosting), **6.4** (build pipeline), and **6.5** (load
testing). This is a de-risking spike, not a shippable feature. Minimum bar: a
`-batchmode -nographics` server process boots and stays up, a separately-built (non-Editor,
non-MPPM) client connects to it over the network, and register→login→spawn→move→fight→camp
works end to end. Production hardening (process supervision, log rotation, AWS deployment) is
explicitly 6.2's job, not this spike's.

## Grounding (read before designing)

- **The 2026-06-21 crash, read from the actual surviving `Player.log`**
  (`C:\Users\acsha\AppData\LocalLow\DefaultCompany\Ueq\Player.log`): the build ran from
  `C:/Users/acsha/source/Ueq Builds/` (a sibling folder next to the repo, **not** under
  OneDrive — checked directly: `C:\Users\acsha\source` is a plain directory, not a reparse
  point, ruling out the "synced folder mangling build output" suspect noted at the time).
  Sequence: `The file '.../Ueq_Data/level0' is corrupted! Remove it and launch unity again!` →
  `[Position out of bounds!]` → `Crash!!!`, immediately after Direct3D/input init, before any
  of our own code runs. Engine version at crash time was **6000.4.0f1**; the project has since
  moved to **6000.4.12f1** (12 point-releases later — worth noting in case whatever caused this
  was already an engine bug that's since been fixed, though not something to bank on without
  retesting).
- **A real, concrete lead the 2026-06-21 session didn't have: `Player.log`'s own loaded-module
  list shows `C:\Program Files\Norton\Suite\aswhook.dll` injected into the crashing player
  process itself.** That's Norton's Avast-derived real-time-protection hook, actively attached
  to this exact executable. Antivirus real-time scanning intercepting/locking files mid-write
  during a Unity build producing a corrupted data file is a well-known class of issue — this is
  the strongest, cheapest-to-test lead, not a guess pulled from nowhere.
- **No headless autostart path exists today — this is required new scope, not just a testing
  gap.** `UIScreenManager.EnsureExists()` (`Assets/Scripts/UI/Screens/UIScreenManager.cs:29`)
  short-circuits entirely under `Application.isBatchMode`, and every existing way to start
  serving (`LoginUI.HostAsDev`/`Server Only`, `MenuPanels` → `UIScreenManager.StartServerOnly()`)
  is a UI button click. A batchmode process has no window and nobody to click it — without new
  code the headless build would sit there doing nothing forever.
- **`DatabaseConfig.Resolve()` already anticipates exactly this case.** Its doc comment says the
  env-var resolution order exists for "a standalone server (AWS later)," ahead of the
  `db.config.json` file fallback that only makes sense for the Editor. This spike is the first
  real exercise of that path from an actual OS process, not just Editor Play mode.
- **Scripting backend**: `ProjectSettings.asset` has no per-platform `scriptingBackend` override
  recorded, which normally means Standalone defaults to Mono, not IL2CPP — worth a quick
  in-editor confirmation (Player Settings → Other Settings) before building, since IL2CPP's
  AOT restrictions were exactly why EF/ORM got rejected for Npgsql back in 1.1 (`roadmap.md`
  M1) — Mono avoids that risk entirely for this spike.
- **This is local-only** — no AWS involvement. Headless server build ↔ the same Dockerized
  Postgres already used for local dev ↔ a second local client build, all on this machine.

## Decisions

**DS1 — Build target: Standalone Windows (`-batchmode -nographics`) vs Unity's dedicated
"Dedicated Server" build target module.**
Recommend **Standalone Windows + `-batchmode -nographics`** for this spike — it's the roadmap's
own stated scope, needs no new Unity Hub module install, and is the direct repro path for the
existing crash (same target that crashed before). Flag Unity's purpose-built "Dedicated Server"
target (strips the graphics/audio modules entirely, smaller/cleaner binary, the more correct
long-term choice) as a good upgrade to make **in 6.2** once this spike proves a build can work
at all — installing a new Hub module and re-validating from scratch isn't worth doing twice.

**DS2 — Root-cause the `level0` corruption before building anything new on top of it.**
A corrupted build makes every later step in this spike unfalsifiable, so this goes first.
Ranked test protocol (cheapest / highest-likelihood first), stop as soon as one produces a
clean build:
  1. **Delete** the old `Ueq Builds` folder entirely (don't just overwrite) before rebuilding —
     rules out stale files from the older 6000.4.0f1 point-release mixing with a fresh build.
  2. Add a Norton Suite / Auto-Protect exclusion for the build output folder (or the whole
     `C:\Users\acsha\source` tree) and rebuild.
  3. If still corrupt: temporarily disable Norton real-time protection entirely for one
     rebuild — stronger isolation test than an exclusion rule alone.
  4. If still corrupt: build to a short, space-free path (e.g. `C:\Builds\Ueq`) to cheaply rule
     out the `Ueq Builds` path/space itself.
  5. If still corrupt: check the Editor's own `Editor.log` for silent warnings *during* the
     build step (not just `Player.log`, which only shows the runtime crash) — a build that
     reports success but writes a corrupt data file would be unusual enough to want the
     build-time evidence, not just the failure symptom.
If all five fail, this is a genuine Unity 6000.4 bug worth searching Unity's issue tracker for,
or isolating further by trying IL2CPP as a structurally different build path — not guessing
past this list blind.

**DS3 — Headless server autostart.** ✅ Resolved — no new logic needed.
Mirror's own `NetworkManager.Start()` (`Assets/Mirror/Core/NetworkManager.cs:224`) already has
this exact mechanism built in: a `headlessStartMode` field (`DoNothing` / `AutoStartServer` /
`AutoStartClient`, default `DoNothing`) checked against `Utils.IsHeadless()` — which is `true`
precisely when `SystemInfo.graphicsDeviceType == GraphicsDeviceType.Null`, i.e. exactly the
condition `-batchmode -nographics` produces (or unconditionally under a `UNITY_SERVER` define,
relevant if 6.2 later adopts the Dedicated Server build target from DS1). `editorAutoStart`
gates whether it also fires inside the Editor — left `false` so normal in-editor testing
(Host/Server Only buttons) is untouched. **Implemented**: `SceneSetup.CreateNetworkManager()`
now sets `headlessStartMode = AutoStartServer` on the NetworkManager GameObject it builds,
alongside the existing `authenticator`/`autoCreatePlayer`/`playerPrefab` wiring — so it survives
every `Tools/Setup All` re-run instead of being a one-off scene hand-edit. Needs
`Tools/Setup All` re-run + scene save to take effect on the current `SampleScene`.

**DS4 — Database connectivity for the built process.**
`DatabaseConfig.Resolve()`'s env-var path (`UEQ_DB_CONNSTRING` or the individual
`UEQ_DB_HOST/PORT/NAME/USER/PASSWORD`) is exactly the right one for a standalone server — no
repo-relative `db.config.json` dependency once shipped. Launch the built `.exe` with those env
vars set to point at the local Dockerized Postgres, confirming the path actually works from a
real OS process rather than just reading correct-looking code.

**DS5 — Verifying a *real* client connection, not Editor Play mode or MPPM.**
MPPM virtual players still run inside the Editor process — they don't prove a genuine
standalone client binary can reach a genuine standalone server binary over the network. Build a
second Standalone Windows **client** (same build, launched normally without batchmode flags)
and connect it to the headless server's `127.0.0.1:<port>` (or LAN IP) from a separate process.
Confirm: connects, authenticates (1.4's `AccountAuthenticator`), reaches character select,
creates/spawns, moves, fights a mob (exercises a DB write), camps, and relogs.

**DS6 — Explicit scope boundary — what this spike does NOT solve.**
No process supervision / auto-restart-on-crash, no log rotation, zero AWS involvement. Also
deliberately not switching to the Dedicated Server build target (DS1) or IL2CPP (unless DS2's
protocol forces it to root-cause the crash) — both are real options but not needed to answer
this spike's one question: *does a real build boot and accept real connections at all.*

## Approach

1. **DS2** — clean the crash. A corrupted build blocks everything downstream. *(Pending —
   next step.)*
2. **DS3** ✅ done (config-only, see above). **DS4** — confirm the env-var DB path when
   launching the built server.
3. Build the headless server. Launch with the Postgres env vars set,
   `-batchmode -nographics -logFile server.log` (batchmode has no visible console — `-logFile`
   is required or the run is silent regardless of success/failure). Watch the log file for the
   existing `[DB] Connected...` / `[Server]` / content-load lines that already print today.
4. Build a second Standalone client (normal windowed launch). Connect to the headless server
   from outside the Editor. Walk the full DS5 checklist.
5. Log findings + a go/no-go verdict in this devplan, same shape as the 2.0 zone-architecture
   spike (`docs/devplans/2.0-zone-architecture-spike.md`).

## Test plan

- Clean rebuild produces a non-corrupt `level0` per DS2's protocol (stop at whichever step
  fixes it; record which one it was).
- `Ueq.exe -batchmode -nographics -logFile server.log` (env vars set) boots, connects to
  Postgres, logs content-load + zone-init lines, and **stays running** — doesn't exit or crash
  on its own.
- A second, separately-built Standalone client (normal window, not batchmode) connects over
  `127.0.0.1` (or a LAN IP) to the headless server: register → login → character create/select
  → spawn → move → basic combat (kill a mob, exercising a DB write) → camp → relog.
- Server process survives the full client session including a disconnect/reconnect.

## Risks / open questions

- If DS2's five-step protocol doesn't resolve the corruption, this spike is blocked on a
  genuine unresolved engine/environment bug — surface that early rather than sinking more time
  into DS3–DS5 against a build that can't be trusted.
- Headless builds are silent without `-logFile`; the existing `OnStartServer` try/catch that
  calls `StopServer()` on DB-down would otherwise fail with no visible symptom beyond "nothing
  happens" — call this out explicitly when walking the user through the test steps so a DB-down
  failure isn't mistaken for a build failure.
- First LAN-external client connection may trigger a Windows Firewall prompt for KCP/UDP — an
  environment step, not a code issue, but worth flagging so it isn't mistaken for one.

## Findings (filled in after running the spike)

**DS2/DS3/DS4 (server) — CONFIRMED working end to end, 2026-07-24.** A fresh headless server
build via `Tools/Build/Build Headless Server (Standalone)` to `C:\Builds\Ueq\Server`
(short/space-free, wiped-before-build) booted clean under `-batchmode -nographics
-logFile server.log` with `UEQ_DB_HOST/PORT/NAME/USER/PASSWORD` env vars pointed at the local
Docker Postgres. `server.log` shows: `Server listening on port 7777` →
`[DB] Connected to tcp://localhost:5432/ueq.` → `[DB] Schema up to date (no pending migrations).`
→ full content load (11 types) → `[DB] PersistenceService started`. Mirror's built-in
`headlessStartMode = AutoStartServer` (DS3) fired with zero manual intervention. Process stayed
up. **Note: this initially looked like it also resolved DS2's crash-repro concern for the*client*
— it did not** (see below); the headless server never loads the second (`UI`) scene at all
(`UIManager.Awake` returns early under `Application.isBatchMode`), so its clean boot said nothing
about the client-only crash that follows.

**DS5 (client) — long diagnostic chain, 2026-07-25, ending in a structural fix.** The Standalone
Client build (same fresh-build discipline as the server) crashed immediately on every launch with
the *exact* 2026-06-21 signature: `The file '.../levelN' is corrupted! Remove it and launch unity
again!` → `[Position out of bounds!]` → `Crash!!!`, on a completely fresh build. Systematically
eliminated candidates, each a real test:
  - `-force-d3d11` vs. default D3D12 — identical crash. Not graphics-API-specific.
  - Norton Auto-Protect folder exclusion for the build output — no change.
  - Norton fully disabled — no change. AV ruled out entirely.
  - `BuildOptions.CleanBuildCache` — no change. (Found via `Editor.log` that a prior build had
    silently reused stale `Library/PlayerDataCache`/`Library/Bee` incremental data — "player data
    was not rebuilt" — a real, separate gotcha worth knowing about even though it wasn't the cause
    here; `ServerBuildTools.cs`'s two build methods now always pass `CleanBuildCache`.)
  - Removing `UI.unity` from the enabled scene list — **booted clean** (no HUD, expected). Isolated
    the corruption to specifically the scene at build index 1 (`UI.unity`, level1).
  - Regenerating `UI.unity` from scratch via `Tools/Build UI Scene` — identical crash. Ruled out
    stale/corrupted scene *content* (the file itself, freshly rewritten, still crashed).
  - Deferring `UIManager`'s additive scene load by one frame (a boot-order-race theory) — identical
    crash. Not a timing race in our own `Awake()` call.
  - Swapping the loaded scene name to `"thornwood"` instead of `"UI"` — **booted clean**. Proved
    additive scene loading itself is *not* broken in a real build on this machine — important,
    since the zone system depends on the same `SceneManager.LoadSceneAsync(..., Additive)`
    mechanism and had never actually been exercised outside the Editor/MPPM before this spike.
  - **Bisected `UI.unity`'s 7 panel-builder functions** (Chat/HUDFrames/Inventory/Equipment/
    Vendor/Loot/Hotbar) via binary search across 3 rebuild rounds: first 4 alone (~clean) →
    +Vendor+Loot, 6 of 7 (clean) → Hotbar alone (clean) — yet all 7 together crashed every time.
    Inspected the regenerated scene's raw YAML directly: no missing-script markers, correct
    `InputSystemUIInputModule` (not the legacy one), all 8 of `HotbarUI.slots[]`'s fileID
    references resolved cleanly to exactly one object each. The `SerializedObject`/`arraySize`
    array-wiring technique used for `HotbarUI.slots` is used identically (and successfully) by
    `InventoryUI.slotTiles`, ruling that pattern out as the differentiator.
  - Concluded a **cumulative-complexity effect** (~700 objects clean, ~855 crashes) rather than any
    one panel's fault, and split the HUD across two additively-loaded scenes (`UI.unity` +
    `UIHotbar.unity`) along that exact proven-clean line.
  - **That still crashed — but on a completely different scene (`grukmars_deep`, now at build
    index 4).** This is the decisive finding: the corruption isn't tied to *any specific scene's
    identity or content* — just to *some* additively-loaded scene at *some* position once total
    cumulative build size crosses a threshold. A genuine engine/environment-level bug, not
    something fixable by rearranging our own content.
  - `WebSearch` turned up multiple real historical Unity Issue Tracker reports of the identical
    "Position out of bounds" native crash symptom across Unity versions, reinforcing this read.
    Also checked and ruled out two other candidates that search surfaced: disk space (330GB free)
    and Addressables' active player-data-builder (`m_ActivePlayerDataBuilderIndex: 2` correctly
    resolves to `BuildScriptPackedMode`, the real Player-build script, not the play-mode-only one).

**Fix shipped:** reworked the UI layer from an additively-loaded scene into a **prefab**.
`SceneSetup.BuildUIScene()` now builds all 7 panels into one temp scene, reparents every root
under a single `HudRoot` GameObject (Canvases order themselves via `sortingOrder`, independent of
hierarchy, so this is visually inert), and saves it via `PrefabUtility.SaveAsPrefabAsset` to
`Assets/Resources/UI/HudRoot.prefab` — and cleans up/deletes the old `UI.unity`/`UIHotbar.unity`
scenes and their Build Settings entries. `UIManager.cs` now does
`Resources.Load<GameObject>("UI/HudRoot")` + `Instantiate()` + `DontDestroyOnLoad`, instead of
`SceneManager.LoadSceneAsync` — sidestepping the buggy mechanism entirely, and matching how every
other asset type in this project already loads successfully (items/abilities/mob & character
bodies via `Resources.Load`+`Instantiate`, none of which have ever hit this bug).

**Status: fix CONFIRMED working.** The prefab-based client boots clean and shows the full HUD. Two
further, separate bugs surfaced once the client was actually usable — both root-caused and fixed
in the same session:

**Bug 2 — Hotbar slots silently lost their script reference (`m_Script: {fileID: 0}`), every
build, reproducibly.** Initially suspected as a one-off recompile race (it wasn't — regenerating
the prefab cleanly didn't fix it). Root cause: `HotbarUI.cs` declared **two** MonoBehaviour classes
in one file — `HotbarUI` (matches the filename) and `HotbarSlotUI` (doesn't). Unity can lose a
non-filename-matching class's script reference during certain serialization operations (here,
`PrefabUtility.SaveAsPrefabAsset`) — confirmed by direct comparison against `InventorySlotUI`
(its own file, matching its class name), which never had the problem despite using an identical
`AddComponent`+wiring pattern. **Fix:** extracted `HotbarSlotUI` into its own `HotbarSlotUI.cs`.
Confirmed fixed — 0 "missing script" warnings on the next build, versus 8 (one per slot) before.

**Bug 3 — `LocalPlayer.Spawned` fired with 0 subscribers, silently breaking PlayerFrame,
TargetFrame, HotbarUI's ability display, EquipmentUI, InventoryUI, and VendorUI all at once** (each
subscribes to the same static event from its own `OnEnable`). Diagnosed via targeted temporary
logging (since removed) rather than guessing: confirmed `NetworkedPlayer.OnStartLocalPlayer()` DOES
fire correctly and DOES call `LocalPlayer.Set(this)` — but `PlayerFrame.OnEnable()`'s earlier
subscription was gone by the time `Spawned` invoked, even though it clearly ran once at HUD boot.
The exact mechanism (why `OnDisable` must have fired in between) was not fully pinned down — no
other code anywhere references these panels by name, ruling out an obvious explicit toggle: this
is genuinely the first time a real standalone client+server pair (not Editor/Host/MPPM) has
exercised this exact binding path, and something about that boot sequence causes a disable/enable
(or a missed-subscription) blip the in-Editor testing never surfaced. **Fix:** rather than keep
chasing the exact trigger, added a self-healing fallback to all six affected panels' `Update()` —
each checks `LocalPlayer.Current` and (re-)binds itself if not yet bound, independent of whether the
one-shot event fired correctly. This guarantees correct binding within one frame of a local player
existing, regardless of the underlying cause. **Confirmed fixed** — user report: "ui issues solved.
everything works as expected."

**Also found and fixed along the way:** the headless server and standalone client must be rebuilt
*together* any time either changes — even a client-only-seeming change (regenerating the UI
prefab, running `Tools/Setup All`) shifts `SampleScene`'s Mirror scene-object hashing enough to
desync an old server, producing `Spawn scene object not found ... hierarchy gets out of sync`.
Standing rule going forward: always rebuild both, not just whichever side changed.

DS5's full checklist (register → login → character create/select → spawn → move → target → basic
combat → loot → camp → relog) is now confirmed working end to end against two genuinely separate,
independently-built processes.
