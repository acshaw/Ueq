# 2.7.3 — World Placement Sync (spawn/patrol/wander ↔ DB, bidirectional)

**Status:** ✅ Done — user confirmed working end-to-end 2026-08-22 (sync → materialize-on-restart → web
Placement Editor edit → config refresh on restart → delete semantics all behaving as designed). See the
implementation log at the bottom.
**Roadmap item:** M2 → 2.7.3 (inserted after 2.7.2/2.7.1 — discovered organically while placing the initial
wolf spawns for West Reach; extends the M2 "DB-backed content" principle to *where things physically are*,
not just *what they are*)
**Pattern:** new. Every other M2 content type is authored in a web form and read by the server. This one
inverts that: the authoring surface stays the **Unity Scene view** (gizmos, terrain-snap, navmesh sampling —
none of that is worth rebuilding as a web form), and the DB becomes a **synced mirror** of what's physically
placed, round-trippable in both directions.

---

## Goal & why now

`SpawnTable` (what spawns) has been DB-backed since 2.7.2 — editing weights/timers/mobs takes effect on a
server restart, no rebuild. But *where a spawn point exists* — its `SpawnPoint`/`PatrolRoute`/`WanderRegion`
GameObjects — still lives baked into the zone's scene file. Adding a new camp (e.g. the West Reach wolf
spawns currently being placed) still means: place it in the Editor → save the scene → rebuild the dedicated
server → redeploy. That's the gap this closes.

The user's proposed shape (confirmed, not just my recommendation): **keep placing things in the Editor
exactly as today** — same gizmos, same terrain/navmesh snapping, same `Tools/Zones/Place Encounter…` /
`New Patrol Route` / `New Wander Region` tools. Add a tool that **exports** a placed object's config into a
DB row. At zone-load time, the server takes DB rows for that zone and **materializes** (instantiates) any
that aren't already present in the currently-running build's scene — so a restart alone picks up anything
authored after the last rebuild. And, symmetrically, an **import** tool pulls DB rows (including ones
created by hand, e.g. a script against the DB) into the open scene as real, editable GameObjects, so nothing
authored outside Unity is a dead end — it can always be pulled in, tweaked visually, and pushed back out.

## Non-goals

- **`ZonePortal`/`ZoneEntry` are out of scope.** They're zone topology (rarely change, tied to the zone's own
  scene design), not population content. The interface below is written so they *could* adopt this later
  with no changes to the sync/import/materialize machinery — just implement `IWorldPlacement` — but nothing
  about this devplan requires or assumes that.
- **Not a general "everything in the scene is DB-backed" system.** Only components that explicitly implement
  the new interface participate. Terrain, static dressing, buildings, etc. are untouched.
- **Position is not web-editable.** See WP7 below — the web editor shows coordinates for reference but only
  Unity edits placement geometry. Editing "what spawns here" / "how big is the radius" remotely, without
  reopening Unity, *is* in scope (same value the 2.7.2 Spawn Editor already provides for table contents).

## Design overview

```
DEV (Unity Editor)                          DB (Postgres)                    SERVER (any build, incl. shipped)
──────────────────                          ─────────────                    ─────────────────────────────────
Place/tweak SpawnPoint,                                                      ZoneManager loads zone scene
PatrolRoute, WanderRegion                                                            │
in the scene, as today          ──export──▶  world_placements                        ▼
        ▲                                    (placement_id, zone_id,          Index IWorldPlacement objects
        │                                     marker_type, data JSONB)        already baked into THIS scene
        └──────────import──────────────────────────┘  │                              │
   (pulls a DB row into the                            └──────────materialize────────▶
    scene as a real, editable                             (ephemeral — never saved     Anything in the DB for
    GameObject; upserts by                                  to a scene asset)          this zone but NOT already
    placement_id, never dupes)                                                         present gets instantiated
```

Both `export` and `materialize`/`import` funnel through the **same two methods** on every participating
component — `CapturePlacementData()` and `ApplyPlacementData()` — so there is exactly one definition of
"what a SpawnPoint's data means," used identically whether the destination is a DB row, a live server
instance, or a persisted Editor scene object.

## Data model

### `IWorldPlacement` (new interface, `Assets/Scripts/Placement/IWorldPlacement.cs`)

```csharp
public interface IWorldPlacement
{
    string PlacementId { get; }                 // GUID, assigned once, stable for the object's lifetime
    string MarkerType  { get; }                 // "SpawnPoint" | "PatrolRoute" | "WanderRegion" | ...
    JObject CapturePlacementData();              // this object's current config + transform → JSON
    void    ApplyPlacementData(JObject data);    // inverse — configure this object from JSON
}

// Only SpawnPoint implements this today — it references other placements by id.
public interface IReferencesOtherPlacements
{
    void ResolveReferences(IReadOnlyDictionary<string, GameObject> byPlacementId);
}
```

`PlacementId` is a `[SerializeField] string`, auto-generated via `OnValidate()` the moment the component is
added in the Editor (standard "assign a GUID once, never regenerate" idiom — same shape as how prefab/asset
GUIDs work) and is therefore baked into the scene file from the start. It is the sole key used everywhere
below — never the GameObject name, never position (position can legitimately change).

### Table — `world_placements`

```sql
CREATE TABLE IF NOT EXISTS world_placements (
    placement_id UUID PRIMARY KEY,
    zone_id      TEXT NOT NULL,
    marker_type  TEXT NOT NULL,
    pos_x        REAL,
    pos_y        REAL,
    pos_z        REAL,
    rot_y        REAL NOT NULL DEFAULT 0,
    data         JSONB NOT NULL DEFAULT '{}',
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_world_placements_zone ON world_placements(zone_id);
```

One generic table for every marker type, not one table per type (WP1 below). `pos_x/y/z`/`rot_y` are pulled
out as real columns (cheap, and useful for the web list view / a future "show on a map" tool); everything
type-specific — `spawnTableId`, `activationRadius`, a `PatrolRoute`'s ordered points, a `WanderRegion`'s
shape/size — lives in `data`. A brand-new marker type invented later needs **zero schema changes** — it just
defines its own JSON shape.

### `CapturePlacementData()` shapes

**SpawnPoint:**
```json
{
  "spawnTableId": "West Reach Wolf Table",
  "mobId": "",
  "activationRadius": 50.0,
  "snapToGround": true,
  "navSampleRadius": 8.0,
  "freeRange": false,
  "freeRangeRadius": 400.0,
  "patrolRoutePlacementId": null,
  "wanderRegionPlacementId": "b3f1...-guid"
}
```
`groundMask` is deliberately **not** round-tripped — every existing spawn point uses the default (`~0`,
"everything"); it's an environment/layer concern, not spawn content, and can stay a local Inspector default.

**PatrolRoute:**
```json
{
  "loop": true,
  "pausePerPoint": 2.0,
  "points": [ {"x":10.2,"y":4.0,"z":-3.1}, {"x":18.7,"y":4.2,"z":2.0}, ... ]
}
```
(`pos_x/y/z` on the row is the route object's own anchor position — not otherwise meaningful, useful only as
a map-pin reference; the actual waypoints are the ordered `points` array, world-space, matching
`PatrolRoute.Points` today.)

**WanderRegion:**
```json
{ "shape": "Box", "boxSize": {"x":30,"y":4,"z":30}, "sphereRadius": 15.0, "sampleRadius": 4.0 }
```

## Stage A — Export + runtime materialize (delivers "restart only" for new spawns)

This is the piece that directly answers the original ask; B and C build on it.

1. **`Tools/Zones/Sync Placements to Database`** (new, alongside the existing `EncounterTools.cs` menu
   items) — walks the *currently open* scene(s), finds every `IWorldPlacement`, assigns a `PlacementId` if
   missing (marks the scene dirty), resolves `zoneId` from `ZoneCatalog` by matching `gameObject.scene.name`
   → `ZoneDefinition.sceneName` (no new authored field — the scene *is* the zone), calls
   `CapturePlacementData()`, and **upserts each row directly into Postgres via `Database.OpenEditorConnection()`**
   — always, no confirmation needed (WP4). **Correction from the original draft:** no Editor tool in this
   project talks to the ASP.NET API over HTTP (`ContentExportImport.cs`, the migration runner, and the
   seeder all write straight to Postgres via Npgsql) — the sync/import tools follow that same convention
   rather than requiring the API process to be running locally. It then reads the DB rows already stored for
   that `zoneId` and diffs them against the `PlacementId`s just found in the scene; anything in the DB but
   not in the scene is shown in a confirm dialog ("these N DB placements have no matching scene object —
   delete them?") and only removed (a direct `DELETE`) if confirmed — never automatically. Reports counts
   (created / updated / deleted / skipped-on-decline).
2. **API — `WorldPlacementsController`** (`api/world-placements`): `GET ?zoneId=`, `PUT {placementId}`
   (upsert), `DELETE {placementId}`. This is **only for the Stage C web editor** — the Unity-side sync/import
   tools never call it, per the correction above. Same mapping-only-EF shape as `SpawnTablesController`.
3. **`WorldPlacementRepository`/`WorldPlacementRegistry`** (server-only, mirrors `SpawnTableRegistry`) —
   loaded once in `ContentLoader.LoadAll()` into `Dictionary<zoneId, List<WorldPlacementSnapshot>>`.
4. **`ZoneManager.RegisterScene`** — right where it already indexes `ZoneEntry`/`ZonePortal` — gains a
   materialize-if-missing **+ refresh-if-present** step:
   - Collect `PlacementId`s already present via `GetComponentsInChildren<IWorldPlacement>` on the scene's
     root objects (these came baked into whatever build is currently running).
   - **Refresh (WP5):** for each of those scene-baked objects, look up a DB row by its `PlacementId`; if one
     exists, call `ApplyPlacementData(row.data)` on it (config only — position/rotation stay whatever the
     scene authored, per WP5). Keeps a shipped build's already-baked placements picking up config edits made
     later in the web editor, on restart alone.
   - **Materialize:** for each DB row for this `zoneId` whose `PlacementId` is **not** in that set: instantiate
     via a small per-`marker_type` factory (`PlacementFactoryRegistry.Get(markerType)`), set position/rotation
     from the row, call `ApplyPlacementData(data)`, `SceneManager.MoveGameObjectToScene` into the zone's scene.
     **Ephemeral — never written to a scene asset**, exactly like `SpawnPoint.SpawnOne`'s mob instantiation;
     thrown away on server stop.
   - **Two passes** for both halves, to handle `SpawnPoint → PatrolRoute`/`WanderRegion` references: pass 1
     handles every non-referencing type (`PatrolRoute`, `WanderRegion` — refresh existing + materialize
     missing); pass 2 handles `SpawnPoint`s the same way, then calls `ResolveReferences` (on anything
     implementing `IReferencesOtherPlacements`) against a `Dictionary<PlacementId, GameObject>` built from
     **all** scene-baked and materialized objects from pass 1.
5. **Factories**: `SpawnPointPlacementFactory`, `PatrolRoutePlacementFactory` (also builds the N ordered
   child waypoint GameObjects from `data.points`, mirroring what `Tools/Zones/Add Patrol Waypoint` does by
   hand, so `PatrolRoute.Points` reads them identically regardless of origin), `WanderRegionPlacementFactory`.
   Adding a future marker type = one new component + one new factory + registering it — no other code
   touched (WP1's payoff).

**Result after Stage A alone:** place a new `SpawnPoint` for West Reach in the Editor → run the sync tool →
the currently-deployed dedicated server (running an older build that never had this GameObject baked in)
picks it up on its next restart, no rebuild. This is the full original ask.

## Stage B — Import tool (DB → scene, persisted)

Completes the round trip the user asked for: anything hand-authored in the DB (a script, a future admin
action) can be pulled into the Editor for visual tweaking, and pushed back out.

- **`Tools/Zones/Import Placements from Database`** — pick a zone (dropdown, defaulting to the open scene's
  own zone); read its rows directly from Postgres (same `Database.OpenEditorConnection()` convention as
  export); for each: if a scene object with that `PlacementId` already exists
  (`GetComponentsInChildren<IWorldPlacement>`), refresh it in place via `ApplyPlacementData` (never
  duplicate); otherwise instantiate via the **same factories** Stage A's runtime path uses, but — the one
  real difference — **persisted**: the new GameObject is saved into the open scene (mark dirty, save scene),
  not thrown away. Reference resolution (`ResolveReferences`) runs the same two-pass way.
- This reuses 100% of Stage A's `Capture`/`Apply`/factory code. The only new logic is "where does the
  materialized object end up" (a live ephemeral runtime scene vs. a persisted Editor scene asset) and the
  upsert-into-scene dedup check.

**Stale-overwrite is a real, named risk, not a bug to design around (per the earlier discussion):** if you
hand-edit a DB row by script, then later export a scene copy that predates that edit, export clobbers it.
Fix is convention (import fresh before you start editing something you didn't just place yourself), not
version-locking — consistent with every other content type in this project, none of which have optimistic
concurrency either.

## Stage C — Web editor + documentation

### Angular — `PlacementEditor`

Mirrors `SpawnEditor`'s `ContentGrid`/`CrudModal` pattern (2.1.1 framework), added to the shell nav
("Placements"). **List view:** zone filter, marker type, position (read-only), and a type-specific summary
column (e.g. a SpawnPoint row shows its `spawnTableId`/`mobId` + activation radius). **Edit modal:** only the
*non-spatial* fields are editable — for a SpawnPoint placement, that's `spawnTableId`/`mobId`/

without reopening Unity, same value proposition 2.7.2's Spawn Editor already provides for table contents).

through a number form is worse than doing it in the 3D viewport, so this deliberately isn't built (WP7).

## Decisions (recommendations in **bold**)

- **WP1 — One generic table vs. one per marker type.** **One generic `world_placements` table with a JSONB
  `data` column.** A table-per-type would need a migration every time a new marker type is invented — directly
  against the user's stated goal of "all the other types we come up with." No query pattern here needs
  relational filtering into the JSON (rows are only ever read wholesale by `zoneId`, or by `placementId`).
- **WP2 — Where does `zoneId` come from?** **Resolved from the containing scene via `ZoneCatalog`, never a
  manually-authored field.** A separate zoneId field on every placement is one more thing to drift from
  reality; the scene a marker lives in already *is* its zone.
- **WP3 — Cross-references (`SpawnPoint → PatrolRoute`/`WanderRegion`).** **String `PlacementId` refs +
  two-pass materialization + a small `IReferencesOtherPlacements` hook**, rather than trying to serialize a
  Unity object reference (which has no meaning across a DB round-trip). Generalizes cleanly to future
  marker types that reference each other.
- **WP4 — Does sync ever delete?** **Auto-upsert always; auto-delete never — but sync surfaces deletion
  candidates for explicit confirmation.** Without *some* delete path, deleting a `SpawnPoint` in the Editor
  leaves its DB row orphaned — the tool has no way to see the GameObject is gone, so the row silently
  survives and re-materializes on the next zone load, which is the opposite of what deleting it meant.
  But blind auto-delete is worse: if only part of a zone's scene is open, or a placement is temporarily
  disabled, a naive "in DB but not found in scene" diff would delete rows for things that still exist. So
  sync does both halves safely: everything it *finds* is upserted with no prompt (adding/updating is always
  safe); anything in the DB for that `zoneId` that it does **not** find among the scene's live
  `IWorldPlacement` components is listed as a **deletion candidate** and requires an explicit confirm (a
  simple review list — "these N DB placements have no matching scene object — delete them?") before anything
  is removed. This is the only path that deletes DB rows from the sync tool (a direct SQL `DELETE`, same
  connection as the upserts); the web editor's own `DELETE` button is a separate, always-explicit path
  (through the API) on top of it.
- **WP5 — Does the scene copy get deleted once synced?** **No — but position and config are split, and
  config always refreshes from the DB.** A scene-baked copy is never deleted or replaced (Play-mode/Host
  testing in the Editor still behaves exactly as today), and **position/hierarchy stays whatever the scene
  says** — moving something physically is legitimately a scene-edit-and-rebuild concern, not something this
  system tries to route around. But **config is always DB-authoritative when a matching row exists**, even
  for a scene-baked object: `ZoneManager.RegisterScene`'s existing indexing loop, for every scene-baked
  `IWorldPlacement` it finds, also looks up a DB row by that object's `PlacementId` and — if one exists —
  calls `ApplyPlacementData(row.data)` on it (skipping position/rotation, which the scene owns), right
  alongside the existing materialize-if-missing step for placements the scene doesn't have at all. Same
  method, no new object, no change to the Play-mode-testing behavior this decision originally protected —
  just an added self-refresh. This means editing a placement's `spawnTableId`/`activationRadius`/etc. in the
  web editor (WP7) now takes effect on **any** server restart, whether that placement originated as a
  scene-baked object or a DB-only one — closing the gap the presence-only version of this decision would
  have left for every already-shipped/backfilled placement (WP6).
- **WP6 — Backfill of existing camps.** **A one-time, explicit adoption step, not automatic.** Running the
  export tool against Creslin's Field / Thornwood's already-placed spawn points (rat/guard/captain camps,
  the wolf spawns currently being placed for West Reach) assigns them `PlacementId`s and uploads rows in one
  pass. Nothing happens silently — it's the same menu command used for any future placement.
- **WP7 — Web editor scope.** **Config fields editable, spatial fields (position/rotation/points/shape)
  read-only.** Matches the existing Spawn Editor's own scope boundary (weights/timers are web-editable;
  *where* a camp is has always been a Unity concern) and avoids building a worse spatial-editing UI in a 2D
  form than the Scene view already provides for free. **Delete, consistent with WP4's reasoning, is
  explicit-confirm and clearly scoped**, not a silent action: the web editor's `DELETE` only ever removes
  the DB row — it cannot know whether a scene-baked copy of that same `PlacementId` still exists in
  whatever build is currently running, and per WP5 that scene-baked copy would keep winning regardless. The
  confirm dialog says so plainly ("this removes the database record only — if this placement is still baked
  into a running server's scene, it will keep appearing until that scene copy is also removed"), so a web
  delete doesn't quietly fail to do what it looks like it did.
- **WP8 — `ZonePortal`/`ZoneEntry`.** **Out of scope**, per the Non-goals section — structural zone topology,
  not population content. The interface is generically adoptable later with no changes elsewhere if that
  ever changes.
- **WP9 — Documentation debt.** **Fix `ContentCreation.md`'s existing staleness in this same pass**, not as
  a separate cleanup item — it's the natural place the new workflow gets documented, and leaving the old
  SO-era description next to new DB-era material would be actively misleading.

6. **Backfill (WP6):** run the sync tool against Creslin's Field's existing rat/guard/captain camps and

8. **Web editor:** edit a placement's `activationRadius` in the Angular editor → restart the server → confirm

   amendment, config always refreshes; this subsumes the old test-5 check but is worth confirming from the
   web-editor side specifically, since that's the actual user-facing workflow).

## Risks

- **Two-pass ordering bugs** — a `SpawnPoint` materializing before its referenced `PatrolRoute`/
  `WanderRegion` would silently resolve to no patrol/no region instead of erroring; worth a defensive log
  warning in `ResolveReferences` when a referenced id isn't found in either pass's lookup.
- **JSON shape drift** — `data`'s shape isn't schema-enforced; adding a new field to `CapturePlacementData`
  later must default sensibly when `ApplyPlacementData` reads an older row missing it (same general
  DTO-versioning consideration every other content type already has, not new here).
- **WP5's remaining tradeoff is narrower now: position only.** Config always refreshes on restart regardless
  of scene-baked vs. DB-only, but a scene-baked object's *position* still only changes via a scene edit +
  rebuild — moving a placement remains the one thing this system doesn't make restart-only, by design.
- **Scene-dirty churn from bulk backfill (WP6)** — syncing every existing camp in one pass touches every
  zone scene file (assigning `PlacementId`s) in one commit-worthy change; expected, not a bug.

## Done when

A new `SpawnPoint`/`PatrolRoute`/`WanderRegion` placed and tuned in the Editor can be pushed to the DB via
one tool and picked up by any already-running (or freshly restarted) server build with no rebuild; a DB row
authored any other way can be pulled into the Editor, visually edited, and pushed back without duplication;
**config edits (web or DB-direct) take effect on restart for every placement, scene-baked or not — only
moving a placement still requires a scene edit + rebuild**; the web content editor exposes the same
non-spatial tuning `SpawnEditor` already does for table contents; and `Docs/ContentCreation.md` reflects
current reality end to end instead of the pre-2.7.2 SO-era workflow.

## Implementation log — 2026-08-22 (Stage A)

Code only — not compiled or run in-editor yet (no Unity instance available this session); every file was
grounded by reading its real consumers/precedents before writing (`SpawnPoint.cs`/`PatrolRoute.cs`/
`WanderRegion.cs`, `ZoneManager.cs`'s existing `RegisterScene` indexing step, `ContentLoader.cs`,
`ItemRepository.cs`/`ContentDbContext.cs`/`ItemsController.cs` as the flat-table precedent, and
`ContentExportImport.cs` for the Editor-tool-talks-directly-to-Postgres convention).

**Real correction made before writing code:** the original draft had the sync/import tools `PUT`/`GET`
against the ASP.NET API. Checked first and found **no** Editor tool in this project ever does that —
`ContentExportImport.cs`, the migration runner, and the seeder all write straight to Postgres via
`Database.OpenEditorConnection()`. Fixed the devplan (Stage A items 1/2, WP4, WP7, Stage B) before
implementing: the Unity-side sync/import tools bypass the API entirely; `WorldPlacementsController` is
needed only by the Stage C web editor and is **deferred to Stage C**, not built now, since it would be
dead/unconsumed code without an Angular UI yet.

**Second correction, caught while wiring `ZoneManager`:** `OnValidate` (the mechanism every placement type
uses to auto-assign its `PlacementId` when hand-placed) only fires from Editor/Inspector interaction —
never from a runtime `AddComponent()` call. A naively-materialized placement would therefore get a
component with an *empty* `placementId`, breaking the whole id-based system. Added `SetPlacementId(string)`
