# 2.7.2 — Spawn tables + timers (DB-backed + web Spawn Editor)

**Status:** 🟢 Implemented 2026-06-26 — pending in-editor verification (all DS1–DS6 accepted; DS3 group spawning **included**). See the implementation log at the bottom.
**Roadmap item:** M2 → 2.7.2 (inserted after 2.7.1; closes the spawn-path gap found verifying 2.7)
**Pattern:** same as 2.2–2.7 — migration owns schema, API owns data, server loads into a registry at startup. **Server-only** (spawning happens on the server). References mobs (2.5) by id.

---

## Goal & why now

Verifying 2.7 surfaced the gap: a DB mob only spawns via `SpawnPoint.mobId` (a **single** mob). The scene's rat/guard camps still use legacy **SO `SpawnTable`** assets, so they spawn an SO `MobDefinition` and **never touch DB content** — DB loot edits (2.7) and DB faction hits (2.7.1) don't apply to them. Forcing every camp onto single-`mobId` SpawnPoints would throw away **weighted / timed / grouped** spawning.

This item migrates `SpawnTable` (weighted mob entries + `groupSize`) and `SpawnTimer` (base + variance) to Postgres + a web **Spawn Editor**, and has `SpawnPoint` reference a **`spawn_table_id`**. The payoff: a camp keeps weighted/timed spawning *and* its mobs are full DB mobs (DB loot + faction hits + faction aggro). **This closes the testing caveat in 2.7 / 2.7.1** — point the rat SpawnPoint at the DB spawn table and the whole chain is DB-driven.

## What these are, in data

- **Spawn table** (`SpawnTable.cs`): a weighted list of entries — each `(mob, weight, groupSize)` — plus a default respawn timer. `Roll()` weighted-picks an entry.
- **Spawn timer** (`SpawnTimer.cs`): `baseSeconds` + `variance`; `Roll()` = `max(0, base + rand(-variance, +variance))`. Tiny — only ever used as a table's default timer (DS1 inlines it).

### Faithful seed data (from the scene's SO assets)
All three existing tables are single-entry (weight 1, groupSize 1) on the **"Fast"** timer (`baseSeconds 30, variance 0`):
- **Mob Spawn Table** → `Giant Rat`
- **Guard Spawn Table** → `City Guard`
- **Captain Spawn Table** → `Captain of the Guard`

## Schema — `0016_spawn_tables.sql` (schema only; seeded idempotently by `DatabaseSeeder`)

```sql
-- A weighted spawn table with an inlined respawn timer (DS1). SpawnPoint references this by id.
CREATE TABLE IF NOT EXISTS spawn_tables (
    spawn_table_id     TEXT PRIMARY KEY,          -- "Mob Spawn Table"
    display_name       TEXT NOT NULL DEFAULT '',
    timer_base_seconds REAL NOT NULL DEFAULT 300,  -- respawn delay center
    timer_variance     REAL NOT NULL DEFAULT 0,    -- ± randomization
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS spawn_table_entries (
    id             BIGSERIAL PRIMARY KEY,
    spawn_table_id TEXT NOT NULL REFERENCES spawn_tables(spawn_table_id) ON DELETE CASCADE,
    mob_id         TEXT NOT NULL,                  -- references mobs.mob_id (soft ref)
    weight         INT  NOT NULL DEFAULT 1,
    group_size     INT  NOT NULL DEFAULT 1,        -- mobs spawned per activation (see DS3)
    sort_order     INT  NOT NULL DEFAULT 0
);
```

## Unity (server-only)

- **`SpawnTableSnapshot`/`SpawnTableRepository`** — `{ id, displayName, timerBase, timerVariance, List<(mobId, weight, groupSize)> }`, header-then-children load.
- **`SpawnTableRegistry`** (new) — `LoadFrom(snapshots)` builds runtime `SpawnTable` instances (`ScriptableObject.CreateInstance`): each entry `mob = MobRegistry.Get(mob_id)`, `defaultTimer` = a runtime `SpawnTimer { baseSeconds, variance }`. `Get(spawn_table_id)`. **Loads after mobs** (entries resolve mob defs).
- **`SpawnPoint`** — add a `spawnTableId` string field. New resolution precedence in `DoSpawn`/respawn (DS2):
  1. `spawnTableId` set → `SpawnTableRegistry.Get(id)` → `Roll()` → entry's `mob` (+ its timer for respawn);
  2. else `mobId` set → `MobRegistry.Get(mobId)` (single DB mob — Merchant/named NPC);
  3. else legacy SO `spawnTable` (deprecated fallback).
  Respawn delay comes from the resolved DB table's inlined timer (or `timerOverride`).
- **`ContentLoader`** — spawn-tables step **after mobs**; log `[Content] Loaded N spawn table(s)`.
- **`DatabaseSeeder.SeedSpawnTables`** — the 3 tables above (Fast timer 30/0, one weight-1 entry each), idempotent.
- **(DS3) Group spawning** — if adopted: rework `SpawnPoint`'s single `_live` into a **live-set**; spawn `group_size` mobs per activation; start the respawn timer when the **last** group member dies. (Today `group_size` is authored but ignored — "reserved".)

## API (.NET, mapping-only EF)

- `SpawnTable` + `SpawnTableEntry` entities + `SpawnTableDto` (header + timer + ordered entries); `SpawnTablesController` (nested CRUD by `spawn_table_id`, replace-children on PUT, cascade on DELETE) — same shape as `LootTablesController`. DbContext DbSet + mapping.

## Angular

- **`SpawnEditor`** + `spawn.service` — spawn-table list; per-table timer (base + variance) and entry rows (**mob dropdown** from the mobs endpoint + weight + group size). Added to the shell nav (Spawn).

## Decisions (recommendations in **bold**)

- **DS1 — Timer storage.** **Inline `timer_base_seconds` + `timer_variance` on `spawn_tables`; retire the `SpawnTimer` SO.** It's a 2-field type only used as a table's default; a separate shared `spawn_timers` table is over-abstraction (the one shared "Fast" timer is fine to duplicate per table).
- **DS2 — `SpawnPoint` resolution precedence.** **`spawnTableId` → `mobId` → legacy SO `spawnTable`.** Keeps single-mob `mobId` for named NPCs (Merchant) and the SO path as a deprecated fallback so unmigrated scenes don't break.
- **DS3 — Group spawning.** **Implement it now** (recommended — you asked for grouped, and `group_size` is already in the data). Entails reworking `SpawnPoint` death/respawn from a single `_live` to a live-set. *Alternative:* data-only (author `group_size`, still spawn one — unchanged behavior) and split actual group-spawn to a fast-follow. Pick based on appetite for the SpawnPoint rework.
- **DS4 — Retire the SO path?** **To a fallback, don't delete classes.** `SpawnTable`/`SpawnTimer` remain the in-memory runtime types the registry builds; the serialized SO field on `SpawnPoint` stays as a deprecated fallback.
- **DS5 — Web editor.** **A dedicated "Spawn" editor** (mob-dropdown entries + weights + group size + timer). Fits the nav alongside Mobs/Loot.
- **DS6 — Seed the 3 existing tables.** **Yes** — so the scene's camps work DB-side the moment their SpawnPoints are pointed at the DB tables.

## Risks

- **Load order** — spawn tables must load **after** mobs (entries resolve `MobRegistry.Get`). Current order ends `… → loot → mobs → xp`; insert spawn tables after mobs.
- **`SpawnPoint` precedence regression** — the new branch must not break existing `mobId` (Merchant) or legacy SO spawns; keep all three paths working.
- **(DS3) live-set rework** — death tracking moves from one `_live` to a set; get respawn-when-all-dead right (don't double-spawn or leak the death subscription).
- **Scene rewiring** — each camp's SpawnPoint needs `spawnTableId` set (a manual step, like `mobId`); the SO fallback covers anything not yet migrated.

## Done when

Spawn tables + timers are authored in the Angular app, stored in Postgres, and loaded at startup; a `SpawnPoint` referencing a `spawn_table_id` spawns weighted/timed (and, with DS3, grouped) **DB mobs** — so a migrated camp's mobs carry DB loot, faction hits, and faction aggro. The SO `SpawnTable`/`SpawnTimer` path is retired to a fallback. This closes the spawn-path gap that blocked full in-game verification of 2.7 and 2.7.1.
