# 6.2 — Dedicated Server Build + Hosting

Status: 🟡 Draft — awaiting review (decisions DH1–DH8 carry recommendations)

## Goal

Get the actual Unity game server running on the Lightsail box (the same one hosting `/web` +
`/api` + Postgres since 5.11) and reachable by a real client over the internet — not localhost.
This is the last piece needed for someone other than the user to actually play the game, not just
author content for it.

Explicitly NOT this item's job: distributing a client build to players (6.4 — build pipeline /
launcher / patcher), transport encryption / hardened auth (6.3), or deciding whether the server
should eventually move off this box onto dedicated capacity (6.5 — load testing, from real data).

## Grounding (read before designing)

- **5.10 already proved a real standalone build works.** A headless `-batchmode -nographics`
  Windows build boots, connects to Postgres via env vars, and accepts real (non-Editor) client
  connections — the full register→login→spawn→move→target→combat→loot→camp→relog loop confirmed
  working. That spike also surfaced and fixed two real bugs (a HUD-loading crash, a silent
  UI-binding failure) that would otherwise have shown up again here. **But it was Windows-only** —
  this project has never built for Linux, and the Lightsail box is Ubuntu 24.04. That's new,
  untested ground, not a rerun of 5.10.
- **5.11 already stood up the box, the deploy mechanism, and reserved room for this.** Lightsail
  instance, Docker Postgres, Caddy (TLS for the web/API only — the game server doesn't go through
  Caddy, it's a raw UDP port), a zero-long-lived-secrets deploy pipeline (GitHub Actions → S3
  presigned URLs → SSM `send-command` runs a deploy script on the box), and — critically — **CD9
  explicitly reserved this as "a fourth co-located process: its own systemd unit, its own UDP
  firewall rule."** `deploy/ueq-api.service` is the existing systemd-unit pattern to mirror
  (`Restart=on-failure`, `EnvironmentFile=` for secrets, not inline).
- **DS1/DS6 from 5.10 explicitly flagged two things as "upgrade in 6.2, not now":** switching from
  Standalone-with-`-nographics` to Unity's purpose-built **Dedicated Server** build target (strips
  graphics/audio modules entirely — smaller, more correct for a real deployment), and **process
  supervision / auto-restart-on-crash / log rotation** (5.10 explicitly shipped without any of
  that). Both are squarely this item's job now.
- **The firewall today is 80/443/SSH-alias only** (`docs/DEPLOY-AWS.md` step 3) — no UDP port open
  at all. The game server needs one opened.
- **KCP transport, confirmed via the running server's own log, listens on port 7777** by default
  (Mirror's/kcp2k's standard default — no override found in `SceneSetup.cs`'s transport wiring).
- **Transport is unencrypted (KCP/UDP), and that's a known, already-accepted-for-now gap** — the
  CLAUDE.md Key Decisions section already documents this as deferred to 6.3, not something 6.2
  needs to solve. Worth restating explicitly here so opening this port to the public internet is a
  conscious call, not an oversight.
- **This project has zero CI-based Unity builds anywhere** — every build so far (client, server)
  has been produced locally via the Editor `Tools/Build/*` menu items from 5.10. Setting up
  Unity Cloud Build or a GameCI-based GitHub Actions Unity build would be new infrastructure with
  its own licensing/activation complexity, unlike the `dotnet build`/`ng build` CI already in place
  for the web/API (which need no per-seat Unity license).

## Decisions

**DH1 — Build platform: add Linux Standalone/Dedicated Server support, don't try to run the
existing Windows build under Wine/emulation.**
Recommend installing Unity Hub's **Linux Dedicated Server** build support module (or Linux
Build Support if the Dedicated Server module isn't offered standalone for this Editor version) and
building a genuine `BuildTarget.StandaloneLinux64` / Dedicated Server target. Running a Windows
`.exe` under Wine on the Lightsail Ubuntu box is a real alternative some hobby projects use, but
it's a second, non-standard runtime layer to debug against with zero upside once native Linux
support is one module install away — reject it.

**DH2 — Build target type: switch to Unity's dedicated "Dedicated Server" target now, per DS1's
own flag.**
Recommend making this switch now rather than deferring again — 6.2 is exactly the point DS1 named
for it. Smaller binary, no graphics/audio modules to accidentally depend on, and it's the
technically-correct target for something that will only ever run headless. Residual risk carried
over from 5.10: the additive-scene crash that spike fixed was specific to the *client* loading the
UI prefab — the server never loads that content at all (`Application.isBatchMode`/dedicated-server
gate), so switching the server's build target/platform shouldn't reopen it, but it's cheap to
re-verify once during DH-stage testing rather than assume.

**DH3 — Where it runs: co-located on the existing Lightsail box, per CD9 — not a new instance.**
Matches 5.11's CD9, which explicitly deferred "stays co-located vs. splits onto dedicated capacity"
to 6.5 (load testing, from real data). Standing up a second instance now would be deciding that
question anyway, just without the data CD9 said to wait for.

**DH4 — Process supervision: systemd unit, mirroring `ueq-api.service`.**
New `ueq-gameserver.service`: `Restart=on-failure`, `RestartSec=5`, `EnvironmentFile=` for the DB
connection secrets (same `UEQ_DB_*` env vars DS4 already proved work), `ExecStart=` the Dedicated
Server Linux binary with whatever headless flags the Linux target still needs (likely just
`-nographics -batchmode` remain relevant, or the Dedicated Server target may not need them at all —
confirm during implementation). `WantedBy=multi-user.target` so it survives a box reboot.

**DH5 — Logging: journald, not a `-logFile` file + logrotate.**
Recommend letting the process's stdout/stderr flow to systemd's journal (the default for a
`Type=simple` unit with no `-logFile` flag) and rely on `journalctl -u ueq-gameserver` for
inspection — matches how `ueq-api.service` already works, needs no new log-rotation
config/cron/logrotate rule to maintain. Reject introducing a second logging convention (file-based)
for just this one service when the API's already-working journald pattern covers it for free.

**DH6 — Firewall: open Mirror's UDP port to everyone, matching the API's now-open access model.**
Add one Lightsail firewall rule: UDP 7777, `0.0.0.0/0`. Consistent with 5.11's CD5 rework (the API
moved from IP-allowlisted to open-with-app-level-auth once dynamic home IPs made allowlisting a
recurring chore) — a game server has the same problem, worse (real players' IPs are never known
in advance at all). Restated from Grounding: this means an *unencrypted* transport is now reachable
by anyone, which is a conscious, already-documented-elsewhere gap (6.3), not new exposure this
decision introduces silently.

**DH7 — Deploy mechanism: build locally in the Editor (as established), upload the binary through
the existing S3-presigned-URL/SSM pipeline — do NOT stand up Unity CI.**
Reuse 5.10's `Tools/Build/Build Headless Server (Standalone)`-style menu item (retargeted at Linux
Dedicated Server) to produce the build locally, then extend `deploy.yml`/`deploy.sh`'s existing
zero-secrets upload+SSM-deploy flow to also ship this artifact and restart `ueq-gameserver.service`
alongside the API/web restarts. Standing up Unity Cloud Build or a GameCI Docker-based CI build is
real, working infrastructure other teams use, but it's new licensing/activation surface this
project has never needed for its `dotnet build`/`ng build` CI — not worth taking on for a
solo/two-person project where a local build-then-upload step is already the established, working
pattern from 5.10.

**DH8 — Scope boundary: no launcher/client-distribution work, no encryption/auth hardening.**
6.2 ends at "the server runs on AWS and a manually-built client (the same Windows Standalone build
process from 5.10) can connect to it over the real internet instead of `127.0.0.1`." Getting a
client into a real player's hands without them building it themselves is 6.4. Encrypting KCP or
hardening login is 6.3. Both stay explicitly out of scope here, same as DS6/CD9 already said.

## Approach

1. Install Linux (Dedicated Server) Build Support in Unity Hub.
2. Build the server for Linux locally via a new/retargeted Editor menu item.
3. Write `deploy/ueq-gameserver.service` (mirrors `ueq-api.service`).
4. Extend `deploy.yml`/`deploy.sh` to upload the server build artifact and restart the new service.
5. Open the UDP 7777 firewall rule.
6. Deploy straight to Lightsail and verify from a real external client (the user's own machine) —
   full register→login→spawn→combat→loot loop against the AWS-hosted server + AWS-hosted Postgres.
7. **Fallback, only if step 6 fails and the cause isn't obvious from `journalctl`:** reproduce
   locally via WSL2 (shares Docker Desktop's backend, so the existing Dockerized Postgres is
   already reachable) for a much faster iteration loop than round-tripping through the deploy
   pipeline on every retry. Not a mandatory step — only reached for if/when needed.
7. Log findings the same way 5.10 did (this is genuinely new ground — Linux, Dedicated Server
   target, and a real internet path are all untested combinations).

## Files touched (planned)

- `Assets/Scripts/Editor/ServerBuildTools.cs` — extend with a Linux/Dedicated-Server build method
  (or retarget the existing one — decide during implementation whether Windows support is still
  wanted for local dev testing alongside the new Linux path).
- `deploy/ueq-gameserver.service` (new).
- `.github/workflows/deploy.yml` / `deploy.sh` — extended, not rewritten.
- Lightsail firewall — one new rule (UDP 7777, open).
- No schema/migration changes; no client-side code changes anticipated.

## Test plan

- Server build for Linux Dedicated Server target succeeds locally.
- Deployed via the existing pipeline; `ueq-gameserver.service` starts, stays up, survives a
  simulated crash (`systemctl kill` → confirm auto-restart).
- `journalctl -u ueq-gameserver` shows the same `[DB] Connected...`/content-load lines 5.10 already
  validated the meaning of.
- A client built on the user's own machine (normal Standalone Windows client, same as 5.10)
  connects to the box's public IP:7777 (or the sslip.io hostname) instead of `127.0.0.1` — full
  register→login→spawn→target→combat→loot→camp→relog, same checklist DS5 already proved once
  locally, now proved over the real internet against real AWS-hosted Postgres.

## Risks / open questions

- First-ever Linux build for this project — genuinely unknown whether Mirror/kcp2k, the DB driver
  (Npgsql), or anything else in the dependency chain has a Linux-specific wrinkle 5.10's Windows
  testing couldn't have caught. Deliberately deploying straight to Lightsail rather than
  pre-validating locally (accepted tradeoff — see Approach step 7 for the fallback if this bites).
- The Dedicated Server build target strips more than Standalone does (no graphics/audio/input
  modules) — if anything in this codebase accidentally assumes one of those exists even
  server-side (unlikely, given 5.10's `Application.isBatchMode` gates already prove the server path
  avoids UI/graphics work, but worth a real test, not an assumption).
- Firewall UDP 7777 open to everyone means this is genuinely live/discoverable once deployed —
  same "hobby-project-acceptable-for-now" posture as the open API, but worth the user explicitly
  saying so given it's a slightly different flavor of exposure (a game server, not a content-admin
  tool).
