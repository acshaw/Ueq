# Devplan 2.1 — Content platform foundation (the rails)

**Roadmap item:** M2 → 2.1 (first M2 item; the foundation 2.2+ content verticals build on)
**Status:** ✅ Done (2026-06-24) — implemented and verified end-to-end: a row authored in the Angular editor → .NET API → Postgres → Unity `ContentLoader` logged it at host start (confirmed in-game). D2 (controllers + EF mapping-only) and D5 (Addressables behind a resolver seam) decided with the user; D1/D3/D4/D6 stand as recommended (restate locked direction). Rails ready for 2.2 (items) to ride.
**Depends on:** M1 ✅ (Postgres + migration runner from 1.1; the registries the loader will adopt)
**Unblocks:** 2.2 (items — first real content type) and every M2 vertical after it

---

## Goal

Stand up the **rails** for DB-backed, web-authored content — without migrating any content type yet.
Three pieces that 2.2+ reuse: a **web editor stack** (Angular SPA + a thin .NET API + Postgres), a
**Unity DB-content loader** pattern the existing registries adopt, and an **asset-binding convention**
for the Unity references that can't live in a database. 2.1 proves the whole chain end-to-end with a
trivial entity; **items (2.2) are the first real vertical.**

> Direction (locked 2026-06-20, see [[project_direction]]): content goes IN Postgres, authored via
> **web editors**, and the game server **loads it at startup** into the existing registries. Pure data
> in the DB; Unity asset refs stored as string ids/paths and resolved at load. Migrations own schema;
> the web tool only touches data.

### Scope guardrails
- **In scope:** the Angular app + .NET API scaffolds, their Postgres connection, a generic Unity
  `ContentLoader`/registry-source pattern, the asset-id/path convention + resolver, repo layout, and
  one **trivial end-to-end smoke** (author a row in Angular → API → Postgres → Unity loads it at
  startup) that proves the pipe.
- **Out of scope:**
  - **Any real content type** — items are **2.2**, the reference vertical everything copies.
  - **Auth on the web stack** — trusted local users only for now (revisit when hosted; ties to 5.3).
  - **Hosting/deploy** — local dev (`localhost`) only; AWS is M5.
  - **Retiring any `Resources/` load path** — that happens per-type as each migrates (2.2+).
- **Locked principle:** **migrations own content schema** (the existing StreamingAssets `.sql` runner);
  the web API only performs **data CRUD**. One schema authority, no drift.

## Approach

### Architecture / data flow
```
Angular SPA (editors)  ──HTTP──▶  .NET API  ──Npgsql──▶  Postgres  ◀──Npgsql──  Unity server
   author content                 thin CRUD              content tables          ContentLoader @ OnStartServer
                                                          (schema via migrations)  → existing registries
```
- **Postgres** — same instance as player data (D1); content tables live alongside (own naming/schema),
  created by the **existing migration runner** so there's one schema authority.
- **.NET API** — a deliberately thin ASP.NET Core service (D2): REST/JSON CRUD over content tables, the
  minimum to feed Angular (which can't hit Postgres directly). No business logic the game needs.
  **Controllers** (a class per resource) over EF Core in **mapping-only mode** — EF maps entity classes
  onto tables the `.sql` runner already created; **EF Migrations stays off** so the migration runner
  remains the single schema authority (D4). EF buys CRUD convenience (LINQ, change tracking, no manual
  row→object mapping); it is deliberately *not* used to manage schema.
- **Angular SPA** — the editors (the complex authoring — quest wizards, ability-effect editors — is why
  Angular over a generated admin panel; chosen for the user's familiarity).
- **Unity `ContentLoader`** — on `OnStartServer`, query the DB and populate the existing registries
  (`ItemRegistry`, `AbilityRegistry`, …), swapping the *source* behind their current lookup-by-id API.

### 1. Repo layout (D6)
Monorepo (one repo, this one): `/web` (Angular) + `/api` (.NET) alongside the Unity project. Simplest
for a solo/duo project; the API may later share a generated model/enum library with Unity to kill
type-drift (deferred).

### 2. Unity DB-content loader (the reusable pattern)
A generic seam the registries adopt:
- A small `IContentSource`/`ContentLoader` that runs in `OnStartServer` (after `Database.InitializeServer`),
  reads rows via a repository (the 1.2 DAL convention), and pushes them into the registry.
- Registries keep their current `Get(id)` API; only how they're *populated* changes (DB instead of
  `Resources.LoadAll`). Hybrid during migration: a type still on `Resources/` keeps working until its
  DB path + editor lands, then its `Resources` load is retired (2.2+).
- 2.1 establishes the base pattern + the startup hook; 2.2 is the first registry to actually use it.

### 3. Asset-binding convention (the Unity refs that can't live in the DB)
Stats/text/prices/formulas go in the DB. **Prefabs/icons/meshes/anims cannot** — store a **string
address** in the content row and resolve it at load:
- The string is an **Addressables address** (logical key, e.g. `sword_01`), not a filesystem path.
  Content rows store the address; assets are marked addressable in Unity and bundled by the Addressables
  build (D5).
- All loads go through one `AssetResolver.LoadAsync<T>(string address)` seam — callers never touch
  `Addressables` directly, so loader config lives in one place.
- **Async-first:** Addressables returns an awaitable handle (unlike `Resources.Load`'s synchronous
  return). The `ContentLoader` and any UI asset fetch must account for this — preload/await at startup
  rather than assume an immediate asset. The resolver owns handle lifetime (release on unload).
- 2.1 specifies the convention + ships the resolver; content rows reference assets without storing them.

### 4. End-to-end smoke (prove the chain, then delete)
A throwaway `content_ping` table (id, label): Angular lists/edits it → API CRUD → Postgres → Unity
`ContentLoader` reads it at host start and logs the rows. Proves Angular→API→DB→Unity works before any
real type rides on it; removed (or repurposed) once 2.2 lands. (Mirrors how 1.1/1.2 used a smoke table.)

## Test plan
1. **DB:** migration creates `content_ping`; `Run Migrations` idempotent.
2. **API:** `GET/POST` `content_ping` works (curl/Swagger); connects to the same Postgres.
3. **Angular:** the app lists `content_ping`, adds/edits a row → persists via the API.
4. **Unity:** host start → `ContentLoader` logs the `content_ping` rows authored in Angular → proves the
   full Angular→API→DB→Unity chain.
5. **Asset resolver:** mark one test asset addressable, then `AssetResolver.LoadAsync<T>(address)`
   resolves it by its address (await completes, asset non-null). Confirms the Addressables build + seam.

## Open decisions (recommendations first)
- **D1 — Content DB location:** **same Postgres instance** as player data, content tables alongside
  (own naming). Alt: a separate DB (more isolation, more connection plumbing — premature).
- **D2 — API stack:** ✅ **DECIDED — ASP.NET Core with controllers + EF Core (mapping-only), REST/JSON,
  no auth, localhost.** Controllers (a class per resource) for organization/familiarity. EF Core for CRUD
  convenience, but in **mapping-only mode**: entity classes map onto migration-created tables, and **EF
  Migrations is never enabled** — the StreamingAssets `.sql` runner stays the single schema authority
  (preserves D4). Accepted cost: EF entity classes are hand-maintained to match the SQL columns (drift
  risk equivalent to hand-written Npgsql DTOs, plus query sugar). Connection config reuses the 1.1
  `db.config`/env approach. *(Considered and rejected: Minimal API + raw Npgsql — leaner but the user
  preferred the controllers+EF structure; letting EF own the schema — rejected, collides with D4 and
  Unity reads the same tables via the proven runner.)*
- **D3 — 2.1 scope:** **rails only + a throwaway end-to-end smoke**; first real type is items (2.2).
  Alt: fold items into 2.1 (bigger first step, muddier foundation).
- **D4 — Schema authority:** **migrations own content schema** (StreamingAssets runner); web API does
  data CRUD only. (Locked principle — restated, not really open.)
- **D5 — Asset binding:** ✅ **DECIDED — string address → Addressables, behind an `AssetResolver` seam,
  now.** Content rows store an Addressables address; a single `AssetResolver.LoadAsync<T>(address)`
  fronts all loads so callers stay loader-agnostic. Chosen over Resources-now because the user is heading
  to a launcher/patcher anyway (M5.4, which wants separately-bundled assets) and prefers to learn
  Addressables while the asset surface is tiny — avoids a second migration later. Accepted cost: upfront
  Addressables setup (install package, mark assets addressable, an addressable content build) **and**
  async loading semantics the loader/UI must handle. *(Considered and rejected: `Resources.Load` behind
  the same seam — zero setup but forces all assets into the build/memory and would need swapping to
  Addressables at content scale anyway.)*
- **D6 — Repo layout:** **monorepo** (`/web`, `/api` beside the Unity project). Alt: separate repos
  (more overhead for one author).

## Risks
- **New stack surface** — first .NET-API + Angular in the project; keep both thin (the API especially —
  it's a data pipe, not a place for game logic). EF stays mapping-only (no EF Migrations) so it never
  contends with the SQL runner for schema authority (D4).
- **Addressables learning curve + async** — first use of Addressables (D5): package setup, marking
  assets, the addressable content build, and async load semantics are all new. Mitigate by keeping the
  asset surface trivial in 2.1 (one test asset) and hiding all of it behind the `AssetResolver` seam;
  verify the addressable build step works headless (server) before any real type depends on it.
- **Schema-authority drift** — if the API ever creates/alters tables, the migration runner and the API
  fight. Enforce: API = data only. (D4.)
- **Two consumers, one DB** — Unity (server) and the API both hit Postgres; fine locally, but connection
  config must stay in sync (reuse the 1.1 `db.config`/env approach for the API too).
- **Type drift Unity↔API** — enum/field mismatches between C# game types and API DTOs; a shared model
  lib is the eventual fix (deferred, noted).

## Implementation (2026-06-24)

Built and partially verified (Unity-side awaits the editor):

**Unity (compiles in-editor only):**
- `Assets/StreamingAssets/Database/Migrations/0008_content_ping.sql` — smoke table (0003 was skipped; 0008 is next free).
- `Assets/Scripts/Server/Content/ContentPingRepository.cs` — read-only Npgsql repo (1.2 DAL convention).
- `Assets/Scripts/Server/Content/ContentLoader.cs` — the reusable seam; `LoadAll()` reads content rows and pushes into registries. 2.2+ add a step per type.
- `Assets/Scripts/Content/AssetResolver.cs` — Addressables-backed `LoadAsync<T>(address)` (+ `LoadBlocking` for startup, handle caching, `Release`/`ReleaseAll`).
- `GameNetworkManager.OnStartServer` — calls `ContentLoader.LoadAll()` right after `Database.InitializeServer()`.
- `Packages/manifest.json` — added `com.unity.addressables` `2.6.0` (verified to exist on Unity's registry for the 6000.x line; valid range is 2.4.4–2.11.1. Bump toward 2.11.1 later if you want newer fixes).

**.NET API (`/api`, verified):** ASP.NET Core (net10.0) controllers + EF Core (`Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.2) in **mapping-only** mode — `ContentDbContext` maps onto the migration-created table, **no EF Migrations**, never calls `Migrate()`/`EnsureCreated()`. `ContentPingController` full CRUD; CORS for `localhost:4200`; connection string from `UEQ_DB_CONNSTRING` env or `appsettings`. **Verified end-to-end against the live Postgres** via curl: POST/GET/PUT/DELETE all correct (bigserial id, snake_case mapping, 204 on delete). Runs on `http://localhost:5144` (http launch profile).

**Angular (`/web`, verified build):** CLI 21 standalone app. `ContentPingService` (typed HTTP) + `App` editor component (list/add/inline-edit/delete, signals + `@for`/`@if`, friendly API-down message). `provideHttpClient` wired. `ng build` succeeds.

**Secrets:** `api/appsettings.json` ships a passwordless placeholder; the real local string lives in gitignored `api/appsettings.Development.json` (parity with `db.config.json`). `.gitignore` covers `/api/bin|obj`, `/web/node_modules|dist|.angular`.

**Remaining (in-editor, user):**
1. Reopen Unity → let it restore the Addressables package (accept the verified version if prompted) and recompile the new scripts.
2. `Tools/Database/Run Migrations` — applies `0008` (the `CREATE TABLE IF NOT EXISTS` no-ops since the smoke test already created the table; the runner records version 8). *(Note: I created `content_ping` directly via psql for the API test but did **not** insert a `schema_version` row, so the runner still applies 0008 cleanly.)*
3. Start Host → expect `[Content] Loaded N content_ping row(s)…` in the Console (one row, `"edited label"`, persists from the API test).
4. Full visual chain: `cd api && dotnet run` + `cd web && npx ng start` (or `ng serve`) → open `http://localhost:4200`, add/edit a row → restart Host → see the new row logged by `ContentLoader`.

## Done when
Angular → .NET API → Postgres → Unity load chain works end-to-end for a trivial entity; the
`ContentLoader` pattern + asset-binding convention + repo layout are in place and documented; no real
content type migrated yet — 2.2 (items) is ready to be the first vertical that rides these rails.
