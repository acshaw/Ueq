# 5.1.5 — ATK-Derived Hit Roll (Combat Tuning Simplification)

**Status:** 🟡 Draft — awaiting review (decisions AD1–AD9 carry recommendations; AD10 already decided)

**Not a new pipeline step** — a targeted revision of 5.1.1's Hit Roll *base-table authoring model*
specifically. Avoidance (5.1.2), Damage (5.1.3), and Mitigation (5.1.4) are untouched; Level
Differential and Position Modifier stay exactly as built. 5.1.1 shipped a raw, hand-authored 7-weight
`CombatTierTable` per class at Level 1 and Level 20 (interpolated between) — mechanically sound, but
`7 weights × 2 levels × N classes` with no formula connecting them, which is genuinely hard to reason
about or keep internally consistent. It also means base stats (STR/AGI/DEX) currently have **no
influence on the hit roll at all** — only on damage scaling (unchanged, stays that way) and, for the
*defender*, avoidance.

The fix: collapse weapon skill + the relevant stat into a single derived **ATK** score (same technique
EQ used, and the user's own instinct going in), and have ATK drive the base table via one shared curve
instead of per-class/level authored numbers. Concretely, this also **implements design doc §2.10 (Stat
Contribution) for the first time** — it was specified back in 5.1.1's own grounding
(`docs/eventide_combat_pipeline.md` §2.10: *"Effective weapon skill = trained weapon skill + (relevant
stat × 0.1)"*) but never actually wired into `CombatResolver`. This devplan isn't a departure from the
original design — it's finishing a piece of it that got skipped, combined with the tuning-surface fix.

## Scope
- **Only the Hit Roll step's base-table SOURCE changes.** Avoidance, Damage, Mitigation, Level
  Differential, and Position Modifier are all unchanged — same code, same formulas, same tuning
  constants.
- Melee/physical auto-attack only, matching 5.1's original scope (abilities keep their own formula).
- Symmetric per 5.1's original design: players derive ATK from stats + skill + level; mobs (no
  `CharacterStats`) get ATK authored directly as one number, replacing their 7-field table.
- **The Angular combat simulator (`web/src/app/combat-sim/`) is rebuilt as part of this devplan, before
  the C# port** — its whole purpose is validating a formula before authoring it for real, so building
  it after the fact defeats the point. See AD7.
- **Weapon damage/delay stay hand-authored, unformalized** — deliberately, per AD10. The only addition
  is a live DPS readout in the Item Editor and simulator; no target curve, no item-level field, no
  change to how weapons are balanced.
- Explicitly **not** in scope: Mitigation's real formula (5.1.4 stays a stub), real per-class HP/Mana
  numbers (unrelated), the TS/C# dual-maintenance drift risk (a known, separate liability — not
  addressed here).

## Grounding — what this replaces
- **`ClassDefinition.combatTierTableLevel1`/`combatTierTableLevel20`** (14 raw fields:
  `tierL1Miss`…`tierL1Crippling`, `tierL20Miss`…`tierL20Crippling`) — replaced by a 2-field ATK formula
  (`classAtkBase`, `atkPerLevel`), mirroring the HP/Mana formula sections already on the same class
  (`classBaseHP`/`hpPerLevel`, `classBaseMana`/`manaPerLevel`).
- **`MobDefinition`'s 7 raw `tier*` fields** (`Assets/Scripts/Combat/MobDefinition.cs`, migration
  `0022_mob_combat_fields.sql`) — replaced by one `atk` field.
- **`CombatResolver.BuildCombatant`** (`Assets/Scripts/Combat/CombatResolver.cs:72-107`) — currently
  interpolates the class's raw L1/L20 table by level (players) or reads the mob's raw table directly.
  Rewritten to compute ATK, then interpolate ONE shared reference-table pair by ATK instead. **The
  method's signature and every call site are unchanged** — `PlayerAutoAttack.cs`/`EnemyAI.cs` need zero
  edits (AD6).
- **`CombatResolver.ApplySkillDifferential`** (HR4, `CombatResolver.cs:181-189`) — retired. Weapon
  skill's influence now flows through ATK instead of a second, separate comparison (AD5).
- **Design doc §2.10** — implemented for real for the first time (AD1).
- **Web**: `combat-math.ts`'s tier-table section (lines ~12–174 of 409 — `interpolateClassTable`,
  `WARRIOR_LEVEL_1`, the skill-differential transfer helper), `combatant-form.ts`'s `loadFromClass`/
  `loadFromMob`/`emptyCombatantForm`, the `Class`/`Mob` API DTOs' 14/7 tier fields, `class-editor.ts`'s
  Combat Tier Table section, `mob-editor.ts`'s tier fields, `combat-guide.ts` (Documentation tab).
- **Unaffected, confirmed by reading the code**: `AvoidanceCurve.cs` (already a stat-driven curve, not
  an authored table — no change needed), `CombatTierDamageConfig.cs`/`ComputeDamage`'s
  `weaponBaseDamage × (1 + relevantStat/400)` term (RelevantStat still feeds Damage independently of
  its new role in ATK — two separate consumers of the same stat value, not a conflict),
  `PlayerWeaponSkills.cs` (Cap/RollSkillUp logic unchanged; only gains a new *consumer* of `.For(category)`).

## Decisions

### AD1 — Implement §2.10's Effective Skill formula — **RECOMMEND**
`EffectiveSkill = WeaponSkill + RelevantStat × 0.1`, exactly as specified in the design doc, wired in
for the first time. `RelevantStat` is the same value already computed today (`PlayerAutoAttack.cs:109`
— raw `Str` for Might weapons, raw `Dex` for Finesse; confirmed the pre-5.1 Might/Finesse-weighted
STR/DEX *blend* was already dropped when 5.1 shipped, so there's no blend to preserve here). For mobs,
`RelevantStat` is 0 (matches `EnemyAI`'s existing "mobs have no STR/DEX" convention) — a mob's
`EffectiveSkill` is just its authored `weaponSkill`.

### AD2 — ATK formula for players — **RECOMMEND**
```
ATK = EffectiveSkill + ClassAtkBase(level)
ClassAtkBase(level) = classAtkBase + (level - 1) × atkPerLevel
```
Two new fields on `ClassDefinition` (`classAtkBase`, `atkPerLevel`), same shape as the existing HP/Mana
formula fields on the same class — not a new paradigm, reapplying one this project already uses twice.
Deliberately **no extra stat-to-ATK ratio** beyond §2.10's own 0.1 — `EffectiveSkill` already grows
sensibly across the level range on its own (weapon skill cap grows via 2.12's `5 + 5×(level-1)`), so an
extra multiplier would just be one more knob with no clear job. Can be added later if the simulator
shows it's needed.

### AD3 — ATK for mobs: authored directly, not derived — **RECOMMEND**
Mobs have no `CharacterStats`, so there's nothing to derive ATK *from* the way a player's is. Replace
the 7 raw `tier*` fields with one `atk` field, authored directly per mob (same "author the final number,
not the ingredients" pattern the mob side already uses for `attackDamage`, which represents a mob's
full power with no STR/DEX either). Default a newly-created mob's `atk` to
`ClassAtkBase(warrior-equivalent)` evaluated at that mob's `mobLevel`, so authors start from a sane,
non-degenerate baseline instead of a blank field — same spirit as 5.1.1/HR5's existing "default to
Warrior Level 1" precedent.

### AD4 — One shared curve replaces per-class/per-mob authored tables — **RECOMMEND**
Retire the concept of an authored `CombatTierTable` per class-or-mob entirely. Keep exactly ONE shared,
game-wide reference pair — reuse the Warrior Level 1 (design doc §2.5) and Warrior Level 20 (§2.11)
tables **verbatim** as this pair, since they're the only numbers in the whole system with real
design-doc backing (Cleric/Wizard's tables were already a budget-ratio-scaled placeholder per 5.1.1's
own HR2 decision — never real hand-authored data — so sharing one curve isn't a loss of fidelity, it's
formalizing what was already effectively true for 2 of 3 classes). `CombatTierTable.Lerp` — already
built, unchanged — gets re-keyed: the interpolation fraction becomes
`Clamp01((ATK - MinAtk) / (MaxAtk - MinAtk))` instead of `(level-1)/19`. `MinAtk`/`MaxAtk` become two
new global tunable constants (not per-class) living alongside `CombatResolver`'s other named tuning
constants.

**This is the core tuning-surface win**: authoring a class goes from 14 numbers (with no formula tying
them together, easy to end up internally inconsistent) to 2 (`classAtkBase`, `atkPerLevel`); a mob goes
from 7 to 1. The one shared curve is tuned *once*, globally, instead of per class.

### AD5 — Retire the separate Skill Differential modifier — **RECOMMEND**
`ApplySkillDifferential` (HR4) compared attacker skill vs. defender skill *in the attacker's own weapon
category* — meaning it often compared the attacker's real proficiency against a category the defender
may never have trained (e.g. a Finesse rogue attacking a Might warrior reads the warrior's near-zero
Finesse skill). Keeping it after AD1/AD2 would also double-count weapon skill's effect, since it now
already drives the base table via ATK. Level Differential and Position Modifier are untouched — they
represent genuinely different things (relative level gap; attack angle) that ATK growth doesn't capture,
so they still layer on top of the ATK-derived base table exactly as today.

### AD6 — `BuildCombatant`'s contract is unchanged — **RECOMMEND**
The rewrite is fully contained inside `CombatResolver.BuildCombatant` — same method signature, same
`Combatant`/`AttackContext`/`AttackResult` shapes. `PlayerAutoAttack.cs` and `EnemyAI.cs` need **zero**
edits; they already just call `BuildCombatant(...)` and `ResolveAttack(...)`.

### AD7 — Rebuild the simulator first, validate, then port to C# — **RECOMMEND**
Per the earlier discussion: nuking the simulator and rebuilding it in a later milestone would mean
validating the new formula by hand-reasoning or live Unity playtesting instead of the simulator's actual
purpose (instant Monte Carlo feedback). Sequence:
1. Rewrite `combat-math.ts`'s Hit Roll section (tier table, `interpolateClassTable`, the skill
   differential helper) to the AD1–AD5 formula. Avoidance/Damage/Monte-Carlo-engine/HP-formula-port
   sections are untouched.
2. Rewrite `combatant-form.ts`'s `loadFromClass`/`loadFromMob`/`emptyCombatantForm` against the new
   `Class`/`Mob` field shapes (AD8).
3. Use the simulator itself to pick real `MinAtk`/`MaxAtk` band values and sanity-check class ATK curves
   across level 1–20 (swing analysis + fight-to-the-death) — this is the "sanity check ahead" step.
4. Only once the formula feels right in the browser, port the same validated numbers into
   `CombatResolver.cs`/`ClassDefinition.cs`/`MobDefinition.cs`.
5. Update `combat-guide.ts` (Documentation tab) to describe the new authoring model — its current text
   documents the 14/7-field tables directly.

### AD8 — DB/API/Angular schema migration, phased — **RECOMMEND**
New migration (next after `0029`, so `0030`) **adds** the new columns alongside the old ones — doesn't
drop anything yet:
```sql
ALTER TABLE classes ADD COLUMN IF NOT EXISTS class_atk_base  REAL NOT NULL DEFAULT 0;
ALTER TABLE classes ADD COLUMN IF NOT EXISTS atk_per_level   REAL NOT NULL DEFAULT 0;
ALTER TABLE mobs    ADD COLUMN IF NOT EXISTS atk             REAL NOT NULL DEFAULT 0;
```
C#/API/Angular/TS all switch to reading the new fields in this same pass. Once verified in-editor *and*
in the simulator, a **follow-up** migration drops the 21 old `tier_l1_*`/`tier_l20_*`/`tier_*` columns —
matches this project's own established convention (the 2026-06-27 "deprecated-field cleanup pass": don't
remove old data until the replacement is confirmed working, but don't leave it around indefinitely
either). Touches: new migration, `api/Models/Class.cs`+`Mob.cs`, `ContentDbContext` mapping,
`ClassesController.cs`/`MobsController.cs`, `class.service.ts`/`mob.service.ts` (`Class`/`Mob`
interfaces), `class-editor.ts` (replace the Combat Tier Table section with a 2-field ATK Formula
section, same visual pattern as the existing HP/Mana Formula sections), `mob-editor.ts` (replace 7 tier
fields with 1 ATK field).

### AD9 — Numeric constants start as placeholders, tuned via the simulator — **RECOMMEND**
`MinAtk`/`MaxAtk` (AD4) and each class's `classAtkBase`/`atkPerLevel` (AD2) are not locked down with
made-up numbers in this devplan — they get picked during implementation using the rebuilt simulator
(AD7 step 3), the same way HP/Mana formula constants were originally tuned. §2.10's stat ratio (0.1)
stays as design-doc-given.

### AD10 — Weapon damage/delay: live DPS readout only, no formula — **DECIDED**
Confirmed a real, separate gap: `ItemDefinition.cs` has no level field at all, and the web Item Editor
is two bare number inputs (`weaponBaseDamage`, `weaponDelay`) with no readout of any kind — the same
"raw numbers, no formula" shape as the old tier table, just in item authoring instead of class
authoring. Deliberately **not** treated the same way as ATK, though — weapon damage/delay is itemization
content (loot design), where hand-authored variance per weapon is often intentional (a slow-hard-hitting
weapon vs. a fast-weak one are both legitimate, differentiated design choices), unlike a class's ATK
growth, which should be systematic. Forcing weapon numbers through a rigid formula would fight that.

Scoped narrowly, per explicit user choice — **just a live `damage / delay` ratio readout**, shown next
to the two fields wherever they're edited. No `intendedLevel` field, no target-DPS-by-level reference
curve, no schema change. Two places:
- **Web Item Editor** (`item-editor.ts`) — a computed readout next to the `weaponBaseDamage`/
  `weaponDelay` inputs, e.g. `{{ (model.weaponBaseDamage / model.weaponDelay) | number:'1.1-1' }} DPS`.
- **Combat simulator's `combatant-panel.ts`** — same live ratio next to its own weapon fields. Distinct
  from the *simulated* `dps` stat already shown further down in `combat-simulator.ts`'s swing-analysis
  results (which factors in hit rate/avoidance/tier — a different, already-existing number); this is the
  simpler raw weapon ratio, useful even before running a simulation.

Independent of AD1–AD9 — doesn't touch `CombatResolver`, doesn't depend on the ATK rework landing, and
could be pulled out and done standalone if useful to land sooner.

## Done when
1. The simulator (rebuilt) shows sane, class-differentiated ATK growth curves across level 1–20 for
   every class, and the swing/fight stats feel reasonable — validated *before* touching Unity.
2. `CombatResolver.ResolveAttack` produces the same class of output as before (a resolved hit tier),
   now driven by ATK instead of an authored table, verified in-editor for both player→mob and
   mob→player swings.
3. Authoring a new class's melee combat identity in the web Class Editor is 2 numbers, not 14; a new
   mob is 1 number, not 7.
4. STR/DEX (via weapon skill) demonstrably shift hit-tier outcomes in play — confirmable by comparing
   two otherwise-identical characters differing only in the relevant stat.

## Deferred / backlog seeds
- Real per-class `classAtkBase`/`atkPerLevel` numbers beyond an initial simulator-validated pass —
  ongoing playtesting-driven tuning, same as HP/Mana always has been.
- Whether `MinAtk`/`MaxAtk` needs to be zone- or content-tier-aware later (e.g. if endgame content wants
  a wider curve than early content) — not needed yet, single global band is simplest and sufficient for
  current content depth.
- The TS/C# dual-maintenance drift risk — flagged, not addressed here; a future shared-codegen approach
  is a bigger, separate investment.
