# Devplan 1.3 — Character-state schema + save/load round-trip

**Roadmap item:** M1 → 1.3 *(implemented after 1.4 per decision O1 — character state keys off a real
account, not a placeholder)*
**Status:** ✅ Done 2026-06-21 — verified in-editor: full round-trip restores XP/level, inventory,
equipment (stat bonus applied exactly once), currency, hotbar, current HP/mana, and position; accounts
stay isolated. Surfaced + fixed a pre-existing host-restart bug (`InventoryUI`/`EquipmentUI` latched
`_bound` and never rebound to the new local player after Stop Host → Start Host). O1–O5 decided.

> **Implementation notes (deviations from the plan, all minor):**
> - Repository is `Load` + `Upsert` only — character creation is folded into `Upsert`
>   (`INSERT … ON CONFLICT (account_id) DO UPDATE … RETURNING character_id`), so no separate
>   `LoadOrCreate`. Added `DeleteByAccount` for the wipe tool.
> - Saves are **driven by `GameNetworkManager`** (not `CharacterPersistence.OnStopServer`) to control
>   ordering vs. the persistence worker's flush: `OnServerDisconnect` saves the leaving player before
>   base destroys it; `OnStopServer` saves **all** connected players *before* `FlushAndStop`. Added
>   `PersistenceService.IsRunning` so post-flush saves no-op silently.
> - Each component got an `ExportX`/`LoadState` pair (capture + restore on the main thread).
> - Race/Class assets moved to `Resources/{Races,Classes}` (GUIDs preserved); Race & Class Editor
>   create-path updated to match so new assets stay registry-discoverable.
**Depends on:** 1.1 ✅ (Postgres + `Database`/`MigrationRunner`), 1.2 ✅ (`PersistenceService` —
off-thread DB + main-thread marshaling + coalescing queue), **1.4 ✅ (account→connection seam:
`conn.authenticationData` as `AccountSession`)**
**Unblocks:** 1.5 (character select/creation — adds the per-account character *list* on top of the
single character 1.3 persists), 1.6 (save cadence / multi-character / clean logout)

---

## Goal

Make the **existing default character survive a server restart**: write its mutable state to
Postgres on disconnect/stop and reload it on the same account's next login, reusing the 1.2 async
save queue + load dispatch. This is the first *real* persisted gameplay entity — it proves the whole
pipeline (capture snapshot → coalescing queue → SQL → load → re-apply to live `NetworkBehaviour`s)
on top of the account identity 1.4 established, **before** character creation (1.5) and save *policy*
(1.6) build on it.

Persisted state (per roadmap 1.3): **level/XP, currency, inventory contents, equipment, faction
scores, hotbar arrangement, current HP/mana, position + bind point**, plus the **race/class**
identifiers needed to reconstruct everything derived.

### Scope guardrails
- **In scope:** the `characters` + child-table schema + migration, a `CharacterRepository` +
  `CharacterSnapshot`, a server-only `CharacterPersistence` component that captures a snapshot on the
  main thread and re-applies a loaded one, minimal `LoadState` setters on the existing player
  components, a `RaceClassRegistry` for name→asset resolution, and **load-on-spawn /
  save-on-disconnect** wiring keyed off the authenticated account.
- **Out of scope:**
  - **Character select/creation UI (1.5).** 1.3 persists exactly **one character per account** — the
    existing default player. The first login with no character row auto-creates one (defaults spawn,
    saved on stop). 1.5 adds the list + name/race/class creation flow on top.
  - **Autosave cadence + multi-character + clean-logout polish (1.6).** 1.3 saves on
    disconnect/stop + a manual editor command only — enough to prove the round-trip.
  - **Race/class *content* in the DB (M2.6).** Race/class stay ScriptableObjects; 1.3 persists only
    their *identifier* and re-resolves the asset via `RaceClassRegistry`. M2.6 swaps the registry
    source for the DB loader behind the same lookup.
- **Hard rule (carried from 1.2):** server-authoritative. The worker thread only ever touches the
  plain `CharacterSnapshot` + Npgsql; the snapshot is captured from live components on the main
  thread, and a loaded snapshot is re-applied on the main thread.

## Approach

### 1. What we persist vs. what we reconstruct

Most character state is **derived** and must not be stored raw, or it desyncs from the formulas:

| State | Source of truth | Persist? |
|---|---|---|
| Level | derived from `_totalXp` (`PlayerExperience.Level`) | ❌ store XP only |
| STR/STA/…/CHA totals | race/class base + equipment bonuses (`CharacterStats`) | ❌ reconstruct from race/class + equipment |
| Max HP / Max mana | class formula × stats × level (`Health.EffectiveMax` / `PlayerMana`) | ❌ recompute via `RefreshMax()` |
| Known abilities | `ClassDefinition.startingAbilities` (`PlayerAbilities._knownAbilities`) | ❌ reconstruct from class |
| **Total XP** | `PlayerExperience._totalXp` | ✅ |
| **Currency** (cp/sp/gp/pp) | `PlayerInventory._copper/_silver/_gold/_platinum` | ✅ |
| **Inventory** (8 × {itemId, qty}) | `PlayerInventory._slots` (`SyncList<InventorySlot>`) | ✅ |
| **Equipment** (13 × itemId) | `PlayerEquipment._slots` (`SyncList<string>`) | ✅ |
| **Faction scores** (faction→score) + actual/apparent race | `PlayerFactionScores._scores` + `ActualRace`/`ApparentRace` | ✅ |
| **Hotbar** (8 × abilityId) | `PlayerAbilities._hotbar` (player-customizable arrangement) | ✅ |
| **Current HP / current mana** | `Health._current` / `PlayerMana._current` | ✅ (O3) |
| **Position + yaw, bind point** | `NetworkedPlayer.transform` + `_bindPoint` | ✅ |
| **Race / class identifier** | prefab default today (`_defaultRace`/`_defaultClass`); char creation in 1.5 | ✅ (needed to reconstruct the ❌ rows) |

So the stored data is small: a handful of scalars + four small collections. Loading **re-applies
XP → race/class → equipment (re-adds bonuses) → faction scores → hotbar → currency/inventory →
current HP/mana → position**, then everything derived recomputes through the existing `RefreshMax()`
paths.

### 2. Character identity — keyed off the account (1.4 seam)

1.4 stashes an `AccountSession { AccountId, Username, Token }` in `conn.authenticationData` and
`GameNetworkManager.OnServerAddPlayer` already reads it. 1.3 resolves the character from that
account:

- `CharacterPersistence` (on the player) reads `connectionToClient.authenticationData as
  AccountSession` in `OnStartServer` → `session.AccountId`.
- The DB key is the **account** (1.3 = one character per account; `UNIQUE(account_id)` enforces it,
  relaxed in 1.6 for multi-character). The resolved/created `character_id` is what the child tables FK
  to.
- Host testing exercises the real path: host logs in as the seeded `dev` account (1.4), so the same
  `dev` character is loaded/saved across restarts.

There is **no placeholder key** — that was the pre-1.4 design and is dropped now that accounts exist.

### 3. Schema — normalized child tables (decision O2)

`characters` holds the scalar core (FK to `accounts` from 1.4); the four variable collections live in
child tables FK'd to `characters` with `ON DELETE CASCADE`. The repository reads/writes the whole set
**atomically in one transaction** (1.2's `RunInTransaction`); the character is always loaded/saved as
a unit by account, never queried by "who owns item X".

> **Migration number = `0005_character_state.sql` (not 0003).** The runner applies any *pending* file
> (version not in `schema_version`) in **ascending version order** (`MigrationRunner.Run`). On a
> **fresh** DB it would therefore run a `0003` *before* `0004_accounts.sql` — and these tables FK to
> `accounts`, so that ordering would fail. Numbering the character migration **above** accounts
> (`0005`) guarantees `accounts` exists first on both fresh and already-migrated DBs. (O5's
> `dal_smoke` drop is already handled by `0004` — nothing to do here.)

```sql
CREATE TABLE IF NOT EXISTS characters (
    character_id    BIGSERIAL   PRIMARY KEY,
    account_id      BIGINT      NOT NULL UNIQUE REFERENCES accounts(account_id) ON DELETE CASCADE, -- 1 char/account in 1.3; UNIQUE relaxed in 1.6
    name            TEXT        NOT NULL DEFAULT '',   -- populated by character creation in 1.5
    race_name       TEXT        NOT NULL,
    class_name      TEXT        NOT NULL,
    total_xp        INTEGER     NOT NULL DEFAULT 0,
    copper          INTEGER     NOT NULL DEFAULT 0,
    silver          INTEGER     NOT NULL DEFAULT 0,
    gold            INTEGER     NOT NULL DEFAULT 0,
    platinum        INTEGER     NOT NULL DEFAULT 0,
    current_health  INTEGER     NOT NULL DEFAULT 0,
    current_mana    INTEGER     NOT NULL DEFAULT 0,
    pos_x           REAL        NOT NULL DEFAULT 0,
    pos_y           REAL        NOT NULL DEFAULT 0,
    pos_z           REAL        NOT NULL DEFAULT 0,
    yaw             REAL        NOT NULL DEFAULT 0,
    bind_x          REAL        NOT NULL DEFAULT 0,
    bind_y          REAL        NOT NULL DEFAULT 0,
    bind_z          REAL        NOT NULL DEFAULT 0,
    actual_race     TEXT        NOT NULL DEFAULT '',
    apparent_race   TEXT        NOT NULL DEFAULT '',
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS character_inventory (
    character_id    BIGINT  NOT NULL REFERENCES characters(character_id) ON DELETE CASCADE,
    slot_index      INTEGER NOT NULL,                 -- 0..7
    item_id         TEXT    NOT NULL,
    quantity        INTEGER NOT NULL,
    PRIMARY KEY (character_id, slot_index)
);

CREATE TABLE IF NOT EXISTS character_equipment (
    character_id    BIGINT  NOT NULL REFERENCES characters(character_id) ON DELETE CASCADE,
    slot            INTEGER NOT NULL,                 -- EquipSlot enum index, 0..12
    item_id         TEXT    NOT NULL,
    PRIMARY KEY (character_id, slot)
);

CREATE TABLE IF NOT EXISTS character_faction_scores (
    character_id    BIGINT  NOT NULL REFERENCES characters(character_id) ON DELETE CASCADE,
    faction_name    TEXT    NOT NULL,
    score           INTEGER NOT NULL,
    PRIMARY KEY (character_id, faction_name)
);

CREATE TABLE IF NOT EXISTS character_hotbar (
    character_id    BIGINT  NOT NULL REFERENCES characters(character_id) ON DELETE CASCADE,
    slot_index      INTEGER NOT NULL,                 -- 0..7
    ability_id      TEXT    NOT NULL,
    PRIMARY KEY (character_id, slot_index)
);
```

Empty inventory/equipment/hotbar slots are stored as rows with `item_id = ''` / `ability_id = ''`
(simplest — fixed slot counts round-trip exactly without sparse-index bookkeeping). Save writes child
tables as **delete-all-for-character then insert** inside the transaction (small fixed row counts;
avoids per-slot upsert/diff logic).

### 4. `CharacterSnapshot` (plain data — main-thread captured)

A serializable, Unity-free class holding exactly the persisted fields above:
`long AccountId; long CharacterId (0 = not yet inserted); string Name, RaceName, ClassName; int
TotalXp, Copper..Platinum, CurrentHealth, CurrentMana; float PosX,PosY,PosZ,Yaw,BindX,BindY,BindZ;
string ActualRace, ApparentRace; InvEntry[] Inventory (8); string[] Equipment (13);
Dictionary<string,int> FactionScores; string[] Hotbar (8)`. `InvEntry` is a tiny `{string Id; int Q}`
so the Mirror `InventorySlot` serializer never crosses the thread boundary. This is the only object
the worker thread touches.

### 5. `CharacterRepository` (raw Npgsql, the 1.2 convention)

```
long LoadOrCreate(NpgsqlConnection conn, NpgsqlTransaction tx, long accountId, CharacterSnapshot defaults)
                                                  // returns character_id; inserts a default row if none
CharacterSnapshot Load(NpgsqlConnection conn, long accountId, NpgsqlTransaction tx = null) // null if no character row
void Upsert(NpgsqlConnection conn, NpgsqlTransaction tx, CharacterSnapshot s)  // characters UPSERT + child delete-then-insert, one tx
```

Parameterized commands only; child tables written via `RunInTransaction` so a partial save can't
leave the character half-written. Reads take an optional `tx` so they work inside a worker job's
transaction or on a standalone load connection (mirrors `DalSmokeRepository` / `AccountRepository`).

### 6. `CharacterPersistence` (new server-only component on the player)

One component coordinates capture/apply so existing gameplay scripts stay focused:

- **`OnStartServer`** → resolve `accountId` from `connectionToClient.authenticationData`; kick off the
  load: `PersistenceService.Instance.LoadAsync(conn => _repo.Load(conn, accountId),
  ApplyOrInitialize)`. The async result lands on the main thread (1.2's pump) **after** every sibling
  component's `OnStartServer` has initialized defaults, so apply cleanly overlays.
- **`ApplyOrInitialize(snapshot)`** → non-null ⇒ `ApplySnapshot`; null (first login) ⇒ leave the
  freshly-defaulted character and mark dirty so the first save inserts the row.
- **`CaptureSnapshot()`** (main thread) → read each sibling component into a `CharacterSnapshot`.
- **`Save()`** → `PersistenceService.Instance.EnqueueSave(new KeyedDelegateSaveJob("character:" +
  accountId, (c,tx) => _repo.Upsert(c, tx, CaptureSnapshot())))`. The coalesce key collapses repeat
  saves of the same character to the latest snapshot (1.2 behavior).
- **`OnStopServer`** → `Save()` (covers both disconnect *and* server shutdown; the queue is drained by
  `GameNetworkManager.OnStopServer` → `FlushAndStop`). Guarded against double-save.

### 7. Minimal restore setters on existing components

Each component keeps its base `OnStartServer` defaults; 1.3 adds a small server-only `LoadState`
overlay that triggers the existing recompute paths. No gameplay logic moves.

- `PlayerExperience.LoadState(int totalXp, RaceDefinition, ClassDefinition)` — set `_totalXp`, call
  the existing `ApplyModifier(race, cls)` (already refreshes stats → HP/mana → known abilities via
  `CharacterStats.SetRaceClass` + `PlayerAbilities.SetRaceClass`).
- `PlayerInventory.LoadState(InvEntry[] slots, int cp, int sp, int gp, int pp)` — overwrite `_slots`
  + currency fields.
- `PlayerEquipment.LoadState(string[] slots)` — for each non-empty slot set `_slots[i]` and **re-add
  its stat bonus once** (the same `CharacterStats.AddEquipmentBonus` path `TryEquip` uses), then it
  triggers `Health.RefreshMax()` / `PlayerMana.RefreshMax()`. Must run **after** `PlayerExperience`
  (race/class base stats) so bonuses stack on the right base, and **without** double-counting.
- `PlayerFactionScores.LoadState(string actual, string apparent, Dictionary<string,int>)` —
  repopulate `_scores` + set `ActualRace`/`ApparentRace`.
- `PlayerAbilities.LoadHotbar(string[] hotbar)` — set `_hotbar` entries (known abilities already
  reconstructed from class; only the *arrangement* is restored, each validated against
  `_knownAbilities`).
- `Health.SetCurrent(int)` / `PlayerMana.SetCurrent(int)` — set `_current` **after** `RefreshMax`,
  clamped to `[0, Max]`.
- `NetworkedPlayer` — add `Position`/`Yaw` getters, `BindPoint` getter (setter `SetBindPoint` exists),
  and a CC-safe `Teleport(Vector3 pos, float yaw)` reusing the existing disable-CC → set-position →
  enable-CC pattern already used by respawn (`NetworkedPlayer.cs:367-386`).

**Apply order matters** and lives entirely inside `ApplySnapshot`:
`XP + race/class → equipment bonuses → faction + hotbar → currency/inventory → RefreshMax → current
HP/mana → position`. (Maxes must settle before clamping current HP/mana.)

### 8. Re-resolving race/class on load — `RaceClassRegistry` (decision O4)

Race/class are ScriptableObjects in `Assets/ScriptableObjects/{Races,Classes}/` — not under
`Resources/`, so there's no runtime name lookup today. 1.3 adds a small server-side
`RaceClassRegistry` (`Resources.Load`-style: scans on first use, `GetRace(name)` / `GetClass(name)`),
and the two asset folders move under `Resources/` (alongside `Resources/Abilities`,
`Resources/Items`). This is the minimal seam; **M2.6 swaps the registry's source for the DB loader**
behind the same two methods. The persisted `race_name`/`class_name` come from
`PlayerExperience.CurrentRace`/`CurrentClass` (the prefab default today, character creation in 1.5).

### 9. Lifecycle wiring

- Migration `0005_character_state.sql` applied by the existing runner (host start or
  `Tools/Database/Run Migrations`).
- `CharacterPersistence` added to the player prefab (server logic only; no client footprint) via
  `Tools/Patch Player Prefab` or manual add.
- Load on player `OnStartServer`; save on player `OnStopServer` (disconnect/shutdown) — drained by the
  existing `GameNetworkManager.OnStopServer` → `FlushAndStop`.
- `Tools/Database/Save Character Now` + `Tools/Database/Wipe Character (by account)` editor menus for
  testing.

## Test plan

1. `Tools/Database/Run Migrations` → applies `0005` (`schema_version` gains a row); re-run → none
   pending. Confirm on a **fresh** DB the full chain applies in order (0001→0002→0004→0005) with no FK
   error.
2. **First-login insert:** start Host as `dev` with empty character tables → load returns null,
   character spawns at defaults, console logs "no saved character — starting fresh."
3. **Round-trip:** as the `dev` host — gain XP (kill a rat), pick up + equip an item, move currency,
   rearrange a hotbar slot, walk to a distinct spot → **Stop Host**. Console shows the save enqueued +
   queue flushed. Inspect in `psql` (`SELECT * FROM characters;` + child tables) — values match.
4. **Reload:** start Host again as `dev` → character loads with the **same** XP/level, inventory,
   equipped item (stat bonuses re-applied — verify totals), currency, hotbar arrangement, position,
   current HP/mana.
5. **No double-applied equipment bonus:** record a stat (e.g. STR) with the item equipped, relog, and
   confirm STR is identical — the bonus is applied exactly once on load.
6. **Derived recompute:** Max HP / Max mana match the formula for the loaded level+stats (not a stored
   stale value), and known abilities repopulate from class.
7. **Account isolation:** register a 2nd account (e.g. `alice`), play, stop → confirm `alice` gets her
   own `characters` row and `dev`'s state is untouched (account_id keying works).
8. **Crash safety:** exit Play mode *without* Stop Host (domain reload) — no orphaned worker; next
   start loads the last *saved* state (unsaved progress since last save is lost, expected for 1.3's
   save-on-stop-only policy; autosave is 1.6).
9. `Tools/Database/Wipe Character (by account)` → rows cascade-deleted → next login is a fresh
   character.

## Resolved decisions (review 2026-06-21 — carried into this rewrite)
- **O1 — Identity → keyed off the account.** No placeholder key; built after 1.4. Character resolves
  from `AccountSession.AccountId` on `conn.authenticationData`. One character per account in 1.3
  (`UNIQUE(account_id)`, relaxed in 1.6).
- **O2 — Storage shape → NORMALIZED child tables.** `characters` (scalar core, FK to `accounts`) +
  `character_inventory` / `character_equipment` / `character_faction_scores` / `character_hotbar`,
  written in one transaction (1.2's `RunInTransaction`). The earlier JSONB single-row sketch is
  superseded.
- **O3 — Current HP/mana → PERSIST current** (truthful resume; applied after `RefreshMax`, clamped).
- **O4 — Race/class re-resolution → ADD `RaceClassRegistry`** + move Race/Class assets under
  `Resources/`. M2.6 later swaps the source for the DB loader behind the same lookup.
- **O5 — `dal_smoke` drop → already handled by `0004_accounts.sql`** (done in 1.4); nothing for 1.3.

## Carried decisions
- **Persist the small mutable set; reconstruct everything derived** (stats, maxes, known abilities,
  level) — avoids formula/stored desync.
- **Reuse 1.2 wholesale:** `KeyedDelegateSaveJob` with coalesce key `character:<accountId>`,
  `LoadAsync` for the read, main-thread apply.
- **Save-on-stop (disconnect/shutdown) + manual editor save only** for 1.3; cadence is 1.6.
- **Raw Npgsql + hand-written SQL** (carried from 1.1/1.2).

## Risks
- **Migration ordering** — the character migration MUST be numbered above `0004` (it FKs to
  `accounts`); numbered `0005` so fresh-DB ascending-order application keeps `accounts` first.
  Verified against `MigrationRunner.Run` (applies pending in version order). Covered by test 1.
- **Equipment double-bonus on load** — if `LoadState` re-adds bonuses on top of an already-applied
  set, stats inflate on every relog. Apply bonuses exactly once, after race/class base, before
  `RefreshMax`. Covered by test 5.
- **Apply-order desync** — current HP/mana clamped before maxes settle would clip the values. Order is
  fixed inside `ApplySnapshot` and is the single source of truth.
- **Connection drop mid-load** — the async load can resolve after the player despawned; `ApplyOrInitialize`
  must null-check the component/`isServer` before touching siblings (same guard discipline as 1.4).

## Done when

A Host logged in as an account can gain progress, stop, and log back in with the **same character
fully restored** — XP/level, currency, inventory, equipment (bonuses re-applied without
double-count), faction scores, hotbar arrangement, current HP/mana, and position — through the 1.2
async queue with no tick stalls, with derived state recomputed (not stored stale), each account
isolated to its own character row, ready for 1.5 to add character creation on top.
