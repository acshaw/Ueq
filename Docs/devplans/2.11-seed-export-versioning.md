OpenConnection()` (`Assets/Scripts/Server/Database/Database.cs`) caches the resolved connection string in

`Tools/Database/...` menu action keeps silently reusing the previously-resolved connection. Hit this twice
during the test (both "no pending migrations" against a table-less DB, and the initial "why is this still
the real DB" moment) before recognizing the pattern.

## Goal

Close out M2 with the cross-cutting tooling named in the roadmap line: a reproducible DB seed (already
mostly solved — confirm, don't rebuild), a way to move a dev DB's actual authored content between
environments (another dev's machine, or promoting to AWS at M6), and a content-change audit trail. Unlike
2.2–2.10, this item isn't "migrate one more content type" — it's ops tooling that sits *above* all of them,
so it's scoped and grounded differently.

## Grounding (read before designing)

- **Reproducible seed already exists and works**: `DatabaseSeeder.Seed(conn)` runs every `SeedX` method
  idempotently (`ON CONFLICT ... DO NOTHING`, or an explicit "already exists → skip children" guard for
  multi-table types). It runs automatically at Host start (`Database.InitializeServer`, gated by
  `SeedOnStart`) or on demand via `Tools/Database/Seed Database`. A fresh DB + migrations + seed reliably
  reproduces the same starting content every time — this is **not a gap**, and 2.11 doesn't need to touch
  it. What `DatabaseSeeder` is *not* is a mechanism for capturing content a web-editor session actually
  added beyond the seeded starters — that's what export/import (SE2) is for.
- **All existing DB tooling lives in Unity Editor menus under `Tools/Database/*`** (`DatabaseTools.cs`):
  Test Connection, Run Migrations, Seed Database, DAL Self-Test, Create Account, Wipe Character, Reset —
  all hand-written Npgsql, no shell scripts, no EF. This is the established convention 2.11's new tooling
  should follow, not a pg_dump/psql wrapper (which would be the more "database-native" choice in a vacuum,
  but breaks from how every other DB operation in this project is exposed to the user).
- **The content/player-state split is already a first-class concept**, stated directly in this roadmap
  file (line 37–39): content/definitions (races, classes, abilities, items, mobs, factions, conversations,
  loot, spawn tables, vendors, XP curve) vs. player/account runtime state (accounts, characters +
  `character_*` child tables). This split is exactly the exclude-list export needs (SE2) — it doesn't need
  inventing, just applying.
- **No auth exists yet** (2.1 decision D2: "No auth for now — trusted users only; revisit when hosted/
  remote"). A real "who changed this row" audit log has no identity to attribute to until that lands
  (tracked as **6.3 — transport security + real auth**). This directly shapes SE4's scope.
- **Real, grounded gap found while checking this**: `updated_at` is already the convention on every
  content *header* table except three — `races`, `classes`, and `ability_tags` (2.10/2.9 didn't add it,
  checked by grepping every migration for the column). Every other header table (`items`, `mobs`,
  `factions`, `loot_tables`, `spawn_tables`, `conversation_sets`, `vendor_inventories`, `abilities`) has
  it and stamps it on every `PUT`. This is a real, fixable inconsistency, not a hypothetical one.

## Decisions

**SE1 — Reproducible seed: confirm, don't rebuild.** No code change. `DatabaseSeeder` already satisfies
this half of 2.11's scope. Document it as done in the roadmap line rather than treating it as an open
build item.

**SE2 — Content export/import: generic, schema-driven, not per-content-type code (the real deliverable).**
Recommend **against** hand-listing every content table in C# (via each type's existing repository) —
that list would need updating every time a new content type ships, exactly the maintenance burden 2.9/
2.10 just demonstrated happens every couple weeks. Instead: **export = enumerate every base table in the
`public` schema via `information_schema.tables`, minus a small explicit exclude-list** (`schema_version`,
`accounts`, `characters`, `character_inventory`, `character_equipment`, `character_faction_scores`,
`character_hotbar`, plus the already-dead `content_ping`) — everything else is content by construction,
matching the roadmap's own stated split. For each included table, read its columns from
`information_schema.columns` (not from the row data — a table with zero rows still needs a correct shape)
and every row via a plain `SELECT`, and serialize the whole thing to one JSON file:
`{ "tables": { "items": { "columns": [...], "rows": [[...], [...]] }, ... } }`.

**SE3 — Import strategy: wipe-and-reload inside one transaction, not upsert.** Row-by-row upsert would
need per-table primary-key knowledge (natural string ids on header tables, serial `id` on children) and
wouldn't remove a row that was deleted in the source DB. Simpler and more correct: inside one transaction,
`SET session_replication_role = replica` (disables FK/trigger enforcement for the session — a standard
Postgres bulk-reload pattern), `TRUNCATE` every included table, bulk-`INSERT` every row from the JSON in
any order (constraints are off, so table order doesn't matter), `SET session_replication_role = DEFAULT`,
then `SELECT setval(...)` against each serial child table's sequence from its current `MAX(id)` so future
API-driven inserts don't collide with imported ids. All of this commits or rolls back as one unit — a
partial import never leaves the DB half-truncated.

**SE4 — Audit trail: fix the real `updated_at` gap now, defer a full change-history log until auth
exists.** A true audit log (who changed what, when, old→new value) needs a "who," which doesn't exist
until 6.3. Building one now would mean either attributing every change to an anonymous placeholder (low
value) or blocking 2.11 on pulling auth forward (out of scope, a bigger item). Recommend: (a) a small
migration adding `updated_at` to the 3 tables missing it (`races`, `classes`, `ability_tags`) + wiring
their controllers' `Update()` to stamp it, closing the real inconsistency found in Grounding — this is
cheap, matches existing convention, and gives a "last touched when" signal for free; (b) explicitly note
in the roadmap that full change attribution is deferred to 6.3, not silently dropped.

**SE5 — Where the tooling lives.** `Tools/Database/Export Content...` (file-save dialog → writes the JSON)
and `Tools/Database/Import Content...` (file-open dialog → confirms "this replaces ALL content in the
target DB" since it's destructive → runs the transaction), both in `DatabaseTools.cs` alongside the
existing menu items, using `Database.OpenConnection()` like every other DB tool. Moving content to AWS is
then: point `db.config.json`/env vars at the target DB, run Import Content with a file exported from dev.
No new multi-DB connection UI — matches the existing single-target-connection-string design.

## Implementation log (2026-07-18)

Implemented as designed (SE1–SE5), with the design tightened on one real correctness question that
came up while writing the transaction logic in SE3: **how JSON round-trips mixed-type row data.** The
devplan didn't spell this out, and the naive approach (store each row as a raw JSON array of
numbers/strings/booleans, `List<object>`) is a real footgun — Newtonsoft's default `object`-typed
deserialization turns JSON numbers into `long`/`double` (not the original `int`/`float`) and can
silently misfire its date-autodetection heuristic on an innocent TEXT value that happens to look
date-shaped. Resolved by having every value round-trip as its **canonical string form** instead (`"123"`,
`"true"`, an ISO-8601 timestamp string, or the literal text) — the column's Postgres type, captured once
per table at export time (`information_schema.columns.data_type`), is stored alongside and is what
import uses to parse each string back into the exact right value and `NpgsqlDbType` for the parameterized
`INSERT`. This removes JSON type-inference from the equation entirely; the only ambiguity left is `null`
vs. a real string, which Newtonsoft/JSON already represent unambiguously.

The TRUNCATE step also needed a specific form to be correct regardless of whether
`session_replication_role = replica` actually suppresses Postgres's TRUNCATE-time FK safety check (it's
documented to suppress row-level trigger-based FK enforcement for DML, but TRUNCATE's own multi-table
FK check is a separate code path and the docs don't unambiguously guarantee replica-role bypasses it) —
so the import truncates **every target table in one single combined `TRUNCATE TABLE a, b, c, ... CASCADE`
statement** rather than relying on the session variable for that step. `session_replication_role =
replica` is still set for the INSERT phase, where it's the standard, well-documented mechanism for
loading rows in any order regardless of FK dependency direction.

**Build verification**: `dotnet build` (API, scratch output dir — live process running) — 0 errors, 0
warnings. Brace-balance check on all 5 touched/new files — all balanced. **Could not compile-check or
exercise the Unity side** (project open in the user's own Editor, same constraint as 2.9/2.10) — the
export/import transaction logic is new, non-trivial SQL that genuinely needs a real round-trip test
against a live DB (see the test plan) before this is trusted, more so than the 2.9/2.10 "same shape,
different fields" work.
