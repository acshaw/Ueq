# 3.3 — NPC Item-Giving (Item-Triggered Conversation Keywords)

**Status:** ⏸️ Held 2026-07-12 — design accepted in shape (G1–G8), **implementation deliberately deferred**
until a concrete in-game need shows up (a real item/NPC pairing to build, not just the illustrative locket
example). Re-open this file and implement directly off the decisions below when that need appears; no
further design work should be needed first unless the use case doesn't fit the shape here.

Lets a player hand an item directly to an NPC — no chat text, no keyword typed — and have that act itself
trigger a conversation response, unlock follow-up keywords, and optionally grant a reward, exactly like a
spoken keyword does today. Concrete motivating case (user-supplied): a player finds a locket engraved "MJ",
realizes it belongs to an NPC named Mary Jane, and hands it to her with no other prompt. She launches into
a response ("Why thank you! I thought this was gone forever...") that opens a brand-new dialogue thread the
player couldn't have discovered by typing — because they didn't know the beast/location existed yet.

## Why

Roadmap 3.3 was originally scoped as "NPC item-giving," but 3.2 already absorbed the *quest turn-in* half
(hand over required items as part of a keyword transaction, gated behind typing that keyword). What's left
is genuinely different: **the item hand-off itself is the trigger**, not a requirement attached to a typed
word. There's no way today for giving an item, on its own, to make an NPC say something new or unlock a
thread the player had no way to ask for by name.

## Grounding — what already exists, what's missing

Read `NpcConversation.cs`, `ConversationKeyword.cs`, `NpcEventDispatcher.cs`, `NpcEvents.cs`,
`KeywordRewardApplicator.cs`, `InventoryUI.cs`, and `NetworkedPlayer.TryTarget` before designing this.
Findings:

- `NpcConversation.HandleMatch(player, kw)` already does everything a hand-off response needs — delivers
  the response (with token substitution), applies `UnlocksKeywords`, dispatches
  `IOnConversationKeyword` to every listener on the NPC, and ends the conversation if flagged. It doesn't
  care *how* a keyword was matched — today the only caller is `HearMessage` (text match), but nothing about
  `HandleMatch` itself is text-specific.
- `KeywordRewardApplicator` (3.2) is itself just another `IOnConversationKeyword` listener — it fires
  whenever `HandleMatch` dispatches, and no-ops unless the keyword `HasTransaction`. An item-give keyword
  gets a free optional reward/second-cost bundle for nothing if it goes through the same dispatch.
- `InventoryUI` already has the exact interaction primitive this needs: click a slot to "hold" an item
  (cursor-follow), then click elsewhere to place it — and clicking in the 3D world with nothing held drops
  it (`InventoryUI.Update`, the `_heldSlotIndex >= 0` branch). It doesn't yet distinguish "clicked on an
  NPC" from "clicked on empty ground."
- `NetworkedPlayer.TryTarget` shows the exact raycast-for-`Targetable` pattern to reuse for "what did I
  click on."
- **Real gap:** there is no path from "player releases an item onto an NPC" to anything happening. This
  devplan adds that one path and reuses everything else.

## Approach

### G1 — Where the trigger lives: extend `ConversationKeyword`, don't build a parallel system

Add two fields to `ConversationKeyword`: `IsItemTrigger` (bool) and `TriggerItemId` (string). When
`IsItemTrigger` is true, this keyword is matched by **giving** `TriggerItemId` to the NPC, not by typing
`Keyword` in chat — `Keyword` becomes an internal label only (used for `Unlocks`/dispatch, not typed).
Every other field keeps its existing meaning unchanged: `Mode` (Passive fires from Idle without a prior
hail; Active requires an open conversation — see G7), `IsConversationOpener`, `EndsConversation`,
`RequiresUnlock`/`UnlocksKeywords`, `RequiredFactionId`/`RequiredStanding`, `Response`, and the whole 3.2
quest-transaction bundle.

**Recommended.** This is a ~15-line addition to an existing class plus one new server entry point
(G3), versus inventing a second authoring surface, a second matching/gating code path, and a second
web editor screen that would duplicate `Mode`/`Unlocks`/faction-gate/response semantics badly. Everything
an author already knows about keywords (opener, unlock chains, faction gates) applies unchanged to an
item-trigger keyword.

### G2 — Consumption semantics

Giving consumes exactly **1 unit** of the matched item, server-side, only on a successful match (right
mode/unlock-state/faction-gate). No match → nothing is removed from the player's inventory; the item stays
in their held slot. This is separate from — and happens *before* — any optional 3.2 quest-transaction on
the same keyword (G4): the trigger item itself is always the "cost of admission," a transaction bundle is
an optional *additional* exchange layered on top.

**Recommended: exactly 1 unit, silent no-op on no match** (mirrors `HearMessage`'s existing silent
no-match behavior for unrecognized chat text — no error, no wasted item). Giving a full stack at once, or
letting the player choose a quantity, is unnecessary for unique/quest-flavored items and adds UI complexity
for no clear use case yet.

### G3 — Server entry point

New `NpcConversation.ReceiveItem(NetworkIdentity player, string itemId)`:
1. Same range/faction checks `HearMessage` already applies (`hearingRange`, `IsPlayerTargetingMe` — see
   G7 on the latter).
2. Scan `EffectiveKeywordSet.Keywords` for the first `IsItemTrigger` keyword whose `TriggerItemId` matches,
   respecting `Mode`/`RequiresUnlock`/faction-gate exactly like `HearMessage` does today (shared filter
   logic — refactor the guard clauses out of `HearMessage` into a small shared predicate rather than
   duplicating them).
3. On a match: remove 1 unit of `itemId` from the player's `PlayerInventory` (`RemoveItem(itemId, 1)`),
   then call the existing `HandleMatch(player, kw)` unchanged.
4. No match: no-op (G2).

### G4 — Item-trigger keywords may also carry a 3.2 quest transaction

Yes — `RequiredItems`/`RequiredCopper`/`RewardXp`/`RewardCopper`/`RewardItems`/`RewardFactionHits` all stay
usable on an item-trigger keyword, unchanged, because `KeywordRewardApplicator` listens to the same
`IOnConversationKeyword` dispatch `HandleMatch` already fires. This costs nothing new and covers "give the
locket, get a small reward too" for free. The trigger item itself is *not* auto-added to `RequiredItems` —
those stay independent (e.g. you could require an *additional* item or coin on top of the hand-off, though
that'll be a rare combination).

**Recommended: yes, reuse as-is, no new code for this part.**

### G5 — A dedicated `IOnItemGiven` hook, for non-dialogue listeners

Add `IOnItemGiven { void OnItemGiven(NetworkIdentity player, string itemId, int quantity); }` to
`NpcEvents.cs`, plus `NpcEventDispatcher.DispatchItemGiven(...)`, fired by `ReceiveItem` alongside (not
instead of) the existing `DispatchConversationKeyword`. This exists so a purely mechanical listener (a
future door/lever/altar component) can react to "I was given item X" directly, without needing to know or
hardcode the keyword's internal label string. Cheap — a handful of lines mirroring the other
`Dispatch*` methods already on `NpcEventDispatcher`.

**Recommended: yes.** It's nearly free given G3 already resolves `(player, itemId)` at the match site, and
it decouples "what unlocks a door" from "what string an author typed into the Keyword field."

### G6 — Scope: NPCs only, not arbitrary world objects

`NpcEventDispatcher` requires a `Health` component (`[RequireComponent(typeof(Health))]`) — it's built for
things that are NPCs/mobs, not generic world props. A literal standalone door (no dialogue, no health, not
a `MobApplicator`) is **out of scope for 3.3** even though G5's hook would make it easy to wire up *if* the
object were dressed as an NPC (e.g. an invisible/inert "door NPC" with `NpcConversation` +
`NpcEventDispatcher` and a `DoorController : IOnItemGiven` sibling component). A lighter-weight
"world interactable" that doesn't require `Health`/mob scaffolding is real future work but not this item —
flagging so it isn't assumed included.

### G7 — Client interaction: extend the existing held-item click, don't add new UI

In `InventoryUI.Update()`, the `_heldSlotIndex >= 0` branch currently drops the item on *any* world click
that isn't over UI. Change it to first raycast for a `Targetable` at the click point (same pattern as
`NetworkedPlayer.TryTarget`) — if hit and it has a `NetworkIdentity`, call a new
`NetworkedPlayer.CmdGiveItem(int slotIndex, NetworkIdentity target)` instead of dropping; otherwise fall
back to the existing drop-on-ground behavior unchanged. `CmdGiveItem` validates the slot server-side,
resolves `target.GetComponent<NpcConversation>()`, and calls `ReceiveItem`. Also sets the player's
`ServerTarget`/highlight on a successful click (mirrors `TryTarget`'s side effect, keeps target-frame UI in
sync) regardless of whether a keyword matched.

**Recommended.** No new button, no context menu, no drag-and-drop rework — "pick the item up, click the
NPC" is one extra branch in code that already exists and matches the physical "hand it over" framing of
the motivating example.

### G8 — `IsPlayerTargetingMe` gate on item-trigger keywords

The Conversation guide (§10) already flags that `HearMessage` requires the player to have the NPC targeted
even for Passive text keywords — a known gap versus the original "always listening" design. For item-give,
requiring a target is *not* a gap — the click that gives the item is itself a targeting action (G7 sets the
target on click), so this restriction is natural here, not a workaround. No new decision needed; `ReceiveItem`
reuses the same guard `HearMessage` uses, and it's correct for this trigger type specifically.

## Schema / API changes

New migration `0021_conversation_item_triggers.sql`:
```sql
ALTER TABLE conversation_keywords ADD COLUMN IF NOT EXISTS is_item_trigger  BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE conversation_keywords ADD COLUMN IF NOT EXISTS trigger_item_id TEXT;
```
Additive, defaults preserve every existing keyword as a text-trigger. No new tables — G4 already reuses the
0020 quest-transaction child tables unchanged.

API: `ConversationKeywordDto`/entity/`ConversationsController` gain the two scalar fields (same pattern as
0020's `reward_xp`/`reward_copper`/`required_copper` scalars — no new mapping shape).

## Test plan

1. Author (web): a keyword on some NPC's set — `IsItemTrigger` on, `TriggerItemId = locket`, Opener on,
   response the MJ line, unlocks a follow-up text keyword (`what_beast`). Restart the Unity host.
2. In-game: acquire a `locket` item (loot/seed it), target-free approach to the NPC, pick the locket up
   from inventory, click the NPC → response fires, locket is consumed (slot empties), the follow-up keyword
   is sayable (typing `what beast` now responds; before giving, it didn't).
3. Give a non-matching item to the same NPC → nothing happens, item stays in inventory.
4. Give the same item again (locket already given, now gone) → obviously can't repeat without acquiring
   another — confirms no free-standing "already triggered" state is needed (repeatable by nature, same as
   3.2's quest keywords, since possession is the gate).
5. Add a small `RewardXp` to the same keyword (G4) → giving now also grants XP with Reward-channel chat.
6. Faction-gate the keyword → giving while under-standing silently does nothing (same as a gated text
   keyword).
7. (Optional, if G5 built) Attach a throwaway `IOnItemGiven` test listener to confirm it fires alongside
   the keyword dispatch.

## Done when

Giving an item to an NPC that has a matching `IsItemTrigger` keyword delivers the response, applies
unlocks/faction-gate/opener exactly like a typed keyword, consumes exactly the one item, and optionally
runs a 3.2 reward bundle — all authored entirely in the web Conversation Editor, with the only Unity-side
step being the click-to-give interaction already living in `InventoryUI`. Non-NPC "give to a door" style
interactions remain explicitly out of scope (G6).
