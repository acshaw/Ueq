# Devplan 1.6 — Save policy + polish (autosave, multi-character, clean logout)

**Roadmap item:** M1 → 1.6 (final M1 functional item; the 1.7 UI refactor + regression follow)
**Status:** ✅ Done 2026-06-21 — verified in editor: multi-character create/select, camp-to-select
switching, and A↔B independence across stop/restart all work; `0007` applied (UNIQUE(account_id)
dropped, confirmed in DB). Camp/chat *polish* found during testing (countdown, not-in-combat gate,
`/camp` + `/help`, chat-clear-on-switch, MOTD) is **beyond 1.6's scope** and split out to **1.6.1**.
(Fixed a CS0128 during testing — a redundant `session` redeclaration in `CharacterPersistence`.)

> **Implementation notes (deviations from the plan, all minor):**
> - `Upsert` became a straight **UPDATE by `character_id`** (the row always exists by save time —
>   created up front by `CreateIdentity`), rather than an `ON CONFLICT (character_id)` upsert; avoids
>   explicit-id inserts and any BIGSERIAL sequence concern. `Load` re-keyed to `character_id` (the
>   SELECT now also reads `account_id` into the snapshot).
> - Save coalesce key is now `character:<characterId>` (was `<accountId>`); the `Save()` guard keys on
>   `_characterId`, and the warned fallback sets `_characterId = 0` so it can't UPDATE a nonexistent row.
> - Confirmed the live DB constraint name: `characters_account_id_key` — `0007` drops it
>   (`IF EXISTS`) and adds a non-unique `characters_account_id_idx` for list lookups.
> - Camp uses `NetworkServer.RemovePlayerForConnection(conn, RemovePlayerOptions.Destroy)`; the client
>   re-requests the roster when `localPlayer` goes null after being in-world.
> - Autosave is an `InvokeRepeating(AutosaveTick, 90s)` folded into `GameNetworkManager` (not a
>   separate component); save-on-quit is `GameNetworkManager.OnApplicationQuit` doing save-then-flush
>   explicitly before `base`.
> - `CharacterListMessage` carries `maxSlots` so the IMGUI roster knows when to disable Create.
**Depends on:** 1.3 ✅ (persistence), 1.4 ✅ (accounts), 1.5 (character select/creation — pending its
in-editor verification; 1.6 evolves the model 1.5 introduced)
**Unblocks:** 1.7 (UI refactor) + the post-M1 regression

## Goal

Round out persistence so progress is durable and an account can hold more than one character:
**periodic autosave** (so a crash loses minutes, not a whole session), **multiple characters per
account** with a real multi-slot select screen, **clean in-game logout** ("camp" back to character
select), and confirmation that **bind points** persist. This is the last functional piece of M1 —
after it, the system is feature-complete enough for the 1.7 client-structure refactor and a full
regression.

### Scope guardrails
- **In scope:** an autosave tick (save-all on an interval) + save-on-quit; relaxing the
  one-character-per-account constraint and making saves/loads key off **character id** (not account);
  a multi-slot create/select/delete screen; a "Camp to Character Select" flow that saves + despawns +
  returns to the select screen without dropping the connection; and verifying bind-point persistence.
- **Out of scope:**
  - **Bind-*setting* gameplay** (bind spells, city bind NPCs) — the bind *value* already persists
    (1.3); choosing *where* you bind is M3/M4 content. 1.6 only confirms the persistence works.
  - **Character appearance / customization, the location-pick step** of the eventual creation flow
    (see [[project_creation_flow_intent]]) — gated on M3 zones.
  - **Polished uGUI** for the now-multi-slot select screen — stays IMGUI; the real version is **1.7**.
  - **Account management** (rename, password change, etc.).
- **Hard rule (carried):** server-authoritative; DB work off the main thread (1.2). The autosave tick
  only *enqueues* coalesced saves — it never blocks the server loop.

## Approach

### 1. Autosave cadence + save-on-quit (O3)

Today saves happen only on disconnect and server stop (1.3, manager-driven). A crash loses everything
since login. Add a **server-side repeating tick** that calls the existing `SaveAllCharacters()` every
*N* seconds. This is cheap because 1.2's write queue **coalesces** per-character saves — a periodic
save-all of idle characters collapses to near-nothing.

- Implement as a timer in `GameNetworkManager` (or a small `AutosaveTicker` component): start an
  `InvokeRepeating`/coroutine in `OnStartServer`, stop it in `OnStopServer`.
- **Save-on-quit:** `PersistenceService.OnApplicationQuit` already *flushes the queue*, but it doesn't
  *capture* a fresh snapshot of live players first. Add a save-all on the quit/stop path so an editor
  Stop or app quit captures current state before the flush. (Disconnect is already covered.)
- Interval is a tunable constant (O3).

### 2. Multiple characters per account (the dominant piece)

1.3 deliberately set `UNIQUE(account_id)` so there was exactly one character per account, and 1.5's
save/load keys off **account id**. 1.6 relaxes this — and the real work is **re-keying persistence on
`character_id` instead of `account_id`:**

- **Schema** (`0007_multichar.sql`): `DROP` the `UNIQUE(account_id)` constraint (keep the FK +
  the index for lookups). `character_id` (already the PK) becomes the save key.
- **`CharacterRepository`:**
  - `Load(conn, characterId)` — load a specific character (replaces 1.5's load-by-account).
  - `Upsert` keys on **`character_id`** (`ON CONFLICT (character_id) DO UPDATE`) instead of
    `account_id`, and the snapshot always carries a valid `CharacterId`.
  - `CreateIdentity(conn, accountId, name, race, class) → long` — INSERT a new row (identity + level-1
    defaults) `RETURNING character_id`, used at creation (see §3).
  - `CountByAccount` — to enforce the slot cap (O1).
- **`CharacterSnapshot`/`CharacterPersistence`:** carry `_characterId`; save coalesce key becomes
  `"character:" + characterId`. (1.5 used `accountId` — correct only for one char; this is the fix.)

### 3. Creation/selection under multi-character (O2)

The clean evolution of 1.5's "create = enter" that stays correct for many characters:

- **Create** (`CharacterSelectController.OnCreate`): validate (name, slot cap O1, name-free) →
  **`CreateIdentity` off-thread to INSERT the row and get its `character_id` now** → stash it in
  `PendingCreation { CharacterId, Name, Race, Class }` → spawn (still create = enter).
- **`CharacterPersistence.InitializeNewCharacter`** records `_characterId` from the pending creation,
  sets the player up as today, and its immediate `Save()` **UPDATEs** that row with full state.
- **Enter** an existing character: `EnterWorldMessage { characterId }` → validate ownership →
  `SelectedCharacterId` → `CharacterPersistence` loads **by character id** → `ApplySnapshot`.
- Assigning the id at creation (before spawn) avoids the alternative wrinkle of *capturing a
  worker-generated id back* after the first save, and keeps every later save a clean UPDATE-by-id.
- **Safety net (O6):** on load, if `current_health <= 0`, `ResetToFull()` instead of `SetCurrent` —
  covers the narrow window where a character's identity row exists but it was never fully initialized
  (e.g. disconnect between create and first save). Harmless for live characters (they never log out at
  0 HP — death respawns to full).

### 4. Multi-slot select screen (IMGUI, extends 1.5)

`CharacterSelectUI` grows from "0-or-1" to a real list:
- Show all of the account's characters (name / level / race / class) with **Enter** + **Delete** each.
- A **Create** button when under the slot cap (O1); the create form is the 1.5 form. Over the cap,
  Create is disabled with a "slots full" note.
- Delete (already confirmed, 2-click) removes the chosen `character_id` (`DeleteById` with an account
  guard, not `DeleteByAccount`).
- Still IMGUI — polished version is 1.7.

### 5. Clean logout — "Camp to Character Select" (O4)

EQ-style: from in-world, the player can **camp** — save, despawn the player object, and return to the
character-select screen **without disconnecting**:
- Client sends a `CampMessage`; server saves that character, calls
  `NetworkServer.RemovePlayerForConnection` (or destroys the player object), clears the connection's
  `SelectedCharacterId`. The client's `localPlayer` goes null → `CharacterSelectUI` reappears → it
  re-requests the list (now showing the just-saved character).
- A simple **Logout/Quit** (full disconnect) also saves first (disconnect path already saves).
- Trigger: a small in-world button (IMGUI, on `GameNetworkHUD` or a dedicated bit) or a `/camp` chat
  command. (Polished UI is 1.7.)

### 6. Bind point — confirm only (O5)

The bind point is already persisted (1.3 stores `bind_x/y/z`; `SetBindPoint` exists; creation sets it
to the spawn point). 1.6 just **verifies** the round-trip (die → respawn at bind → relog → bind
intact). No new mechanic; bind-*setting* gameplay is deferred.

## Schema / API changes

- **`0007_multichar.sql`** — `ALTER TABLE characters DROP CONSTRAINT <unique account_id>` (keep a
  non-unique index on `account_id` for list lookups). *(Confirm the constraint name from `0005`'s
  `UNIQUE` — likely `characters_account_id_key`.)*
- **`CharacterRepository`** — `Load(conn, characterId)`; `Upsert` re-keyed to `character_id`;
  `CreateIdentity(...) → long`; `CountByAccount`; `DeleteById(conn, accountId, characterId)`.
- **`CharacterSnapshot`** — `CharacterId` already exists (populated by `Load`); ensure it round-trips
  and drives `Upsert`.
- **`CharacterPersistence`** — `_characterId`; load-by-id; save coalesce key `character:<id>`;
  `<=0 HP → fill` safety net; `Camp()` entry point.
- **`AccountSession`** — already has `SelectedCharacterId` + `PendingCreation`; `PendingCharacter`
  gains `CharacterId` (assigned at creation).
- **`CharacterSelectController`** — slot-cap check; create via `CreateIdentity`; delete-by-id; camp
  handling (or a dedicated handler).
- **`GameNetworkManager`** — autosave tick start/stop; save-on-quit.
- **New messages** — `CampMessage` (client → server).

## Test plan

1. **Migrations:** `0007` applies; re-run → none pending. Verify a fresh DB applies 0001→0007 in order.
2. **Multi-character:** create char A, camp to select, create char B (distinct name) → both appear;
   enter A, gain XP, camp, enter B → B is independent; relog → both persist with correct state.
3. **Slot cap (O1):** create up to the cap → Create disabled / "slots full"; delete one → Create re-enabled.
4. **Save key correctness:** play A, camp, play B, stop server → both rows updated independently (no
   cross-contamination, no duplicate rows for one character).
5. **Autosave:** play, gain XP, **hard-stop the editor without camping/stopping** (simulate crash) →
   relog → progress up to the last autosave tick is retained.
6. **Save-on-quit:** play, then Stop the editor normally → latest state saved (better than the autosave tick).
7. **Camp:** in-world → camp → returns to select without disconnect; the character shows updated state;
   enter again → resumes.
8. **Bind point:** die → respawn at bind; relog → bind intact.
9. **Account isolation + delete:** account B never sees A's characters; deleting A's char B leaves char A.

## Resolved decisions (approved 2026-06-21 — all recommendations accepted)
- **O1 — Max characters per account → 8 slots.** Create disabled at the cap until a delete.
- **O2 — Multi-char create/save model → assign `character_id` at creation (identity INSERT) +
  re-key all saves on `character_id`; keep create = enter.** (Rejected: capturing a worker-generated
  id after the first save — fragile/duplicate-row risk.)
- **O3 — Autosave interval → 90 s** (save-all on a server tick, coalesced) **+ save-all on quit/stop.**
- **O4 — Clean logout → include "Camp to Character Select"** (save + despawn + return to select with no
  disconnect) alongside save-on-disconnect.
- **O5 — Bind point → confirm-only** (already persisted by 1.3); bind-setting gameplay deferred to M3/M4.
- **O6 — `<=0 current HP` fills to max on load → yes** (safety net for the create-then-crash window;
  harmless for live characters).

## Risks
- **Save re-keying is the high-risk change.** If a save still keys off `account_id` anywhere after the
  switch, two characters on one account corrupt each other. Test 4 is the guard; grep for any
  remaining `account_id`-keyed save path after the change.
- **Constraint name in `0007`** — `DROP CONSTRAINT` needs the exact name Postgres generated for the
  `UNIQUE` in `0005`; verify in `psql` (`\d characters`) before writing the migration, or drop by a
  known name with `IF EXISTS`.
- **Camp despawn/rebind** — returning to select must cleanly null `localPlayer` and let the UI
  re-show; mishandling could strand the client on a blank screen. Mirror's `RemovePlayerForConnection`
  is the intended API; verify it leaves the connection usable for a subsequent `AddPlayerForConnection`.
- **Autosave vs. coalescing** — confirm the tick enqueues *coalesced* jobs (it does, via the existing
  `KeyedDelegateSaveJob` path) so idle players don't pile up writes.

## Done when

Progress autosaves on an interval and on quit (not just disconnect); an account can hold several
characters, each created/entered/deleted from a multi-slot select screen and persisted independently
(saves keyed by character id); a player can camp back to character select without disconnecting; and
bind points survive a relog — completing M1's functional scope ahead of the 1.7 UI refactor.
