# Devplan 1.7 — UI architecture refactor (additive UI scene + separation of concerns)

**Roadmap item:** M1 → 1.7 (the M1→M2 bridge; finishes the *playable-client* foundation)
**Status:** ✅ Done 2026-06-21 — verified in editor: HUD loads from the additive `UI.unity`, all panels
behave as before, and camp/character-switch/host-restart all rebind cleanly through `LocalPlayer`.
Built in two passes (A: binding/separation; B: additive UI scene). **O5 deferred** (login/select/HUD
kept IMGUI — own later item). One follow-up fix: the recurring hotbar slot-label wiring quirk
(some slots' refs left unset by edit-time serialization — a *different random set each rebuild*). The
`Init` call alone didn't resolve it, so it was fixed for good with **runtime self-wiring** (2026-06-22):
`HotbarSlotUI.Awake` resolves its `Name`/`CDText`/`CDOverlay` children if the serialized refs are null,
and `HotbarUI.Awake` heals its `slots[]` via `GetComponentsInChildren` if any element is null. Immune
to the editor quirk; needs only a recompile (no scene rebuild).

> - **Pass A (done):** `LocalPlayer` service (`Current` + `Spawned`/`Despawned`), fed by
>   `NetworkedPlayer.OnStartLocalPlayer/OnStopClient`; all 8 panels rebound onto it — zero
>   `FindObjectsByType<NetworkedPlayer>` left in UI. This permanently retires the per-panel bind-once

**Depends on:** 1.5 ✅ + 1.6 (character select/creation + multi-char UI exist; 1.7 relocates/cleans them)

## Goal

Get the UI out of the gameplay scene and onto its own **additive UI layer**, with a single place that
resolves "the local player" and real **separation of concerns** — so panels stop each re-discovering
the player (the fragile pattern behind the host-restart rebind bug and the hotbar-wiring quirk), and
the UI no longer reloads when the world scene changes. This is an architecture/organization pass, not
a visual restyle (re-skinning can follow once the structure is clean).

### What's wrong today (the motivation)
- **~10 canvases** (Chat, HUD/player+target frames, Inventory, Equipment, Vendor, Loot, Hotbar) are
  built by **~900 lines of `Create*UI()` in `SceneSetup.cs`** and live in `SampleScene` — UI is
  tangled into the gameplay-scene bootstrap.
- **8 UI scripts each re-implement local-player binding** (`FindObjectsByType<NetworkedPlayer>` /
  `NetworkClient.localPlayer`), several latching a `_bound` flag — the exact duplication that caused
  the host-restart rebind bug (patched in 1.3) and contributed to the hotbar quirk.
- **No additive scenes**, so UI is married to the world scene — a problem the moment M3.5 loads a
  second zone.
- The most player-facing screens (login, character select) are throwaway **IMGUI** (deferred from 1.4/1.5).

### Scope guardrails
- **In scope:** a dedicated additive **UI scene** + a `UIManager`/bootstrap that loads it; a
  centralized **`LocalPlayer`** service (spawned/despawned events) that every panel binds through;
  a **view-vs-controller** split per panel; relocating all HUD construction off the gameplay-scene
  path; and converting the pre-spawn IMGUI panels (login, character select, in-world HUD) to uGUI in
  the UI scene (O5).
- **Out of scope:**
  - **Visual restyle / art pass** (icons, theming, fonts) — 1.7 fixes *structure*; re-skinning is a
    lighter follow-on.
  - **New UI features** (tooltips, drag-rearrange polish, context menus) — backlog items, not this.
  - **Gameplay/networking logic** — panels keep talking to the same `NetworkedPlayer`/components and
    `Cmd`s; only *how the UI is organized and bound* changes.
  - **Dedicated-server headless rendering** — the UI scene loads on clients/host only (O1).
- **Hard rule:** behavior parity. Every panel that works today works after the move — verified by the
  post-M1 regression that immediately follows.

## Approach

### 1. Additive UI scene + bootstrap (O1)

A new `Assets/Scenes/UI.unity` holds all the canvases. A small **`UIManager`** (in the boot/gameplay
scene, or a tiny boot scene) loads it additively at startup and keeps it loaded across gameplay-scene
changes:
- `SceneManager.LoadSceneAsync("UI", LoadSceneMode.Additive)` once, early.
- **Gate for headless:** skip the load when `Application.isBatchMode` (a dedicated server needs no UI),
  so only clients/host build the layer. (Editor/host always loads it.)
- The UI scene persists when the world scene unloads/loads (M3.5), so the HUD doesn't flicker or
  re-wire on zone changes.

### 2. `LocalPlayer` service — one place resolves the player (O2)

The keystone fix. A single static/singleton **`LocalPlayer`** with:
```
static NetworkedPlayer Current { get; }
static event Action<NetworkedPlayer> Spawned;    // local player entered the world
static event Action                  Despawned;  // local player left (camp / disconnect / host restart)
```
Fed by the player itself — `NetworkedPlayer.OnStartLocalPlayer` → `LocalPlayer.Set(this)`,
`OnStopClient` (when local) → `LocalPlayer.Clear()`. Panels **subscribe** to `Spawned`/`Despawned`
instead of polling `FindObjectsByType`. On `Spawned` a panel grabs the components it needs (inventory,
health, abilities…) and subscribes to their events; on `Despawned` it clears.

This **permanently retires** the per-panel bind-once fragility — host restart, camp, and reconnect all
flow through one event, so the class of bug we patched in 1.3 can't recur.

### 3. View-vs-controller separation per panel (O4)

Each panel becomes a **prefab with one controller script** that:
- gets its data source from `LocalPlayer` events (never from `FindObjectsByType`),
- subscribes to the relevant component's events (e.g. `Health.OnHealthUpdated`, `SyncList.Callback`),
- pushes values into **serialized view references** (the TMP texts / Images / fill bars).

Pragmatic, not dogmatic MVC — presentation (the serialized refs + a `Refresh`/`Set…` method) is
cleanly separated from binding (subscribe/unsubscribe driven by `LocalPlayer`), which is the split
that actually matters here. (Full separate View/Controller *classes* are the heavier alternative —
overkill for this size; see O4.)

### 4. Construction model — code-driven, into the UI scene (O3)

Keep the **re-runnable, code-driven** construction the project relies on (no fragile hand-wiring; it's
how `Tools/Setup All` stays idempotent) — but **relocate it** out of `SceneSetup`'s gameplay flow into
a dedicated **`Tools/Build UI Scene`** that constructs the canvases into `UI.unity`. This delivers the
user's two asks — *separation* (own scene, binding centralized) and *additive layer* — without a large
manual prefab-authoring effort, and it sidesteps the hand-wiring quirks we've repeatedly hit.
(Authored-by-hand prefabs are the alternative — more "conventional," but much more manual work and
reintroduces the wiring fragility; see O3.)

### 5. Panels to migrate

All onto `LocalPlayer` + the UI scene: **PlayerFrame, TargetFrame, InventoryUI (+InventorySlotUI),
EquipmentUI (+EquipSlotRowUI), HotbarUI (+HotbarSlotUI), LootUI, VendorUI, ChatUI.** `Nameplate` +
`Billboard` stay on the world objects (they're worldspace, not HUD). `UIDrag`/`UIResizeHandle` are
reused as-is.

### 6. IMGUI → uGUI for the pre-spawn panels (O5)

Convert **LoginUI, CharacterSelectUI, and the in-world GameNetworkHUD** from IMGUI to uGUI in the UI
scene — the polish 1.4/1.5 explicitly deferred here. Same messages/flow (1.4 auth handshake, 1.5/1.6
select/create/camp); only the rendering changes. The character-select roster + create form become real
uGUI, which is the most player-facing win.

### 7. `SceneSetup` changes

- Remove the `Create*UI()` calls from `SetupScene` (gameplay scene no longer builds HUD).
- Add `Tools/Build UI Scene` (constructs `UI.unity`).
- `UIManager` added to the gameplay/boot scene to load the UI scene additively.
- Pre-spawn panels move off the NetworkManager GO into the UI scene (LoginUI/CharacterSelectUI no
  longer sit on `NetworkManager`).

## What this fixes
- The **host-restart / camp rebind fragility** — one `LocalPlayer` event replaces 8 ad-hoc binders.
- **UI surviving zone changes** (M3.5 enabler).
- The **~900-line `SceneSetup` UI blob** → a focused UI builder + a clean scene.
- The **IMGUI login/creation screens** → real uGUI.

## Schema / API changes
None (no DB, no migration). Pure client/editor restructure.

## Files touched (indicative)
**New:** `Assets/Scenes/UI.unity`; `Assets/Scripts/UI/UIManager.cs`; `Assets/Scripts/UI/LocalPlayer.cs`;
a `Tools/Build UI Scene` editor builder (likely `Assets/Scripts/Editor/UISceneSetup.cs`).
**Modified:** every panel controller (`PlayerFrame`, `TargetFrame`, `InventoryUI`, `EquipmentUI`,
`HotbarUI`, `LootUI`, `VendorUI`, `ChatUI`, and the converted `LoginUI`/`CharacterSelectUI`/HUD) to
bind via `LocalPlayer`; `NetworkedPlayer` (feed `LocalPlayer.Set/Clear`); `SceneSetup` (drop `Create*UI`
from the gameplay flow, add the UI-scene builder + `UIManager`).

## Test plan
> Behavior parity is the bar — this overlaps the post-M1 regression that follows.
1. **Boot:** UI scene loads additively; HUD/login present; headless/batchmode skips it cleanly.
2. **Binding via LocalPlayer:** enter world → all panels populate (health/target/inventory/equipment/
   hotbar/chat). Camp → panels clear; re-enter → repopulate. Host-restart in one Play session → panels
   rebind (the old bug stays fixed). Switch characters (1.6) → panels reflect the new character.
3. **Each panel parity:** inventory move/equip/drop, equipment equip/unequip, hotbar cast + cooldowns,
   loot, vendor buy/sell, chat channels/whisper, target frame, player frame — all behave as before.
4. **uGUI pre-spawn (O5):** login, character select (roster + create + delete + camp) work in uGUI.
5. **Zone-change dry run (if feasible):** load/unload a second scene → UI persists (proves the M3.5 win).

## Open decisions (recommendations first)
- **O1 — UI scene load:** **`UIManager` loads `UI.unity` additively at startup, skipped in
  `Application.isBatchMode`** (headless server). Alt: a dedicated boot scene that loads gameplay + UI.
- **O2 — Local-player binding:** **central `LocalPlayer` service with Spawned/Despawned events**, fed
  by `NetworkedPlayer.OnStartLocalPlayer/OnStopClient`; panels subscribe. (This is the core fix.)
- **O3 — Construction model:** **keep code-driven, relocated into a `Build UI Scene` tool** (re-runnable,
  no hand-wiring). Alt: hand-authored prefabs (more conventional, much more manual, wiring-fragile).
- **O4 — Separation depth:** **pragmatic — one controller per panel + serialized view refs + binding
  via `LocalPlayer`.** Alt: full separate View/Controller classes (overkill at this size).
- **O5 — Convert IMGUI panels to uGUI now:** **yes — Login + CharacterSelect + in-world HUD** (the
  deferred 1.4/1.5 polish; most player-facing). Alt: keep them IMGUI, refactor only the gameplay HUD.
- **O6 — Migration scope:** **foundation first (UI scene + `LocalPlayer`), then migrate all panels in
  1.7** for consistency. Alt: migrate panel-by-panel across several items.

## Risks
- **Broad blast radius** — this touches every UI script; high regression surface. Mitigated by the
  behavior-parity test plan + the full-system regression scheduled immediately after.
- **Additive-scene timing** — panels must not bind before the UI scene + `LocalPlayer` exist; the
  event-driven model (`Spawned` fires *after* both exist) handles ordering, but verify nothing reads
  `LocalPlayer.Current` in `Awake` before it's set.
- **Camp/host-restart edge** (the recurring one) — `Despawned`/`Spawned` must fire on camp (1.6) and
  on host-restart; covered by test 2.
- **Scope creep into restyling** — resist; 1.7 is structure only, or it balloons.

## Done when

All HUD/menus live in an additive UI scene that survives world-scene changes; every panel binds through
a single `LocalPlayer` service (no per-panel `FindObjectsByType`); login/character-select are uGUI; the
gameplay scene + `SceneSetup` no longer build UI; and every panel behaves exactly as before — leaving
M1 feature-complete and ready for the full-system regression, then M2.
