# 2.7.1 — Mob faction hits on kill

**Status:** ✅ Done — verified in-editor 2026-06-29 (all DH1–DH6 accepted as recommended). Killing a Giant Rat moves Vermin −10 / CityGuards +2 and persists across relog on the re-keyed `faction_id` column — also closes 2.6's deferred aggro/gate/round-trip verification. See the implementation log at the bottom.
**Roadmap item:** M2 → 2.7.1 (inserted after 2.7, before 2.8 — the deferred faction-consequence work from the 2.6/2.7 discussion)
**Pattern:** extends the **mobs** content type (2.5) with a child list + adds **runtime wiring** in `MobKillReward`. Server-only authoring; the consequence is applied server-side. This is the first item that makes 2.6's faction system *do something on the player side*.

---

## Goal

Killing a mob currently has **zero faction consequence** — `MobKillReward.OnDeath` only grants XP, and a mob's `faction_id` is used **only for perception/aggro**. This item adds a per-mob **faction hit list** — `(faction_id, delta)` pairs applied to the killer's standing on death — authored in the Mob Editor and applied via `PlayerFactionScores.ModifyScore`.

Why a list and not a single value derived from the mob's own faction (the question that kicked this off): **killing one creature usually moves several factions, not just its own.** The classic case — *kill a guard → guard faction down, their enemies up* — is the whole point of a faction economy ("grind X to earn standing with Y"). A pure `faction_id` derivation can only ever lower the mob's own faction; it can't express the gain side. So the hit list is authoritative; the mob's own `faction_id` is just a convenient default to pre-fill.

**Bonus:** this delivers the first **in-game way to change a faction score**, which retroactively makes the 2.6 verification (aggro flip, conversation gate, persistence round-trip) actually testable.

## Where it lives — on the mob, not the loot table

(Settled in the 2.7 discussion.) Loot tables are items+coin and are **shared** across many mobs; faction consequence is tied to a mob's **identity/allegiance**, which is per-mob. It's a *kill reward*, so it sits with `xpReward` in `MobDefinition`'s `[Rewards]` block — not on the shared loot table.

## Schema — `0015_mob_faction_hits.sql` (schema only; demo rows seeded by `DatabaseSeeder`)

```sql
-- A faction adjustment applied to the killing player when this mob dies (M2.7.1). delta < 0 lowers
-- standing, > 0 raises it. faction_id is a soft ref to factions.faction_id.
CREATE TABLE IF NOT EXISTS mob_faction_hits (
    id          BIGSERIAL PRIMARY KEY,
    mob_id      TEXT NOT NULL REFERENCES mobs(mob_id) ON DELETE CASCADE,
    faction_id  TEXT NOT NULL,
    delta       INT  NOT NULL,
    sort_order  INT  NOT NULL DEFAULT 0
);
```

**Demo seed (DH5)** — small placeholder hits on the existing mobs so the loop is immediately testable and there's an in-game lever for the 2.6 tests:
- **Giant Rat** → `Vermin -10`, `CityGuards +2` (kill vermin → vermin like you less, guards like you a bit more — demonstrates the multi-faction model).
- **City Guard** / **Captain of the Guard** → `CityGuards -50` (killing guards tanks your guard standing).
- Values are **placeholders** flagged for the balance pass (6a).

## Unity (server-only)

- **`MobDefinition`** — add (under `[Rewards]`, next to `xpReward`):
  ```csharp
  [System.Serializable]
  public struct FactionHit { public string factionId; public FactionDefinition faction; public int delta; }
  public List<FactionHit> factionHits = new();
  ```
  `faction` is resolved at build (like the top-level `faction`); SO-authored mobs may leave it null.
- **`MobSnapshot` + `MobRepository`** — add a `List<MobFactionHitSnapshot> { FactionId, Delta }`. **This is the notable change:** `MobRepository.LoadAll` is currently a *flat single-query* load with no children — it must become **header-then-children** (build mob rows into a dict, then a second `SELECT … FROM mob_faction_hits ORDER BY mob_id, sort_order, id` attaching to each, the shared-list-ref trick used by `ConversationRepository`/`LootRepository`).
- **`MobRegistry.Build`** — populate `def.factionHits` from the snapshot, resolving each `faction = FactionRegistry.Get(factionId)` (factions already load before mobs, 2.6).
- **`MobKillReward.OnDeath`** — after the XP grant, for each `factionHits` entry with a resolved `faction` and `delta != 0`:
  - `attacker.GetComponent<PlayerFactionScores>()?.ModifyScore(hit.faction, hit.delta);`
  - send a Faction-flavored chat line to the killer, e.g. *"Your standing with {faction.FactionName} has {improved|worsened}."* (one line per faction changed).
  (Killer-only for now — same attribution as XP; group split deferred, DH4.)
- **`DatabaseSeeder.SeedMobFactionHits`** — idempotent; only seed a mob's hits on first insert (guard with a `NOT EXISTS`/`ON CONFLICT`-style check per mob so web edits aren't clobbered).

## API (.NET, mapping-only EF)

- `MobFactionHit` entity (`mob_faction_hits`) + `Mob.FactionHits` navigation (HasMany, cascade).
- `MobDto` gains `factionHits: [{ factionId, delta }]`. **`MobsController` is currently flat** (no children) — add `.Include(m => m.FactionHits)` on reads and replace-children semantics on PUT/POST (mirror `FactionsController`/`LootTablesController`). DbContext mapping for the child + the HasMany.

## Angular

- **Mob Editor** — new **"Faction hits on kill"** section: rows of `(faction dropdown from the factions endpoint, delta number, remove)` + "Add hit". A small **"+ own faction"** convenience button pre-fills a row with the mob's selected `faction_id` and a negative delta (DH3). `mob.service` `Mob` interface gains `factionHits`.

## Decisions (recommendations in **bold**)

- **DH1 — Storage shape.** **Per-mob child table (`mob_faction_hits`).** Most mobs have a small, unique hit list; a shared/referenced "hit set" is premature abstraction. (Revisit if many mobs end up sharing identical lists.)
- **DH2 — Auto-spread via 2.6 relations?** **No — explicit list only.** The hit list is authoritative; deriving secondary hits from ally/hostile relations is a tempting but separate behavior — defer it so authoring stays predictable. (Easy to layer on later: "also apply −X to factions hostile-to / +X to allied-with each hit.")
- **DH3 — Own-faction default.** **Editor convenience, not a runtime default.** A "+ own faction" button pre-fills `(mob.faction_id, −N)`; nothing is applied implicitly, so an unauthored mob has no faction consequence (matches today's behavior).
- **DH4 — Group handling.** **Killer-only, like XP.** Distributing faction hits across a group waits for grouping (4.1), same as XP distribution.
- **DH5 — Seed demo hits?** **Yes (placeholders).** Seed the small hits above so the loop is testable out of the box and the 2.6 score-change tests have a lever. Flagged for the 6a balance pass.
- **DH6 — Player feedback.** **One chat line per faction changed** ("Your standing with X has improved/worsened"). Simple and EQ-familiar; threshold-crossing messages ("X now regards you as Dubious") are a nice future polish, not required here.

## Test plan

1. **API (curl vs Postgres):** mob CRUD now round-trips `factionHits` (children replace on PUT, cascade on DELETE); existing flat mob fields unchanged.
2. **Load:** `Run Migrations` (0015) → `Seed Database` → host; seeded mobs build with their `factionHits` resolved (non-null factions).
3. **The loop (closes 2.6's deferred tests):** as a Human, kill a **Giant Rat** → faction chat lines fire → query `character_faction_scores` (after a save) shows **Vermin** down 10 and **CityGuards** up 2, keyed by `faction_id`. Relog → values persist (proves the 2.6 re-key round-trip). Keep killing rats → eventually a **Vermin-faction mob aggroes** / the **CityGuards `help` gate** opens or closes as standing crosses thresholds.
4. **Editor:** add/remove a hit in the web Mob Editor → restart host → the new consequence applies on kill.

## Risks

- **`MobRepository` flat→children restructure** — the highest-touch change; preserve every existing flat column exactly (regression risk for all of 2.5).
- **Faction resolution timing** — `MobRegistry.Build` resolves hits via `FactionRegistry.Get`; factions already load before mobs (2.6), so this holds — but the loot step was also inserted before mobs (2.7), so double-check `ContentLoader` order stays factions → loot → mobs.
- **Unresolved/zero hits** — skip a hit whose `faction_id` doesn't resolve (log once) or whose `delta == 0`; never call `ModifyScore(null, …)`.
- **Sign convention** — document that `delta < 0` worsens standing; make the editor sign-explicit so authors don't invert it.

## Done when

Mobs carry a web-authored faction-hit list, killing a mob adjusts the killer's standing (with chat feedback), and the change persists across relog on the re-keyed `faction_id` column. This both completes the faction loop opened in 2.6 and provides the in-game lever to verify 2.6's aggro/gate/round-trip behavior. After this, M2's remaining content types are quests (2.8), abilities (2.9), races/classes (2.10), and seed/export (2.11).
