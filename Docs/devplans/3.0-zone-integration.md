## Goal

Make the world **zone-aware** for real: the production version of the 2.0 sandbox. After 3.0, the server
can host **multiple zone scenes concurrently** on one process, players belong to exactly one zone at a
time and only see that zone, players **transition** between zones landing at the entry that matches their
exit, a character's **zone is persisted** and restored on login, and every per-zone server system
(spawns, chat, AI, regen) operates **scoped to its zone** instead of one shared world.

This is plumbing + a framework, **not content**. Success is "the existing game still works, now inside a
named starter zone, and a second test zone proves isolation + transitions." Real zone content is 3.1.

## Background — what the spike already settled

From `docs/devplans/2.0-zone-architecture-spike.md` (Findings, the deliverable that scopes this item):

- **Feasibility: GO.** Additive zone scenes + `SceneInterestManagement` gives concurrent, isolated zones
  on one Mirror server with stable transitions. No architectural blocker.
- **Interest mechanism:** `SceneInterestManagement` (one component on the NetworkManager GO) partitions
  visibility by `gameObject.scene`. Cheap. Caveat: a local physics scene is **not auto-stepped**.
- **Player movement A→B:** `SceneManager.MoveGameObjectToScene` + a client `SceneMessage`. The hard part
  is transforms — must be **server-authoritative**, teleport via **`NetworkTransform.ServerTeleport`**
  (never a raw `transform.position` set), and the player should carry **no client-side physics body**.
- **Portals:** server-side **proximity/volume** check, **not** physics triggers (a kinematic body stops
  firing `OnTriggerEnter` after a cross-scene move).
- **Integration surface (the to-do list this devplan executes):** player movement/transform, portals,
  spawn system, ChatManager grid, persistence (+zone id), character-select spawn, per-scene AI/regen
  ticks, server physics.
- **Spawn-state strategy:** start **keep-loaded** for the small initial world; defer load-on-demand +
  persisted spawn snapshots until zone count forces it. (So 3.0 keeps all zones loaded.)

The real `NetworkedPlayer` is **already server-authoritative** (`CmdSendInput` → server `ApplyMovement`
on a `CharacterController`), so the spike's #1 transform requirement is largely met — the gap is the
teleport path, the no-client-physics rule, and the per-scene physics question (Z3).

## Approach

### Zone model & catalog (Z1)
A **zone** = an additively-loaded scene + a small data record (`zoneId`, scene name, default spawn
point, world-space origin offset). Introduce a lightweight **`ZoneCatalog`** (start as a serialized list
on a `ZoneManager` component / a `Resources` asset; migrate to DB under M2's umbrella later — *not* now,
to keep 3.0 about the framework). The starter zone gets a real `zoneId` (e.g. `"qeynos_hills"`); a throwaway
second zone (`"test_zone_b"`) exists only to prove isolation + transitions and is deleted/kept-as-reference
like the spike sandbox.

### Scene management & bootstrap
- A new server-side **`ZoneManager`** (on the NetworkManager GO, created in
  `GameNetworkManager.OnStartServer` after `ContentLoader.LoadAll()`) loads every catalog zone as a
  **normal additive scene** (default physics scene, no `LocalPhysicsMode`) and records `scene` +
  **world-space offset** per zone (Z3-B).
- Adopt **`SceneInterestManagement`** on the NetworkManager GO (the spike's proven mechanism).
- The **UI scene** already survives scene changes (1.7 `UIManager`, `DontDestroyOnLoad` + additive
  `UI.unity`) — no change needed; panels bind through `LocalPlayer`, so they don't care which zone scene
  the player object lives in. This is the M1→M3 dividend 1.7 was built for.

### Server physics (Z3) — the headline decision → **B (shared physics + world offsets)**
**Decided (2026-06-29): B**, gated on the MVP scope (3 zones, ~12 players, polish-before-expand).

The reframing constraint: **Unity's runtime NavMesh is a single global mesh** — `NavMeshAgent` /
`NavMesh.SamplePosition` ignore physics scenes entirely, so two zones baked at the same coordinates
*merge* and agents path across both. The **only** fix is **distinct world-space coordinates per zone
(an offset)**. That offset is therefore **mandatory regardless of the physics model** — and once zones
sit far apart in world space, the offset already isolates everything spatial (navmesh + any
naturally-bounded query: a 30-unit say-radius or 50-unit activation sphere can't reach a zone thousands
of units away).

Given the offset is required anyway, physics-scene isolation buys little for real cost. The two shapes:
- **(B, chosen) Shared default physics scene + world-space offsets.** Zones load as normal additive
  scenes, so all colliders register in the **default** physics scene Unity **auto-steps** — **no manual
  `Simulate`, no `ZonePhysicsStepper`** (trigger-based perception/aggro just works), and **no query
  redirection** (`Physics.OverlapSphere`/raycasts/ground-snap/targeting work exactly as today; they hit
  the right zone because only that zone's geometry is near the player's offset coords). The
  `CharacterController` collides with the correct zone automatically. Essentially "the game as it works
  now + offsets + interest management." **The one thing to get right is offset spacing** — large enough
  no query radius can bridge zones, small enough to stay in safe float precision.
- **(A, deferred scale-up path) Physics-isolated per-scene at local origin.** Each zone in its own
  `PhysicsScene` near `(0,0,0)`; the server manually steps each. True isolation + immune to float-origin
  jitter, at the cost of redirecting every spatial query to the right `PhysicsScene` + a stepper. Only
  pays off at **large** zone counts where far offsets (~100k+ units) hit float32 precision limits.

**Why B for the MVP:** 3 zones offset a few thousand units apart are nowhere near float-precision
trouble; B adds **zero** new physics infrastructure (keeping the framework rework contained before the
deferred full M1 regression); and A's payoff is a "decide on data, not intuition" scaling concern — the
same posture taken on single-server-vs-zone-server (deferred to M6b). **A vs B is an implementation
detail of the physics/coordinate layer**; the zone architecture above it (ZoneManager, transitions,
zone-aware chat/spawn/persistence) is identical either way, so migrating B→A later (if the world ever
grows past the MVP's 3 zones) is a contained swap, not a fork.

### Player transform & transitions (Z4)
- Keep `NetworkedPlayer` **server-authoritative** (already true). Audit for any client-side physics body
  the spike says to drop; confirm `NetworkTransformReliable` sync direction is `ServerToClient`.
- Add a **`ServerWarpTo(Vector3 pos, float yaw)`** path on `NetworkedPlayer` that uses
  `NetworkTransformReliable.ServerTeleport` (not a raw position set) — reused for transitions, respawn,
  and character-select spawn.
- **Transition flow** (`ZoneManager.ServerMovePlayer(conn, targetZoneId, entryId)`):
  1. capture exit zone (for relative entry resolution),
  2. `MoveGameObjectToScene(player, targetScene)`,
  3. send the client the additive `SceneMessage` (load dest / unload prev) so its local scene matches,
  4. `ServerWarpTo` the mapped entry point (in the destination zone's offset space),
  5. re-register the player with the destination zone's chat/spawn systems; update persisted `zoneId`.
- **Portals are server-side proximity checks** (Z4): a `ZonePortal` data marker (`targetZoneId`,
  `entryId`, world position + radius) polled by `ZoneManager` on the server — **no physics triggers**.
  A per-player debounce (spike used 1s) absorbs sync lag.

### Per-zone system rework (the integration surface)
- **ChatManager (Z7):** key delivery by zone. Cleanest: a `zoneId` alongside each connection in the
  grid, and `SendArea` only considers candidates in the **same zone** before the distance check. (With
  Z3-A's world offsets, distance math already can't cross zones, but the explicit zone key keeps it
  correct regardless of offset spacing and is cheap.) Registration/`UpdatePosition` calls gain a zone arg.
- **SpawnPoint (Z8):** spawn points live **inside their zone scene**; `Instantiate` then
  `MoveGameObjectToScene(go, this.gameObject.scene)` (or instantiate already-in-scene) so mobs belong to
  the right zone for interest mgmt; activation `OverlapSphere` is naturally zone-correct under Z3-B's
  world offsets (only the owning zone's players are near the spawn point). No change to the
  spawn-table/mob resolution logic from 2.5/2.7.2.
- **Persistence (Z5):** add `zoneId` (+ keep the existing pos/yaw, now interpreted in that zone's space)
  to `CharacterSnapshot` and the `characters` row; restore the player into the persisted zone on load.
- **Character-select spawn (Z6):** `CharacterSelectController.SpawnPlayer` does **move-into-zone before
  `AddPlayerForConnection`** (spike's analytical answer): resolve the character's persisted zone (new
  character → starter zone), instantiate, `MoveGameObjectToScene`, then `AddPlayerForConnection`, then
  `ServerWarpTo` the persisted/entry position.
- **AI / regen / per-frame ticks (Z9):** `EnemyAI` is already server-only and operates on its own
  agent/target, so it's per-zone by construction; audit for any global `FindObjectsByType` /
  single-world assumption. `PlayerRegen` is per-player — fine. Under Z3-B the global navmesh + default
  auto-stepped physics scene mean agents/triggers need no per-zone stepping. The work here is mostly
  **verification + removing any global lookups**.

## Decisions (resolved 2026-06-29)

All nine settled in review. Z2/Z4/Z5/Z6/Z7/Z8/Z9 inherit the 2.0 spike answers; Z1 + Z3 discussed in depth.

- **Z1 — Zone catalog source → serialized.** A `ZoneCatalog` SO in `Resources/` (boot list: id → scene →
  offset) + in-scene `ZonePortal` markers (position comes free from the transform). Defer DB-backed zones
  to a future M2-style item; a zone can't be web-authored end-to-end anyway (the scene is a Unity build),
  so the DB buys little now. Keeps 3.0 about the framework, not another content vertical.
- **Z2 — Interest mechanism → `SceneInterestManagement`** (spike-proven; one component on the NM GO).
- **Z3 — Server physics → B (shared default physics scene + world-space offsets).** Gated on the MVP
  scope (3 zones / ~12 players / polish-before-expand). The world offset is mandatory anyway (global
  navmesh), and at 3 zones it provides all the isolation needed with **zero** new physics infrastructure.
  A (isolated per-scene at local origin) is the **documented scale-up path** if the world grows past the
  MVP — a contained swap of the physics/coordinate layer, not an architecture fork. **Sub-risk to validate
  first:** mobs navigating in two offset zones simultaneously (confirm the global navmesh's offset islands
  behave). **Get right:** offset spacing (no query radius can bridge zones; stay in safe float precision).
- **Z4 — Transition/portal mechanism → spike answer.** Server-side proximity poll + `ServerTeleport` +
  per-player debounce. No physics triggers.
- **Z5 — Persisted zone → spike answer.** Add `zone_id` to `characters` (migration 0017); pos/yaw
  reinterpreted in that zone's offset space.
- **Z6 — Character-select spawn → spike answer.** Move-into-zone before `AddPlayerForConnection`.
- **Z7 — Chat scoping → spike answer.** Explicit `zoneId` key on the chat grid (cheap; correct regardless
  of offset spacing).
- **Z8 — Spawn ownership → spike answer.** Spawn points live in their zone scene; spawned mobs moved into it.
- **Z9 — Per-frame ticks → spike answer.** Audit-and-fix only; no redesign expected (AI/regen already
  per-entity; no stepper needed under Z3-B).

**Two gaps found in this (approved) devplan while grounding against source — folded into the plan:**
1. **Chat delivery breaks under `SceneInterestManagement`, not just scoping.** `OnCheckObserver` makes an
   object visible only to same-scene players, so `ChatManager` (a base-scene networked singleton) is
   un-observed by players in other zones → its `TargetRpc`/`ClientRpc` delivery silently drops. **Fix:**
   deliver via `conn.Send` + a client handler (the pattern `ContentCatalog` already uses), which is
   observation-independent. (Z7's zone-key filter is still added, in Stage B.)
2. **Additive zones must be *authored at* their world offset, not runtime-shifted.** Unity's baked NavMesh
   data stays at authored coords, so moving roots at load would divorce navmesh from geometry. So the
   `ZoneSetup` builder places Thornwood's content (incl. its navmesh bake) at +5000; `ZoneManager` just
   additive-loads — no runtime shift. (Also noted for Stage C: `PlayerCorpse` Instantiate lands in the
   active scene, not the player's zone.)

**2026-07-04 — Stage C verified in-editor; two real bugs found + fixed en route (both were latent, exposed by
Server-Only + remote-MPPM-client testing that Stage C required):**
1. **Enemy prefab had no NetworkTransform** — mob movement never synced to remote clients (masked for months
   by host-only testing, where the host renders the server transform directly). Symptom: mobs frozen on
   clients while server AI chased/attacked; player attacks read "out of range" (server measured to the mob's
   real moved position). Fix: `SceneSetup.AddEnemyNetworkTransform()` adds a server-authoritative
   `NetworkTransformReliable` (position-only, `coordinateSpace = World`) in both the build + patch paths;
   `EnemyAI.Awake` disables the NavMeshAgent so it only drives the transform on the server (OnStartServer
   re-enables) and doesn't fight the NT on clients. User applied via `Tools/Patch Enemy Prefab`.
2. **Thornwood navmesh didn't persist** — the scripted `NavMeshSurface.BuildNavMesh()` didn't save the
   NavMeshData asset (and re-running the tool rebuilds thornwood from scratch, wiping any manual bake), so
   the additive scene loaded with no navmesh at +5000 → mobs spawned off-navmesh and couldn't wander. Fix:
   `ZoneSetup.BuildThornwoodScene` saves the NavMeshData to `Assets/Scenes/Zones/thornwood_navmesh.asset` and
   keeps the surface pointed at it. Confirmed: the two offset zone navmeshes coexist fine (no conflict — the
   earlier "ping-pong" was bug #1, not navmesh). All Stage C checks (per-zone mobs, corpse-into-zone, per-zone
   death respawn, login-into-persisted-zone) verified after both fixes. (An aggro scare was a false alarm —
