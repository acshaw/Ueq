# Devplan 2.0 — Zone architecture spike (throwaway)

**Roadmap item:** Spike, runs **before 2.1** (M2 timeframe); informs the M3 zone integration.
**Status:** 🟢 Approved — ready to implement (reviewed 2026-06-22)
**Depends on:** M1 ✅ (the single-scene systems this will eventually need to make zone-aware)
**Unblocks:** an informed **zone-integration** plan (front of M3); de-risks every content decision that
would otherwise bake in single-scene assumptions.

---

## Why this exists (and why now)

The project currently rests on vanilla Mirror's **one shared server scene** — every player is in the
same world. The target needs something fundamentally different:

- **Concurrent occupancy:** Player 1 in Zone A *while* Player 2 is in Zone B, on one server.
- **Relative placement on transition:** zoning lands you at the entry that corresponds to your exit.
- **Spawn state without holding the whole zone in memory:** unload empty zones, but don't lose mob
  spawn state.

The **concurrent-occupancy** requirement is the one that breaks the current model — and a lot of M1
code assumes a single world (spawn system, ChatManager spatial grid, player spawn, persisted position).
If M2/M3 content and systems get built on that assumption and 3.5 then introduces zones, the expensive
part isn't the content — it's retrofitting zone-awareness into all those systems. So we **spike the
risky unknown cheaply now**, before pouring content on the assumption.

This is a **throwaway** experiment: prove the model in a sandbox, capture findings, then plan the real
integration. It must **not** modify shipping systems (so it can't invalidate the M1 regression — that's
the point of keeping it isolated).

> Encouraging prior art: 1.7 already moved the UI to its own additive scene that survives world-scene
> changes — the project is partway into the additive-scene mindset, and the HUD won't fight zoning.

## Scope guardrails
- **In scope (sandbox only):**
  - Two instances of a bare test zone scene **loaded additively on the server**.
  - **Per-scene interest management** so P1 (Zone A) and P2 (Zone B) don't see each other or each
    other's objects.
  - **Player→scene assignment** (a player belongs to one zone scene at a time).
  - **One A→B transition**: a trigger volume → move the player from scene A to scene B, placed at an
    entry point **relative to the exit**.
  - A couple of dummy mobs per zone to confirm they're independent / scene-scoped.
- **Out of scope (these are the *integration*, front of M3 — informed by this):**
  - Real zone content, art, layout.
  - **Spawn-state persistence across unload/reload** (start simple: zones stay loaded, or reload =
    fresh spawns; the persistence refinement is integration work).
  - Reworking the production spawn system / ChatManager / persistence / character-select spawn to be
    zone-aware (the spike *lists* what's needed; it doesn't do it).
  - Polished transition UX (loading screen, fades).
- **Hard rule:** isolated/throwaway. A separate scene set and/or branch; nothing merged into the
  shipping spawn/UI/persistence flow. If it proves out, the *real* integration is a fresh, planned item.

## Review decisions (2026-06-22)
- **R1 — Isolation: dedicated branch.** `spike/zone-architecture` with its own sandbox scenes; deleted
  when the spike concludes. Main stays pristine; this is the throwaway boundary the "hard rule" calls for.
- **R2 — Sandbox player: minimal capsule.** A stripped player — `NetworkedPlayer` movement +
  `NetworkTransformReliable` only, **no** persistence/abilities/experience/regen, **no** Postgres
  dependency. Keeps the sandbox about interest + scene movement. Q3 (character-select /
  `AddPlayerForConnection` interaction) is answered **analytically in the findings note**, not by wiring
  real character-select spawn into the sandbox.
- **R3 — Interest mechanism starting point is chosen, not open research** (see Approach below).
- **R4 — Time-box: 1–2 focused MPPM sessions.** If per-scene interest/physics isn't proving out in that
  window, that is itself a finding — stop and write it up rather than pushing on.
- **R5 — Findings note lands in this devplan** (a "## Findings" section appended at the end), so the
  go/no-go and integration-surface list live with the plan that produced them.

## Approach
- Use Mirror's **additive-scene + interest-management** model (its *Multiple Additive Scenes* example is
  exactly this: multiple instances of a scene on one server, players partitioned, visibility separated).
  This makes it an **integration spike, not research** — the pattern is supported.
- **Start with the canonical mechanism (R3):** `SceneInterestManagement` for visibility partitioning +
  each additive zone scene loaded with **`LocalPhysicsMode.Physics3D`** so triggers/raycasts/movement
  don't bleed across zones. Q2 then just *confirms the setup cost* rather than choosing a mechanism from
  scratch.
- Server boot: load Zone A and Zone B additively. Assign connecting players to a scene; use Mirror's
  scene/physics interest separation so each player only sees their scene's objects.
- Transition: a trigger in Zone A → server removes the player from A and re-adds them into B at the
  mapped entry point (record exit position/facing → place relative in B).
- Drive two clients (MPPM): put one in each zone, confirm isolation; walk one through the transition.

## Questions the spike must answer (the deliverable)
1. **Feasibility/perf:** does concurrent multi-zone on one Mirror server hold up at our scale? Any
   showstoppers?
2. **Interest mechanism:** which Mirror mechanism (scene interest management / physics scenes) cleanly
   separates zones, and what does it cost to set up?
3. **Player movement between scenes:** the exact API/flow to move a spawned player A→B (and how that
   interacts with `NetworkServer.AddPlayerForConnection` / our character-select spawn).
4. **The integration surface:** a concrete list of M1 systems that need zone-awareness — spawn system,
   ChatManager (per-zone delivery), persisted position (add a zone id), character-select spawn
   (spawn into a zone), regen/AI ticks per scene. This list **scopes the M3 zone-integration devplan.**
5. **Spawn-state strategy:** evidence to choose between keep-loaded / reload-fresh / persisted-snapshot
   for empty zones.

## Success criteria
- Two MPPM clients: P1 in Zone A, P2 in Zone B **simultaneously**, not seeing each other or the other
  zone's mobs.
- P1 crosses a trigger → lands in Zone B at the entry corresponding to the exit.
- Each zone's dummy mobs are independent.
- A short written **findings note** answering the five questions above (lands in this devplan or a
  sibling), which becomes the input to the real M3 zone-integration item.

## Risks
- **Mirror interest/physics-scene setup** is the genuine unknown — that's *why* this is a spike.
- **Scope creep into the real integration** — resist; the moment you're editing the production spawn/
  chat/persistence systems, you've left the spike and should stop + write the integration plan.
- **Throwaway discipline** — keep it isolated so it can't destabilize M1 (and so the deferred full
  regression stays valid until the real integration).

## Done when
Concurrent two-zone occupancy + one relative transition are demonstrated in a sandbox with two clients,
and the findings note answers the five questions — giving a clear go/no-go and a scoped integration
plan for the front of M3. No shipping system was modified.
