# Devplan 2.0 — Zone architecture spike (throwaway)

**Roadmap item:** Spike, runs **before 2.1** (M2 timeframe); informs the M3 zone integration.
**Status:** ✅ Done — **GO** (proven 2026-06-22). Findings below scope the M3 zone-integration item.
**Depends on:** M1 ✅ (the single-scene systems this will eventually need to make zone-aware)
**Unblocks:** an informed **zone-integration** plan (front of M3); de-risks every content decision that
would otherwise bake in single-scene assumptions.

---

## Why this exists (and why now)

The project currently rests on vanilla Mirror's **one shared server scene** — every player is in the
same world. The target needs something fundamentally different:

- **Concurrent occupancy:** Player 1 in Zone A *while* Player 2 is in Zone B, on one server.
- **Relative placement on transition:** zoning lands you at the entry that corresponds to your exit.
- **Spawn state without holding the whole zone in memory:** unload empty zones, but don't lose mob
  spawn state.

The **concurrent-occupancy** requirement is the one that breaks the current model — and a lot of M1
code assumes a single world (spawn system, ChatManager spatial grid, player spawn, persisted position).
If M2/M3 content and systems get built on that assumption and 3.5 then introduces zones, the expensive
part isn't the content — it's retrofitting zone-awareness into all those systems. So we **spike the
risky unknown cheaply now**, before pouring content on the assumption.

This is a **throwaway** experiment: prove the model in a sandbox, capture findings, then plan the real
integration. It must **not** modify shipping systems (so it can't invalidate the M1 regression — that's
the point of keeping it isolated).

> Encouraging prior art: 1.7 already moved the UI to its own additive scene that survives world-scene
> changes — the project is partway into the additive-scene mindset, and the HUD won't fight zoning.

## Scope guardrails
- **In scope (sandbox only):**
  - Two instances of a bare test zone scene **loaded additively on the server**.
  - **Per-scene interest management** so P1 (Zone A) and P2 (Zone B) don't see each other or each
    other's objects.
  - **Player→scene assignment** (a player belongs to one zone scene at a time).
  - **One A→B transition**: a trigger volume → move the player from scene A to scene B, placed at an
    entry point **relative to the exit**.
  - A couple of dummy mobs per zone to confirm they're independent / scene-scoped.
- **Out of scope (these are the *integration*, front of M3 — informed by this):**
  - Real zone content, art, layout.
  - **Spawn-state persistence across unload/reload** (start simple: zones stay loaded, or reload =
    fresh spawns; the persistence refinement is integration work).
  - Reworking the production spawn system / ChatManager / persistence / character-select spawn to be
    zone-aware (the spike *lists* what's needed; it doesn't do it).
  - Polished transition UX (loading screen, fades).
- **Hard rule:** isolated/throwaway. A separate scene set and/or branch; nothing merged into the
  shipping spawn/UI/persistence flow. If it proves out, the *real* integration is a fresh, planned item.

## Review decisions (2026-06-22)
- **R1 — Isolation: dedicated branch.** `spike/zone-architecture` with its own sandbox scenes; deleted
  when the spike concludes. Main stays pristine; this is the throwaway boundary the "hard rule" calls for.
- **R2 — Sandbox player: minimal capsule.** A stripped player — `NetworkedPlayer` movement +
  `NetworkTransformReliable` only, **no** persistence/abilities/experience/regen, **no** Postgres
  dependency. Keeps the sandbox about interest + scene movement. Q3 (character-select /
  `AddPlayerForConnection` interaction) is answered **analytically in the findings note**, not by wiring
  real character-select spawn into the sandbox.
- **R3 — Interest mechanism starting point is chosen, not open research** (see Approach below).
- **R4 — Time-box: 1–2 focused MPPM sessions.** If per-scene interest/physics isn't proving out in that
  window, that is itself a finding — stop and write it up rather than pushing on.
- **R5 — Findings note lands in this devplan** (a "## Findings" section appended at the end), so the
  go/no-go and integration-surface list live with the plan that produced them.

## Approach
- Use Mirror's **additive-scene + interest-management** model (its *Multiple Additive Scenes* example is
  exactly this: multiple instances of a scene on one server, players partitioned, visibility separated).
  This makes it an **integration spike, not research** — the pattern is supported.
- **Start with the canonical mechanism (R3):** `SceneInterestManagement` for visibility partitioning +
  each additive zone scene loaded with **`LocalPhysicsMode.Physics3D`** so triggers/raycasts/movement
  don't bleed across zones. Q2 then just *confirms the setup cost* rather than choosing a mechanism from
  scratch.
- Server boot: load Zone A and Zone B additively. Assign connecting players to a scene; use Mirror's
  scene/physics interest separation so each player only sees their scene's objects.
- Transition: a trigger in Zone A → server removes the player from A and re-adds them into B at the
  mapped entry point (record exit position/facing → place relative in B).
- Drive two clients (MPPM): put one in each zone, confirm isolation; walk one through the transition.

## Questions the spike must answer (the deliverable)
1. **Feasibility/perf:** does concurrent multi-zone on one Mirror server hold up at our scale? Any
   showstoppers?
2. **Interest mechanism:** which Mirror mechanism (scene interest management / physics scenes) cleanly
   separates zones, and what does it cost to set up?
3. **Player movement between scenes:** the exact API/flow to move a spawned player A→B (and how that
   interacts with `NetworkServer.AddPlayerForConnection` / our character-select spawn).
4. **The integration surface:** a concrete list of M1 systems that need zone-awareness — spawn system,
   ChatManager (per-zone delivery), persisted position (add a zone id), character-select spawn
   (spawn into a zone), regen/AI ticks per scene. This list **scopes the M3 zone-integration devplan.**
5. **Spawn-state strategy:** evidence to choose between keep-loaded / reload-fresh / persisted-snapshot
   for empty zones.

## Success criteria
- Two MPPM clients: P1 in Zone A, P2 in Zone B **simultaneously**, not seeing each other or the other
  zone's mobs.
- P1 crosses a trigger → lands in Zone B at the entry corresponding to the exit.
- Each zone's dummy mobs are independent.
- A short written **findings note** answering the five questions above (lands in this devplan or a
  sibling), which becomes the input to the real M3 zone-integration item.

## Risks
- **Mirror interest/physics-scene setup** is the genuine unknown — that's *why* this is a spike.
- **Scope creep into the real integration** — resist; the moment you're editing the production spawn/
  chat/persistence systems, you've left the spike and should stop + write the integration plan.
- **Throwaway discipline** — keep it isolated so it can't destabilize M1 (and so the deferred full
  regression stays valid until the real integration).

## Done when
Concurrent two-zone occupancy + one relative transition are demonstrated in a sandbox with two clients,
and the findings note answers the five questions — giving a clear go/no-go and a scoped integration
plan for the front of M3. No shipping system was modified.

## Sandbox build — iteration 1 (2026-06-22)

Scaffolded on branch `spike/zone-architecture`, fully isolated under deletable trees
(`Assets/Scripts/Spike/`, `Assets/Scenes/Spike/`, `Assets/Prefabs/Spike/`):

- `ZoneSpikeNetManager` — loads ZoneA + ZoneB additively (each `LocalPhysicsMode.Physics3D`),
  alternates players A/B on connect, `ServerMovePlayer` does the A↔B transition (scene move +
  client scene-swap messages + owner reposition). Host-aware (skips scene messages for the host
  connection). Subclasses `NetworkManager` — **no** DB/auth/persistence.
- `ZoneSpikePlayer` — minimal capsule, client-authoritative `NetworkTransformReliable` movement,
  kinematic Rigidbody so server-side trigger detection is reliable; `[ServerCallback] OnTriggerEnter`
  → `ServerMovePlayer`; `TargetTeleport` places the owner at the entry point.
- `ZonePortal` — plain trigger marker (`targetZone` + `entryPosition`).
- `ZoneDummyMob` — per-zone networked marker, SyncVar tint (Zone A red / Zone B blue) to make
  interest isolation visible.
- `ZonePhysicsStepper` — steps each zone's local physics scene on the server (self-contained copy
  of Mirror's `PhysicsSimulator`; **no asmdef dependency**). Without it, portal triggers never fire.
- `ZoneSpikeSetup` — `Tools/Spike/Build Zone Sandbox`: builds both zone scenes + a bootstrap
  container scene + the two prefabs, wires the NetworkManager, registers the 3 scenes in Build
  Settings. Re-runnable.

All Mirror type/API names verified against the in-project Mirror version before handoff.

### Run steps (MPPM — R4 time-box: 1–2 sessions)
1. In Unity: **`Tools/Spike/Build Zone Sandbox`** (opens `ZoneSpikeBootstrap`).
2. Press **Play**, click **Server Only** in the HUD (cleanest — avoids the host rendering both
   zone scenes at once). Console should log both zones loaded + dummy mobs spawned.
3. `Window → Multiplayer Play Mode`: activate **two** virtual players; each presses **Client** in
   its HUD. They alternate into Zone A and Zone B.
4. **Verify isolation** (success criteria 1 & 3): the Zone-A client sees only red mobs, the Zone-B
   client only blue; neither sees the other player.
5. **Verify transition** (criterion 2): walk the Zone-A player north into the portal → it should
   land in Zone B at the south entry, now seeing blue mobs (and the Zone-B player, if present).
6. Fill in the five findings below.

### First run (2026-06-22, Host + 1 MPPM client)
- ✅ **Per-scene interest isolation works** — Zone-A client sees red mobs, Zone-B client sees blue;
  they don't see each other.
- ✅ **Server-side trigger detection works** — the player moved by the synced (client-auth) transform
  *does* fire `OnTriggerEnter` in the server's stepped local physics scene.
- 🐞 **Transition bounce (fixed).** Both zones share local coords → both portals at `(0,1,8)`.
  `MoveGameObjectToScene` preserves world position, so a transitioning player materialises inside the
  *destination's* portal and ping-pongs A↔B↔A forever (scene flicker + frozen player). Fix:
  `ServerMovePlayer` repositions to the entry on the **server** immediately + a 1s per-player
  **debounce** covering the client-auth position-sync lag. → **Finding for Q4:** any zone-aware
  teleport must reposition server-side atomically with the scene move, not rely on a client-auth
  teleport RPC; and identical-coord zones need either offset world placement or this debounce.
- ⚠️ **Host renders both zones superimposed.** The server process holds both scenes at the same
  coords, so a Host client's camera shows red+blue overlap. Interest mgmt still isolates *networked*
  objects, but static geometry bleeds. → Test as **Server Only + 2 MPPM clients** (not Host).

### Second run (2026-06-22, Server Only + 2 MPPM clients)
- ✅ **Both players transitioned** (P1 A→B, P2 B→A) and the bounce is gone — server reposition +
  debounce fixed it.
- ✅ **Interest isolation confirmed live** — the two players see each other only once co-located in
  the same zone; otherwise isolated.
- 🐞 **Couldn't portal *back* after the first hop (fixed).** A kinematic Rigidbody stops firing
  `OnTriggerEnter` once `MoveGameObjectToScene` relocates it to a different physics scene — the fresh
  body fires on the first portal, the moved body never fires again. Fix: replaced physics-trigger
  detection with a **server-side proximity poll** (`Update()`, distance ≤ 2.5 to a cached per-zone
  portal). Deterministic across scene moves. → **Finding for Q4:** zone portals should NOT be gated
  on physics triggers; a server-side proximity/volume check is the reliable mechanism.

### Third run (2026-06-22, Server Only + 2 clients)
- 🐞 **Return hop still failed + players appeared sunk into the floor from the other client's view
  (fixed).** Both traced to **client-authoritative movement fighting the server-initiated teleport**:
  the server reposition desyncs `NetworkTransformReliable`'s baseline, so (a) observers render an
  offset position (the sink) and (b) the server's own transform copy is wrong, so the proximity poll
  (which reads the server transform) never sees the player reach the portal → return never fires.
  Fix: **switched the spike player to server-authoritative movement** — owner sends `CmdMove(dir)`,
  the server integrates it, `NetworkTransformReliable` (default `ServerToClient`) syncs to all.
  → **Finding for Q4:** zone players must be **server-authoritative** (matches the real
  `NetworkedPlayer` CmdSendInput model); client-auth + a cross-scene teleport desyncs position for
  both observers and the server itself. Requires re-running the sandbox builder (syncDirection is
  serialized on the prefab).

### Fourth run (2026-06-22, Server Only + 2 clients)
- ✅ **WASD + continuous round-trip A↔B↔A both ways** now work (server-authoritative movement landed).
- 🐞 **Per-hop Y ratchet + drifting X/Z (fixed).** Each transition the players spawned incrementally
  higher until they couldn't reach the portal; coords were inaccurate. Cause: teleporting via a raw
  `transform.position = entryPos` set — per Mirror's `NetworkTransformBase` comments this desyncs
  `NetworkTransformReliable`'s **delta compression** (drift) and makes clients **interpolate toward
  the far point** (the Y ratchet). Fix: teleport via `NetworkTransformReliable.ServerTeleport()`
  (clears snapshot buffer, `Physics.SyncTransforms()`, RPCs a clean jump). → **Finding for Q4:** zone
  transitions must use NetworkTransform's teleport API, never a raw transform set.

### Fifth run (2026-06-22, Server Only + 2 clients)
- ✅ **Infinite zoning is stable** — no ratchet, no drift; the `ServerTeleport` fix held.
- 🐞 **Owner sees himself sunk into the floor in the destination zone (fixed).** Owner-only +
  destination-only; observers render him correctly → server position is fine. NT's `Apply` sets
  position identically for owner/observers, so the divergence is the local player coupling to
  **client-side physics** (the prefab still had a kinematic Rigidbody + CapsuleCollider) across the
  scene move. Fix: strip all physics from the player (pure NT-driven visual) + sync in world space.
  → **Finding for Q4:** zone players should carry **no client-side physics body**, or the owner's
  view desyncs across scene moves.

## Findings (R5) — the deliverable that scopes M3

1. **Feasibility/perf — GO.** One Mirror server hosted two distinct zone scenes additively with a
   player in each *simultaneously*, isolated, plus stable infinite A↔B transitions both ways. No
   showstoppers at spike scale (2 zones, 2 clients, dummy mobs). The concurrent-occupancy requirement
   that breaks vanilla single-scene Mirror is satisfied by the additive-scene + interest model.

2. **Interest mechanism — `SceneInterestManagement` + per-scene additive load. Cheap.**
   `SceneInterestManagement` partitions visibility by `gameObject.scene` (one component on the
   NetworkManager GO). Zones load with `LocalPhysicsMode.Physics3D` so each gets an isolated physics
   scene. Setup cost is low. **Caveat:** a local physics scene is **not** auto-stepped — triggers/
   collisions need a manual `physicsScene.Simulate()` per scene, or avoid server physics entirely.

3. **Player movement A→B — `SceneManager.MoveGameObjectToScene` + `SceneMessage`, but transforms are
   the work.** Server: `MoveGameObjectToScene(player, targetScene)` then send the client
   `SceneMessage{Load/UnloadAdditive}`; `SceneInterestManagement` auto-rebuilds observers in LateUpdate.
   Hard-won requirements: movement **must be server-authoritative**; the reposition **must use
   `NetworkTransform.ServerTeleport`** (a raw `transform.position` set desyncs NTReliable delta
   compression + ratchets interpolation); players should carry **no client-side physics body**; and an
   **owner-side coordinate/parent offset across the scene move still needs massaging** (left unsolved —
   it's presentation, not feasibility). **Character-select spawn (analytical, per R2):** same pattern —
   `MoveGameObjectToScene` into the assigned zone *before* `AddPlayerForConnection`.

4. **Integration surface — M1 systems that need zone-awareness (scopes the M3 item):**
   - **Player movement/transform** — server-authoritative; teleport via NetworkTransform API; no
     client physics body; coordinate-space massaging.
   - **Portals/transitions** — server-side **proximity/volume** check, NOT physics triggers.
   - **Spawn system (`SpawnPoint`)** — spawn into the correct zone scene; per-zone activation.
   - **`ChatManager` spatial grid** — per-zone delivery (key the grid by zone/scene; don't bleed across).
   - **Persistence** — add a **zone id** to character state; spawn into the persisted zone on load.
   - **Character-select spawn** — spawn the player into a zone scene (move-before-AddPlayer).
   - **EnemyAI / regen / any per-frame server tick** — ensure per-scene (AI is already server-only).
   - **Server physics** — avoid relying on per-scene physics, or step each scene manually.

5. **Spawn-state strategy — deferred (out of scope), but evidence points to start-simple.** The spike
   kept both zones loaded the whole session and that was trivially fine for 2 zones. Recommendation for
   integration: **keep-loaded** for the small initial world; move to **load-on-demand + persisted spawn
   snapshot** only when zone count/memory makes always-loaded impractical. No data forces the harder
   option yet.

**Go / no-go: GO.** Mirror supports the target model — concurrent, isolated zones on one server with
working transitions. The cost is **not** architectural; it's (a) making the M1 systems above
zone-aware and (b) careful transform/movement handling (server-authoritative + teleport API + no
client physics + coordinate-space massaging). Those become the scope of the **M3 zone-integration**
item. The user's own conclusion: *"conceptually Mirror will support my needs; it may be challenging to
massage the transforms, but it can be done."*
