Conversation System — User Guide

How to make an NPC talk — greetings, gated dialogue, keyword unlocks, opening a shop — entirely in the Conversation Editor. There is no dialogue tree and no clickable UI: the NPC listens to chat and matches keywords. Read the Big Picture, then the Recipes.

1. The big picture

An NPC's dialogue is a conversation set: a named list of keywords. A player talks to an NPC by simply typing the keyword in chat near it (after targeting it) — there's no menu. When the NPC hears a keyword it knows, it replies (and optionally does more: opens a shop, runs a quest turn-in, changes what you can ask next).

Mental model: a conversation set is an NPC's whole vocabulary; a keyword is one entry in it — a trigger word, a response, and a few switches that control when it fires and what it unlocks. Everything you author for dialogue is web-side data; Unity just runs it.

2. Key concepts

  • Conversation set — a named bundle of keywords (set_id, e.g. GuardKeywords). One set can be shared by many NPCs (every City Guard can point at the same set); a unique NPC usually gets its own.
  • Keyword — one dialogue entry: the trigger word, the response text, and behavior flags (§5).
  • Mode: Passive vs. Active — Passive keywords are always heard; Active keywords only fire mid-conversation (after a hail).
  • Opener (hail) — a keyword flagged Opener starts a conversation when heard while the NPC is idle. Any keyword can be an opener, not just one literally named "hail" — it's just convention to use that word.
  • Unlock — a keyword can list other keywords it unlocks; an Active + Requires unlock keyword only fires for a player who has triggered one of its unlockers first, in that same conversation.
  • Faction gate — a keyword can require a minimum standing with a faction; if the player doesn't meet it, the NPC doesn't respond at all (not even an error) — see the Faction System / Faction Editor for standings.
  • Response tokens — response text can include <name>, <race>, <class>, <gender>, substituted per-player at delivery time.
  • Quest transaction — any keyword can carry a turn-in/reward bundle (requirements consumed, rewards granted). This is the game's whole quest system — see the Quest Rewards guide for the details; this guide only covers wiring the surrounding conversation.

3. Where each piece lives

Same three programs as the rest of the content pipeline:

  1. Postgres — started with Docker: docker compose up -d.
  2. The web app — where conversation sets, keywords, and their faction/quest data are authored.
  3. Unity — hosts the game server, which loads every conversation set from the database when the host starts, and runs the NPC that speaks it.
⚠️ Important: Unity reads the database once, at host start. Edit a conversation in the web app while the game is running, and you must restart the Unity host to see the change.

4. The conversation flow

Each NPC that can talk runs a small state machine:

Idle → (player says an Opener keyword) → InConversation(that player) → Idle
                                                    ↓ 30s of silence, "farewell", or the player un-targets the NPC
                                              closing line + a short cooldown → Idle
  • While Idle, the NPC only reacts to Passive keywords.
  • Saying an Opener keyword while Idle both starts the conversation and delivers that keyword's own response in the same beat.
  • While InConversation with a player, the NPC also reacts to that player's Active keywords (and keeps reacting to Passive ones). It ignores other players' Active keywords.
  • The conversation ends — the NPC says its closing line (default "Farewell.", fixed in Unity, §10) — when: a keyword marked Ends conversation fires, 30 seconds pass with nothing said, or the player stops targeting the NPC.
  • Unlocked keywords are session-scoped — they reset to locked when the conversation ends. There's no server-side memory of what a player has unlocked before.
A player must have the NPC targeted (clicked) and be within its hearing range to be heard at all — this currently applies to Passive keywords too; see §10 for the design-vs-implementation gap.

5. Anatomy of a keyword

Every keyword in the Conversation Editor has these fields:

FieldMeaning
KeywordThe trigger word. Matching is case-insensitive substring containment in the chat message (e.g. keyword wares matches "show me your wares").
ModePassive = always heard while in range/targeted. Active = only heard from the player currently in conversation with this NPC.
ResponseWhat the NPC says back (NPC-channel chat, visible to everyone nearby). Supports <name> <race> <class> <gender>. Bracketing a word like [patrol] is just an authoring convention to hint what's sayable next — it has no special engine behavior.
Opener (hail)If checked, this keyword starts a conversation when heard while the NPC is Idle.
Ends conversationIf checked, the NPC says its closing line and returns to Idle right after this keyword's response.
Requires unlockIf checked, this keyword only fires once one of its unlockers has already fired for this player, this conversation.
UnlocksA comma-separated list of other keywords in this set that become sayable once this one fires (for that player, that conversation).
Required faction / Required standingOptional gate — the NPC only responds if the player's standing with that faction is at least the given threshold. Leave both empty for no gate.
Quest transactionOptional turn-in/reward bundle. Covered in the Quest Rewards guide.

6. Wiring a conversation to an NPC

This part is entirely web-authored — no Unity Inspector editing needed, assuming the mob already exists and its prefab has been patched once (§10):

  1. Web app Author the conversation set (Conversation Editor) as in §5.
  2. Web app Open the NPC's mob in the Mob Editor and set Conversation set to your set's id. Save.
  3. Unity Give the mob a body if it doesn't have one yet, and place/confirm its Spawn Point — see the Spawn System guide §6–7 (a talking NPC still needs to be spawned and targetable like any mob).
  4. Unity Restart the Unity host to load the new/edited conversation content.
  5. Unity Test: target the NPC, type a Passive/Opener keyword in chat (e.g. hail).

7. Special case: opening a shop

A vendor NPC uses the same conversation system — "wares" is just a keyword. In the Mob Editor, a mob has a separate Vendor dropdown (pick a vendor inventory) and a Vendor open keyword field (default wares). When a player says that exact keyword to the NPC, its shop UI opens automatically — in addition to whatever response you wrote for that keyword.

⚠️ The vendor-open keyword must have "Ends conversation" unchecked. If it's checked, the shop opens and is immediately closed in the same beat (ending the conversation closes any open shop). Give the keyword a normal response like "What would you like?" and leave the conversation open.

8. Quests ride on keywords too

There's no separate "quest" entity — a quest is a keyword with a Quest transaction attached (requirements consumed, rewards granted, all-or-nothing, repeatable). Everything in §1–§7 above still applies: the transaction rides on top of a normal keyword's mode/opener/unlock/faction-gate behavior. See the Quest Rewards guide for the transaction fields, the all-or-nothing rule, and worked recipes.

9. Recipes (step-by-step)

These assume Postgres + the web app are running, and you have the game scene open in Unity. Every step is tagged by where you do it. After any Web-app change, restart the Unity host before testing.

Web app in this browser UI Unity in the Unity editor (Hierarchy / Inspector / Scene)

Recipe A — A simple greeter (no gate, no quest)

Goal: a villager who says hello and nothing else.

  1. Web app Conversation Editor → New set, id VillagerGreeting. Add one keyword: hail, mode Passive, Opener checked, Ends conversation checked, response "Oh, hello there, <name>." Save.
  2. Web app Mob Editor → author (or open) the villager mob, leave faction empty (peaceful), set Conversation set = VillagerGreeting. Save.
  3. Unity Give the mob a body and a Spawn Point (Spawn System guide) if it doesn't have one. Restart the Unity host.
  4. Unity Test: target the villager, type hail — it greets you by name and the conversation ends immediately (single-line NPC, nothing more to say).

Recipe B — A gated helper + a keyword unlock

Goal: a guard with an open greeting, a faction-gated "help" response, and a topic ("patrol") that unlocks a follow-up ("danger"). (This mirrors the game's seeded GuardKeywords set.)

  1. Web app Faction Editor — confirm a CityGuards faction (or your own) exists with a standing ladder.
  2. Web app Conversation Editor → New set GuardKeywords, add these keywords:
    • hail — Passive, Opener. Response: "Hail, <name>! Ask me about [guards] or [patrol]."
    • guards — Passive. Response: "The guards are stationed at the north gate."
    • patrol — Active. Response: "We patrol these roads to keep travelers like you safe, <race>." Unlocks: danger.
    • danger — Active, Requires unlock checked. Response: "Strange creatures have been seen to the east. Be wary."
    • help — Active. Response: "What do you need, adventurer?" Required faction = CityGuards, Required standing = Indifferent.
    • farewell — Passive, Ends conversation checked. Response: "Safe travels, <name>."
    Save.
  3. Web app Mob Editor → set the guard's Conversation set = GuardKeywords. Save.
  4. Unity Restart the Unity host.
  5. Unity Test: say danger first — nothing happens (locked). Say patrol — unlocks it. Say danger — now it responds. Say help — only responds if your standing with CityGuards is Indifferent or better; say farewell to close.

Recipe C — A shopkeeper

Goal: a merchant who greets you and can open her shop.

  1. Web app Vendor Editor — create/confirm a vendor inventory with some stock.
  2. Web app Conversation Editor → set with a hail Opener keyword, and a wares keyword — Passive, response "What would you like?", Ends conversation unchecked (§7). Save.
  3. Web app Mob Editor → set Conversation set to that set, Vendor to your inventory, and confirm Vendor open keyword = wares (the default). Save.
  4. Unity Give her a body + Spawn Point if needed. Restart the Unity host.
  5. Unity Test: hail her, then say wares — she responds and the shop window opens.

Recipe D — A quest-giver

Goal: an NPC that takes an offering and grants a reward on a keyword.

  1. Do Recipe A or B first to get the NPC talking normally (an opener + a keyword describing the task).
  2. Web app On the turn-in keyword, open its Quest transaction panel and fill in requirements/rewards — see the Quest Rewards guide, Recipe A, for the full walkthrough.
  3. Unity Restart the host and test as in that guide.

10. Known gaps — what still needs Unity (or isn't built yet)

Most of a conversation is fully web-authored. A few things are not (yet):

  • Unity The NPC's prefab must carry the conversation components once. Every mob normally uses the shared Enemy prefab, which already carries NpcConversation, NpcEventDispatcher, VendorApplicator, and KeywordRewardApplicator after Tools → Patch Enemy Prefab has been run once (it almost certainly already has, from spawn/quest setup). You only need to worry about this if you build a custom NPC prefab from scratch.
  • Unity Hearing range, conversation timeout, cooldown, and the closing line are not web-authored. They're plain fields on the NpcConversation component (defaults: 20 units hearing range, 30s timeout, 5s cooldown, closing line "Farewell.") baked onto the shared Enemy prefab — so every conversation NPC uses the same values. Giving one NPC a longer hearing range or a custom farewell line currently means editing that value on the prefab (affecting all NPCs) or forking a variant prefab in Unity; there's no per-mob override from the web yet.
  • Passive keywords still require the player to have the NPC targeted. The original design called for Passive listening to work by proximity alone (e.g. overhearing a password through a door without targeting anything), but the current implementation checks the player's target before anything else, regardless of mode. Until that's built, every keyword — Passive or Active — needs the player to have clicked the NPC first.
  • NPC-initiated speech isn't wired up yet. The design calls for NPCs to greet/warn players on perception (OnPerceived) and speak ambient lines on a timer (IOnTimer). The hooks exist, but today OnPerceived's friendly/warning branches only write a debug log — no chat message is sent, and there's no generic "say a line" component to wire from the web. A hostile faction still aggroes correctly (that part is live); it just won't greet or warn you first.
  • Unity A non-mob NPC (one without a MobApplicator, e.g. a hand-placed one-off) falls back to a keywordSet ScriptableObject reference assigned in the Inspector instead of the DB set — not relevant if you always author NPCs through the Mob Editor, which is the normal path.

11. Troubleshooting

SymptomLikely cause / fix
NPC never responds to anythingYou haven't targeted it (click it first — required even for Passive keywords, §10); you're out of its hearing range (default 20 units); or its conversationSetId doesn't point at a real set (check the Mob Editor).
NPC responds to some keywords but not othersThe others are Active and you're not in a conversation with it yet (say an Opener first); or they're Requires unlock and you haven't said their unlocker yet; or a faction gate is blocking them (§5).
My web edit didn't show upUnity loads content at host start — restart the Unity host. Also confirm Postgres + the API are running.
Vendor keyword opens and instantly closes the shopThe keyword has Ends conversation checked — uncheck it (§7).
Keyword matches when I didn't mean it toMatching is substring, not whole-word — a short keyword like ore also matches "before". Use a more specific keyword.
<class>/<gender> shows a fallback word instead of the real value The player's character predates the class/gender system, or has no class assigned — otherwise this resolves normally.
Two NPCs sharing a set diverge in what a player has unlockedExpected — unlocks are per-player, per-conversation, and reset when a conversation ends; they aren't shared across NPCs or saved between sessions.
NPC doesn't greet me on approach / doesn't warn before attackingNot built yet — see §10 (NPC-initiated speech). Aggro itself still works even without a warning line.
