Build & Deploy — Regenerating the Client and Server

How to cut a new release when the Unity project itself changed (code, scenes, prefabs) — not for content edits made through the other editors on this site, which take effect on their own the next time the Unity host restarts and need no rebuild at all.

1. Do you even need to rebuild?

What changedRebuild needed?
An item, mob, ability, quest, faction, loot table, race/class, XP curve, spawn table — anything edited through this website's other tabsNo. Content loads from the database at server startup / on demand. Restart the Unity host (or the deployed ueq-gameserver.service) if it's not picking up a change, but that's a restart, not a rebuild.
Any C# script, prefab, scene, or ScriptableObject default inside the Unity project Yes — both the client and the server are compiled from that project, so a code/scene change is baked into the binary and can only reach players through a new build.

2. The golden rule: client and server travel together

⚠️ Never deploy a server built from a different point in the project than the client players are running. This project has been bitten by this more than once — a scene change alone is enough to desync Mirror's internal object bookkeeping between an old server and a new client (or vice versa), producing confusing symptoms like "Spawn scene object not found" instead of a clean error. The build-id check (§6) now catches the login-time version of this mistake automatically, but it can't fix a deployed server that's out of sync with the database or scene content it expects — always rebuild and redeploy both sides together whenever either changed.

3. The three pieces

PieceWhat it isHow often it changes
Server (ueq-gameserver.service on AWS)Linux Dedicated Server build, Tools/Build/Build Linux Dedicated Server in UnityEvery release that touches server-relevant code/scenes
Client (what a player runs)Windows Standalone build, Tools/Build/Build Standalone Client in Unity, zipped and served for downloadEvery release — see the golden rule above
Launcher (UeqLauncher.exe)A small separate .NET app (launcher/Ueq.Launcher/) that checks for a new client and downloads/launches it Rarely. Its own logic is meant to stay simple and stable — most releases don't touch it at all, only the client/server do.

4. Recipe A — routine release (server and/or client code changed)

Unity in the Unity editor Local shell PowerShell / Git Bash on your machine AWS your own AWS-authenticated terminal (this sandbox can't reach AWS)
  1. Unity Make and test your code/scene changes as usual.
  2. Unity Tools/Build/Stamp New Build Id — do this once per release, not once per build method. It writes one timestamp id into Assets/Resources/BuildInfo.asset and a sibling C:\Builds\Ueq\version.txt. Stamping separately from building is deliberate: if you stamped inside each build method instead, building the client a minute after the server would give them two different ids and the version check (§6) would reject every login.
  3. Unity Build whichever of client/server actually needs it — Tools/Build/Build Linux Dedicated Server and/or Tools/Build/Build Standalone Client. Per the golden rule (§2), if you're not sure, build both.
  4. Local shell Zip the client (PowerShell's Compress-Archive is fine here — the launcher's own .NET code extracts it, never Linux unzip): 
    Compress-Archive -Path "C:\Builds\Ueq\Client\*" -DestinationPath "C:\Builds\Ueq\client.zip" -Force
  5. AWS Upload whatever changed: 
    aws s3 cp "C:\Builds\Ueq\client.zip" "s3://<bucket>/client.zip"
aws s3 cp "C:\Builds\Ueq\version.txt" "s3://<bucket>/version.txt"
# if the server changed too, tar it (Linux unzip DOES choke on Compress-Archive's backslash
# paths for this one — see §7):
cd "C:\Builds\Ueq\ServerLinux"; tar czf ../gameserver.tar.gz .
aws s3 cp "..\gameserver.tar.gz" "s3://<bucket>/gameserver.tar.gz"
  6. Local shell Commit and push your code changes — git push to main auto-triggers the deploy workflow, which presigns whatever's in the bucket and restarts the affected services (web/api always; gameserver and the client download only if their artifacts changed since the last deploy — redeploying an unchanged one is harmless).
  7. Verify: log in with a freshly built client — should connect normally. If you deliberately want to test the version check, connect with an old client build after redeploying a new server — expect a clear "Your client is out of date" rejection, not a silent desync.
  8. Tell whoever's testing (e.g. your brother) there's something new — running the launcher picks it up automatically, no manual redownload needed on their end.

5. Recipe B — first-time / rare: publishing the launcher itself

Most releases don't need this — only do it if you've actually changed something in launcher/Ueq.Launcher/, or the very first time you hand the launcher to someone.

  1. Local shell 
    cd launcher\Ueq.Launcher
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
    Produces one self-contained UeqLauncher.exe (~100+ MB — that's the bundled .NET runtime, so the recipient needs nothing else installed).
  2. AWS Get that one file onto the box's /downloads/ path (a one-off — via SSM port-forwarding, the browser SSH file upload, or by wiring a LAUNCHER_URL into the deploy pipeline the same way client.zip works, if this starts happening often enough to be worth automating).
  3. Send the download link once. From then on, running the launcher always fetches whatever's newest per Recipe A — no further launcher-side action needed on routine releases.

6. How the version check works

The login handshake (AccountAuthenticator) now carries a clientBuildId. The server compares it to its own stamped id before doing any database work and, on a mismatch, rejects with a clear message instead of letting a stale client limp along into a desync. If nobody has ever run Stamp New Build Id (e.g. a fresh Editor Play session), the id is empty on both sides and the check is skipped entirely — it only enforces once there's actually something to compare.

Separately, the launcher checks a tiny version.txt file over HTTP before the game even starts, so most players never see the login-time rejection at all — they get an automatic update instead. The login check is the safety net for someone who runs the extracted game .exe directly, bypassing the launcher.

7. Known gaps

  • No true delta/patch downloads. Any update re-downloads the whole client zip (hundreds of MB), not just the changed files. Deliberately not built yet — real delta patching (per-file hashing, partial downloads, integrity checks) is a meaningfully bigger project, worth it if update size or frequency ever becomes a real pain, not before.
  • The launcher doesn't update itself. If its own logic ever needs to change, that's a manual one-off handoff (Recipe B), not automatic.
  • Client zip vs. gameserver artifact use different archive formats on purpose — the client zip is .zip/Compress-Archive (extracted by the launcher's own .NET code on a Windows machine); the gameserver artifact is .tar.gz/tar (extracted by Linux unzip... which can't actually parse the backslash-style paths Compress-Archive writes for nested folders — that's exactly why the server side uses tar instead). Don't swap them.
  • The download page/artifacts are public, unauthenticated — same exposure posture as the open game port and API. Fine at hobby scale with a small, trusted set of players; revisit if that ever changes.

8. Troubleshooting

SymptomLikely cause / fix
Client gets "Your client is out of date" even though you just built itYou built it before running Stamp New Build Id, or stamped again after building it — the stamp must happen first, then the build. Re-stamp, then rebuild.
Weird desync symptoms (missing objects, "Spawn scene object not found") even though login succeeded The version check only compares build ids, which are just a timestamp you control by remembering to stamp — it can't catch "you rebuilt the client but forgot to rebuild/redeploy the server" if you never re-stamped in between. Follow the golden rule (§2): rebuild both together whenever either changed.
A brand-new player/tester falls through the world or spawns oddlyNot a build/deploy issue — check the scene's spawn points, not this pipeline.
The deploy workflow shows the gameserver or client step as skipped, not failedExpected the very first time — the artifact hasn't been uploaded to S3 yet. Upload it once (Recipe A step 5) and the next deploy picks it up.
