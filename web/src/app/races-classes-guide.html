1. The big picture

A race and a class are independent, fully web-authored content types — stats, formulas, and starting abilities all live in Postgres and are editable here, no Unity Inspector needed for the numbers. What's not web-authored is which (gender, race, class) combinations a player can actually pick at character creation, and what body model + weapon prop each one shows — that lineup lives in a single Unity-only asset called CharacterRoster (§4). Adding a race or class here is necessary but not sufficient to make it playable.

Everything text/numeric here is entirely web-authored. Restart the Unity host after any web edit before testing — content loads once at host start. See §3 before adding a brand-new race or class, not just tuning an existing one.

2. Anatomy of a race

Flat and small — no children. A race modifies XP rate and gives flat stat bonuses/penalties applied on top of a class's base stats when a character is created.

FieldMeaning
race_idThe permanent identifier — matches what's stored on a character row and what CharacterRoster entries reference by name (§4). Don't rename an id already in use by a saved character or a roster entry.
Display namePlayer-facing text.
XP modifier1.0 = standard. Below 1 = less XP required to level (faster leveling); above 1 = more required.
7 stat modifiers (STR/STA/AGI/DEX/INT/WIS/CHA)Flat additive bonuses/ penalties on top of the class's base stats. E.g. Dwarf: +2 STR, +3 STA, −2 AGI, −2 INT, +1 WIS.

4. The one thing NOT in the web editor: weapon props & body art

If you go looking for "which weapon prop does the Warrior hold" in the Class Editor, it isn't there. Weapon props (a cosmetic prefab attached to the right-hand bone, e.g. Warrior's sword) and everything about which Synty body model represents a given (gender, race, class) tuple both live in one Unity-only asset: Resources/CharacterRoster.asset, edited via Tools → Character → Build Character Roster in the Unity Editor, not the web app.

Why: a weapon prop is a prefab reference with no numeric/text content a web form would add — it's pure Unity-asset wiring. Moving it into the database would have left one dangling asset field on an otherwise clean DB row, so it stays alongside the roster's other prefab wiring instead (mirrors how mob art also stays Unity-side in MobModelCatalog).

The bigger consequence: adding a race or class here does not make it selectable at character creation by itself. The create-form's gender→race→class cascade, and the server-side whitelist that validates a create request, both read CharacterRoster's list of legal tuples — not the races/classes tables directly. A race or class that exists in the web editor but has no matching roster entry simply never appears as an option, and a hand-crafted client request for it would be rejected server-side. To make a new race/class combination playable, someone needs to add a row to CharacterRoster in Unity (gender + race name + class name + a body prefab) and re-run the build tool — see Recipe B.

5. The HP / Mana formulas, briefly

effectiveStat = min(STA or mana-stat, cap), then modifier = baseRatio + (level−1) × growthRate, then max = classBase + (level−1) × perLevel + effectiveStat × modifier. Tune the 5 HP fields or 6 mana fields to reshape a class's HP/mana curve across the level range — the archetypes already seeded (Warrior: high HP, no mana · Wizard: low HP, high INT-scaled mana · Cleric: mid HP, WIS-scaled mana) are a reasonable starting reference for a new class's numbers.

6. The Combat Tier Table, briefly

The same 7-weight hit-tier table mobs use, authored twice per class (Level 1 and Level 20) — CombatResolver interpolates between them by the character's actual level. See the Combat Pipeline guide for the full mechanics (tier weights are relative, not percentages; the total matters because runtime modifiers move fixed weight units). One class-specific note: only Warrior's tables are the design doc's real numbers — Wizard and Cleric ship a budget-ratio-scaled placeholder, not a hand-tuned target curve. Keep that in mind when balancing a new class against them.

7. Starting abilities

An ordered list of ability ids (dropdown-populated from the Ability Editor's live list — see the Abilities guide). PlayerAbilities.SetRaceClass auto-fills the hotbar from this list in order at character creation, one ability per slot starting at slot 0. This only fires at creation — changing a class's starting abilities has no effect on already-created characters of that class.

8. Recipes (step-by-step)

Web app in this browser UI Unity in the Unity editor

Recipe A — Tune an existing class's numbers

Goal: adjust HP growth, mana, or the combat tier table on a class that's already playable. No roster changes needed — this is the common case.

  1. Web app Class Editor → open the class → edit whichever section (Base Stats, HP Formula, Mana Formula, Combat Tier Table, Starting Abilities). Save.
  2. Unity Restart the host. New characters (and existing ones, whose stats are recomputed from the formula on load, not stored as a fixed number) reflect the change.

Recipe B — Add a brand-new race or class (full path, including the roster)

Goal: a genuinely new race or class that shows up as a real, selectable option — not just a row in the database.

  1. Web app Race Editor or Class Editor → + New → fill in the fields per §2/§3. Save.
  2. Unity For a new class, first give it at least one starting ability if you want anything on its hotbar (see the Abilities guide) — this can also be done back in the web Class Editor.
  3. Unity Open CharacterRosterSetup.cs (or hand-edit Resources/CharacterRoster.asset in the Inspector) and add the new (gender, race, class) tuple(s) with a body prefab — and, for a new class, a classWeaponProps entry if it should hold a weapon. Run Tools → Character → Build Character Roster.
  4. Unity Restart the host. The new combination should now appear in the character-create cascade and spawn with the right body.
Skipping step 3 is the single most common way a new race/class "doesn't show up" — see §10.

Recipe C — Give a class a new starting ability

Goal: a class gains a second hotbar ability at creation.

  1. Web app Create the ability first if it doesn't exist (see the Abilities guide).
  2. Web app Class Editor → open the class → Starting Abilities → + Ability → pick it from the dropdown. Save.
  3. Unity Restart the host. Only newly created characters of that class get the new hotbar slot (§7) — existing characters are unaffected.

9. Known gaps — what's still placeholder or unimplemented

  • The character-creation lineup (gender/race/class tuples + body art) is Unity-only — see §4. There's no web UI for it today, by deliberate design (it's prefab wiring, not authorable content).
  • Wizard and Cleric's combat tier tables are placeholders, not real design targets — only Warrior's are the doc's actual numbers (§6).
  • No in-place stat rebalance tooling beyond hand-editing the fields — changing a class's HP formula affects every character of that class uniformly and immediately on next load; there's no versioning or "preview before applying."
  • Starting abilities only apply at creation (§7) — there's no retroactive grant and no way to remove/replace an already-known ability from the web editor.

10. Troubleshooting

SymptomLikely cause / fix
A new race/class I created in the web editor doesn't appear at character creationExpected until a matching CharacterRoster entry exists in Unity (§4) — the web editors alone don't make a tuple selectable.
A class's weapon doesn't show, or shows the wrong propNot a web-editor field — check CharacterRoster.classWeaponProps in Unity (§4), not the Class Editor.
A character of a class with no starting abilities has an empty hotbar Expected — add ability ids to that class's Starting Abilities in the web editor, then create a new character (§7, existing ones aren't retroactively updated).
My web edit to a race/class didn't change in-game behaviorUnity loads race/class content at host start — restart the Unity host. Also confirm Postgres + the API are running.
A saved character's stats look wrong after editing a class's formula Expected behavior, not a bug — HP/mana are recomputed from the current formula on every load, not stored as a fixed number, so editing a live class's numbers retroactively changes every character of that class.
