Quest Turn-Ins & Rewards — User Guide

How to make an NPC accept a hand-off and give a reward — the game's "quest" system. There is no quest log or quest UI: a quest is simply a conversation keyword that carries a transaction. Say the word to the NPC, it takes what it asked for and gives you the reward. Read the Big Picture, then the Recipes.

1. The big picture

The world has no explicit quests — players infer objectives from dialogue and clues. A "quest" is authored entirely in the Conversation Editor: you attach a quest transaction to one of an NPC's keywords. When a player is in conversation with that NPC and types the keyword, the NPC:

  1. Checks the player has the required items/coin (and that the reward will fit).
  2. Consumes the required items and coin.
  3. Grants the reward — XP, coin, items, and/or faction standing — with Reward-channel chat.
Mental model: a keyword's response text is what the NPC says; its transaction is what the NPC does. "Bring me 4 wolf pelts and I'll reward you" is the response; requiring 4 wolf_pelt and granting 100 XP is the transaction. They ride on the same keyword.

Where each piece lives

(2) The NPC must have the KeywordRewardApplicator component — it ships on the shared Enemy prefab patch list (Tools → Patch Enemy Prefab), inert unless one of its keywords carries a transaction, so you normally don't touch it.

2. Anatomy of a turn-in keyword

In the Conversation Editor, every keyword has an expandable Quest transaction (turn-in → reward) section at the bottom of its card. When any requirement or reward is filled in, the summary shows an active badge. A keyword is a turn-in when that section has anything set; otherwise it's a plain talk keyword.

  • The keyword still behaves like any other — it has a mode (Passive = always heard / Active = only mid-conversation), an optional faction gate, and can unlock other keywords. The transaction rides on top.
  • Most turn-in keywords should be Active (spoken during a conversation after hailing) and set to not end the conversation, so the exchange completes before any closing line.

3. What a transaction can require and grant

The panel has two columns:

ColumnFieldMeaning
Requirements
(consumed on turn-in)		 Coin (copper)Copper the player must have and will spend. 0 = none.
Required item(s)One row per item: pick the item id + quantity. All are consumed.
Reward
(granted)		 XPExperience awarded to the player (drives leveling). 0 = none.
Coin (copper)Copper added to the player's purse (auto-normalized to PP/GP/SP/CP).
Reward item(s)One row per item + quantity, added to the player's inventory.
Faction hit(s)One row per faction: pick the faction + a signed delta (e.g. +50 or -100) applied to the player's standing.

Any combination is valid. A pure reward (no requirements) is a keyword that just gives something — a "gift". A requirement with no reward is a hand-off that only takes (rare, but allowed). Coin is always in copper; the game formats it up to silver/gold/platinum for display.

4. The all-or-nothing rule

The NPC validates the entire transaction before consuming anything, so a player can never lose items without getting the reward. It refuses (System-channel chat, nothing consumed) if:

  • The player is missing any required item → "You don't have what I asked for."
  • The player lacks the required coin → "You don't have the coin I asked for."
  • The reward won't fit after the hand-off — inventory full, or a LORE reward the player already holds (§6) → "You'll need to make room for the reward first."

Only when all checks pass does it consume the requirements and grant the reward, each line reported on the Reward channel ("You gain 100 experience.", "You receive Silver Ring.", "Your standing with Villagers has improved.").

The fit check simulates the full swap — turning in bag-filling items and receiving one reward works even from a nearly full inventory, because the required items are removed before the reward is placed.

5. Faction gating a quest

A turn-in obeys the keyword's own faction gate (the Required faction + Required standing fields on the keyword). If the player's standing is too low, the NPC never even acknowledges the keyword — so the transaction never runs and nothing is consumed. This lets you lock a quest behind reputation: only players the NPC likes can turn it in. Leave the gate empty for an open-to-all quest.

6. Repeatable quests & the LORE anti-farm lever

Quests are repeatable — there's no completion tracking. Say the keyword again with the requirements in hand and it fires again. That's intentional: XP and coin from a repeatable turn-in are farmable by design (bounded by the effort of gathering the requirements, the classic EQ model).

To stop players stockpiling a specific reward item, mark that item LORE in the Item Editor. A LORE item can be held at most once (inventory + equipped). The turn-in grants reward items with LORE enforced, so a player who already holds the LORE reward is refused ("make room…") until they no longer have one. Use LORE on unique quest rewards; leave ordinary rewards non-LORE so they stack normally.

7. Recipes (step-by-step)

These assume Postgres + the web app are running, the Enemy prefab has been patched, and you'll restart the Unity host after web edits before testing.

Recipe A — A classic collect-and-return quest

Goal: "Bring the hunter 4 wolf pelts for 150 XP and 50 copper."

  1. Make sure the item exists (Item Editor): an item id wolf_pelt that drops from wolves. (Rewards can reference any item id too.)
  2. Open the hunter's conversation set (Conversation Editor) — or make a new set and point the hunter mob's conversationSetId at it in the Mob Editor.
  3. Add a keyword, e.g. pelts, mode Active, Ends conversation unchecked. Response: "You've got them? The Hunters' Lodge thanks you."
  4. Open its Quest transaction: under Requirements add a required item wolf_pelt × 4. Under Reward set XP 150 and Coin 50. Save.
  5. Add an opener keyword too (e.g. hail, marked Opener) plus a plain keyword hinting at the task, so the player can start the conversation and learn what to bring.
  6. Restart the Unity host. In-game: hail the hunter, then say pelts with 4 pelts in your bag → they vanish, you gain XP + coin (Reward chat). Without 4, you're refused.

Recipe B — A paid service (coin in → item out)

Goal: "Pay the smith 5 silver and he forges you an Iron Key."

  1. Ensure the reward item iron_key exists in the Item Editor (mark it LORE if a player should only ever hold one — §6).
  2. On the smith's set add keyword forge (Active). Response: "Here's your key."
  3. Quest transaction: Requirements → Coin 50 (copper; 5 silver = 50 copper). Reward → Reward item iron_key × 1. Save, restart host.
  4. Test: say forge with ≥50 copper → coin spent, key received. Too poor → "You don't have the coin I asked for." Already holding the LORE key → "make room…"

Recipe C — A reputation-gated reward that shifts faction

Goal: only players the Villagers trust can turn in a relic, gaining Villager standing and losing Bandit standing.

  1. Confirm the factions exist (Faction Editor): villagers, bandits.
  2. On the elder's set add keyword relic (Active). Set the keyword's Required faction = villagers, Required standing = e.g. Amiable (the gate, §5).
  3. Quest transaction: Requirements → required item ancient_relic × 1. Reward → XP 300, and two Faction hits: villagers +100, bandits -100. Save, restart host.
  4. Test: a player below Amiable with Villagers gets no response at all (gate blocks it). At/above Amiable, the relic is consumed, XP granted, and both standings shift (Reward chat reports each).

8. Troubleshooting

SymptomLikely cause / fix
NPC ignores the keyword entirelyYou're not in conversation and the keyword is Active (hail first, or make it Passive); the keyword's faction gate is blocking you (§5); or the NPC's conversationSetId doesn't point at this set.
NPC responds but gives no reward / takes nothingThe Quest transaction is empty (no "active" badge), or you edited the web app but didn't restart the Unity host. Also confirm the API was restarted after the 3.2 changes so saves include the transaction fields.
Always refused with "make room for the reward"Inventory is full, or a LORE reward item is one the player already holds (§6). Free a slot / drop the held LORE copy.
"You don't have what I asked for" though I have the itemsThe required itemId or quantity is wrong, or the items are equipped not in the bag (only inventory + equipped counts toward LORE, but requirements are consumed from inventory — unequip first).
Reward faction line doesn't appearThe faction id doesn't resolve (typo, or the faction isn't seeded/loaded), or the delta is 0. Pick the faction from the dropdown.
Turn-in fires but the item reward is missingThe reward item id doesn't exist in the DB, or it's LORE and already held (silently blocked by the fit check — you'd have been refused; confirm via the "make room" line).
Players farm a reward I didn't want farmableQuests are repeatable by design. Mark the reward item LORE to cap it at one held (§6); XP/coin farming is intended.

9. Quick reference

Quest transaction fields (Conversation Editor → keyword)

FieldMeaning
Requirements → Coin (copper)Copper the player must have; spent on turn-in.
Requirements → Required item(s)Item id + quantity, consumed from the bag.
Reward → XPExperience granted.
Reward → Coin (copper)Copper added to the purse.
Reward → Reward item(s)Item id + quantity added (LORE enforced).
Reward → Faction hit(s)Faction id + signed delta applied to standing.

Behavior rules

  • All-or-nothing: validated fully before anything is consumed (§4).
  • Faction-gated: obeys the keyword's own faction gate; blocked = no transaction (§5).
  • Repeatable: no completion tracking; LORE items cap reward stockpiling (§6).
  • Chat: refusals on the System channel; grants on the Reward channel.

Setup checklist

  1. Referenced items exist (Item Editor); factions exist (Faction Editor).
  2. Keyword + transaction authored (Conversation Editor); NPC's conversationSetId points at the set (Mob Editor).
  3. Enemy prefab patched so the NPC has KeywordRewardApplicator (Tools → Patch Enemy Prefab).
  4. API restarted, migrations run, then Unity host restarted to load the content.
Authoritative behavior lives in Assets/Scripts/Networking/KeywordRewardApplicator.cs, ConversationKeyword.cs, and PlayerInventory.CanExchange; LORE enforcement in PlayerInventory.AddItem(enforceLore).
